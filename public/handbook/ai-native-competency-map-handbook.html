요구사항 정의와
문제 분해

이 문서는 일반 풀스택 기능을 만들기 전에 AI agent와 함께 요구사항을 질문, 비목표, 엣지케이스, 수용 기준으로 분해하는 방법을 다룹니다.

읽기 전에

이 문서에서 AI Agent는 스스로 도구를 실행하는 runtime agent가 아니라, 역할을 분리한 역할 프롬프트(Requirements Analyst, UX Reviewer 등)를 뜻한다. 실제 tool-use·자율 실행 agent 런타임은 08–10 practice-AX 트랙에서 다룬다.

이 트랙의 모든 단계는 하나의 canonical loop를 공유한다: Plan → Act → Verify → Reflect를 stop condition에 도달할 때까지 반복한다. 아래 단계별 화살표는 이 loop를 한 단계에 한 번 통과시킨 단면이다.

REQ-00

왜 이 단계에 AI를 쓰는가

AI Native한 요구사항 정의는 기획서를 길게 다시 쓰는 일이 아닙니다. 개발자가 바로 구현으로 뛰어들기 전에 AI를 질문 생성자와 모순 탐지자로 써서, 사람이 결정해야 할 문제를 드러내는 작업입니다.

기존 방식AI Native 방식
요청을 기능 목록으로 바꾼다요청을 사용자, 목표, 비목표, 정책, 위험, 엣지케이스로 쪼갠다
모호한 점은 구현 중 발견한다AI가 먼저 모호한 질문 목록을 만들고 사람이 답을 확정한다
성공 기준이 화면 완성에 머문다acceptance criteria와 반려 조건을 작업 전에 고정한다

USE

실제로 이렇게 사용한다

요구사항 단계에서 AI를 쓰는 목적은 정답 기획서를 받는 것이 아니라, 내가 놓친 질문을 빨리 밖으로 꺼내는 것입니다.

내 입력:
백오피스 환불 승인 기능을 만들려고 해.

상세에서 주문/결제/고객 문의 내용을 확인한 뒤 승인 또는 반려하는 기능이야.
모든 결정은 감사 로그로 남아야 해.

너는 Requirements Analyst야.
바로 구현하지 말고 아래 형식으로 정리해줘.
1. 요구사항 한 문장 요약
2. 구현 전에 물어봐야 할 질문 10개
3. 엣지케이스
4. 이번 MVP에서 제외할 범위
5. acceptance criteria 초안

개념

AI 출력은 결정이 아니라 질문 후보입니다. AI가 만든 질문 중 무엇을 받아들이고 무엇을 버렸는지가 요구사항 정의의 핵심 산출물입니다.

DONE

완료 가능성 패킷 (dev workflow)

이 단계 산출물은 제품에 배포된 AI 시스템이 아니라 개발 과정에 AI를 쓴 기록이다. 그래서 완료 기준은 hallucination률·p95 latency·cost가 아니라, 사람의 결정이 분리·검증·추적되는가이다. 런타임 AI 품질 지표가 필요한 작업은 LLM 로드맵과 AI Native 작업 표준을 따른다.

항목기록 기준통과 기준
검증일·환경작업일, 사용한 AI 도구/모델, 대상 코드 브랜치를 남긴다.재실행자가 같은 입력과 도구로 결과를 다시 만들 수 있다.
결정 분리AI가 만든 질문·제안과 사람이 확정한 결정을 나눠서 남긴다.채택/거절한 AI 제안과 그 근거가 로그로 남는다.
범위 고정non-goal과 acceptance criteria를 작업 전에 적는다.MVP와 후속 범위가 분리되고 수용 기준이 테스트 가능한 문장이다.
구현 연결각 결정이 UI/API/DB 중 어디에 영향을 주는지 연결한다.결정이 코드 변경 지점으로 추적된다.
검증 증거실행한 검증 명령(test/build/수동 QA)과 결과를 남긴다.테스트·빌드가 통과했고 실패 케이스가 회귀로 고정됐다.
중단·롤백배포 후 되돌릴 조건을 정량으로 적는다. 에러율은 분모·측정 시간창·최소 트래픽을 함께 명시한다.feature flag·이전 버전·수동 처리 루트가 준비돼 있다.
