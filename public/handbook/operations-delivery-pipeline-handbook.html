CD-00

pipeline stage

좋은 pipeline은 install, lint, typecheck, test, build, artifact publish, deploy, smoke test, metric gate가 분리되어 있다. 실패한 stage가 명확해야 재시도와 rollback 판단이 빨라진다.

pipeline을 하나로 뭉뚱그려진 "빌드 후 배포" 과정으로 보면, 뭔가 잘못됐을 때 원인을 찾기가 어렵다. 그래서 install, lint, typecheck, test, build, artifact publish, deploy, smoke test, metric gate처럼 각 단계를 독립적으로 나눠 두는 것이 중요하다. 이렇게 나눠두면 배포가 실패했을 때 설치 단계에서 죽었는지, 타입체크에서 걸렸는지, 아니면 실제 배포 이후 smoke test에서 걸렸는지를 즉시 구분할 수 있다. 반대로 stage가 뭉쳐 있으면 실패 로그 하나만 보고 어디서부터 잘못됐는지 처음부터 다시 추적해야 한다.

이 판단을 실제로 검증하려면 각 stage가 남긴 증거를 봐야 한다. CI run 로그, artifact publish log, deploy marker, smoke test 결과, metric gate 통과 여부가 그 증거다. 여기서 흔히 하는 착각이 "CI가 초록불이면 배포는 끝났다"는 생각이다. 하지만 CI green은 코드가 빌드되고 테스트를 통과했다는 뜻일 뿐이지, production에서 정상적으로 동작한다는 보장은 아니다. 진짜 검증은 배포 이후 smoke test와 metric gate까지 통과해야 끝난다.

예를 들어 deploy 자체는 성공했는데 smoke test 없이 넘어가서 오류율이 슬금슬금 올라가는 상황을 생각해보자. 이때 급하게 배포를 멈추는 것은 임시방편일 뿐이고, 진짜 고쳐야 할 것은 pipeline 구조다. stage를 더 잘게 나누고, 배포 직후 자동으로 도는 metric gate와 rollback trigger를 추가해야 같은 문제가 다음에도 반복되지 않는다.

CD-01

artifact

운영에 배포되는 단위는 branch가 아니라 artifact다. image digest, commit SHA, migration version, config version, build provenance를 묶어야 어떤 코드가 어디에 배포됐는지 추적된다.

많은 팀이 "지금 production에 뭐가 배포돼 있어?"라는 질문에 branch 이름이나 최근 merge된 PR로 답하려 한다. 하지만 branch는 계속 움직이는 참조일 뿐, 실제로 어떤 코드가 빌드되고 실행되는지를 보장해주지 않는다. 그래서 운영에서 진짜 추적해야 하는 단위는 branch가 아니라 artifact다. artifact는 commit SHA, image digest, migration version, config version, build provenance가 한 덩어리로 묶여서 "이 버전이 정확히 무엇으로 만들어졌는지"를 증명하는 불변의 실행 단위다.

이 원칙이 실제로 지켜지고 있는지 확인하려면 branch 이름이 아니라 release note, registry의 image digest, deploy manifest, migration 이력, config diff를 봐야 한다. 여기서 자주 나오는 실수가 "v1.2.3 태그로 배포했으니 뭐가 배포됐는지 안다"고 생각하는 것이다. 태그나 branch 이름은 사람이 읽기 위한 라벨일 뿐, 재현성이나 rollback을 보장하는 증거가 되지 못한다. 같은 태그라도 다시 빌드하면 의존성 버전이 미묘하게 달라질 수 있기 때문이다.

실제로 장애 상황에서 지금 production에 어떤 이미지가 떠 있는지조차 모르는 경우가 생긴다. 이런 사고를 막는 영구적인 방법은 release note에 artifact digest와 config version을 항상 함께 기록해서, 언제든 "이 배포는 정확히 이 digest, 이 config로 만들어졌다"고 즉시 답할 수 있게 만드는 것이다.

CD-02

environment

development, staging, production은 같은 artifact에 다른 environment config를 주입하는 구조가 안정적이다. secret, public config, runtime config를 분리하고 권한 있는 approval 없이 production 변경이 나가지 않게 한다.

환경마다 코드를 다시 빌드하면 staging에서 통과한 코드와 production에 올라가는 코드가 실제로 같은지 확신할 수 없게 된다. 그래서 안정적인 구조는 반대로 간다 — 하나의 artifact를 만들고, 환경마다 다른 config만 주입해서 dev, staging, production으로 승격시킨다. 이렇게 하면 "이 코드가 staging에서는 됐는데 production에서 안 된다"는 문제가 코드 차이가 아니라 config 차이로 좁혀진다.

이 구조가 실제로 지켜지는지는 environment config, secret source, approval gate, feature flag, 그리고 public config와 runtime config가 분리돼 있는지로 확인한다. 흔한 실수는 secret과 일반 설정을 같은 곳에 두는 것이다. 예를 들어 production의 API key 같은 secret이 build-time에 번들에 그대로 박혀버리면, 그 번들을 누구나 열어볼 수 있는 순간 경계가 뚫린 것이다.

staging에서는 멀쩡한데 production에서만 이상하게 동작하는 상황을 만나면, 먼저 config diff와 secret 소스부터 비교해야 한다. 코드가 아니라 설정이 다르기 때문에 생기는 문제일 가능성이 높다. 이런 문제를 다시 겪지 않으려면 배포 전에 config를 자동으로 검증하는 절차와, 배포 직후 실제로 정상 동작하는지 확인하는 smoke test를 pipeline에 넣어두는 것이 영구적인 해법이다.

CD-03

rollback과 release strategy

rolling, blue-green, canary, feature flag는 모두 rollback 비용을 줄이기 위한 선택지다. DB 변경은 expand-contract로 나누고, rollback이 불가능한 변경은 forward fix와 feature off 절차를 먼저 준비한다.

배포 전략을 고르는 기준은 무엇이 최신 유행인가가 아니라, 문제가 생겼을 때 얼마나 빨리 얼마나 적은 피해로 되돌릴 수 있는가다. rolling, blue-green, canary, feature flag는 모두 이 rollback 비용을 낮추기 위한 선택지들이다. 여기서 특히 까다로운 것이 DB 변경이다. 코드는 이전 버전으로 되돌리기 쉽지만, 이미 DB schema가 바뀌어버리면 코드만 되돌린다고 문제가 풀리지 않는다. 그래서 DB 변경은 expand-contract 방식으로 나눠서, 언제든 옛 코드와 새 코드가 동시에 동작할 수 있는 호환 구간을 만들어야 한다.

이 원칙이 실제로 지켜지는지 확인하려면 canary metric, rollout 상태, feature flag 상태, migration version, rollback 명령이 실제로 준비돼 있는지를 봐야 한다. rollback이 아예 불가능한 변경이라면 배포 전에 미리 사전 승인을 받고, 문제가 생겼을 때 쓸 완화책을 따로 준비해둬야 한다.

migration이 포함된 배포를 했는데 문제가 생겨서 이전 artifact로 rollback하려 했더니 DB schema 때문에 rollback 자체가 실패하는 상황이 실제로 벌어진다. 이럴 때 취할 수 있는 조치는 feature flag를 꺼서 문제 있는 기능만 비활성화하거나, 새 코드를 유지한 채 문제를 고치는 forward fix로 가거나, 애초에 expand-contract 구조로 다시 설계하는 것이다.

CHECK

실무 체크리스트

CI/CD·Artifact·Environment 체크리스트는 pipeline stage, artifact, environment, rollback과 release strategy의 변경 위험을 사전에 드러내기 위한 검토표다. 각 항목은 리뷰, 배포 승인, 운영 인수에서 같은 증거로 다시 확인되어야 한다.

  • install, test, build, artifact publish, deploy, smoke test를 stage로 분리한다.
  • commit SHA, image digest, migration version, config version을 release note에 묶는다.
  • environment별 approval과 secret 주입 경계를 둔다.
  • rollback trigger와 metric gate를 배포 전에 정한다.

이 체크리스트가 실제로 힘을 발휘하는 곳은 세 갈래의 관문이다. 설계 단계에서 놓치기 쉬운 것은 무엇을 만들 것인가만 정하고 무엇을 건드리지 않을 것인가는 정하지 않는 것이다. 목적, 영향 범위, 비목표, owner가 문서로 남아 있지 않으면 나중에 리뷰어도 이 변경이 어디까지 영향을 주는지 판단할 근거가 없다. 그래서 영향 범위가 사용자·시스템·비용 기준으로 구체적으로 설명되지 않으면 이 단계에서 진행을 막아야 한다.

변경 단계에서는 diff, 승인 기록, 검증 명령이 세트로 남아야 한다. 여기서 자주 생기는 문제가 "staging에서는 확인했다"고만 말하고 정작 production에 적용할 때 무엇이 다른지는 설명하지 못하는 경우다. production 변경과 staging 검증의 차이가 명확히 설명되지 않는다면 배포해서는 안 된다.

복구 단계는 문제가 생기면 그때 생각하자는 태도로 가장 자주 생략되는 부분이다. rollback 또는 forward fix 중 무엇을 쓸지, 누가 담당하는지, 얼마나 걸릴지가 배포 전에 정해져 있어야 한다. 실패했을 때 되돌릴 방법이 없는데 사전 승인과 공지도 없다면, 그 배포는 아직 나갈 준비가 안 된 것이다.

PLAYBOOK

실무 플레이북

CI/CD·Artifact·Environment 플레이북은 RELEASE SAFETY PLAYBOOK 기준으로 증상, 범위, 최근 변경, 계층별 증거를 연결한다. 목표는 명령어 암기가 아니라 어떤 가설을 버리고 어떤 완화책을 실행할지 결정하는 것이다.

RELEASE SAFETY PLAYBOOK symptom → scope → recent change → evidence
→ mitigation → verification → runbook diff

장애가 터졌을 때 이 플레이북을 따라가는 이유는 증상만 보고 성급하게 결론 내리지 않기 위해서다. 먼저 Artifact 표면에서는 commit SHA, image digest, SBOM/provenance, migration version을 확인한다. 여기서 세우는 원칙은 하나다. branch가 아니라 불변의 artifact가 운영의 기본 단위라는 것이다. 다음으로 Environment 표면에서는 config diff, secret source, feature flag, approval gate를 본다. 같은 artifact가 환경 설정만 바뀐 채 승격되고 있는지를 확인하는 것이 핵심이다. 마지막으로 Release gate 표면에서는 smoke test, canary metric, error budget, rollback trigger를 본다. 배포가 성공했다는 것은 pipeline이 초록불이라는 뜻이 아니라 실제 운영 지표가 기준을 통과했다는 뜻이어야 한다.

이 세 표면을 실제로 조사할 때는 순서가 있다. 먼저 배포 추적 단계에서 release note, image digest, deploy marker, config version을 비교해서 지금 production에 정확히 무엇이 올라가 있는지부터 확정한다. 그다음 검증 단계에서 smoke endpoint, synthetic transaction, error rate, p95/p99, business KPI를 본다. 여기서 흔한 함정이 헬스체크 하나만 초록불이면 안심하는 것인데, 헬스체크는 서버가 켜져 있다는 것만 말해줄 뿐 실제 사용자 흐름이 정상인지는 말해주지 않는다. 마지막으로 복구 단계에서는 rollback artifact, feature flag off, forward fix, migration compatibility를 확인한다. DB 변경이 포함된 배포라면 rollback 가능 여부를 반드시 따로 판단해야 한다.

PRACTICE

출력 판독 훈련

CI/CD·Artifact·Environment는 개념을 아는 것보다 실제 출력에서 정상과 비정상을 구분하는 훈련이 중요하다. 아래 lab은 명령, 출력, 판단, 완화, 영구 수정을 한 번에 연결한다.

PRACTICE LAB 01 · 배포 metric gate 판독

production deploy는 성공했지만 checkout error rate가 canary에서 증가한다.

release gate를 확인하면 다음과 같은 값이 나온다. 이 값을 보는 목적은 pipeline이 성공했다는 사실과 운영 배포가 실제로 성공했다는 사실을 분리해서 판단하는 것이다.

release gate
artifact=sha-9f31
config=prod-v42
canary_error_rate=7.8%
baseline_error_rate=0.4%
p95=980ms
rollback=available

정상적인 경우라면 canary_error_rate가 baseline과 비슷하고 metric_gate가 pass로 나온다.

canary_error_rate=0.3%
baseline_error_rate=0.4%
p95=180ms
metric_gate=pass

하지만 이번 배포처럼 비정상 상황에서는 다음과 같이 나타난다.

canary_error_rate=7.8%
baseline_error_rate=0.4%
p95=980ms
metric_gate=fail

이 출력을 보고 "배포는 성공했으니 넘어가자"고 판단하면 안 된다. CI/CD의 각 stage는 전부 통과했지만, 실제 사용자에게 영향을 주는 canary error rate가 baseline 대비 20배 가까이 뛰었기 때문이다. 즉 pipeline 관점에서는 성공이어도 운영 관점에서는 실패다. 그래서 즉시 완화 조치는 canary를 멈추고, 이전 artifact로 rollback하거나 feature flag를 꺼서 사용자 영향을 먼저 없애는 것이다. 이건 어디까지나 응급처치이고, 영구 수정은 metric gate를 배포 파이프라인에 필수 관문으로 넣어서 이런 상황이 사람이 알아채기 전에 자동으로 걸리게 만드는 것, 그리고 release note에 artifact, config, migration version을 항상 함께 묶어 남기는 것이다. 이 조치가 제대로 됐는지는 canary error rate가 baseline 수준으로 돌아오고, p95 latency가 회복되고, rollback한 artifact가 실제로 검증됐는지로 판단한다.

TERM

용어사전

CI/CD·Artifact·Environment에서 반복적으로 등장하는 운영 용어를 정의, 증거, 오해, 관련 항목 기준으로 정리한다. 장애 중에는 용어 자체보다 해당 용어가 어떤 로그, 지표, 설정, 책임 경계와 연결되는지를 확인한다.

pipeline stage
install, test, build, publish, deploy처럼 서로 독립적으로 검증되는 단계다. stage result, CI run, smoke result로 실제로 어느 단계에서 무슨 일이 있었는지 확인할 수 있다. pipeline은 성공/실패 하나만 보면 충분하다고 생각하기 쉽지만, 그렇게 보면 배포가 실패했을 때 원인을 처음부터 다시 뒤져야 한다. CI, deploy, metric gate 각각의 결과를 따로 봐야 실패 지점을 빠르게 좁힐 수 있다.
artifact
운영에 실제로 배포되는, 다시 만들어도 같은 결과가 나오는 불변의 실행 단위다. image digest, commit SHA, SBOM, provenance로 확인한다. branch명이나 tag만으로 충분하다고 생각하기 쉽지만, 그건 사람이 읽기 위한 라벨일 뿐 실제로 무엇이 배포됐는지 증명해주지 않는다. registry의 digest와 release note, rollback 절차가 함께 있어야 진짜 추적이 가능하다.
environment config
development, staging, production처럼 같은 artifact에 환경별로 다르게 주입되는 설정이다. config diff, env inventory, approval log로 확인한다. 환경 차이를 아예 빌드 시점에 코드에 박아 넣어도 된다고 생각하기 쉽지만, 그러면 환경마다 다른 artifact가 생기고 재현성이 깨진다. runtime config, secret, feature flag는 반드시 빌드와 분리해서 관리해야 한다.
metric gate
배포 직후 운영 지표가 정해진 기준을 통과해야만 다음 단계로 넘어가게 만드는 차단점이다. canary metric, error rate, p95/p99로 확인한다. deploy가 끝났으면 release도 끝난 것이라고 생각하기 쉽지만, deploy는 코드가 서버에 올라갔다는 뜻일 뿐이고 실제 사용자에게 문제가 없는지는 별개로 확인해야 한다. smoke test, SLO, canary 결과가 모두 통과해야 진짜 release가 끝난 것이다.
expand-contract
DB 변경을 한 번에 밀어붙이지 않고, 호환되는 확장 단계와 이후 정리 단계로 나누는 방식이다. migration compatibility, migration version으로 진행 상황을 확인한다. DB migration도 코드처럼 즉시 되돌리면 된다고 생각하기 쉽지만, 이미 데이터가 새 schema로 쓰이기 시작했다면 코드만 되돌리는 것으로는 복구되지 않는다. forward fix, rollback, schema migration의 순서를 미리 설계해둬야 한다.
CASE

장애/운영 시나리오

staging에서는 정상인데 production 배포 후 오류율이 증가한다. 배포된 artifact digest와 config version을 먼저 확인하고, feature flag를 끄거나 이전 artifact로 rollback한다. 이후 pipeline에 production smoke test와 error rate gate를 추가한다.

Triage frame

CI/CD·Artifact·Environment 장애는 증상 → 영향 범위 → 최근 변경 → Artifact 증거 → 완화책 → 복구 검증 → 재발 방지 순서로 기록한다. 이 흐름이 있어야 담당자가 바뀌어도 같은 결론에 도달한다.

장애 대응은 시간에 따라 해야 할 일이 다르다. 처음 10분 동안은 원인을 알아내려 하지 말고 영향 범위부터 고정한다. commit SHA, image digest, SBOM/provenance, migration version을 기준으로 이번 배포에서 뭐가 바뀌었는지를 확정하는 것이다. 다음 30분 동안은 release note, image digest, deploy marker, config version을 비교하면서 증거를 모으고, 그 증거를 바탕으로 완화 조치를 실행한다. 이 사이클은 같은 실패가 다시는 사람 눈에 의존하지 않고 자동으로 차단될 때 비로소 끝난 것으로 본다.

이 과정을 나중에 다시 볼 수 있도록 Incident packet에는 증상, 완화, 사후 조치 세 가지를 남긴다. 증상은 "production 배포 후 오류율 상승"처럼 관찰된 사실이고, 이걸 artifact, config, migration, flag, dependency 변경과 대조해서 원인 후보를 좁힌다. 완화는 flag off, canary stop, previous artifact rollback, traffic shift 중에서 가장 적은 범위로 되돌릴 수 있는 조치를 고른다. 굳이 전체를 rollback할 필요가 없다면 flag 하나만 끄는 것이 더 안전하다. 사후 조치에서는 이번에 놓쳤던 부분을 metric gate와 smoke test에 반영해서, 같은 실패가 다음에는 사람이 알아채기 전에 자동으로 걸리도록 만든다.

RISK

자주 틀리는 판단

CI/CD·Artifact·Environment에서 자주 틀리는 판단은 pipeline stage와 rollback과 release strategy의 책임 경계를 흐리는 데서 시작된다. 아래 신호가 보이면 설계, runbook, 답변 구조를 다시 점검한다.

  • branch 이름만 보고 어떤 artifact가 배포됐는지 모른다.
  • CI 통과를 운영 배포 가능성과 동일하게 본다.
  • DB migration rollback 가능성을 확인하지 않는다.
  • production secret을 build-time bundle에 섞는다.
EVIDENCE

운영 증거 패킷

CI/CD 변경은 성공한 배포 로그만으로 승인하지 않는다. artifact가 어떤 기준 버전과 도구로 만들어졌고, 어떤 증거로 검증됐으며, 실패하면 어디까지 되돌릴 수 있는지 한 묶음으로 남긴다.

CI/CD 변경을 승인할 때는 배포 로그가 성공이라고 나왔다는 것만으로는 부족하다. 그 artifact가 정확히 어떤 기준 버전과 도구로 만들어졌는지부터 남겨야 한다. runner image, build tool, package manager lockfile, container base image, SBOM generator, signer/cosign version이 그 기록이다. lockfile이나 artifact digest가 빠져 있거나 runner 권한이 production secret에 직접 닿을 수 있는 구조라면 승인해서는 안 된다. 재현할 수 없는 빌드는 나중에 문제가 생겨도 무엇이 원인인지 되짚을 방법이 없기 때문이다.

실제로 무엇을 확인했는지도 명령 출력으로 남긴다. npm ci, unit/integration test, image build digest, SBOM 생성, vulnerability scan, signature verify 결과가 그것이다. critical 취약점이 있거나 image에 서명이 안 됐거나 provenance가 빠졌거나 원인이 안 밝혀진 flaky test가 있다면 release를 block해야 한다.

한 번의 배포만 보지 말고 대시보드·쿼리로 추세도 본다. deploy frequency, change failure rate, rollback rate, failed job reason, artifact age를 보는 이유는, 같은 이유로 실패가 2회 이상 반복된다면 그건 우연이 아니라 pipeline 자체에 구조적인 문제가 있다는 신호이기 때문이다. 이때는 pipeline owner가 runbook diff를 직접 승인하도록 한다.

마지막으로 severity와 rollback 가능성을 함께 판단한다. SEV2 이상의 사용자 영향, migration 포함 여부, feature flag off 가능 여부, 이전 image digest를 기준으로 삼는다. rollback에 걸리는 예상 시간이 SLO의 error budget보다 길다면, 이건 자동으로 진행할 수 있는 배포가 아니라 사람이 수동으로 승인하고 고객 공지 초안까지 미리 준비해야 하는 배포다.

delivery_evidence_packet:
  기준일: "2026-07-09"
  artifact: "registry.example.com/payments/api@sha256:..."
  tools: "node 20.x, pnpm 9.x, cosign, syft/grype, SLSA provenance"
  command_outputs: ["test summary", "sbom path", "signature verify", "scan result"]
  severity_rule: "P1: payment/auth path failure, P2: partial tenant degradation"
  rollback: "previous digest + feature flag off + DB migration forward/backward note"
  approvers: ["service owner", "security reviewer when supply-chain policy changes"]
