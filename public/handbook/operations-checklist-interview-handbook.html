프론트엔드 개발자 연결점

시작 증거상황

볼 증거 내가 직접 본 장애, 배포, 대시보드, runbook, postmortem

학습 전환 경험과 학습 지식을 면접에서 정확히 분리한다.

자주 만나는 상황상황

볼 증거 직접 운영하지 않은 클라우드 질문, 장애 대응 꼬리질문

학습 전환 아는 척보다 검증 계획과 증거 언어로 답한다.

완료 산출물상황

볼 증거 30초 답변, 90초 증거 확장, 직접 경험/설계 지식 구분표

학습 전환 운영 역량을 과장 없이 강하게 보여준다.

CHK-00

운영 인수

운영 인수에는 owner, escalation, architecture diagram, DNS, TLS 인증서, secret 위치, deployment pipeline, dashboard, alert, runbook, rollback, backup, RPO/RTO, 비용 owner가 포함되어야 한다.

OPERATIONS DECISION

운영 질문 운영 인수가 권한과 책임까지 넘겨졌는가?

확인할 증거 owner, escalation, architecture, DNS/TLS, secret location, dashboard, alert, runbook, backup, cost owner

판단 기준 문서 전달만으로는 인수 완료가 아니다.

배제 확인 운영 인수를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 service catalog, access review, dashboard/runbook link, alert route, DR plan

명령 해석 첫 장애 때 찾을 사람과 실행 권한이 있어야 한다.

임시 완화와 영구 수정 인수 후 첫 장애에서 owner와 권한을 찾지 못함 기준으로 영향 범위를 좁히고, critical owner와 access grant를 인수 조건으로 되돌린다.

CHK-01

배포 전 체크

변경 범위, artifact, migration, config, secret, feature flag, smoke test, metric gate, rollback 조건을 확인한다. 하나라도 말로만 존재하면 운영 준비가 끝난 것이 아니다.

OPERATIONS DECISION

운영 질문 배포 전 체크가 artifact, config, migration, rollback을 모두 막는가?

확인할 증거 artifact digest, config diff, migration compatibility, secret source, feature flag, smoke test, metric gate

판단 기준 하나라도 말로만 있으면 배포 준비가 아니다.

배제 확인 배포 전 체크를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 release note, deploy manifest, migration plan, smoke result, rollback command

명령 해석 rollback 불가 항목은 사전 승인과 forward fix가 필요하다.

임시 완화와 영구 수정 production 배포 후 config mismatch로 장애 기준으로 영향 범위를 좁히고, config 검증과 smoke/metric gate를 release gate에 추가한다.

CHK-02

장애 대응 체크

증상, 영향 범위, 시작 시각, 최근 변경, 주요 metric, log, trace, 의사결정, 사용자 공지, 복구 시각을 기록한다. 장애가 끝난 뒤에는 runbook과 alert를 반드시 업데이트한다.

OPERATIONS DECISION

운영 질문 장애 대응 기록이 재현 가능한 timeline과 의사결정을 남기는가?

확인할 증거 symptom, impact, start time, recent change, metric/log/trace, decision, comms, recovery time

판단 기준 기록이 없으면 사후 분석이 추측이 된다.

배제 확인 장애 대응 체크를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 incident packet, dashboard snapshot, log sample, decision log, customer update

명령 해석 복구 시각과 검증 신호가 함께 남아야 종료할 수 있다.

임시 완화와 영구 수정 복구는 됐지만 어떤 조치가 효과였는지 모름 기준으로 영향 범위를 좁히고, incident packet과 runbook diff를 필수 종료 조건으로 둔다.

CHK-03

면접 답변

인프라·운영 질문에는 '요청 경로를 먼저 그리고, 실패 지점을 계층별로 좁혔고, 배포와 rollback은 artifact와 metric gate로 통제했으며, 장애 후에는 SLO와 runbook을 개선했다'는 구조로 답한다. 직접 해본 일과 설계 지식의 경계도 함께 말한다.

OPERATIONS DECISION

운영 질문 면접 답변이 경험 수준과 증거를 정직하게 구분하는가?

확인할 증거 direct experience, partial participation, design knowledge, incident packet, postmortem, dashboard evidence

판단 기준 직접 하지 않은 일을 경험처럼 포장하지 않아야 한다.

배제 확인 면접 답변을 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 project notes, incident review, runbook diff, architecture diagram, metric screenshot

명령 해석 답변은 주장보다 증거와 판단 순서가 중요하다.

임시 완화와 영구 수정 도구명은 많지만 실패 모드와 검증 증거가 없음 기준으로 영향 범위를 좁히고, 요청 경로, 배포 경로, 관측, 장애 대응, 인수 산출물 순서로 답한다.

CHECK

실무 체크리스트

운영 인수·릴리즈 리뷰·면접 답변 체크리스트는 운영 인수, 배포 전 체크, 장애 대응 체크, 면접 답변에서 놓치기 쉬운 운영 증거를 작업 전후로 고정하기 위한 검토표다. 각 항목은 프론트엔드 증상, 배포 승인, 운영 인수에서 같은 기준으로 다시 확인한다.

  • owner, escalation, dashboard, alert, runbook을 운영 인수 표에 채운다.
  • 배포 전 artifact, migration, config, secret, rollback을 확인한다.
  • 장애 대응 기록 양식과 사용자 공지 기준을 준비한다.
  • 면접 답변은 직접 경험, 일부 경험, 설계 지식을 구분해 말한다.
설계작업 단계

필수 산출물 목적, 영향 범위, 비목표, owner

차단 기준 영향 범위가 사용자·시스템·비용 기준으로 설명되지 않음

변경작업 단계

필수 산출물 diff, 승인 기록, 검증 명령

차단 기준 production 변경과 staging 검증의 차이가 설명되지 않음

복구작업 단계

필수 산출물 rollback 또는 forward fix, 담당자, 예상 시간

차단 기준 실패 시 되돌릴 수 없는데 사전 승인과 공지가 없음

실무 플레이북

운영 인수·릴리즈 리뷰·면접 답변 플레이북은 OPERATIONS HANDOFF REVIEW PLAYBOOK 기준으로 증상, 범위, 최근 변경, 계층별 증거를 연결한다. 목표는 명령어를 많이 아는 것이 아니라 어느 가설을 버리고 어떤 완화책을 선택할지 설명하는 것이다.

OPERATIONS HANDOFF REVIEW PLAYBOOK 1 symptom → 2 scope → 3 recent change → 4 evidence
→ 5 mitigation → 6 verification → 7 runbook diff
1 · 증상symptom
무엇이 안 되는가를 사용자 관점 한 문장으로. "느리다"가 아니라 어떤 요청이 언제부터 어떻게 실패하는지 적는다
2 · 영향 범위scope
전체인가 일부인가. region·tenant·경로·클라이언트 중 무엇으로 갈리는지가 가설의 절반을 지운다
3 · 최근 변경recent change
직전 배포, 설정·권한 변경, 인증서·route 교체를 같은 시간축에 올린다. 대부분의 장애는 최근 변경에서 온다
4 · 증거evidence
인수 대상의 owner, escalation, 의존성, 접근 권한, 비용을 카탈로그에서 확인하고 runbook·dashboard·DR 계획을 실제로 열어본다
5 · 완화mitigation
빠진 것이 있으면 인수를 미루는 대신 임시 owner와 기한을 정해 공백을 막는다. 면접 답변에서는 직접 경험과 설계 지식의 경계를 흐리지 않는다
6 · 복구 검증verification
완화가 실제로 먹혔는지 같은 증거로 다시 확인한다. 사용자 경로를 한 번 통과시켜야 끝난 것이다
7 · 런북 갱신runbook diff
이번에 내린 판단을 문서에 되돌린다. 다음 사람이 같은 순서를 다시 발명하지 않게 하는 단계

PRACTICE

출력 판독 훈련

운영 인수·릴리즈 리뷰·면접 답변은 개념을 아는 것보다 실제 출력에서 정상과 비정상을 구분하는 훈련이 중요하다. 아래 lab은 명령, 출력, 판단, 완화, 영구 수정을 한 번에 연결한다.

PRACTICE LAB 01 · 운영 인수 gap 판독

서비스를 인수받았지만 첫 장애에서 알림 owner와 runbook 실행 권한이 없다.

Command / Query

handoff review
architecture=present
dashboard=present
alert_owner=missing
runbook_access=denied
backup_restore_drill=unknown
cost_owner=missing

목적 문서 전달과 실제 운영 가능 상태를 구분한다.

정상 출력

alert_owner=oncall-core
runbook_access=granted
backup_restore_drill=2026-06-18 pass
cost_owner=platform-finops

비정상 출력

alert_owner=missing
runbook_access=denied
backup_restore_drill=unknown
cost_owner=missing

판단 훈련 아키텍처 문서는 받았지만 운영 책임, 권한, 복구 증거가 빠진 인수 실패 상태다.

즉시 완화 임시 owner 지정, runbook access grant, critical alert route 보정.

영구 수정 인수 완료 기준에 owner/access/drill/cost 항목을 차단 gate로 추가한다.

검증 기준 첫 장애 대응자가 dashboard, alert, runbook, rollback, restore 권한을 모두 실행 가능.

TERM

용어사전

운영 인수·릴리즈 리뷰·면접 답변에서 반복적으로 등장하는 운영 용어를 정의, 증거, 오해, 관련 항목 기준으로 정리한다. 장애 중에는 용어 자체보다 해당 용어가 어떤 로그, 지표, 설정, 책임 경계와 연결되는지를 확인한다.

ownerTERM
서비스, 비용, 접근, 장애 대응 책임자. 운영에서는 owner matrix, cost owner, access owner로 확인한다. 흔한 오해는 "문서가 있으면 owner가 없어도 된다."라고 보는 것이다. 관련해서 escalation, service catalog, access review를 함께 본다.
escalationTERM
장애나 권한 문제를 다음 책임 단계로 올리는 경로. 운영에서는 alert route, channel owner, comms timeline로 확인한다. 흔한 오해는 "슬랙에 물어보면 escalation이다."라고 보는 것이다. 관련해서 Incident Commander, SME, support trend를 함께 본다.
operational handoffTERM
운영 권한, 절차, 지표, 복구 책임을 넘기는 인수 과정. 운영에서는 dashboard/runbook link, access grant, DR plan로 확인한다. 흔한 오해는 "repo 권한 이전이면 인수 완료다."라고 보는 것이다. 관련해서 owner, runbook, backup를 함께 본다.
release gateTERM
배포 전후에 artifact, config, metric 기준으로 진행을 막거나 허용하는 기준. 운영에서는 smoke test, metric gate, migration plan로 확인한다. 흔한 오해는 "사람 승인만 있으면 release gate다."라고 보는 것이다. 관련해서 artifact, rollback, approval를 함께 본다.
incident packetTERM
장애 증상, 영향, 지표, 로그, 결정, 복구 시각을 묶은 기록. 운영에서는 dashboard snapshot, log sample, decision log로 확인한다. 흔한 오해는 "복구됐으면 기록은 선택 사항이다."라고 보는 것이다. 관련해서 postmortem, timeline, runbook diff를 함께 본다.
CASE

장애/운영 시나리오

서비스를 다른 팀에서 인수받는다. 아키텍처 다이어그램만 받지 않고 DNS, TLS, 배포 pipeline, secret 위치, SLO, dashboard, alert, backup, RPO/RTO, 비용 owner까지 확인한다. 빠진 항목은 인수 후 리스크로 남기지 않고 인수 조건으로 되돌린다.

Triage frame

운영 인수·릴리즈 리뷰·면접 답변 장애는 프론트엔드에서 보인 증상 → 영향 범위 → 최근 변경 → Handoff 증거 → 완화책 → 복구 검증 → 재발 방지 순서로 기록한다.

INCIDENT FLOW

RISK

자주 틀리는 판단

운영 인수·릴리즈 리뷰·면접 답변에서 자주 틀리는 판단은 운영 인수와 면접 답변의 책임 경계를 흐리는 데서 시작된다. 아래 신호가 보이면 설계, runbook, 답변 구조를 다시 점검한다.

  • 운영 인수를 코드 저장소 권한 이전으로 끝낸다.
  • 면접에서 도구 이름만 나열하고 실패 모드와 검증 증거를 말하지 않는다.
  • runbook이 있지만 최신 배포 구조와 다르다.
  • 장애 대응 권한과 승인자가 불분명하다.
