IAC-00

IaC의 목적

IaC는 콘솔 클릭을 코드로 바꾸는 것이 아니라 변경 이력, 리뷰, 재현성, 감사 가능성을 얻는 방식이다. Terraform, Pulumi, CloudFormation 모두 state와 실제 리소스의 관계를 이해해야 한다.

OPERATIONS DECISION

운영 질문 IaC가 재현성뿐 아니라 감사 가능한 변경 절차를 제공하는가?

확인할 증거 module version, provider version, state backend, review history, audit ticket

판단 기준 코드화보다 plan/state/리뷰/검증 절차가 핵심이다.

배제 확인 IaC의 목적을 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 terraform plan/show, state backend, provider lock, PR review, resource readback

명령 해석 콘솔 클릭을 코드로 옮겼어도 검증이 없으면 운영 품질이 낮다.

임시 완화와 영구 수정 콘솔 hotfix가 코드에 반영되지 않아 drift 발생 기준으로 영향 범위를 좁히고, drift 원인을 코드 흡수 또는 수동 변경 금지 정책으로 닫는다.

IAC-01

plan과 apply

plan은 생성, 수정, 교체, 삭제, 권한 변경을 분류해 리뷰한다. apply 전에는 state lock, workspace, provider version, target environment, destructive change를 확인한다.

OPERATIONS DECISION

운영 질문 plan이 생성/수정/교체/삭제/권한 확대를 분리해 보여주는가?

확인할 증거 create/update/replace/delete, IAM diff, network diff, downtime risk, state lock

판단 기준 replace/delete/IAM 확대는 별도 승인 기준이 필요하다.

배제 확인 plan과 apply를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 terraform plan -out, terraform show, state lock, workspace, provider version

명령 해석 apply 전 destructive change와 권한 확대를 먼저 표시한다.

임시 완화와 영구 수정 LB replace가 plan에 포함됐지만 영향 검토 없이 apply 기준으로 영향 범위를 좁히고, create-before-destroy, staged apply, maintenance window를 검토한다.

IAC-02

drift

drift는 코드와 실제 인프라가 달라진 상태다. 콘솔 hotfix, 자동 확장, 외부 시스템 변경이 원인이 된다. drift를 무조건 되돌리지 말고 왜 발생했는지, 코드에 흡수할지, 수동 변경을 금지할지 결정한다.

OPERATIONS DECISION

운영 질문 drift가 왜 발생했고 코드에 흡수할지 되돌릴지 판단했는가?

확인할 증거 drift detection, console hotfix, autoscaling change, import target, moved block

판단 기준 drift를 무조건 덮어쓰면 운영 hotfix를 잃을 수 있다.

배제 확인 drift를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 terraform plan refresh, cloud readback, state list/show, audit log

명령 해석 실제 리소스와 state, 코드의 차이를 세 방향으로 비교한다.

임시 완화와 영구 수정 보안 hotfix가 다음 apply에서 되돌아감 기준으로 영향 범위를 좁히고, hotfix를 코드에 흡수하고 변경 금지/예외 정책을 정리한다.

IAC-03

변경 티켓

운영 인프라 변경에는 목적, 영향 범위, plan 요약, 적용 시간, 검증 명령, rollback 또는 forward fix가 필요하다. DB, DNS, network 변경은 전파와 lock 때문에 더 보수적으로 쪼갠다.

OPERATIONS DECISION

운영 질문 변경 티켓이 적용 전후 검증과 복구 기준을 포함하는가?

확인할 증거 purpose, impact, plan summary, apply window, validation command, rollback/forward fix

판단 기준 DB/DNS/network 변경은 전파와 lock 때문에 더 작게 쪼개야 한다.

배제 확인 변경 티켓을 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 change ticket, plan artifact, post-apply readback, rollback note, owner approval

명령 해석 적용 성공보다 의도한 상태 검증이 중요하다.

임시 완화와 영구 수정 적용 후 장애인데 rollback/forward fix가 없음 기준으로 영향 범위를 좁히고, 검증 명령과 복구 owner를 티켓 필수 항목으로 만든다.

CHECK

실무 체크리스트

IaC·변경관리·Drift 체크리스트는 IaC의 목적, plan과 apply, drift, 변경 티켓에서 놓치기 쉬운 운영 증거를 작업 전후로 고정하기 위한 검토표다. 각 항목은 프론트엔드 증상, 배포 승인, 운영 인수에서 같은 기준으로 다시 확인한다.

  • plan diff를 생성, 수정, 교체, 삭제, 권한 변경으로 분류한다.
  • state lock, workspace, provider version, module version을 확인한다.
  • drift 원인을 콘솔 hotfix, 외부 자동화, 코드 누락으로 나눈다.
  • 적용 후 검증 명령과 forward fix를 티켓에 남긴다.
설계작업 단계

필수 산출물 목적, 영향 범위, 비목표, owner

차단 기준 영향 범위가 사용자·시스템·비용 기준으로 설명되지 않음

변경작업 단계

필수 산출물 diff, 승인 기록, 검증 명령

차단 기준 production 변경과 staging 검증의 차이가 설명되지 않음

복구작업 단계

필수 산출물 rollback 또는 forward fix, 담당자, 예상 시간

차단 기준 실패 시 되돌릴 수 없는데 사전 승인과 공지가 없음

PLAYBOOK

실무 플레이북

IaC·변경관리·Drift 플레이북은 IAC CHANGE REVIEW PLAYBOOK 기준으로 증상, 범위, 최근 변경, 계층별 증거를 연결한다. 목표는 명령어를 많이 아는 것이 아니라 어느 가설을 버리고 어떤 완화책을 선택할지 설명하는 것이다.

IAC CHANGE REVIEW PLAYBOOK 1 symptom → 2 scope → 3 recent change → 4 evidence
→ 5 mitigation → 6 verification → 7 runbook diff
1 · 증상symptom
무엇이 안 되는가를 사용자 관점 한 문장으로. "느리다"가 아니라 어떤 요청이 언제부터 어떻게 실패하는지 적는다
2 · 영향 범위scope
전체인가 일부인가. region·tenant·경로·클라이언트 중 무엇으로 갈리는지가 가설의 절반을 지운다
3 · 최근 변경recent change
직전 배포, 설정·권한 변경, 인증서·route 교체를 같은 시간축에 올린다. 대부분의 장애는 최근 변경에서 온다
4 · 증거evidence
plan diff에서 create/update/replace/delete와 IAM·network 변경을 먼저 읽고, state lock·workspace·provider version을 확인한 뒤 실제 리소스를 readback한다
5 · 완화mitigation
되돌릴 수 있는 변경이면 이전 코드로 apply하고, replace/delete가 섞였으면 forward fix를 고른다. 콘솔 수동 수정은 drift로 남으므로 마지막 수단이다
6 · 복구 검증verification
완화가 실제로 먹혔는지 같은 증거로 다시 확인한다. 사용자 경로를 한 번 통과시켜야 끝난 것이다
7 · 런북 갱신runbook diff
이번에 내린 판단을 문서에 되돌린다. 다음 사람이 같은 순서를 다시 발명하지 않게 하는 단계
Plan diff운영 표면

볼 증거 create/update/replace/delete, IAM diff, network diff, downtime risk

판단 기준 replace와 delete는 별도 승인 기준이 필요하다.

State / Drift운영 표면

볼 증거 state lock, workspace, provider version, import/moved block

판단 기준 drift를 무조건 덮어쓰지 않는다.

Apply proof운영 표면

볼 증거 apply output, post-check command, rollback/forward-fix, audit ticket

판단 기준 적용 성공보다 의도한 상태 검증이 중요하다.

리뷰확인 단계

명령·확인 위치 terraform plan -out, terraform show, provider/module version diff

해석 기준 리소스 교체와 권한 확대를 먼저 표시한다.

상태확인 단계

명령·확인 위치 state lock, workspace, drift detection, import 대상 확인

해석 기준 state 조작은 변경 티켓과 백업이 필요하다.

명령·확인 위치 cloud resource readback, route/listener/SG/IAM 실제 상태 확인

해석 기준 plan 결과와 실제 리소스를 대조한다.

PRACTICE

출력 판독 훈련

IaC·변경관리·Drift는 개념을 아는 것보다 실제 출력에서 정상과 비정상을 구분하는 훈련이 중요하다. 아래 lab은 명령, 출력, 판단, 완화, 영구 수정을 한 번에 연결한다.

PRACTICE LAB 01 · Terraform replace 판독

네트워크 변경 PR에서 Load Balancer replacement가 plan에 포함됐다.

Command / Query

terraform plan -out=tfplan

terraform show tfplan

목적 create/update/replace/delete와 downtime risk를 분리한다.

정상 출력

Plan: 0 to add, 2 to change, 0 to destroy.

비정상 출력

# aws_lb.app must be replaced
-/+ resource "aws_lb" "app"
Plan: 1 to add, 0 to change, 1 to destroy.

판단 훈련 이 변경은 단순 설정 변경이 아니라 downtime 가능성이 있는 교체다.

즉시 완화 apply 중단, create-before-destroy 가능성 검토, maintenance window 설정.

영구 수정 LB name/resource identity 변경을 금지하고 destructive plan review gate를 추가한다.

검증 기준 plan에서 replace/delete 0, 실제 LB DNS와 target group 유지.

PRACTICE LAB 02 · State lock 판독

긴급 변경 중 Terraform apply가 lock 오류로 실패한다.

Command / Query

terraform apply tfplan

목적 동시 apply인지 stale lock인지 구분한다.

정상 출력

Apply complete! Resources: 0 added, 2 changed, 0 destroyed.

비정상 출력

Error acquiring the state lock
Lock Info:
  Operation: OperationTypeApply
  Who: ci@runner-12

판단 훈련 다른 apply가 진행 중이거나 이전 실패 lock이 남아 있다. 강제 unlock은 마지막 수단이다.

즉시 완화 현재 apply owner 확인, CI job 중단 여부 확인, 변경 freeze.

영구 수정 state lock owner alert와 apply concurrency guard를 추가한다.

검증 기준 state lock 해제 근거 기록, plan 재생성 후 apply 성공.

TERM

용어사전

IaC·변경관리·Drift에서 반복적으로 등장하는 운영 용어를 정의, 증거, 오해, 관련 항목 기준으로 정리한다. 장애 중에는 용어 자체보다 해당 용어가 어떤 로그, 지표, 설정, 책임 경계와 연결되는지를 확인한다.

IaCTERM
인프라 변경을 코드, 리뷰, 상태, 검증으로 관리하는 방식. 운영에서는 module version, provider lock, PR review로 확인한다. 흔한 오해는 "콘솔 클릭을 코드로 옮기면 IaC 품질이 충분하다."라고 보는 것이다. 관련해서 Terraform, state, plan를 함께 본다.
Terraform state lockTERM
Terraform state에 대한 동시 변경 충돌을 막는 잠금. 운영에서는 state lock, lock owner, apply job로 확인한다. 흔한 오해는 "lock 오류가 나면 즉시 강제 unlock하면 된다."라고 보는 것이다. 관련해서 state backend, apply, concurrency guard를 함께 본다.
planTERM
apply 전 생성, 수정, 교체, 삭제, 권한 변경을 보여주는 변경 예측. 운영에서는 terraform plan/show, IAM diff, network diff로 확인한다. 흔한 오해는 "plan은 통과 의례라 자세히 볼 필요가 없다."라고 보는 것이다. 관련해서 apply, destructive change, review를 함께 본다.
replaceTERM
리소스를 제자리 수정하지 못해 destroy/create로 교체하는 변경. 운영에서는 plan replace, downtime risk, LB replace로 확인한다. 흔한 오해는 "이름 변경은 무해한 수정이다."라고 보는 것이다. 관련해서 create-before-destroy, maintenance window, DNS를 함께 본다.
driftTERM
코드, state, 실제 인프라가 달라진 상태. 운영에서는 drift detection, cloud readback, audit log로 확인한다. 흔한 오해는 "drift는 항상 즉시 되돌려야 한다."라고 보는 것이다. 관련해서 console hotfix, import, moved block를 함께 본다.
CASE

장애/운영 시나리오

Terraform plan에서 Load Balancer가 replace로 표시된다. 단순 apply가 아니라 왜 교체가 필요한지, downtime이 발생하는지, create-before-destroy가 가능한지, DNS와 target group 영향이 무엇인지 리뷰한 뒤 적용 여부를 결정한다.

Triage frame

IaC·변경관리·Drift 장애는 프론트엔드에서 보인 증상 → 영향 범위 → 최근 변경 → Plan diff 증거 → 완화책 → 복구 검증 → 재발 방지 순서로 기록한다.

INCIDENT FLOW

처음 10분 create/update/replace/delete, IAM diff, network diff, downtime risk 기준으로 영향 범위를 고정한다.

다음 30분 terraform plan -out, terraform show, provider/module version diff 항목에서 증거를 모아 완화책을 실행한다.

종료 조건 운영 hotfix가 반복되면 프로세스 문제다.

증상Incident packet

기록할 내용 plan에서 LB replace 또는 SG open 변경

판정 기준 downtime, DNS, target group, 보안 영향 범위를 먼저 계산한다.

완화Incident packet

기록할 내용 create-before-destroy, staged apply, targeted rollback 금지 검토

판정 기준 부분 apply가 state를 더 망칠 수 있음을 고려한다.

사후Incident packet

기록할 내용 drift 원인을 코드에 흡수하거나 콘솔 변경 금지 정책 추가

판정 기준 운영 hotfix가 반복되면 프로세스 문제다.

RISK

자주 틀리는 판단

IaC·변경관리·Drift에서 자주 틀리는 판단은 IaC의 목적와 변경 티켓의 책임 경계를 흐리는 데서 시작된다. 아래 신호가 보이면 설계, runbook, 답변 구조를 다시 점검한다.

  • plan을 보지 않고 apply를 실행한다.
  • drift를 무조건 코드로 덮어써 운영 hotfix를 잃는다.
  • state 파일 권한과 locking을 가볍게 본다.
  • 리소스 이름 변경이 실제 destroy/create로 이어지는 것을 놓친다.
SUMMARY

총정리

IaC·변경관리·Drift의 핵심은 프론트엔드에서 보이는 증상을 운영 계층의 증거와 연결해, 원인 후보를 줄이고 복구 기준을 명확히 말하는 것이다. 아래 표는 리뷰나 면접 직전에 마지막으로 훑는 압축본이다.

주제확인할 증거판단 기준
IaC의 목적module version, provider version, state backend, review history, audit ticket코드화보다 plan/state/리뷰/검증 절차가 핵심이다.
plan과 applycreate/update/replace/delete, IAM diff, network diff, downtime risk, state lockreplace/delete/IAM 확대는 별도 승인 기준이 필요하다.
driftdrift detection, console hotfix, autoscaling change, import target, moved blockdrift를 무조건 덮어쓰면 운영 hotfix를 잃을 수 있다.
변경 티켓purpose, impact, plan summary, apply window, validation command, rollback/forward fixDB/DNS/network 변경은 전파와 lock 때문에 더 작게 쪼개야 한다.
실무 플레이북Plan diff → State / Drift → Apply proofterraform plan -out, terraform show, provider/module version diff; state lock, workspace, drift detection, import 대상 확인; cloud resource readback, route/listener/SG/IAM 실제 상태 확인
복구 기준plan에서 LB replace 또는 SG open 변경운영 hotfix가 반복되면 프로세스 문제다.
