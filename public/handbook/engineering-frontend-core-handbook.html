FE-01

실무 프론트엔드의 역할

프론트엔드의 성공 기준은 디자인 시안을 화면에 옮겼는지가 아니라 사용자가 목적을 끝까지 달성할 수 있는지입니다. 정상·대기·빈 결과·오류·권한 없음 상태가 일관되게 설명되고, 기능이 바뀌어도 그 흐름을 안전하게 유지할 수 있어야 합니다.

관점기본 구현제품 기능시스템 품질
성공 기준디자인과 비슷하게 구현상태·에러·권한·빈 화면까지 흐름을 완성제품과 팀이 유지 가능한 UI 시스템 설계
컴포넌트props를 받아 화면 출력역할·소유 상태·합성 경계를 명확히 함도메인 변화와 디자인 시스템 확장을 흡수
네트워크API 호출 후 데이터 표시로딩·재시도·낙관 업데이트·캐시 무효화 설계사용자 경험과 백엔드 계약을 함께 조율
품질로컬에서 동작 확인접근성·성능·테스트·관측가능성을 기본값으로 둠품질 기준을 자동화하고 팀의 반복 비용을 줄임

이 세 수준은 직급을 나누는 표가 아니라 한 기능을 어디까지 책임질지 보여주는 범위입니다. 예를 들어 목록 화면을 만든다면 데이터를 표시하는 것만으로는 충분하지 않습니다. 첫 요청이 느릴 때 무엇을 보여줄지, 결과가 없을 때 사용자가 다음에 무엇을 할지, 권한이 바뀌거나 저장이 실패했을 때 기존 입력을 어떻게 보존할지까지 연결되어야 제품 기능이 됩니다.

여기에 팀 차원의 재사용과 운영을 더하면 시스템 품질의 문제가 됩니다. 같은 로딩·오류·권한 패턴을 화면마다 다시 만들지 않도록 공통 계약을 두고, 테스트와 관측 지표로 회귀를 발견할 수 있게 만드는 단계입니다. 따라서 프론트엔드의 책임은 화면 구현에서 끝나지 않고 사용자가 작업을 완료하는 흐름과 팀이 그 흐름을 지속적으로 변경할 수 있는 구조까지 이어집니다.

CORE STANCE

프론트엔드 역량은 사용한 라이브러리 수보다 사용자 흐름, 상태의 소유권, 실패 뒤 복구 방법을 명확히 설계하는 능력에서 드러납니다. “클릭하면 모달이 열린다”에서 끝내지 않고, 권한이 없거나 저장이 지연되고 네트워크가 끊겨도 사용자가 현재 상태와 다음 행동을 이해하는지까지 확인해야 합니다.

FE-02

브라우저를 알아야 하는 이유

React와 Vue도 브라우저의 실행·렌더링·네트워크 규칙 안에서 동작합니다. 이벤트 처리와 화면 갱신이 언제 지연되는지 알아야 프레임워크의 재렌더링 문제와 브라우저 자체의 병목을 구분할 수 있습니다. 세부 진단 방법은 뒤의 브라우저 동작 원리에서 다룹니다.

개념의미실무 영향
이벤트 루프콜스택, 태스크, 마이크로태스크, 렌더링 기회를 순서대로 처리긴 JS 작업은 입력 반응성을 막음. 무거운 계산은 쪼개거나 worker로 이동
DOM문서 객체 모델. 브라우저가 화면 구조를 표현하는 트리빈번한 레이아웃 읽기·쓰기 섞임은 reflow를 유발
CSSOMCSS 규칙 트리복잡한 selector와 전역 cascade는 예측 비용을 키움
렌더링 파이프라인style → layout → paint → compositetransform/opacity는 비교적 싸고, width/height/top 변경은 layout 비용이 큼

이 개념들은 따로 움직이지 않습니다. 사용자가 버튼을 누르면 이벤트 핸들러가 실행되고 상태가 바뀌며, 그 결과 DOM이나 스타일이 변경됩니다. 브라우저는 변경된 부분의 스타일과 배치를 다시 계산한 뒤 픽셀을 그리고 화면에 합성합니다. 어느 단계가 오래 걸려도 사용자는 같은 현상, 즉 “눌렀는데 늦게 반응한다”로 경험합니다.

실무 성능 최적화는 대부분 "무엇이 비싼지"를 구분하는 일입니다. 렌더링을 줄인다고 무조건 빨라지는 것이 아니라, 사용자가 체감하는 병목이 JS 실행인지, 네트워크인지, layout인지, 이미지인지 먼저 측정해야 합니다.

MEASURE FIRST

렌더링 병목을 React memo로 해결하려 하기 전에 Chrome Performance, React Profiler, Network 탭을 먼저 봅니다. "느린 것 같다"는 근거가 아니고, "입력 후 main thread가 220ms 막힌다" 또는 "초기 JS가 900KB라 hydration 전까지 버튼이 죽어 있다"가 근거입니다.

FE-03

HTML·CSS UI 계약

HTML은 콘텐츠와 행동의 의미를 정의하고, CSS는 그 의미와 상태를 시각적으로 표현합니다. 브라우저·보조기술·자동화 테스트는 이 구조를 함께 읽으므로 요소 선택과 문서 구조는 곧 UI 계약입니다. 접근 가능한 이름, ARIA, 키보드 상호작용은 웹접근성 파트에서 이어서 다룹니다.

선택좋은 기본값피해야 할 패턴
버튼<button type="button"><div onClick>에 role만 붙이기
링크이동은 <a href>페이지 이동을 button으로 처리
폼label, name, 오류 메시지 연결placeholder만 라벨처럼 사용
레이아웃semantic landmark, heading 순서 유지시각 크기 때문에 heading 레벨 건너뛰기

CSS는 "꾸미기"가 아니라 상태와 구조의 표현입니다. 전역 cascade, specificity 경쟁, 임의 spacing이 쌓이면 작은 변경도 위험해집니다. 토큰, 컴포넌트 경계, 반응형 제약을 일관되게 두면 디자인 품질과 유지보수성이 같이 올라갑니다.

UI CONTRACT

개요 문서에서는 기본 계약만 잡습니다. 버튼은 버튼으로, 이동은 링크로, 폼은 label과 name으로 시작합니다. 세부 접근성 판단은 별도 접근성 파트에서 한 번만 깊게 다룹니다.

FE-04

컴포넌트 설계와 합성

컴포넌트는 재사용 가능한 조각이기 전에 책임 경계입니다. 좋은 컴포넌트는 "무엇을 하는지, 무엇을 몰라도 되는지, 어디까지 바꿔도 소비자가 깨지지 않는지"가 명확합니다.

패턴언제 쓰나주의점
Presentational데이터를 받아 그리기만 할 때비즈니스 로직이 섞이면 테스트와 재사용성이 떨어짐
Container데이터 조회, mutation, 권한, 라우팅 맥락을 묶을 때너무 커지면 페이지 전체가 한 컴포넌트가 됨
CompoundTabs, Dialog, Menu처럼 내부 부품이 협력할 때암묵적 규칙이 많아지면 사용법이 어려움
Headless동작과 UI 스타일을 분리해야 할 때접근성 책임이 호출자에게 넘어가지 않게 주의

패턴 이름보다 중요한 것은 컴포넌트가 소유할 결정입니다. 데이터 조회와 권한 판단은 기능 경계에서 맡고, 버튼의 크기나 색처럼 제품 전체에서 반복되는 표현은 디자인 시스템이 맡는 편이 자연스럽습니다. 호출자가 컴포넌트 내부의 세부 동작을 계속 조종해야 한다면 책임 경계가 잘못 나뉘었을 가능성이 큽니다.

합성은 이런 경계를 유지하면서 변형을 허용하는 방법입니다. 부모는 전체 구조와 공통 규칙을 제공하고, 자식은 각 영역의 콘텐츠를 맡습니다. 반대로 boolean 속성을 계속 추가하면 가능한 조합이 급격히 늘고, 어떤 조합이 유효한지 컴포넌트 내부에서도 설명하기 어려워집니다.

COMPOSITION OVER CONFIGURATION

이 카드는 절차나 구조를 키워드로만 외우지 않고, 실제 작업에서 어떤 판단 순서와 검증 증거를 함께 봐야 하는지 확인하기 위한 실행 맥락입니다. 각 줄은 구현 단계, 실패 가능성, 리뷰 기준을 같이 점검하라는 신호입니다.

좋은 방향
<Card>
  <CardHeader>프로젝트</CardHeader>
  <CardBody><ProjectList /></CardBody>
</Card>

위험 신호
<Card title="프로젝트" body={list} padded bordered compact interactive />

props가 늘어나는 것은 컴포넌트가 너무 많은 결정을 떠안고 있다는 신호일 수 있습니다. variant가 제품의 실제 의미를 표현하는지, 아니면 호출자가 내부 구현을 조종하기 위한 스위치인지 구분해야 합니다.

BOUNDARY CHECK

컴포넌트를 나눌 때 "파일 수를 줄이는가"가 아니라 "변경 이유를 분리하는가"를 봅니다. 디자인만 바뀌는 컴포넌트와 데이터 계약이 바뀌는 컴포넌트는 다른 속도로 변합니다. 같은 파일에 묶이면 작은 디자인 변경이 데이터 로직 회귀로 이어집니다.

FE-05

상태 관리와 서버 상태

상태 설계의 출발점은 저장 도구가 아니라 소유권과 생명주기입니다. 누가 값을 바꾸는지, URL로 공유하거나 새로고침 뒤 복원해야 하는지, 서버가 최종 진실인지에 따라 상태의 위치와 동기화 방법이 달라집니다.

상태의 위치는 “몇 군데에서 쓰는가”만으로 정하지 않습니다. 주소를 복사했을 때 같은 화면을 보여줘야 하는 필터는 URL에 있어야 하고, 서버에서 다시 받을 수 있는 목록은 서버 상태 캐시가 맡아야 합니다. 모달의 열림 여부처럼 해당 화면을 떠나면 의미가 사라지는 값은 가능한 가까운 컴포넌트에 두는 편이 좋습니다.

전역 저장소는 여러 곳에서 접근하기 쉽지만 값의 생성·변경·폐기 시점을 흐리게 만들 수 있습니다. 먼저 상태가 유지되어야 하는 기간과 진실의 원천을 정한 뒤, 그 조건을 만족하는 가장 좁은 위치를 선택합니다. 도구는 이 판단 뒤에 따라옵니다.

서버 상태는 클라이언트가 소유하지 않습니다. 캐시된 복사본일 뿐입니다. 그래서 stale time, refetch, optimistic update, invalidation 같은 개념이 필요합니다. "전역 store에 API 결과 저장"은 캐시 무효화, 중복 요청, stale data 문제를 직접 떠안겠다는 뜻입니다.

FE-06

API 연동과 에러·로딩 UX

API 연동은 원격 상태의 불확실성을 UI에 번역하는 일입니다. 응답을 기다리는 동안의 상태, 데이터 없음, 권한 거부, 부분 실패, 재시도 가능 여부, 중복 제출까지 정의해야 하나의 사용자 흐름이 완성됩니다.

오류 메시지는 기술적 원인을 그대로 노출하는 대신 사용자가 선택할 행동을 알려야 합니다. 다시 시도하면 되는지, 입력을 고쳐야 하는지, 로그인이나 권한 요청이 필요한지를 구분합니다. 복구할 수 없는 오류라면 입력 내용을 보존하고 문의에 사용할 추적 번호를 제공하는 편이 단순한 “오류가 발생했습니다”보다 유용합니다.

백엔드 API는 완벽히 안정적이지 않습니다. 프론트엔드는 실패를 감추는 층이 아니라 실패를 사용자가 이해 가능한 행동으로 바꾸는 층입니다. 같은 500이라도 저장 실패, 조회 실패, 결제 실패의 UI는 다릅니다.

FE-07

폼·검증·사용자 입력

폼은 입력값만 저장하는 화면이 아니라 사용자 입력을 검증된 서버 명령으로 바꾸는 상태 흐름입니다. 초기값과 현재 값, 방문 여부, 검증 결과, 제출 중 상태, 서버의 거절 사유를 구분해야 오류를 정확히 보여주고 입력을 잃지 않습니다.

세 검증은 서로 대체하지 않습니다. 브라우저의 기본 제약은 입력 단계에서 빠른 피드백을 주고, 클라이언트 검증은 여러 필드의 관계나 제품 문구를 다듬습니다. 서버는 클라이언트를 신뢰하지 않고 권한·중복·현재 데이터까지 다시 확인합니다. 같은 규칙이 여러 층에 있더라도 각 층의 목적이 다릅니다.

제출 실패 뒤의 동작도 폼 계약에 포함됩니다. 사용자가 고칠 수 있는 필드 오류는 해당 입력과 연결하고, 인증 만료나 서버 장애처럼 폼 전체의 문제는 요약 영역에서 설명합니다. 오류가 발생했다고 모든 입력을 초기화하면 사용자가 이미 수행한 작업을 잃으므로, 성공적으로 저장되기 전까지 초안을 보존하는 것이 기본값에 가깝습니다.

클라이언트 검증은 사용자 경험을 위한 것이고, 서버 검증은 시스템 무결성을 위한 것입니다. 클라이언트에서 막았다고 서버가 믿으면 안 됩니다. 반대로 서버만 믿고 클라이언트 피드백을 없애면 사용자는 실패 이유를 너무 늦게 알게 됩니다.

FE-08

성능: 번들·렌더링·메모이제이션

프론트엔드 성능은 초기 로드, 상호작용 반응성, 화면 안정성으로 나뉩니다. "빠르다"는 하나의 숫자가 아니라 사용자 여정의 여러 지점입니다.

영역주요 병목대응
초기 로드JS 번들, CSS, 폰트, 이미지code splitting, lazy loading, preload 기준 정리
렌더링불필요한 re-render, 큰 리스트, layout thrash컴포넌트 경계, virtualization, 측정 후 memo
상호작용긴 main thread 작업작업 분할, worker, transition, debounce
화면 안정성이미지·폰트·동적 콘텐츠 크기 변화크기 예약, skeleton, font-display 전략

성능 영역은 사용자 여정의 서로 다른 순간을 설명합니다. 초기 로드는 콘텐츠를 보기까지의 시간이고, 상호작용 성능은 클릭이나 입력 뒤 변화가 보이기까지의 시간이며, 화면 안정성은 사용자가 누르려던 요소가 갑자기 이동하지 않는지를 뜻합니다. 한 지표가 좋아도 다른 경험은 나쁠 수 있으므로 “페이지가 빠르다”는 말만으로는 개선 대상을 정할 수 없습니다.

최적화는 측정값과 원인을 연결한 뒤 적용합니다. 초기 JavaScript가 크다면 코드 분할이 후보지만, 이미 필요한 코드만 내려받고 있다면 네트워크 요청을 더 잘게 나누는 것이 오히려 지연을 늘릴 수 있습니다. 입력 지연이 큰 경우에도 재렌더링 횟수보다 이벤트 핸들러의 동기 작업이나 큰 데이터 변환이 실제 원인일 수 있습니다.

memo, useMemo, useCallback은 성능 마법이 아닙니다. 비교 비용과 복잡도를 추가합니다. 문제가 "같은 props인데 자주 다시 그려진다"일 때 유효하고, 네트워크나 큰 번들이 병목일 때는 효과가 없습니다. React.memo는 props 얕은 비교에만 관여하므로 자신의 state나 context 변경에는 다시 렌더링되고, 객체·배열·함수 props의 identity가 매번 바뀌면 효과가 줄어듭니다.

useTransition은 상태 업데이트를 non-urgent로 표시해 입력 같은 urgent update가 먼저 반영될 수 있게 하는 도구입니다. 무거운 계산을 worker처럼 다른 thread로 옮기는 기능은 아니므로 작업 분할, virtualization, worker 이동과 함께 판단합니다.

PERFORMANCE SMELL

초기 번들에 관리자 화면, 차트 라이브러리, markdown parser, 에디터가 모두 들어 있으면 첫 화면이 느려집니다. 사용자가 지금 당장 쓰지 않는 기능은 route 단위나 기능 단위로 늦게 불러옵니다. 단, code splitting 후 route 진입 시 JS/CSS chunk와 데이터 요청 waterfall이 생길 수 있으므로 treemap과 Network waterfall로 실제 효과를 확인합니다.

FE-10

테스트 전략

프론트엔드 테스트는 DOM 구조를 얼리는 것이 아니라 사용자 행동을 검증해야 합니다. 좋은 테스트는 refactor를 방해하지 않으면서 회귀를 잡습니다.

테스트검증 대상좋은 예
단위순수 함수, formatter, reducer가격 포맷, 권한 계산, validation schema
컴포넌트사용자 상호작용과 DOM 결과필터 입력 후 목록이 줄어듦, 저장 실패 메시지 표시
E2E핵심 사용자 여정로그인, 생성, 결제, 권한별 접근

테스트 종류는 서로의 상위·하위 관계가 아니라 다른 위험을 잡는 도구입니다. 가격 계산처럼 입력과 출력이 분명한 규칙은 단위 테스트가 빠르고 정확합니다. 반면 저장 버튼을 누른 뒤 오류가 필드에 연결되는지는 컴포넌트와 네트워크 응답을 함께 실행해야 확인할 수 있습니다. 로그인부터 결제 완료까지 여러 시스템이 이어지는 흐름은 적은 수의 E2E 테스트로 보호합니다.

테스트 범위는 구현 구조가 아니라 실패했을 때의 피해를 기준으로 정합니다. 데이터 손실·결제·권한처럼 위험이 큰 흐름은 정상 경로뿐 아니라 시간 초과, 중복 제출, 권한 거부도 검증합니다. 스타일 변경이 여러 화면에 퍼지는 공통 컴포넌트는 시각 회귀와 키보드 검사를 함께 두는 편이 효과적입니다.

테스트는 구현 세부가 아니라 계약을 잡아야 합니다. "이 hook이 두 번 호출된다"보다 "사용자가 저장하면 성공 메시지와 새 데이터가 보인다"가 더 오래 갑니다.

2. 사용자 플로우는 통합 테스트에서 네트워크 성공·실패를 모두 검증한다.
3. 결제, 권한, 데이터 손실 가능성이 있는 흐름은 E2E로 행복 경로와 실패 경로를 둔다.
4. 접근성 회귀는 키보드 이동, accessible name, 오류 연결을 PR 체크리스트에 포함한다.

FE-12

보안: XSS·CSRF·토큰 저장

프론트엔드 보안의 시작은 브라우저가 적대적 입력을 어떻게 실행 가능한 코드로 바꾸는지 이해하는 것입니다. DOM에 넣는 순간, URL로 이동하는 순간, storage에 저장하는 순간 위험이 달라집니다.

위험원인대응
XSS사용자 입력을 HTML/JS로 실행escape 기본값 유지, sanitize, CSP, dangerouslySetInnerHTML 최소화
CSRF쿠키가 cross-site 요청에 자동 첨부SameSite, CSRF token, 중요 mutation 재인증
토큰 탈취localStorage token을 XSS가 읽음짧은 access token, HttpOnly cookie 검토, refresh rotation
open redirect검증 안 된 redirect URL 사용상대 경로만 허용, allowlist 검증

React는 기본적으로 문자열을 escape하지만, 그 안전장치를 직접 끄는 순간 책임이 개발자에게 넘어옵니다. 외부 HTML, markdown, CMS 콘텐츠를 렌더링할 때는 sanitize가 필수입니다.

TOKEN STORAGE TRADEOFF

localStorage는 다루기 쉽지만 XSS에 취약합니다. HttpOnly 쿠키는 JS가 읽을 수 없지만 CSRF 방어가 필요합니다. 정답은 서비스의 위협 모델에 따라 다릅니다. 중요한 것은 "어디가 위험한지"를 알고 access token 수명, refresh token 회전, SameSite, CSP를 함께 설계하는 것입니다.

시니어 프론트엔드 아키텍처는 폴더 구조를 예쁘게 나누는 일이 아니라 변경이 어디까지 전파되는지 제한하는 일입니다. route, feature, entity, shared layer, design system, platform adapter가 서로 무엇을 알고 무엇을 몰라야 하는지 규칙으로 남겨야 합니다.

사용자가 끝내야 하는 작업 단위. 폴더 구조가 아니라 이것이 경계의 출발점이다

DEPENDENCY RULE AND PUBLIC API GATE

4. platform SDK는 adapter 뒤에서만 접근한다
5. public API 변경은 consumer diff와 migration note를 남긴다
FE-16

서버 상태·캐시 일관성

서버 상태는 클라이언트가 소유한 데이터가 아니라 특정 시점의 복사본입니다. 고급 프론트엔드는 데이터를 “가져왔다”에서 멈추지 않고 stale, invalidation, optimistic rollback, conflict, multi-tab drift, URL 복원까지 하나의 일관성 모델로 다룹니다.

SERVER STATE CONSISTENCY MODEL
1 query key → 2 fetch policy → 3 stale time → 4 mutation scope
→ 5 optimistic patch → 6 rollback snapshot → 7 invalidation target
→ 8 conflict resolution → 9 multi-tab sync → 10 release telemetry
1 · 쿼리 키query key
무엇이 데이터의 정체성을 바꾸는가. route params, 필터, auth scope, locale을 키에 명시한다
2 · 조회 정책fetch policy
언제 가져오는가 — mount, focus, 재연결, polling 중 무엇을 켤지 정한다
3 · 허용 낡음stale time
얼마나 낡아도 안전한가. 가격·권한은 짧게, 문서·코드는 길게 잡는다
4 · 변경 범위mutation scope
이 쓰기가 어떤 키의 데이터를 바꾸는가. 여기서 무효화 대상이 결정된다
5 · 낙관적 패치optimistic patch

BR-01

브라우저는 앱 런타임이다

브라우저는 문서를 보여주는 뷰어를 넘어 네트워크 요청, 문서 파싱, JavaScript 실행, 픽셀 렌더링, 저장소, 보안 경계를 함께 관리하는 애플리케이션 런타임입니다. 프론트엔드 코드는 이 실행 환경의 순서와 자원 제약 안에서 동작합니다.

영역하는 일프론트엔드 판단
파싱HTML/CSS/JS를 읽어 구조화blocking script와 critical CSS 관리
JS 엔진코드 실행, microtask 처리긴 작업을 쪼개 input delay를 줄임
렌더링 엔진layout, paint, composite비싼 스타일 변경과 layout thrash 회피
네트워크요청 우선순위, cache, connection 관리preload, lazy loading, cache header 이해

사용자가 페이지를 열면 브라우저는 HTML을 받는 동시에 필요한 CSS·JavaScript·이미지를 발견하고 요청합니다. 파싱 결과로 DOM과 CSSOM을 만들고, JavaScript가 상태나 구조를 바꾸면 렌더링 엔진이 필요한 단계를 다시 수행합니다. 이 과정이 한 번 끝나는 것이 아니라 입력, 네트워크 응답, 애니메이션마다 반복됩니다.

따라서 프론트엔드 문제는 한 계층만 보고 판단하기 어렵습니다. 버튼 반응이 늦은 원인이 이벤트 핸들러일 수도 있고, 그 뒤 실행된 대규모 레이아웃 계산일 수도 있습니다. 먼저 사용자가 느끼는 증상을 고정한 뒤 Network와 Performance 기록에서 실제로 시간이 쓰인 계층을 찾아야 합니다.

핵심 관점

브라우저는 한 번에 모든 일을 하지 않습니다. JS가 main thread를 오래 점유하면 클릭, 스크롤, 렌더링이 밀립니다. UI 성능은 "코드가 빠른가"보다 브라우저에게 렌더링할 기회를 주는가에 가깝습니다.

BR-02

이벤트 루프와 태스크 큐

JavaScript는 한 번에 하나의 작업을 실행하며, 이벤트 루프는 태스크와 마이크로태스크를 처리한 뒤 브라우저가 화면을 갱신할 기회를 만듭니다. 한 작업이 오래 걸리면 다음 입력 처리와 렌더링도 함께 늦어집니다.

EVENT LOOP ORDER
1 task 하나 실행 (click, timer, network callback 등)
→ 2 microtask queue 모두 비움 (Promise, queueMicrotask)
→ 3 필요하면 style/layout/paint/composite
→ 4 다음 task 선택
1 · 태스크 실행task
큐에서 콜백 하나를 꺼내 끝까지 실행한다. 실행이 끝나기 전에는 렌더링도 다른 태스크도 끼어들지 못한다
2 · 마이크로태스크 비우기microtask
태스크가 끝나면 Promise 후속 처리를 남김없이 실행한다. 여기서 또 microtask를 만들면 렌더링이 계속 미뤄진다
3 · 렌더링style/layout/paint
필요할 때만 화면을 갱신한다. 앞의 태스크가 길면 이 단계가 오지 못해 화면이 멈춘 것처럼 보인다
4 · 다음 태스크 선택next task
그다음 큐에서 하나를 꺼낸다. 긴 작업을 잘게 쪼개야 하는 이유가 여기 있다
도구특징사용 기준
Promise.thenmicrotask. 렌더링 전에 몰아서 실행짧은 후속 처리
setTimeouttask. 다음 turn으로 미룸작업 분할, UI 반응성 확보
requestAnimationFrame다음 repaint 전에 애니메이션 콜백 실행을 요청애니메이션과 layout 읽기 타이밍
requestIdleCallbackidle period에 낮은 우선순위 작업 예약. 지원 범위와 timeout 필요성 확인필수 작업, 입력 직후 피드백, animation에는 사용하지 않음

중요한 점은 Promise가 “비동기”라는 사실만으로 화면을 양보하지는 않는다는 것입니다. 현재 태스크가 끝난 뒤 마이크로태스크가 모두 처리되어야 렌더링 기회가 오므로, 긴 Promise 연쇄도 화면 갱신을 막을 수 있습니다. 반대로 다음 태스크로 작업을 넘기면 브라우저가 그 사이 입력과 렌더링을 처리할 기회를 얻습니다.

작업 분할은 전체 계산량을 줄이지 않지만 사용자가 느끼는 멈춤을 줄입니다. 계산 자체가 크고 DOM이 필요 없다면 Web Worker로 옮겨 메인 스레드와 분리하고, 화면 갱신에 필요한 작은 작업이라면 여러 태스크로 나누어 진행 상태를 보여주는 방식을 검토합니다.

접근성은 UI의 계약

사용자는 마우스와 화면만으로 UI를 경험하지 않습니다. 키보드, 스크린 리더, 확대 화면 등 어떤 방식으로 접근하더라도 요소의 이름·역할·상태와 가능한 행동이 같은 의미로 전달되어야 합니다.

품질나쁜 기준좋은 기준
탐색마우스로만 가능키보드만으로 모든 기능 접근
의미div와 span으로 전부 구현button, a, nav, main, form 등 의미 요소 사용
상태색으로만 알림텍스트, aria, focus, live region으로 전달
오류빨간 테두리만 표시오류 문구와 필드를 연결하고 수정 방법 제공

접근성 계약은 세 부분으로 볼 수 있습니다. 먼저 요소가 무엇인지 알려주는 이름과 역할이 있어야 합니다. 다음으로 선택됨, 펼쳐짐, 오류 같은 현재 상태가 전달되어야 합니다. 마지막으로 키보드나 보조기술로 실제 행동을 완료할 수 있어야 합니다. 셋 중 하나라도 빠지면 화면은 보이지만 일부 사용자에게는 기능이 없는 것과 같습니다.

예를 들어 휴지통 아이콘이 시각적으로 명확해 보여도 스크린 리더가 “버튼”이라고만 읽으면 무엇을 삭제하는지 알 수 없습니다. 이름을 제공했더라도 키보드로 도달할 수 없거나 삭제 뒤 포커스가 사라지면 작업 흐름은 완성되지 않습니다. 접근성은 속성 하나를 추가하는 일이 아니라 의미와 행동 전체를 맞추는 일입니다.

PRODUCT QUALITY

접근성은 법적 요구이기 전에 제품 품질입니다. 키보드 탐색, 명확한 label, 충분한 contrast는 장애 사용자뿐 아니라 빠른 작업자, 모바일 사용자, 임시 장애 상황의 사용자에게도 직접적인 개선입니다.

A11Y-04

ARIA 사용 기준

ARIA는 기본 HTML만으로 표현하기 어려운 이름·관계·상태를 보조기술에 전달합니다. 역할을 선언해도 키보드 동작과 상태 관리는 자동으로 생기지 않으므로, 기본 요소를 대체할 때는 그 행동까지 직접 구현해야 합니다.

원칙설명

role은 행동까지 책임role만 붙이면 키보드 동작은 자동으로 생기지 않음
이름을 제공아이콘 버튼에는 aria-label 필요
관계를 연결aria-controls, aria-describedby로 상태/오류 연결

ARIA 실패 모드

패턴문제수정

aria-hidden="true"를 부모에 적용내부 focus 가능한 요소가 보조기술에서 사라짐숨김 영역 안에 focusable 요소가 남지 않게 처리

ARIA 속성은 접근성 트리에 전달되는 정보만 바꿉니다. aria-expanded="true"를 붙여도 패널이 열리지 않고, role="button"을 붙여도 Space 키 처리나 비활성 동작이 생기지 않습니다. 시각적 상태, DOM 상태, ARIA 상태를 같은 상태 값에서 파생해야 서로 어긋나지 않습니다.

복잡한 위젯에서는 역할 사이의 관계도 중요합니다. 탭은 자신이 제어하는 패널과 연결되어야 하고, 콤보박스는 현재 활성화된 선택지와 목록의 열림 상태를 알려야 합니다. 속성을 개별적으로 암기하기보다 “사용자가 지금 무엇을 조작하며 결과가 어디에 나타나는가”를 접근성 트리에서도 설명할 수 있는지 확인합니다.
