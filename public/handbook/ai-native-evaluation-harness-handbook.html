프론트엔드
구현 루프

AI agent는 컴포넌트 초안을 빠르게 만들 수 있지만, 풀스택 개발자는 상태, 접근성, 반응형, 기존 디자인 시스템을 검증해야 합니다.

FE-00

프론트 구현에서 AI를 쓰는 방식

AI에게 화면 전체를 맡기기보다 작고 검증 가능한 단위로 위임합니다. 예를 들어 백오피스 환불 승인 기능에서는 RefundRequestTable, RefundDetailDrawer, RefundDecisionForm, AuditLogPanel처럼 상태 경계가 분명한 컴포넌트 단위로 나눕니다.

위임하기 좋은 일사람이 직접 판단할 일
컴포넌트 초안, props 타입, 상태 분기디자인 시스템 일관성
폼 validation 후보제품 문구와 오류 우선순위
테스트 후보진짜 위험 케이스 선택
리팩터링 제안기존 코드 경계 유지
FE-01

프론트엔드 AI Loop

FRONTEND LOOP UI 계약 제공 -> 컴포넌트 초안 -> 상태/접근성 검토 -> 테스트 추가 -> 브라우저 확인 -> diff 기록

  constraints:

    - "승인/반려 중 중복 제출 방지"
    - "already_processed와 payment_provider_failed 오류 분리"
  output:
    - component_outline
    - state_cases
    - test_cases
USE

실제로 이렇게 사용한다

프론트 구현에서 AI를 쓸 때는 컴포넌트 전체를 알아서 만들게 하지 않습니다. 기존 컴포넌트, props, 상태, 오류 코드를 먼저 주고 초안을 받습니다.

내 입력:
RefundDecisionForm 컴포넌트를 만들 거야.
기존 디자인 시스템의 Button, Textarea, Modal을 사용해야 해.

상태:
- idle
- submitting
- success
- error

오류 코드:
- missing_reason
- invalid_refund_amount
- already_processed
- payment_provider_failed
- forbidden

너는 Frontend Builder야.
코드를 바로 많이 쓰지 말고 먼저:
1. 컴포넌트 구조
2. props
3. 상태 분기
4. 테스트 케이스
를 제안해줘.
AI 출력 예사람이 검토할 점
컴포넌트 내부에서 직접 fetch 호출프로젝트의 mutation hook과 optimistic update 정책에 맞는지 확인
새로운 Button 스타일 추가기존 디자인 시스템 사용으로 수정
already_processed와 provider 실패를 unknown으로 처리already_processed와 payment_provider_failed를 분리하도록 수정

개념

프론트엔드에서 AI Loop의 핵심은 코드량이 아니라 상태 계약입니다. 상태와 오류 코드가 고정되지 않으면 AI가 만든 UI는 쉽게 그럴듯한 데모가 됩니다.

FE-02

구현 계약

항목계약
propsrefundRequestId, currentStatus, refundableAmount, onDecisionSaved
상태idle, editing, confirming, submitting, success, error
오류missing_reason, invalid_refund_amount, already_processed, payment_provider_failed, forbidden, unknown
접근성reason label 연결, error aria-describedby, modal focus trap
반응형좁은 화면에서 drawer가 full-screen panel로 전환
FE-03

검증 기준

검증확인
상태 검증각 오류 코드와 권한 없음 상태가 다른 메시지로 보이는가
접근성 검증키보드만으로 drawer 확인, confirm, 취소가 가능한가
반응형 검증좁은 화면에서 텍스트와 버튼이 겹치지 않는가
회귀 검증기존 주문 상세와 환불 목록 화면이 깨지지 않는가
GATE

프론트 구현 Eval gate

AI가 만든 UI 초안은 눈으로 보기 전에 fixture로 먼저 거른다. 승인/반려 기능처럼 운영 리스크가 큰 화면은 happy path, 중복 제출, 권한 없음, 이미 처리됨, 모바일 좁은 폭, 키보드 조작을 최소 eval gate로 둔다.

Fixture통과 기준반려 조건
already_processed409 오류가 전용 메시지로 보이고 버튼이 다시 활성화되지 않음unknown error toast 하나로 처리
forbidden승인/반려 버튼은 read-only 상태와 이유로 대체프론트에서 버튼만 숨기고 API 권한 테스트가 없음
double_submitsubmitting 중 approve/reject 모두 disabled, idempotency key 유지빠른 더블클릭으로 두 요청이 나감
keyboard_modalfocus trap, Escape, confirm/cancel 순서가 키보드로 동작마우스로만 닫히거나 focus가 배경으로 빠짐
mobile_360drawer가 full-screen panel로 바뀌고 버튼 텍스트가 겹치지 않음고정 폭 때문에 금액/사유/버튼이 겹침
frontend_eval_gate:
  command_examples:
    - "npm test -- RefundDecisionForm"
    - "npm run test:e2e -- refund-decision.spec.ts"
    - "npm run build"
  fixtures:
    already_processed:
      api_status: 409
      expected_ui: "이미 처리된 환불 요청입니다"
    double_submit:
      action: "approve button clicked twice within 300ms"
      expected_network_calls: 1
    mobile_360:
      viewport: "360x740"
      expected_layout: "full-screen decision panel, no clipped button text"
  rejected_submission:
    symptom: "AI 초안은 시각적으로 맞지만 fixture 3개가 unknown error로 합쳐짐"
    reviewer_comment: "상태 계약을 검증하지 않았으므로 반려"
  ci_gate:
    pass: "unit + a11y smoke + e2e critical fixtures pass"
    fail: "권한/중복/이미 처리됨 fixture 중 하나라도 실패하면 merge 금지"
