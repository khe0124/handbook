CS-01

Q. Big-O 시간/공간 복잡도는 어떻게 설명하나요?

핵심 개념

Big-O는 입력 크기가 커질 때 실행 시간이나 메모리 사용량이 어떻게 증가하는지 상한 관점으로 표현합니다.

개념 해부

Big-O는 특정 컴퓨터에서 몇 ms 걸리는지를 맞히는 도구가 아니라 입력이 커질 때 비용이 어떤 모양으로 증가하는지 보는 언어입니다. 낮은 차수 항과 상수를 버리는 이유는 큰 입력에서 지배적인 증가율을 보기 위해서입니다. 다만 실무에서는 입력 크기, 호출 빈도, I/O 비용, 메모리 locality 때문에 이론 복잡도만으로 판단하면 안 됩니다.

30초 답변

Big-O는 입력 n이 커질 때 비용 증가 추세를 보는 표기입니다. O(1), O(log n), O(n), O(n log n), O(n²)처럼 표현하며, 실무에서는 데이터가 커졌을 때 현재 알고리즘이 버틸 수 있는지 판단하는 데 씁니다.

90초 답변

상수 시간도 실제로는 상수가 크면 느릴 수 있고, O(n)도 n이 작으면 충분할 수 있습니다. 면접에서는 “이중 루프라 O(n²)입니다”보다 입력 크기, 호출 빈도, 메모리 trade-off, 캐시/DB 같은 외부 비용을 함께 말하면 좋습니다.

꼬리질문

질문답변 방향
공간 복잡도?추가 자료구조나 recursion stack이 쓰는 메모리 증가량입니다.
O(log n) 예?정렬된 배열 binary search, balanced tree 탐색입니다.
실무 연결?대용량 grid filtering, API pagination, DB scan 비용으로 연결합니다.
CS-02

Q. Array/List/Map/Set/Heap/Queue/Stack/Tree/Graph는 언제 쓰나요?

핵심 개념

자료구조 선택은 접근 패턴, 삽입/삭제 비용, 정렬 필요성, 중복 허용, 우선순위, 관계 표현에 따라 달라집니다.

개념 해부

자료구조는 데이터를 담는 통이 아니라 필요한 연산의 비용표입니다. Array는 index 접근이 빠르지만 중간 삽입/삭제가 비싸고, HashMap은 평균 조회가 빠르지만 hash 품질과 resize 비용이 있습니다. Tree와 Heap처럼 구조적 제약을 둔 자료구조는 정렬, 우선순위, 범위 탐색 같은 특정 요구를 위해 일반성을 포기합니다.

30초 답변

순서 기반 index 접근은 Array/List, key 기반 조회는 Map, 중복 제거와 membership check는 Set, 우선순위 처리는 Heap, FIFO는 Queue, LIFO는 Stack, 계층은 Tree, 복잡한 관계는 Graph를 씁니다.

90초 답변

면접에서는 자료구조 이름보다 비용을 말해야 합니다. HashMap 조회는 평균 O(1)이지만 hash collision과 resize 비용이 있고, TreeMap은 O(log n)이지만 정렬 순서를 유지합니다. Queue는 작업 처리, Stack은 call stack/undo, Heap은 top-k나 scheduler에 연결할 수 있습니다.

꼬리질문

질문답변 방향
Set 중복 기준?equals/hashCode 또는 비교 기준에 따라 달라집니다.
Heap 정렬?최솟값/최댓값을 빠르게 꺼내는 데 유리합니다.
Graph 저장?인접 리스트와 인접 행렬을 규모와 밀도에 따라 선택합니다.
CS-03

Q. Hash collision은 무엇이고 왜 중요한가요?

핵심 개념

Hash collision은 서로 다른 key가 같은 hash bucket에 배치되는 현상입니다. 충돌이 많으면 HashMap의 평균 O(1) 성능이 나빠집니다.

개념 해부

hash collision은 예외 상황이 아니라 hash 공간이 유한하기 때문에 언제든 생길 수 있는 정상 현상입니다. 좋은 hash 함수는 key를 고르게 분산시켜 bucket 길이를 짧게 유지하고, 최종 동등성은 equals가 판단합니다. collision이 많아지면 평균 O(1)이라는 기대가 깨지고, 공격자가 의도적으로 몰리게 만들면 보안 이슈가 될 수 있습니다.

30초 답변

HashMap은 hashCode로 bucket을 찾고 equals로 실제 key를 비교합니다. 서로 다른 key가 같은 bucket에 몰리는 Hash collision이 많으면 조회 성능이 떨어지고, equals/hashCode 계약이 깨지면 조회 자체가 실패할 수 있습니다.

90초 답변

좋은 hash 함수는 key를 bucket에 고르게 분산시켜야 합니다. Java HashMap은 충돌이 심하면 bucket 구조를 tree로 바꾸는 최적화가 있지만, 기본적으로 equals/hashCode를 올바르게 구현해야 합니다. 보안 관점에서는 의도적인 hash flooding 공격도 고려할 수 있습니다.

꼬리질문

질문답변 방향
equals가 true면?hashCode도 반드시 같아야 합니다.
hashCode 같으면 equals true?아닙니다. 충돌 가능성이 있습니다.
mutable key?Map에 넣은 뒤 hash 기준 값이 바뀌면 찾지 못할 수 있습니다.
CS-04

Q. BFS/DFS는 언제 쓰나요?

핵심 개념

BFS는 가까운 노드부터 넓게 탐색하고, DFS는 한 경로를 깊게 탐색합니다. 그래프/트리 탐색의 기본입니다.

개념 해부

BFS와 DFS의 차이는 방문 순서가 아니라 문제의 증거를 어떤 순서로 찾는가입니다. BFS는 같은 거리의 노드를 먼저 모두 확인하므로 무가중치 최단 거리와 단계별 확산에 적합합니다. DFS는 한 경로를 끝까지 파고들기 때문에 조합 탐색, cycle detection, dependency 탐색에서 자연스럽지만 깊이가 크면 stack 위험이 있습니다.

30초 답변

BFS는 queue를 사용해 최단 거리나 단계별 탐색에 유리하고, DFS는 stack 또는 recursion으로 깊은 경로 탐색, cycle detection, backtracking에 자주 씁니다.

90초 답변

무가중치 그래프의 최단 경로는 BFS가 적합합니다. DFS는 모든 조합 탐색이나 dependency graph에서 cycle을 찾는 데 유용합니다. 실무에서는 메뉴 트리, 권한 그래프, 빌드 dependency, 조직도, workflow graph 같은 문제로 연결해 설명할 수 있습니다.

꼬리질문

질문답변 방향
visited가 왜 필요?cycle이 있는 그래프에서 무한 반복을 막기 위해 필요합니다.
DFS recursion 위험?깊이가 크면 stack overflow가 날 수 있어 iterative 방식이 필요할 수 있습니다.
가중치 최단 경로?Dijkstra 같은 알고리즘을 검토합니다.
CS-05

Q. race condition, deadlock, mutex/semaphore를 설명해보세요.

핵심 개념

race condition은 실행 순서에 따라 결과가 달라지는 문제입니다. deadlock은 둘 이상의 작업이 서로가 가진 자원을 기다리며 멈추는 상태입니다. mutex는 상호 배제, semaphore는 제한된 개수의 permit으로 동시 접근을 제어합니다.

개념 해부

동시성 문제는 코드가 틀렸다기보다 가능한 실행 순서가 너무 많아 일부 순서에서 불변식이 깨지는 문제입니다. mutex는 공유 자원에 한 번에 하나만 들어가게 하고, semaphore는 제한된 수만 들어가게 합니다. deadlock은 네 가지 조건이 동시에 맞을 때 생기므로 lock 순서, timeout, 범위 축소로 조건을 깨는 식으로 접근합니다.

30초 답변

공유 상태를 여러 thread가 동시에 수정하면 race condition이 생길 수 있어 lock, atomic operation, transaction으로 보호합니다. deadlock은 lock 순서 불일치가 대표 원인이고, mutex는 하나만 들어가게, semaphore는 정해진 수만 들어가게 제어합니다.

90초 답변

실무에서는 중복 클릭, 중복 결제, 재고 차감, DB row lock, thread pool 고갈 같은 문제로 나타납니다. deadlock 예방은 lock 순서 통일, lock 범위 축소, timeout, retry가 기본입니다. 동시성 문제는 재현이 어렵기 때문에 테스트와 로그, transaction isolation 이해가 필요합니다.

꼬리질문

질문답변 방향
atomic?중간 상태를 다른 작업이 볼 수 없는 단위 연산입니다.
semaphore 예?DB connection pool처럼 동시에 사용할 수 있는 자원 수 제한입니다.
frontend 연결?중복 요청, stale response, optimistic update 충돌로 나타날 수 있습니다.
CS-06

Q. process vs thread, context switching, memory, file descriptor를 설명해보세요.

핵심 개념

process는 독립된 실행 단위와 주소 공간을 가지고, thread는 process 안에서 메모리를 공유하는 실행 흐름입니다. context switching은 CPU가 실행 대상을 바꾸며 상태를 저장/복원하는 비용입니다. file descriptor는 열린 파일, socket 같은 OS resource를 가리키는 핸들입니다.

개념 해부

process는 격리된 주소 공간과 자원을 가진 실행 단위이고, thread는 같은 process 안에서 메모리를 공유하는 실행 흐름입니다. thread는 가볍지만 공유 메모리 때문에 race condition이 생기고, process는 격리가 강하지만 IPC와 전환 비용이 큽니다. file descriptor는 파일뿐 아니라 socket, pipe 같은 OS 자원 핸들이므로 누수되면 네트워크 서버가 새 연결을 받지 못할 수 있습니다.

30초 답변

process는 메모리 공간이 분리되어 안정적이지만 생성/전환 비용이 크고, thread는 같은 process 메모리를 공유해 가볍지만 동시성 버그가 생길 수 있습니다. context switching이 많으면 CPU가 실제 작업보다 전환에 시간을 쓰고, file descriptor가 누수되면 파일이나 socket을 더 열 수 없습니다.

90초 답변

웹 서버에서 thread pool이 고갈되면 요청이 대기하고, DB connection pool이 작거나 누수되면 API가 멈춘 것처럼 보입니다. socket도 file descriptor로 관리되므로 connection leak은 FD 고갈로 이어질 수 있습니다. OS 기본기를 알면 “서버가 느리다”를 CPU, memory, thread, FD, network로 나눠 볼 수 있습니다.

CS-12

OS NETWORK INTERNALS DRILL

심화 CS 면접은 정의 암기에서 끝나지 않고, 요청 하나가 OS·네트워크·런타임을 지나며 어떤 비용과 실패 모드를 만드는지 시간순으로 설명하게 합니다.

OS NETWORK INTERNALS DRILL 브라우저가 API를 호출하면 DNS 조회 후 TCP 3-way handshake, TLS handshake, HTTP request 전송, 서버 accept, kernel/user mode 전환, application handler, DB/network I/O, response write, TCP ACK 흐름이 이어집니다. keep-alive와 connection pool이 있으면 일부 handshake는 생략되지만, TLS 재협상, packet loss, head-of-line blocking, server queue 대기는 여전히 tail latency를 만들 수 있습니다.

메모리와 커널 경계

virtual memory는 process마다 독립된 주소 공간을 제공하고, page table을 통해 virtual address를 physical frame에 매핑합니다. 접근한 page가 메모리에 없거나 권한이 맞지 않으면 page fault가 발생하며, 정상적인 minor fault는 매핑만 보정하고 major fault는 disk I/O를 동반할 수 있습니다. page cache는 파일과 socket I/O의 반복 접근을 빠르게 하지만, cache pressure가 커지면 reclaim과 writeback이 응답 지연으로 보일 수 있습니다. system call은 user mode에서 kernel mode로 넘어가므로 너무 잦은 read/write, context switching, copy 비용도 병목이 됩니다.

동시성 내부 모델

happens-before는 한 작업의 write가 다른 작업의 read에 관측될 수 있음을 보장하는 순서 관계입니다. lock, volatile, channel, thread start/join 같은 동기화 지점이 없으면 CPU cache와 compiler reorder 때문에 값이 보이지 않을 수 있습니다. CAS는 compare-and-swap으로 lock 없이 상태를 바꾸는 원자 연산이지만, 값이 A에서 B로 갔다가 다시 A가 되는 ABA 문제를 놓칠 수 있어 version stamp나 hazard pointer 같은 보완이 필요합니다. thread pool starvation은 pool 안 작업이 같은 pool의 다른 작업 완료를 기다리거나 blocking I/O가 pool을 모두 점유할 때 발생하며, 별도 executor, bounded queue, timeout, backpressure로 완화합니다.

압박 포인트

“CPU가 낮은데 API가 느립니다”라는 질문에는 thread pool starvation, connection pool wait, kernel I/O wait, page fault, TLS handshake, DNS 지연을 같은 타임라인 위에 올려서 좁혀야 합니다.

DBD-02

Q. MVCC는 무엇이고 왜 필요한가요?

핵심 개념

MVCC는 row version을 관리해 reader와 writer가 서로를 덜 막으면서 일관된 snapshot을 보게 하는 동시성 제어 방식입니다.

개념 해부

MVCC는 독자가 쓰기를 막고 쓰기가 독자를 막는 상황을 줄이기 위해 row version을 유지하는 모델입니다. transaction은 자기 snapshot을 보고, DB는 오래된 version을 일정 기간 보존합니다. 오래 열린 transaction은 vacuum이나 undo 정리를 막아 bloat와 성능 문제를 만들 수 있습니다.

30초 답변

MVCC는 update가 기존 row를 덮어쓰는 대신 새 version을 만들고, transaction은 자신의 snapshot에서 보이는 version을 읽습니다. 그래서 읽기가 쓰기를 항상 막지 않아 동시성이 좋아집니다. 대신 오래 열린 transaction이 있으면 오래된 version 정리가 늦어져 bloat나 vacuum 문제가 생길 수 있습니다.

90초 답변

PostgreSQL 같은 MVCC DB에서는 각 transaction이 볼 수 있는 row version이 정해져 있습니다. Read Committed에서는 statement마다 snapshot이 바뀌고, Repeatable Read에서는 transaction 시작 시점 snapshot이 유지됩니다. MVCC는 lock을 없애는 것이 아니라 읽기/쓰기 충돌을 줄이는 방식이며, 쓰기-쓰기 충돌이나 unique constraint, row lock은 여전히 중요합니다.

꼬리질문

질문답변 방향
vacuum은 왜 필요한가요?더 이상 보이지 않는 오래된 row version을 정리해 bloat를 줄입니다.
long transaction 문제는?old version 정리를 막아 bloat, xid wraparound, replication lag 위험을 키웁니다.
MVCC면 lock이 필요 없나요?아닙니다. 쓰기 충돌, DDL, FK, unique check에는 lock이 필요합니다.

면접에서 말할 증거

autovacuum, dead tuple, long running transaction, lock wait를 실제 지표로 언급하면 깊이가 생깁니다.

DBD-03

Q. 트랜잭션 격리 수준은 어떻게 선택하나요?

핵심 개념

격리 수준은 transaction들이 서로의 중간 상태나 변경을 어느 정도 볼 수 있는지 정하는 정책입니다. 높을수록 anomaly는 줄지만 충돌과 retry 비용이 커질 수 있습니다.

개념 해부

격리 수준은 anomaly를 얼마나 허용할지의 선택입니다. dirty read, non-repeatable read, phantom, write skew 같은 현상 중 도메인이 허용하지 않는 것이 무엇인지 먼저 정해야 합니다. DB마다 같은 이름의 isolation도 구현이 다를 수 있으므로 PostgreSQL, MySQL 차이를 분리해 말하는 편이 정확합니다.

30초 답변

Read Committed는 statement마다 commit된 최신 데이터를 보고, Repeatable Read는 transaction 동안 같은 snapshot을 유지합니다. Serializable은 직렬 실행과 같은 결과를 목표로 하지만 serialization failure에 대한 retry 설계가 필요합니다. 선택 기준은 막아야 하는 anomaly와 성능 비용입니다.

90초 답변

실무에서는 isolation level만 올리는 것이 답이 아닐 수 있습니다. 재고 차감은 조건부 update나 row lock이 더 명확할 수 있고, 편집 충돌은 optimistic locking이 사용자 경험에 맞을 수 있습니다. Serializable을 쓰면 더 안전해 보이지만 충돌 시 재시도 로직과 idempotency가 없으면 장애로 이어질 수 있습니다.

DBD-04

Q. 락과 deadlock은 어떻게 다루나요?

핵심 개념

락은 동시 변경의 정합성을 지키기 위한 제어이고, deadlock은 transaction들이 서로가 가진 락을 기다리며 진행하지 못하는 상태입니다.

개념 해부

락은 데이터 정합성을 지키지만 대기와 deadlock이라는 비용을 만듭니다. row lock, gap lock, table lock, metadata lock은 발생 조건과 영향 범위가 다릅니다. deadlock은 단순 오류가 아니라 DB가 교착을 감지해 한쪽 transaction을 희생시킨 것이므로 retry와 lock 순서 통일이 필요합니다.

30초 답변

락 문제는 긴 transaction, 누락 인덱스, 일관되지 않은 락 획득 순서, transaction 안의 외부 API 호출에서 자주 생깁니다. deadlock을 줄이려면 같은 순서로 row를 잠그고, transaction을 짧게 유지하고, lock timeout과 retry를 설계합니다.

90초 답변

lock wait가 길면 먼저 어떤 query가 어떤 lock을 잡고 있는지 봅니다. 인덱스가 없어 더 많은 row를 스캔하며 잠그는 경우, 사용자 입력을 기다리거나 외부 API를 호출하는 동안 transaction이 열려 있는 경우가 흔합니다. deadlock은 DB가 하나를 abort할 수 있으므로 애플리케이션은 안전한 retry와 idempotency를 갖춰야 합니다.

꼬리질문

질문답변 방향

lock timeout은 왜?무한 대기를 막고 장애를 빨리 감지하기 위해 둡니다.
외부 API를 transaction 안에서 호출하면?transaction 시간이 길어져 lock wait와 deadlock 위험이 커집니다.

면접에서 말할 증거

lock table, slow query, transaction duration, deadlock log를 확인한 경험을 말합니다.

DBD-05

Q. lost update는 왜 생기고 어떻게 막나요?

핵심 개념

lost update는 두 transaction이 같은 값을 읽고 각각 수정해 한쪽 변경이 사라지는 동시성 문제입니다.

개념 해부

lost update는 두 transaction이 같은 값을 읽고 각각 수정했는데 나중 commit이 앞선 변경을 덮어쓰는 문제입니다. version column, 조건부 update, row lock, serializable isolation 등으로 막을 수 있습니다. 어떤 방법이든 충돌 감지 후 사용자나 시스템이 어떻게 재시도할지 정해야 합니다.

30초 답변

lost update는 사용자가 같은 데이터를 동시에 수정할 때 자주 생깁니다. 해결은 version column 기반 optimistic locking, row lock 기반 pessimistic locking, 조건부 atomic update, isolation level 조정 중 요구사항에 맞게 선택합니다.

90초 답변

문서 편집처럼 충돌이 드문 작업은 optimistic locking이 적합합니다. update where id=? and version=?로 갱신하고 영향 row가 0이면 충돌을 알려 최신 데이터를 다시 보여줍니다. 재고 차감처럼 경쟁이 높은 작업은 update stock = stock - 1 where stock > 0 같은 조건부 update나 row lock을 검토합니다.

꼬리질문

질문답변 방향
optimistic lock의 UX는?충돌 시 최신 데이터와 내 변경을 비교해 재시도하게 합니다.
pessimistic lock 단점은?대기와 deadlock, throughput 감소가 생길 수 있습니다.
재고 차감은?조건부 update, unique constraint, idempotency를 함께 봅니다.

주의

“트랜잭션이면 됩니다”로는 부족합니다. 어떤 격리 수준에서 어떤 update가 어떻게 충돌하는지 말해야 합니다.

DBD-06

Q. 느린 쿼리는 어떤 순서로 분석하나요?

핵심 개념

느린 쿼리 대응은 감으로 인덱스를 추가하는 일이 아니라 실제 실행 계획, row 수 추정, I/O, sort, join 비용을 확인하는 과정입니다.

개념 해부

느린 쿼리 분석은 실행 계획의 한 줄을 읽는 일이 아니라 planner의 예상과 실제 실행의 차이를 보는 일입니다. estimated rows와 actual rows가 크게 다르면 통계나 데이터 분포 문제가 있을 수 있습니다. sort, hash, nested loop, buffer read, lock wait를 함께 봐야 원인을 정확히 좁힙니다.

30초 답변

먼저 재현 가능한 쿼리와 파라미터를 확보하고 EXPLAIN ANALYZE로 실제 실행 계획을 봅니다. estimated rows와 actual rows 차이, seq scan이 적절한지, join 방식, sort/hash 메모리, index 사용 여부를 확인합니다. 그 다음 인덱스, 쿼리 구조, 통계, pagination 방식을 조정합니다.

90초 답변

Seq Scan은 항상 나쁜 것이 아닙니다. 작은 테이블이나 selectivity가 낮은 조건에서는 합리적일 수 있습니다. 오히려 planner가 row 수를 크게 잘못 예측하면 잘못된 join 순서나 nested loop 폭증이 생깁니다. offset pagination은 뒤 페이지로 갈수록 비용이 커질 수 있어 keyset pagination을 검토합니다.

꼬리질문

질문답변 방향
estimated와 actual 차이가 크면?통계 갱신, 컬럼 상관관계, skew, extended statistics를 봅니다.
index를 추가하면 항상 빨라지나요?읽기는 빨라질 수 있지만 write 비용, 저장 공간, planner 선택 문제가 생깁니다.

면접에서 말할 증거

DBD-07

Q. 인덱스는 어떻게 설계하나요?

핵심 개념

인덱스는 자주 쓰는 WHERE, JOIN, ORDER BY 패턴을 빠르게 하지만 write 비용과 저장 공간을 늘립니다.

개념 해부

인덱스 설계는 where 절 컬럼을 모두 넣는 작업이 아닙니다. equality, range, order by, covering 여부, selectivity, update 빈도를 고려해 컬럼 순서와 포함 범위를 정합니다. partial index나 expression index는 강력하지만 쿼리 조건이 정확히 맞아야 효과가 납니다.

30초 답변

인덱스는 쿼리 패턴과 cardinality를 보고 설계합니다. equality 조건, range 조건, sort 조건의 순서를 보고 composite index 컬럼 순서를 정하고, active row만 자주 조회하면 partial index, projection이 제한되면 covering index를 검토합니다.

90초 답변

복합 인덱스는 왼쪽 prefix와 range 조건 이후 활용도를 이해해야 합니다. 예를 들어 tenant_id, status, created_at 조건이 반복되면 tenant_id와 status 같은 equality 조건을 앞에 두고 created_at range/order를 뒤에 둘 수 있습니다. 하지만 모든 조합에 인덱스를 만들면 write와 vacuum 비용이 커집니다. 실제 workload와 slow query 기준으로 관리해야 합니다.

꼬리질문

질문답변 방향

partial index는?deleted_at is null 같은 자주 쓰는 subset에만 인덱스를 만들어 크기를 줄입니다.
인덱스가 안 타면?조건식, 타입 캐스팅, 함수 사용, selectivity, 통계, predicate 일치를 확인합니다.

오답/주의점

주의

“자주 검색하는 컬럼에 인덱스”는 너무 얕습니다. 복합 조건, 정렬, 카디널리티, write 비용까지 봐야 합니다.

DBD-08

Q. 트랜잭션 경계는 어떻게 잡나요?

핵심 개념

트랜잭션 경계는 함께 성공하거나 함께 실패해야 하는 비즈니스 정합성 단위입니다.

개념 해부

트랜잭션 경계는 비즈니스 불변식을 지키는 최소 단위여야 합니다. 너무 짧으면 중간 상태가 노출되고, 너무 길면 lock과 connection을 오래 잡습니다. 외부 API 호출, 파일 처리, 사용자 입력 대기 같은 느린 작업을 transaction 안에 넣으면 장애가 DB로 전파됩니다.

30초 답변

트랜잭션은 DB 작업을 많이 묶는 것이 아니라 정합성 단위로 묶어야 합니다. 외부 API 호출, 사용자 입력 대기, 긴 batch 처리는 transaction 밖으로 빼거나 outbox, saga, idempotency 같은 패턴을 검토합니다.

90초 답변

예를 들어 주문 생성과 결제 요청은 하나의 DB transaction으로 외부 API까지 묶기 어렵습니다. DB에는 주문 pending과 outbox event를 같은 transaction으로 저장하고, 별도 worker가 결제 요청을 처리한 뒤 상태를 전이할 수 있습니다. 이렇게 하면 DB 정합성과 외부 시스템 실패를 분리할 수 있습니다.

DBD-09

Q. Connection Pool은 왜 필요하고 어떤 문제가 생기나요?

핵심 개념

Connection Pool은 DB connection 생성 비용을 줄이고 동시 접근을 제어하지만, 설정을 잘못하면 DB를 과부하시키거나 app request를 대기시킵니다.

개념 해부

Connection Pool은 DB connection 생성 비용을 줄이고 동시 접근 수를 제한하는 backpressure 장치입니다. pool이 너무 작으면 대기가 늘고, 너무 크면 DB가 context switching과 lock 경합으로 무너질 수 있습니다. leak, slow query, 긴 transaction은 pool 고갈로 먼저 드러나는 경우가 많습니다.

30초 답변

DB connection은 생성 비용이 크고 DB가 처리할 수 있는 수가 제한적이므로 pool로 재사용합니다. 하지만 app instance가 늘 때 pool size도 곱해져 DB max connection을 초과할 수 있습니다. pool size, timeout, transaction duration, slow query를 함께 봐야 합니다.

90초 답변

connection pool 문제는 트래픽 증가, autoscaling, slow query와 같이 나타납니다. DB connection이 부족하면 app은 pool 대기 시간이 늘고, timeout이 발생하며, retry가 더 큰 부하를 만들 수 있습니다. 해결은 pool size를 무작정 키우는 것이 아니라 query 최적화, transaction 단축, read/write 분리, pooler 사용, backpressure를 함께 검토하는 것입니다.

DBD-10

Q. WAL과 replication은 어떤 역할을 하나요?

핵심 개념

WAL은 변경 내용을 데이터 파일보다 먼저 로그에 기록해 crash recovery와 replication의 기반이 됩니다. replication은 가용성과 읽기 확장을 돕지만 복구와 백업을 대체하지 않습니다.

개념 해부

WAL은 변경을 먼저 순차 로그로 남겨 crash recovery와 replication의 기반을 제공합니다. replication은 읽기 확장과 장애 대응에 유리하지만 lag가 있으면 stale read와 read-your-writes 문제가 생깁니다. 복제본은 백업이 아니며, 잘못 삭제한 데이터도 빠르게 복제될 수 있습니다.

30초 답변

WAL은 DB 변경을 먼저 로그로 남겨 장애 후 복구할 수 있게 합니다. replica는 WAL을 받아 primary 변경을 따라가며 읽기 부하 분산이나 failover에 쓰입니다. 하지만 replication lag가 있으면 replica read가 stale할 수 있고, 논리적 삭제나 잘못된 update는 replica에도 전파됩니다.

90초 답변

replication은 고가용성 도구이지 과거 시점 복구 도구가 아닙니다. primary에서 잘못 삭제한 데이터는 replica에도 반영될 수 있으므로 backup과 PITR이 필요합니다. read replica를 사용할 때는 read-after-write 요구가 있는 기능을 primary에서 읽거나 session consistency를 보장해야 합니다.

꼬리질문

질문답변 방향

DBD-11

Q. 백업과 복구는 어떻게 검증하나요?

핵심 개념

백업은 존재하는 것만으로 충분하지 않습니다. 실제 복구에 걸리는 시간, 복구된 데이터의 정합성, 운영 전환 절차를 검증해야 합니다.

개념 해부

백업은 존재한다는 사실보다 복구해봤다는 증거가 중요합니다. RPO/RTO 목표에 맞게 full/incremental backup, PITR, restore drill을 설계해야 합니다. 백업 파일이 있어도 암호화 키, 권한, 절차, 복구 시간 검증이 없으면 실제 사고에서 쓸 수 없습니다.

30초 답변

backup은 과거 시점 복구와 실수 복구를 위해 필요하고, replication은 가용성을 위한 것입니다. RPO와 RTO를 정하고, 정기적으로 restore drill을 수행해 백업 파일이 실제로 복구되는지, 권한과 secret, app config까지 맞는지 확인해야 합니다.

90초 답변

복구 훈련에서는 DB만 띄우는 것으로 끝나면 안 됩니다. 특정 시점으로 복구한 뒤 schema version, application compatibility, user count, checksum, 핵심 쿼리, 권한, connection string 전환까지 확인해야 합니다. 개인정보와 보안 요구가 있다면 백업 암호화, 접근 통제, 보관 기간, 삭제 정책도 필요합니다.

DBD-12

Q. 무중단 DB migration은 어떻게 설계하나요?

핵심 개념

무중단 migration은 구버전과 신버전 애플리케이션이 동시에 동작할 수 있도록 schema 변경을 backward compatible하게 나누는 방식입니다.

개념 해부

무중단 migration은 schema 변경과 애플리케이션 배포가 동시에 깨지지 않도록 시간을 나누는 작업입니다. expand 단계에서 새 구조를 추가하고 양쪽 코드가 호환되게 만든 뒤, backfill과 dual read/write를 거쳐 contract 단계에서 오래된 구조를 제거합니다. lock을 유발하는 DDL과 backfill 부하를 별도로 관리해야 합니다.

30초 답변

expand-contract 방식으로 진행합니다. 먼저 nullable column이나 새 table처럼 호환되는 schema를 추가하고, 앱이 양쪽 schema를 읽고 쓸 수 있게 배포합니다. 그 다음 backfill과 검증을 거쳐 not null/constraint 적용, old column 제거를 마지막에 합니다. 큰 index는 가능하면 concurrently 생성합니다.

90초 답변

위험한 변경은 column rename, type 변경, not null 추가, default backfill, 대형 table index 생성, FK validation입니다. 한 번에 바꾸면 lock과 구버전 앱 호환성 문제가 생깁니다. 따라서 migration은 배포 순서와 함께 설계해야 합니다. backfill은 batch로 나누고, 진행률과 lock wait, replication lag를 관찰합니다.

꼬리질문

질문답변 방향

column rename은?새 컬럼 추가, dual write, read fallback, 전환, old column 제거로 나눕니다.
migration rollback은?파괴적 변경은 rollback이 어려우므로 호환 단계와 feature flag가 중요합니다.

dry-run, lock timeout, batch backfill, migration version, rollback plan을 말하면 운영 경험이 드러납니다.

MVCC INDEX PLAN DEEP DIVE

DB 심화 면접에서 강한 답변은 MVCC 내부, 인덱스 접근 조건, 실행 계획의 실제 수치를 한 문장 안에서 연결합니다.

MVCC INDEX PLAN DEEP DIVE PostgreSQL은 row version마다 xmin/xmax로 생성·삭제 transaction 정보를 기록하고 snapshot이 어떤 version을 볼 수 있는지 판단합니다. InnoDB는 read view와 undo log를 통해 consistent read를 제공하며, 오래 열린 transaction은 undo 정리를 지연시킵니다. 성능 분석에서는 btree leftmost prefix, index-only scan 가능성, EXPLAIN ANALYZE의 rows/loops/buffers를 함께 확인해야 합니다.

인덱스와 실행 계획 해석

B-tree 복합 인덱스는 leftmost prefix가 중요합니다. (tenant_id, status, created_at) 인덱스는 tenant_id 단독, tenant_id+status, tenant_id+status+created_at 조건에는 잘 맞지만 status만 있는 조건에는 일반적으로 효율이 낮습니다. range 조건이 등장한 뒤에는 뒤 컬럼의 filtering/order 활용도가 제한될 수 있으므로 equality 조건, range 조건, ORDER BY를 순서대로 설명해야 합니다.

index-only scan은 인덱스만 읽는다는 뜻처럼 보이지만, PostgreSQL에서는 visibility map이 충분히 표시되어 있어야 heap visibility 확인을 줄일 수 있습니다. 필요한 컬럼이 모두 인덱스에 있어도 최근 변경이 많거나 visibility map이 깨져 있으면 heap fetch가 생길 수 있습니다. 그래서 covering index 설계와 vacuum 상태를 함께 봐야 합니다.

답변 주의

“인덱스를 타서 빠릅니다”는 충분하지 않습니다. 어떤 prefix로 접근했고, index-only scan이 실제 heap fetch를 줄였는지, rows/loops/buffers가 예측과 맞는지를 함께 말해야 합니다.

DBD-15

DB 개념 인과관계

DB 심화 답변은 MVCC, index, isolation을 각각 외우는 것이 아니라 동시 읽기와 쓰기를 어떻게 동시에 허용하면서도 어떤 이상 현상이 남는가를 설명해야 합니다.

DBD-16

실행계획 실전 해석: MVCC, 인덱스, 락을 함께 읽기

DB 심화 면접에서 전문가처럼 보이려면 “인덱스를 탔습니다”가 아니라 실행 계획의 rows, loops, buffers, lock wait, MVCC visibility를 같은 현상으로 읽어야 합니다.

EXPERT DB PLAN CASE시나리오는 tenant_id, status, created_at 조건으로 주문 목록을 조회하는 API가 뒤 페이지에서 느려지는 경우입니다. 초보 답변은 “복합 인덱스를 추가합니다”입니다. 전문가 답변은 먼저 쿼리의 목적을 나눕니다. tenant 범위가 강한지, status 선택도가 높은지, date range가 넓은지, ORDER BY가 created_at desc인지, offset pagination인지, 필요한 컬럼이 인덱스에 포함되는지 확인합니다. 그 뒤 실행계획에서 planner 예상 rows와 actual rows가 얼마나 다른지, sort가 발생하는지, heap fetch가 많은지, buffers read가 큰지 봅니다.

1. estimated rows와 actual rows

planner는 통계를 기반으로 어떤 plan이 싸다고 추정합니다. 하지만 tenant별 데이터 분포가 심하게 다르거나 status와 created_at이 강하게 상관되어 있으면 예상 rows가 틀릴 수 있습니다. 예상은 1,000 row인데 실제는 500,000 row라면 nested loop가 폭발하거나 잘못된 index가 선택될 수 있습니다. 이때 해결은 단순히 인덱스를 더 만드는 것이 아니라 ANALYZE, extended statistics, query rewrite, partial index, tenant별 partitioning 가능성까지 검토하는 것입니다.

2. Index scan이 항상 좋은 것은 아니다

Index scan은 필요한 row가 적을 때 강합니다. 하지만 선택도가 낮아 테이블 대부분을 읽어야 한다면 index를 따라 random access하는 비용이 sequential scan보다 클 수 있습니다. PostgreSQL의 index-only scan도 visibility map이 충분히 설정되어 있어야 heap fetch를 줄입니다. 최근 update가 많아 visibility 확인이 필요하면 인덱스에 컬럼이 다 있어도 heap을 읽게 됩니다. 따라서 “covering index라 빠르다”가 아니라 heap fetch와 buffers를 함께 봐야 합니다.

3. Offset pagination의 비용

OFFSET 100000 LIMIT 50은 앞의 100,000개를 건너뛰어야 합니다. 사용자는 50개만 받지만 DB는 정렬된 후보를 많이 처리합니다. cursor/keyset pagination은 마지막으로 본 created_at, id를 기준으로 다음 범위를 좁히므로 뒤 페이지 비용이 안정적입니다. 다만 임의 페이지 이동이 어렵고 정렬 기준이 안정적이어야 합니다. 관리자 화면에서 “페이지 번호 이동”이 꼭 필요한지, 아니면 필터와 cursor 탐색으로 충분한지 제품 요구와 같이 판단해야 합니다.

4. MVCC와 오래 열린 transaction

MVCC는 reader와 writer 충돌을 줄이지만, 오래 열린 transaction은 오래된 row version 정리를 막습니다. PostgreSQL에서는 dead tuple이 쌓이고 vacuum이 지연되면 table bloat와 index bloat가 생깁니다. 이 상태에서는 같은 쿼리도 더 많은 page를 읽게 되어 buffers가 늘고 cache 효율이 떨어집니다. “쿼리는 그대로인데 점점 느려졌다”면 데이터 증가뿐 아니라 long transaction, autovacuum 지연, bloat를 의심해야 합니다.

5. 락과 격리 수준

실행 시간이 길어 보이는 쿼리가 실제로는 실행 중이 아니라 lock을 기다리고 있을 수 있습니다. row lock, relation lock, migration DDL lock, foreign key check가 대기 원인이 됩니다. Read Committed에서는 statement마다 snapshot이 달라질 수 있고, Repeatable Read에서는 transaction 동안 snapshot이 유지됩니다. Serializable은 더 강한 보장을 목표로 하지만 serialization failure가 발생할 수 있어 retry가 설계 일부가 됩니다. 격리 수준을 올리는 답변에는 반드시 retry, 사용자 안내, idempotency가 따라와야 합니다.

면접에서의 90초 답변

“저는 먼저 EXPLAIN ANALYZE에서 estimated rows와 actual rows 차이, loops, sort, buffers, heap fetch를 봅니다. index scan이 있어도 선택도가 낮거나 heap fetch가 많으면 느릴 수 있습니다. offset pagination이면 뒤 페이지 비용이 커지므로 keyset pagination을 검토하고, 통계가 틀리면 ANALYZE나 extended statistics를 봅니다. 동시에 lock wait와 long transaction, autovacuum 지연, bloat도 확인합니다. 격리 수준이나 락을 바꾸는 선택은 정합성 이상 현상을 막는 대신 abort와 retry 비용이 생기므로 도메인 불변식 기준으로 결정합니다.”

전문가 기준

DB 답변에서 중요한 것은 “인덱스 추가”가 아니라 왜 planner가 그 plan을 선택했고, 실제 실행에서 어디에 시간이 쌓였으며, 그 해결책이 읽기 성능·쓰기 비용·운영 변경 위험을 어떻게 바꾸는지 설명하는 것입니다.

DBD-17

Q. NoSQL은 언제 선택하고 RDBMS와 어떻게 병행하나요?

핵심 개념

NoSQL은 느슨한 스키마와 수평 확장(Scale-Out)으로 RDBMS의 스키마 경직성과 확장 한계를 보완하는 모델이며, CAP만이 아니라 PACELC로 정상 상황의 트레이드오프까지 봐야 선택이 정확해집니다.

개념 해부

Redis(키-값, 캐시·세션), MongoDB(문서, 유연한 스키마), Cassandra(컬럼형, 쓰기 성능·AP), DynamoDB(관리형 키-값·문서), Neo4j(그래프)처럼 유형마다 최적 사용처가 다릅니다. PACELC는 파티션(P) 발생 시 가용성(A)과 일관성(C) 중 무엇을 포기할지뿐 아니라, 평상시(E, Else)에도 지연시간(L)과 일관성(C) 중 하나를 선택해야 한다고 봅니다. 즉 장애가 없어도 시스템은 이미 트레이드오프 중입니다.

30초 답변

트래픽이 크고 스키마가 자주 바뀌는 서비스는 NoSQL이 유리합니다. 유연한 스키마로 변경에 대응하고 Scale-Out으로 트래픽을 처리하기 때문입니다. 다만 결제·재고처럼 강한 정합성이 필요한 도메인은 RDBMS를 병행하는 Polyglot Persistence 전략을 씁니다. MySQL의 JSON 컬럼은 저장은 되지만 인덱싱과 중첩 쿼리가 제한적이므로, 비정형 데이터가 핵심이면 MongoDB 같은 네이티브 문서 DB가 더 맞습니다.

90초 답변

CAP은 파티션 상황에서의 C vs A만 다루지만, PACELC는 정상 상황에서도 시스템이 지연시간과 일관성 사이에서 선택하고 있다는 점을 드러냅니다. 예를 들어 노드 간 데이터 검증을 거쳐 응답하면 일관성은 높아지지만 지연이 늘고(PC/EC), 검증 없이 즉시 응답하면 빠르지만 오래된 값을 돌려줄 수 있습니다(PA/EL). 실무 판단은 이 도메인이 잠깐의 정합성 지연을 감내할 수 있는가로 귀결됩니다. 주문 상태나 재고 차감처럼 감내할 수 없는 도메인은 RDBMS로 남기고, 게시글 요약·활동 로그·추천 피드처럼 감내 가능한 도메인만 NoSQL로 분리하는 것이 Polyglot Persistence의 실제 적용 기준입니다.

오답/주의점

주의

"NoSQL이 더 빠르다"는 얕은 답변입니다. NoSQL은 빠른 게 아니라 확장 방식과 일관성 보장 수준이 다른 것이며, 어떤 anomaly를 감내할 도메인인지 먼저 규정해야 선택 근거가 됩니다.

DBD-18

Q. 검색 성능이 한계에 부딪히면 왜 Elasticsearch를 검토하나요?

핵심 개념

Elasticsearch는 Lucene 기반 분산 검색 엔진으로, 역색인 구조 덕분에 %LIKE% 풀스캔과 달리 데이터가 늘어도 검색 속도 저하가 미미합니다.

개념 해부

RDBMS의 %LIKE%는 모든 행을 풀스캔하므로 데이터량에 선형적으로 느려지지만, ES는 저장 시점에 텍스트를 토큰화해 term 사전을 만들어두므로 검색 시 term을 O(1)에 가깝게 찾고 연결된 document ID만 조회합니다. 다만 ES는 인메모리 버퍼에 있는 동안 세그먼트가 생성되기 전까지는 검색되지 않아 완전한 실시간은 아니며, 트랜잭션을 지원하지 않고 삭제·수정도 soft-delete 후 새 세그먼트를 만드는 방식이라 RDBMS와 저장 모델 자체가 다릅니다.

30초 답변

역색인은 문서 텍스트를 토큰화해 term 사전을 만들고, 검색어도 같은 전처리를 거쳐 term으로 변환한 뒤 역색인에서 매칭해 연결된 document ID로 원본을 즉시 조회하는 방식입니다. RDBMS는 엄격한 스키마와 B-Tree 인덱스를 가진 트랜잭션 저장소이고 ES는 스키마 프리(Schema Free) 검색 엔진이므로, 실무에서는 RDBMS를 원본 저장소로 두고 ES는 검색 전용으로 병행하는 구성이 일반적입니다.

90초 답변

ES는 트랜잭션을 지원하지 않으므로 RDB 쓰기와 ES 색인을 하나의 트랜잭션으로 묶을 수 없습니다. 이 정합성 문제는 RDB 트랜잭션이 커밋된 후에만 이벤트를 발행하는 방식으로 풉니다. Spring의 @TransactionalEventListener를 쓰면 트랜잭션이 실제로 커밋된 시점에만 이벤트가 발행되고, 이 이벤트를 메시지 큐로 전달해 ES의 bulk API로 반영하면 RDB가 원본, ES가 최종적으로 일관된 파생 인덱스가 되는 구조를 만들 수 있습니다. %LIKE%가 느려서 도입을 검토하는 경우라면 MySQL Full-Text 인덱스로도 부분적으로 해결되지만, 형태소 분석·동의어 처리·다중 필드 랭킹이 필요하면 ES가 적합합니다.

DBD-19

Q. 캐싱 대상과 만료 전략은 어떤 기준으로 정하나요?

핵심 개념

캐시는 읽기 빈도가 높고 쓰기 빈도가 낮은 데이터, 또는 만드는 데 비용이 큰 연산 결과에 적합하며, 만료 전략은 정합성과 인프라 복잡도의 트레이드오프입니다.

개념 해부

구독 정보, 사용자 프로필, 인기 게시물 목록처럼 자주 읽히고 드물게 바뀌는 데이터, 또는 복잡한 조인이나 집계 쿼리의 결과가 좋은 캐싱 대상입니다. 반대로 자주 변경되는 데이터는 캐시 무효화가 빈번해 캐싱 자체가 오버헤드가 됩니다.

30초 답변

만료 전략은 세 가지입니다. TTL 기반은 일정 시간 후 자동 만료되며 변경 빈도에 따라 TTL 길이를 조절합니다. 이벤트 기반은 원본 데이터가 바뀌는 순간 즉시 캐시를 무효화해 정합성이 좋지만 무효화 이벤트를 전파하는 인프라가 필요합니다. 실무에서는 TTL로 기본 만료를 걸고 변경 이벤트로 즉시 무효화하는 혼합 방식을 가장 많이 씁니다.

90초 답변

TTL만 쓰면 원본이 바뀐 뒤에도 TTL이 끝날 때까지 오래된 값이 노출되는 구간이 생기고, 이벤트 기반만 쓰면 무효화 이벤트가 유실됐을 때 캐시가 영원히 stale 상태로 남을 위험이 있습니다. 혼합 전략은 이벤트로 즉시 무효화를 시도하되, 이벤트가 실패하거나 누락되더라도 TTL이 상한선 역할을 해 일정 시간 안에는 반드시 정합성이 회복되도록 만드는 안전망입니다. 어떤 데이터를 캐싱할지 정할 때도 같은 논리가 적용됩니다. 자주 바뀌는 재고 수량 같은 값을 캐싱하면 무효화 비용이 캐싱 이득을 상쇄하므로, 캐싱 여부는 항상 읽기/쓰기 비율과 무효화 인프라 유무를 함께 봐야 합니다.

DBD-20

Q. 분산 환경에서 비관적 락이 무너지는 지점과 대안은 무엇인가요?

핵심 개념

비관적 락(SELECT FOR UPDATE)은 데이터의 최신 복사본이 하나라는 전제 위에서 동작하므로, 쓰기 DB가 여러 대인 분산 환경에서는 정합성이 깨질 수 있습니다.

개념 해부

클러스터링은 스토리지가 1개이므로 비관적 락이 그대로 동작하고, 샤딩은 애초에 같은 데이터가 다른 DB에 없으므로 락 충돌 자체가 발생하지 않습니다. 반면 쓰기 DB가 여러 대로 나뉜 구조에서는 한쪽에서 건 잠금이 다른 쪽에 반영되지 않아, 서로 다른 노드가 같은 데이터를 동시에 수정할 수 있습니다. 이때는 Redis SETNX 기반 분산 락(TTL로 데드락 방지)이나, 클러스터 환경에서는 N개 노드 중 과반수 획득을 요구하는 Redlock 알고리즘으로 단일 노드 장애에도 안전한 락을 구성합니다.

30초 답변

쓰기 스큐(Write Skew)는 두 트랜잭션이 같은 조건을 읽고 각자 다른 로우를 수정해 로우 레벨 충돌 없이 둘 다 커밋되지만 비즈니스 불변식이 깨지는 현상입니다. 당직 의사 최소 1명 규칙에서 Alice와 Bob이 각자 2명이니 빠져도 된다고 판단해 동시에 자신을 해제하면, 서로 다른 로우를 고쳤으므로 충돌이 감지되지 않고 둘 다 성공해 당직자 0명이 됩니다. SERIALIZABLE 격리 수준이나 SELECT FOR UPDATE 같은 명시적 잠금 없이는 막을 수 없습니다.

90초 답변

맥북 100대 한정 판매를 설계한다면 비관적 락은 재고 로우 하나에 모든 요청이 직렬화되어 10만 요청 앞에서 DB 병목이 심각해집니다. 대안으로 Redis에 재고 100을 세팅하고 DECR 원자 연산으로 0 이하이면 거부한 뒤, 통과한 요청만 DB에 주문을 생성하는 방식을 씁니다. 인메모리라 응답이 빠르고 DB 부하가 없어 실무에서 가장 널리 쓰는 패턴입니다. Lock timeout과 Connection timeout은 원인이 다릅니다. Connection timeout은 TCP 연결 자체를 못 맺는 인프라 문제(서버 다운, 커넥션 풀 고갈)이고, Lock timeout은 연결은 맺었지만 다른 트랜잭션이 점유한 락을 못 얻는 경합 문제입니다(InnoDB innodb_lock_wait_timeout 기본 50초). SELECT FOR UPDATE도 Tx1이 row A를 잠그고 row B를 요청하는 동시에 Tx2가 row B를 잠그고 row A를 요청하면 데드락이 나며, InnoDB는 이를 자동 감지해 비용이 적은 트랜잭션을 rollback합니다.

질문답변 방향

낙관적 락 버전 관리를 DB 트리거로 할 수 있나요?가능하지만 디버깅이 어렵고 재시도 로직 제어가 힘들어 JPA @Version 같은 애플리케이션 레벨 관리가 일반적입니다.

DBD-21

Q. Connection Pool 설정값은 어떤 기준으로 잡고, 무엇을 신호로 보나요?

핵심 개념

HikariCP의 maximumPoolSize·connectionTimeout·idleTimeout·maxLifetime은 각자 다른 실패 모드를 막는 값이므로, 하나라도 근거 없이 정하면 풀이 고갈되거나 DB가 과부하됩니다.

개념 해부

maximumPoolSize는 흔히 (CPU 코어 수 * 2) + 디스크 수 공식을 시작점으로 삼고, connectionTimeout은 풀에서 커넥션을 못 받았을 때 대기 상한(기본 30초), idleTimeout은 유휴 커넥션 정리 시점, maxLifetime은 DB의 wait_timeout보다 짧게 잡아야 DB가 먼저 끊어버려 애플리케이션이 죽은 커넥션을 잡는 상황을 피할 수 있습니다.

30초 답변

커넥션 수를 무제한에 가깝게 늘리면 메모리보다 먼저 DB 서버의 스레드 수가 문제가 됩니다. DB는 커넥션마다 전용 스레드를 할당하므로 커넥션이 늘수록 컨텍스트 스위칭 오버헤드가 커지고, 여러 스레드가 동시에 디스크에 접근하면 I/O 경합이 심해집니다. 특히 HDD는 한 번에 하나의 I/O만 처리하므로 특정 시점부터는 커넥션을 늘려도 처리량이 늘지 않고 오히려 떨어집니다.

90초 답변

이 값들은 부하 테스트로 검증하고 운영 중에는 Micrometer 같은 메트릭으로 실시간 관찰해야 실제 신호가 보입니다. connectionTimeout 초과가 늘면 풀 크기 부족이나 장시간 트랜잭션으로 인한 고갈을 의심하고, DB 쪽 스레드/커넥션 수가 애플리케이션 인스턴스 수 × maximumPoolSize보다 커지면 DB의 max_connections를 초과할 위험 신호입니다. maxLifetime을 DB wait_timeout보다 길게 두면 DB가 이미 닫은 커넥션을 풀이 살아있다고 착각해 재사용을 시도하다 실패하는 상황이 생기므로, 두 값의 순서를 항상 맞춰야 합니다.

꼬리질문

질문답변 방향
풀 크기를 무작정 늘리면 안 되는 이유는?DB 서버의 스레드·디스크 I/O가 한계에 부딪히면 커넥션을 늘려도 처리량이 늘지 않고 컨텍스트 스위칭만 커집니다.
인스턴스를 여러 대로 늘리면 뭐가 달라지나요?인스턴스 수만큼 풀 크기가 곱해지므로 DB max_connections 초과 위험이 커져 인스턴스별 풀 크기를 재계산해야 합니다.
idleTimeout과 maxLifetime의 역할 차이는?idleTimeout은 안 쓰는 커넥션 정리, maxLifetime은 커넥션 자체의 최대 수명 제한으로 목적이 다릅니다.

주의

DBD-22

Q. JPA에서 N+1과 대량 데이터 처리는 어떻게 다루나요?

핵심 개념

N+1은 연관 데이터를 지연 로딩하며 엔티티마다 추가 쿼리가 발생하는 문제이고, 대량 데이터 처리는 ORM의 편의 기능이 오히려 메모리와 네트워크 비용을 키우지 않도록 별도 전략이 필요합니다.

개념 해부

N+1 해결책은 세 가지입니다. Fetch Join(JOIN FETCH)은 한 번의 쿼리로 연관 데이터를 함께 가져오고, @BatchSize(size=100)는 N번의 쿼리를 IN 절로 묶어 N/100번으로 줄이며, @EntityGraph는 특정 조회에서만 즉시 로딩을 적용합니다. 기본은 Lazy로 두고 필요한 조회에서만 Fetch Join을 쓰는 것이 실무 기준입니다.

30초 답변

OneToMany 페치 조인은 부모 1건과 자식 3건을 조인하면 3행이 되는 카테시안 곱을 만들어 DB의 LIMIT/OFFSET이 의도대로 동작하지 않습니다. Hibernate는 이를 감지하면 전체 데이터를 메모리에 올린 뒤 애플리케이션에서 페이지네이션을 수행하므로 데이터가 많으면 OOM 위험이 있습니다. Batch Size를 쓰거나 ManyToOne 방향에서 페치 조인하는 방식으로 피합니다.

90초 답변

대량 데이터를 다룰 때는 saveAll()과 hibernate.jdbc.batch_size로 여러 INSERT를 하나의 네트워크 왕복으로 묶는 배치 INSERT를 씁니다. 다만 MySQL은 JDBC URL에 rewriteBatchedStatements=true를 추가해야 실제 multi-row INSERT로 변환되므로, 이 옵션이 빠지면 배치 설정을 해도 여전히 건건이 INSERT가 나갑니다. 대량 조회는 @QueryHints로 읽기 전용을 걸어 변경 감지를 끄고, 커서 기반 조회(Stream)나 페이징으로 메모리를 절약합니다. JPA와 JOOQ의 선택은 이 지점에서 갈립니다. JPA는 영속성 컨텍스트의 1차 캐시·변경 감지로 객체 중심 개발에 유리하지만 복잡한 쿼리 튜닝이 어렵고, JOOQ는 타입 안전한 SQL 빌더로 복잡한 조인·서브쿼리와 컴파일 타임 오류 검출에 강한 대신 변경 감지·캐싱을 직접 구현해야 합니다.

DBD-23

Q. B-Tree를 채택한 이유와 SQL 안티패턴은 어떻게 설명하나요?

핵심 개념

B-Tree는 디스크 I/O 최소화라는 단일 목적 때문에 배열이나 레드블랙트리 대신 채택됐고, SQL 안티패턴 상당수는 이 디스크 I/O 특성을 무시할 때 발생합니다.

개념 해부

정렬된 배열은 이진 탐색으로 읽기는 O(log N)이지만 삽입·삭제 시 데이터 이동이 O(N)이라 쓰기가 잦은 DB에 맞지 않고, 레드블랙트리 같은 이진 트리 계열은 노드당 키 1개만 저장해 트리 높이가 높아 디스크 I/O가 많이 발생합니다(인메모리 Java TreeMap에는 유리). B-Tree는 노드 하나에 여러 키를 저장해 한 번의 디스크 I/O(보통 4KB 페이지 단위)로 많은 키를 비교할 수 있어 트리 높이가 3~4 수준으로 낮고, 4억 건도 디스크 3~4번만 읽으면 찾을 수 있습니다.

30초 답변

순차 IO(연속된 디스크 위치를 읽는 풀 스캔)는 디스크 헤드 이동이 적어 빠르고, 랜덤 IO(흩어진 위치를 읽는 인덱스 레인지 스캔)는 매번 헤드를 이동해야 해 느립니다. SSD에서는 랜덤 IO 페널티가 HDD보다 작지만 순차 IO가 여전히 더 빠릅니다. SQL Injection은 PreparedStatement로 값과 쿼리 구조를 분리하는 것이 핵심 방어이며, ORM은 내부적으로 이를 사용하므로 문자열 연결로 직접 SQL을 조립하는 코드만 없애면 됩니다.

90초 답변

페이지네이션이 뒤로 갈수록 느려지는 이유도 같은 원리입니다. OFFSET 100000은 그만큼의 행을 읽고 버려야 하므로, 마지막 조회 PK 이후만 가져오는 No Offset 방식(WHERE id < ? ORDER BY id DESC LIMIT 20)으로 바꾸면 InnoDB 클러스터링 인덱스 특성상 PK 기반 조회가 가장 빠릅니다. 다만 No Offset은 마지막 조회 ID를 알아야 하고 데이터 생성·삭제로 범위가 깨질 수 있어, 정렬 기준 컬럼과 PK의 복합 인덱스나 커버링 인덱스로 보완합니다. 결과 집합 비교도 자주 나옵니다. EXISTS, INTERSECT, IN은 모두 두 테이블의 교집합에 해당하는 결과를 반환하지만, RIGHT OUTER JOIN은 오른쪽 테이블의 모든 행을 포함해 교집합에 없는 행도 NULL과 함께 나오므로 이 넷 중 RIGHT OUTER JOIN만 결과가 다릅니다.

DBD-24

Q. Replication 구현체와 변경 관리 도구는 실제로 어떻게 동작하나요?

핵심 개념

PostgreSQL은 WAL 파일 단위 Log Shipping과 레코드 단위 Streaming Replication을 병행해 지연과 유실 위험을 함께 관리하고, 애플리케이션은 AbstractRoutingDataSource로 이 복제 구조를 코드 변경 없이 활용합니다.

개념 해부

Log Shipping은 WAL 파일이 가득 차야 전송되므로 파일 생성까지 복제 지연(gap)이 있고, Streaming Replication은 레코드 단위 실시간 전송이라 지연은 적지만 Slave 장기 장애 시 Master가 오래된 WAL을 덮어써 유실 위험이 있습니다. 그래서 실무는 Streaming을 기본으로 하고 Log Shipping을 유실 방지용으로 병행합니다.

30초 답변

Spring에서는 AbstractRoutingDataSource를 구현해 @Transactional(readOnly=true)면 Slave로, 쓰기 트랜잭션이면 Master로 라우팅합니다. ThreadLocal에 현재 트랜잭션의 readOnly 여부를 저장해두고 DataSource 선택 시 참조하는 방식이라, 코드 변경 없이 어노테이션만으로 읽기/쓰기가 자동 분리됩니다. Master-Slave는 비동기 복제이므로 쓰기 직후 Slave에서 읽으면 반영 전 데이터가 조회될 수 있어, 결제 직후 주문 상태 확인처럼 정합성이 중요한 읽기는 Master로 직접 보냅니다.

90초 답변

WAL과 Binlog는 목적이 다릅니다. WAL(InnoDB의 redo log)은 데이터를 변경하기 전에 먼저 순차 기록해 장애 복구(crash recovery)를 위한 것이고, Binlog 같은 Logging은 변경 후 기록되며 리플리케이션과 감사(audit), 특정 시점 복구가 목적입니다. InnoDB는 redo log로 커밋된 변경을 복원하고 undo log로 미커밋 변경을 롤백합니다. 운영 도구 쪽에서는 변경 이력을 남겨야 하는 테이블에 원본 컬럼과 동일한 구조에 변경일시·변경유형·변경자 컬럼을 추가한 이력 테이블을 두고 대용량이면 날짜 기반 파티셔닝을 적용합니다. 스키마 변경은 Flyway가 flyway_schema_history 테이블과 마이그레이션 파일(V1__, V2__)을 비교해 미적용 버전만 순서대로 실행하고, 이미 적용된 파일을 수정하면 체크섬 불일치로 에러를 냅니다. 테스트는 H2가 MySQL과 GROUP BY 규칙·JSON 함수 등에서 동작이 달라 Testcontainers로 실제 MySQL 컨테이너를 띄워 검증해야 신뢰할 수 있습니다.

꼬리질문

질문답변 방향
동기 복제를 쓰면 무엇이 희생되나요?Slave 반영까지 응답을 보류하므로 정합성은 보장되지만 쓰기 지연이 늘어납니다.
Flyway 마이그레이션 파일을 실수로 수정하면?체크섬이 달라져 다음 배포에서 에러가 나므로, 수정이 필요하면 새 버전 파일을 추가해야 합니다.
이력 테이블을 트리거로 채우는 것과 애플리케이션에서 채우는 것의 차이는?트리거는 누락 없이 모든 변경을 잡지만 디버깅이 어렵고, 애플리케이션 레벨은 제어가 쉽지만 우회 경로(직접 SQL)를 놓칠 수 있습니다.

주의

SEC-01

Q. 보안 질문은 어떤 프레임으로 답하나요?

핵심 개념

보안 답변은 취약점 이름보다 보호할 자산, 공격자가 조작할 수 있는 입력, 신뢰 경계, 서버 방어선, 탐지와 복구를 함께 설명해야 합니다.

개념 해부

보안 답변은 취약점 이름을 나열하는 것이 아니라 asset, actor, trust boundary, attack path, control을 연결하는 일입니다. 무엇을 지키는지와 누가 어떤 경로로 침해할 수 있는지 정의해야 방어선이 의미를 가집니다. UI 제어, API 인증, DB 제약, 로그는 서로 다른 방어층입니다.

30초 답변

먼저 보호할 자산과 신뢰 경계를 정의합니다. 그 다음 공격자가 바꿀 수 있는 입력을 식별하고, 서버 측 검증과 권한 확인을 설명합니다. 마지막으로 방어 우회 가능성, audit log, rate limit, alert, 테스트로 어떻게 검증할지 말합니다.

90초 답변

예를 들어 “파일 다운로드 API가 안전한가”라는 질문은 URL을 숨겼는지보다 현재 사용자가 해당 파일을 읽을 권한이 있는지, tenant scope가 맞는지, presigned URL 만료가 짧은지, 다운로드 로그가 남는지, 민감 파일이 cache되지 않는지까지 봐야 합니다. 클라이언트 제어는 UX 보조일 뿐 최종 방어선은 서버입니다.

꼬리질문

질문답변 방향

보안과 UX가 충돌하면?위험도와 자산 중요도를 기준으로 단계적 인증, 세션 정책, 로깅을 설계합니다.

SEC-02

Q. Threat Modeling은 어떻게 하나요?

핵심 개념

Threat Modeling은 기능을 만들기 전에 공격자가 어떤 경로로 어떤 자산을 해칠 수 있는지 구조적으로 보는 활동입니다. OWASP Top 10은 이 위협을 코드 리뷰와 테스트 체크리스트로 구체화할 때 유용한 기준입니다.

개념 해부

Threat Modeling은 완벽한 공격 목록을 만드는 행사가 아니라 설계 단계에서 신뢰 경계를 눈에 보이게 만드는 작업입니다. 데이터 흐름을 그리고 외부 입력, 권한 상승, 민감정보 저장, 외부 호출 지점을 찾습니다. STRIDE 같은 프레임은 누락을 줄이는 체크리스트이지 목적 자체가 아닙니다.

30초 답변

먼저 자산, 사용자 역할, 데이터 흐름, 신뢰 경계를 그립니다. 그 다음 각 경계에서 조작 가능한 입력, 권한 상승, 데이터 유출, 위조, 재전송, 서비스 거부 가능성을 봅니다. 위험도에 따라 서버 검증, 권한 모델, 암호화, rate limit, 로그, 알림을 설계합니다.

90초 답변

예를 들어 multi-tenant 관리자 화면에서는 tenant A 사용자가 tenant B 데이터를 볼 수 있는지, URL id를 바꾸면 접근되는지, export 기능이 과도한 데이터를 내보내는지, audit log가 충분한지 봅니다. STRIDE 같은 프레임은 Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege로 위협을 빠짐없이 보는 데 도움을 줍니다.

꼬리질문

질문답변 방향

모든 기능에 하나요?위험도 기반으로 깊이를 조절하고 checklist를 코드 리뷰에 반영합니다.
산출물은?데이터 흐름, 신뢰 경계, 위협 목록, 완화책, 잔여 위험, 테스트 케이스입니다.

면접에서 말할 증거

권한 기능, 파일 업로드, OAuth callback, webhook 같은 기능에서 threat model을 적용한 예를 준비합니다.

SEC-03

Q. IDOR와 접근 제어 취약점은 어떻게 막나요?

핵심 개념

IDOR는 사용자가 식별자를 바꿔 다른 사용자의 리소스에 접근하는 취약점입니다. 방어는 id를 숨기는 것이 아니라 서버가 actor, action, resource 관계를 검증하는 것입니다.

개념 해부

IDOR는 사용자가 인증됐다는 사실과 특정 객체에 접근할 권한이 있다는 사실을 혼동할 때 생깁니다. URL이나 body의 id를 신뢰하지 말고 서버에서 actor, resource, action 관계를 확인해야 합니다. tenant id 누락은 B2B SaaS에서 가장 치명적인 접근 제어 실수 중 하나입니다.

30초 답변

IDOR는 URL이나 body의 id를 바꿨을 때 권한 검증 없이 다른 리소스가 노출될 때 생깁니다. UUID를 쓰거나 버튼을 숨기는 것으로는 충분하지 않습니다. 모든 API에서 현재 사용자, 역할, tenant, resource owner, action 권한을 서버에서 검증해야 합니다.

90초 답변

접근 제어는 인증 후 한 번만 하는 것이 아니라 리소스마다 해야 합니다. 관리자 화면에서는 role만 보면 부족하고 organization, tenant, project, data scope를 함께 확인해야 합니다. 목록 API와 상세 API, export API, bulk action, 파일 다운로드 API 모두 같은 권한 모델을 적용해야 합니다.

SEC-04

Q. 인증과 세션 관리는 어떻게 설계하나요?

핵심 개념

인증은 사용자가 누구인지 확인하는 것이고, 세션 관리는 그 인증 상태를 안전하게 유지하고 종료하는 체계입니다.

개념 해부

세션 관리는 로그인 순간보다 로그인 이후의 수명 관리가 더 중요합니다. 세션 만료, rotation, revoke, device 관리, CSRF/XSS 위협, refresh token 재사용 탐지가 모두 포함됩니다. 인증 정보가 유출됐을 때 피해를 줄이는 설계가 안전한 세션 설계입니다.

30초 답변

세션은 발급, 저장, 만료, 갱신, 폐기, 탈취 대응을 함께 설계해야 합니다. Cookie를 쓴다면 HttpOnly, Secure, SameSite, CSRF 방어를 보고, server-side session이면 session store, device revoke, idle timeout, absolute timeout을 봅니다.

90초 답변

세션 fixation을 막으려면 로그인 성공 시 session id를 재발급해야 합니다. 로그아웃은 클라이언트 토큰 삭제뿐 아니라 server-side session invalidate나 refresh token revoke가 필요합니다. 민감 작업에는 step-up authentication이나 재인증을 적용할 수 있습니다. 여러 기기 로그인, 비밀번호 변경 후 세션 폐기 정책도 중요합니다.

꼬리질문

질문답변 방향
session fixation은?공격자가 정한 session id로 피해자가 로그인하게 하는 공격이며 로그인 시 재발급합니다.
remember me는?장기 토큰 저장과 rotation, device revoke, 탈취 탐지를 설계해야 합니다.
로그아웃은?클라이언트 삭제와 서버 revoke/invalidate를 함께 봅니다.

면접에서 말할 증거

세션 만료 정책, cookie flag, refresh token revoke, device 관리 경험을 말합니다.

SEC-05

Q. OAuth2와 OIDC는 어떻게 다르나요?

핵심 개념

OAuth2는 권한 위임 프레임워크이고, OIDC는 OAuth2 위에 identity layer를 얹어 로그인과 사용자 정보를 표준화한 프로토콜입니다.

개념 해부

OAuth2는 권한 위임 프레임워크이고, OIDC는 그 위에 identity layer를 얹어 사용자가 누구인지 확인하게 해줍니다. access token은 API 접근 권한을 나타내고, id token은 client가 사용자의 인증 정보를 확인하기 위한 token입니다. redirect URI, state, PKCE, nonce를 혼동하면 공격 표면이 커집니다.

30초 답변

OAuth2의 access token은 API 접근 권한을 나타내고, OIDC의 id token은 사용자가 누구인지에 대한 인증 정보를 담습니다. 로그인에는 authorization code flow와 PKCE를 사용하고, redirect URI, state, nonce, token audience, scope 검증이 중요합니다.

90초 답변

보안상 implicit flow보다 authorization code + PKCE가 권장됩니다. state는 CSRF 방어, nonce는 id token replay 방어에 사용됩니다. redirect URI를 넓게 허용하면 authorization code 탈취 위험이 있고, id token을 API authorization에 쓰면 audience와 목적이 맞지 않을 수 있습니다. refresh token rotation과 reuse detection은 장기 토큰 탈취를 탐지하고 피해를 줄이는 핵심 방어선입니다.

꼬리질문

질문답변 방향
PKCE는 왜 필요한가요?authorization code를 탈취해도 code verifier 없이는 token 교환을 못 하게 합니다.
state와 nonce 차이는?state는 요청 위조 방어, nonce는 id token replay 방어입니다.
refresh token은?장기 권한이므로 rotation, reuse detection, revoke가 필요합니다.

오답/주의점

주의

OAuth를 “소셜 로그인”으로만 말하면 부족합니다. 권한 위임과 identity layer를 구분하세요.

SEC-06

Q. JWT는 어떻게 검증해야 안전한가요?

핵심 개념

JWT는 서명된 claim 묶음이며, 안전하려면 서명뿐 아니라 issuer, audience, expiry, algorithm, key rotation, revoke 전략을 함께 검증해야 합니다.

개념 해부

JWT 검증은 서명만 확인하는 것으로 끝나지 않습니다. issuer, audience, expiration, not-before, algorithm, key id, clock skew, token type을 모두 검증해야 합니다. claim은 사용자가 바꿀 수 없도록 서명되어 있지만, 서버가 그 claim을 어떤 권한으로 해석할지는 별도 정책입니다.

30초 답변

JWT는 header, payload, signature로 구성됩니다. 서버는 signature를 검증하고 exp, nbf, iss, aud, scope를 확인해야 합니다. algorithm confusion을 막기 위해 허용 algorithm을 고정하고, key rotation과 JWKS cache, clock skew도 고려합니다.

90초 답변

JWT의 장점은 stateless 검증이지만 즉시 revoke가 어렵다는 단점이 있습니다. 그래서 access token은 짧게 유지하고 refresh token은 server-side 저장과 rotation을 둡니다. 민감 권한 변경이나 계정 차단 시에는 token version, denylist, introspection 같은 보완책을 검토합니다. payload는 암호화가 아니므로 민감정보를 넣지 않습니다.

꼬리질문

질문답변 방향
JWT를 localStorage에 저장하면?XSS에 취약하므로 threat model을 보고 HttpOnly cookie 등 대안을 검토합니다.
audience 검증은 왜?다른 API용 토큰이 우리 API에서 재사용되는 것을 막습니다.
서명만 맞으면 되나요?아닙니다. 만료, 발급자, 대상, 권한, algorithm까지 검증해야 합니다.

면접에서 말할 증거

JWT 검증 middleware에서 checked claim 목록과 실패 로그를 설명하면 좋습니다.

SEC-07

Q. XSS와 CSRF는 어떻게 다르고 어떻게 막나요?

핵심 개념

XSS는 공격자 입력이 브라우저에서 스크립트로 실행되는 문제이고, CSRF는 사용자의 인증 상태를 이용해 원치 않는 요청을 보내는 문제입니다.

개념 해부

XSS는 공격자가 우리 origin에서 JavaScript를 실행하게 만드는 문제이고, CSRF는 사용자의 인증 상태를 이용해 원치 않는 요청을 보내게 하는 문제입니다. XSS 방어는 context-aware escaping, sanitization, CSP가 중심이고, CSRF 방어는 SameSite, CSRF token, origin 검증이 중심입니다. 둘은 원인과 방어선이 다릅니다.

30초 답변

XSS는 output escaping, sanitization, CSP, dangerous HTML 제한으로 막고, CSRF는 SameSite cookie, CSRF token, Origin/Referer 검증으로 막습니다. XSS는 토큰 탈취와 사용자 대신 행동을 가능하게 하므로 CSRF 방어만으로는 부족합니다.

90초 답변

React는 기본적으로 문자열을 escape하지만 dangerouslySetInnerHTML, markdown/html rendering, third-party widget, URL injection에서는 위험이 남습니다. CSRF는 cookie 기반 인증에서 특히 중요합니다. JSON API라도 preflight가 항상 보안 장벽은 아니며 state-changing 요청은 서버에서 origin과 token을 검증해야 합니다.

꼬리질문

질문답변 방향
CSP는 만능인가요?피해를 줄이는 방어선이지만 escaping과 sanitization을 대체하지 않습니다.
SameSite=Lax면 충분한가요?요구사항과 browser 동작을 보고 민감 요청에는 token 검증도 고려합니다.
stored XSS와 reflected XSS는?저장된 입력이 나중에 실행되는지, 요청에 반사되어 실행되는지 차이입니다.

오답/주의점

주의

“React라 XSS가 없습니다”는 틀린 답변입니다. HTML 삽입과 URL, 외부 콘텐츠를 봐야 합니다.

SEC-08

Q. SQL Injection과 Command Injection은 어떻게 막나요?

핵심 개념

Injection은 사용자 입력이 명령이나 쿼리의 데이터가 아니라 구조로 해석될 때 발생합니다.

개념 해부

Injection은 신뢰할 수 없는 입력이 명령이나 쿼리의 구조로 해석될 때 생깁니다. SQL은 parameterized query로 값과 쿼리 구조를 분리하고, command execution은 가능하면 shell 호출 자체를 피해야 합니다. allowlist validation은 입력 공간을 좁히는 보조 방어선입니다.

30초 답변

SQL Injection은 prepared statement와 parameter binding으로 막고, 동적 order by나 column name처럼 바인딩할 수 없는 부분은 allowlist를 씁니다. Command Injection은 shell 문자열 조합을 피하고, 인자 배열 API와 allowlist validation, 권한 제한, sandbox를 사용합니다.

90초 답변

ORM을 쓴다고 injection이 자동으로 사라지는 것은 아닙니다. raw query, string interpolation, 동적 검색 조건, report query에서 위험이 남습니다. 입력 검증은 보조 방어선이고 핵심은 코드와 데이터를 분리하는 것입니다. 에러 메시지에 SQL이나 내부 경로를 노출하지 않는 것도 중요합니다.

꼬리질문

질문답변 방향
LIKE 검색은?parameter binding과 wildcard escape를 함께 봅니다.
동적 정렬은?사용자 입력을 column allowlist에 매핑합니다.
파일 변환 명령은?shell=false, 인자 배열, 파일명 검증, 임시 디렉터리 격리를 씁니다.

면접에서 말할 증거

raw query 리뷰, allowlist validation, negative test, scanner 결과 대응 경험을 말합니다.

SEC-09

Q. SSRF는 왜 위험하고 어떻게 방어하나요?

핵심 개념

SSRF는 서버가 공격자가 지정한 URL로 요청을 보내게 되어 내부망, metadata endpoint, admin service에 접근할 수 있는 취약점입니다.

개념 해부

SSRF는 서버가 내부망이나 metadata endpoint에 접근할 수 있다는 점을 공격자가 악용하는 취약점입니다. URL allowlist, DNS rebinding 방어, private IP 차단, egress policy, metadata service 보호가 필요합니다. 단순히 client에서 URL 형식을 검사하는 것으로는 부족합니다.

30초 답변

SSRF는 URL fetch, webhook test, image import, PDF generation 같은 기능에서 생길 수 있습니다. 방어는 URL allowlist, private IP/link-local 차단, DNS rebinding 대응, redirect 제한, timeout, response size 제한, metadata endpoint 차단입니다.

90초 답변

단순히 문자열이 http로 시작하는지만 보면 우회됩니다. DNS 해석 결과가 private IP인지 확인하고, redirect 후 최종 주소도 검사해야 합니다. IPv6, decimal/hex IP, localhost alias, internal DNS 이름도 고려합니다. 가능하면 외부 fetch는 별도 egress 제한 환경에서 수행하고, 접근 가능한 네트워크를 최소화합니다.

꼬리질문

질문답변 방향
metadata endpoint가 왜 위험한가요?클라우드 credential이나 instance metadata가 유출될 수 있습니다.
allowlist와 blocklist 중?가능하면 allowlist가 안전하고 blocklist는 우회가 많습니다.
redirect는?초기 URL뿐 아니라 redirect 최종 URL도 검증해야 합니다.

오답/주의점

주의

SSRF는 “외부 URL 호출” 기능 전체의 egress 통제 문제로 봐야 합니다.

SEC-10

Q. 비밀번호와 Secret은 어떻게 저장하나요?

핵심 개념

비밀번호는 복호화 가능한 암호화가 아니라 password hashing으로 저장하고, secret은 저장·주입·회전·감사 체계를 갖춰야 합니다.

개념 해부

비밀번호는 복호화할 필요가 없는 secret이므로 느린 password hashing 함수와 salt로 저장해야 합니다. API key나 OAuth secret처럼 다시 사용해야 하는 secret은 암호화, 접근 제어, rotation, audit가 필요합니다. Secret은 코드, 로그, error report, analytics로 새어나가지 않게 경로를 점검해야 합니다.

30초 답변

비밀번호는 bcrypt, scrypt, Argon2 같은 password hashing을 사용하고 salt와 work factor를 둡니다. secret은 코드와 이미지에 넣지 않고 secret manager에서 관리하며, 접근 권한, rotation, 로그 마스킹, 유출 시 revoke 절차를 마련합니다.

90초 답변

비밀번호 reset token은 충분히 랜덤해야 하고 짧은 만료와 1회 사용 정책이 필요합니다. 로그인과 reset, OTP endpoint에는 rate limit과 abuse detection이 필요합니다. secret rotation은 새 secret과 구 secret이 잠시 공존할 수 있는지, 배포 순서가 안전한지까지 봐야 합니다.

꼬리질문

질문답변 방향
암호화와 hashing 차이는?암호화는 복호화 가능, password hashing은 검증만 가능하도록 설계합니다.
pepper는?DB와 별도 저장소에 둔 추가 secret으로 hash 방어를 보강할 수 있습니다.
secret 유출 시?revoke/rotate, 로그 확인, 영향 범위 산정, 재발 방지를 수행합니다.

면접에서 말할 증거

secret scan, rotation runbook, log redaction, password reset abuse 방어를 말하면 좋습니다.

SEC-11

Q. Multi-tenant SaaS에서 보안상 가장 중요한 것은 무엇인가요?

핵심 개념

Multi-tenant 보안의 핵심은 tenant isolation입니다. 한 고객의 사용자나 관리자가 다른 고객의 데이터에 접근하지 못해야 합니다.

개념 해부

Multi-tenant 보안의 핵심은 모든 데이터 접근 경로에 tenant boundary가 빠지지 않게 하는 것입니다. UI 메뉴, API query, background job, export, search index, cache key까지 tenant 조건이 들어가야 합니다. 한 곳의 누락이 다른 고객 데이터 노출로 이어질 수 있습니다.

30초 답변

모든 query와 API에서 tenant scope를 강제해야 합니다. URL id, filter, export, background job, cache key, search index, object storage path, audit log까지 tenant_id가 누락되지 않게 설계합니다. 권한 검증은 role뿐 아니라 tenant membership과 resource scope를 함께 봐야 합니다.

90초 답변

tenant isolation은 코드 리뷰만으로 보장하기 어렵습니다. repository layer에서 tenant filter를 기본 적용하거나 row-level security, scoped service API, integration test를 둡니다. cache key에 tenant가 빠지거나 object storage prefix 권한이 넓으면 DB 권한이 맞아도 데이터가 샐 수 있습니다.

꼬리질문

질문답변 방향
admin은 모든 tenant를 볼 수 있나요?운영자 권한도 승인, 감사, 최소 권한, break-glass 절차가 필요합니다.
batch job은?tenant별 범위와 실패 격리, audit log를 남겨야 합니다.
검색 인덱스는?tenant filter가 index query에도 강제되어야 합니다.

오답/주의점

주의

tenant_id를 “프론트에서 넘겨준다”는 설계는 위험합니다. 서버가 세션과 권한에서 scope를 결정해야 합니다.

SEC-12

Q. 감사 로그는 일반 로그와 어떻게 다르나요?

핵심 개념

감사 로그는 디버깅 로그가 아니라 누가, 언제, 어떤 권한으로, 어떤 대상에, 어떤 변경을 했는지 추적하는 보안 증거입니다.

개념 해부

감사 로그는 디버깅 로그가 아니라 나중에 누가 어떤 민감한 행동을 했는지 증명하는 기록입니다. actor, target, action, result, reason, before/after, request id, timestamp가 중요하고 임의 수정이 어려워야 합니다. 개인정보와 secret을 과하게 남기면 감사 로그 자체가 위험 자산이 됩니다.

30초 답변

audit log에는 actor, action, target, tenant, result, reason, source IP, user agent, traceId, before/after summary를 남깁니다. 민감정보 원문은 남기지 않고 마스킹하며, 변경 불가능성, 보관 기간, 접근 권한도 관리해야 합니다.

90초 답변

감사 로그는 사고 대응과 고객 문의, 규제 대응에 필요합니다. 예를 들어 관리자가 권한을 바꾸거나 파일을 export하거나 결제 상태를 수정한 경우 누가 왜 했는지 확인할 수 있어야 합니다. 로그가 너무 많아도 찾기 어려우므로 중요 action을 정의하고 검색 가능한 구조로 남깁니다.

꼬리질문

질문답변 방향
민감정보는?원문 저장을 피하고 tokenization/masking/redaction을 적용합니다.
위변조 방지는?append-only 저장, 권한 제한, 별도 계정, checksum 또는 외부 로그 저장을 봅니다.
alert는?권한 변경, 대량 export, 실패한 로그인, 비정상 지역 접근 같은 이벤트를 봅니다.

면접에서 말할 증거

운영자 action, 권한 변경, 데이터 export에 audit log를 설계한 경험을 말합니다.

SEC-13

Q. 보안 사고가 발생하면 어떤 순서로 대응하나요?

핵심 개념

보안 사고 대응은 탐지, 격리, 영향 범위 산정, 증거 보존, 근절, 복구, 고지, 재발 방지의 순서로 진행합니다.

개념 해부

보안 사고 대응은 원인 분석보다 격리와 증거 보존이 먼저입니다. 영향 범위, 공격 경로, 노출 데이터, credential rotation, 임시 차단, 법적/고객 공지 기준을 순서대로 봐야 합니다. 로그를 지우거나 시스템을 성급히 재배포하면 포렌식 단서가 사라질 수 있습니다.

30초 답변

먼저 사고인지 확인하고 영향 범위를 좁힙니다. 유출된 token이나 secret은 revoke/rotate하고, 취약 endpoint나 계정을 격리합니다. 로그와 증거를 보존한 뒤 패치, 복구, 사용자 고지 판단, postmortem과 재발 방지 action을 진행합니다.

90초 답변

사고 대응에서는 원인 분석보다 확산 방지가 먼저일 수 있습니다. 예를 들어 access key 유출이면 즉시 비활성화하고 어떤 리소스에 접근했는지 audit log를 봅니다. 개인정보 가능성이 있으면 법무/보안/운영 커뮤니케이션 경로를 따르고, 임의로 로그를 지우면 증거가 사라질 수 있습니다.

꼬리질문

질문답변 방향
secret 유출이면?rotate/revoke, 접근 로그 확인, downstream credential 재발급, scan rule 추가를 말합니다.
사용자 고지는?영향 데이터, 법적 요구, 회사 프로세스에 따라 판단합니다.
postmortem에는?timeline, detection gap, blast radius, root cause, action owner와 due date를 남깁니다.

오답/주의점

주의

“패치하면 끝”이 아닙니다. 영향 범위, 증거, 고지, 재발 방지까지 사고 대응입니다.

NET-01

Q. 브라우저에서 HTTPS 요청 하나는 어떤 주소 체계와 단계를 거쳐 서버까지 도달하나요?

핵심 개념

IP는 최종 목적지를 찾기 위한 논리 주소이고 MAC은 같은 링크 안에서 실제로 프레임을 넘기기 위한 주소이며, 포트는 4-tuple로 여러 연결을 구분합니다. 요청 하나는 DNS 조회부터 TLS handshake, 렌더링까지 여러 계층을 순서대로 통과합니다.

개념 해부

목적지 IP는 경로 전체에서 유지되지만, MAC은 홉마다 바뀝니다. 목적지가 같은 네트워크면 ARP로 그 장비의 MAC을 바로 찾고, 다른 네트워크면 MAC은 링크 로컬이라 최종 서버까지 직접 도달할 수 없으므로 ARP로 기본 게이트웨이의 MAC을 찾아 우선 그쪽으로 넘깁니다. 라우터는 프레임을 벗겨 IP를 보고 다음 구간의 새 프레임을 만듭니다. 포트는 IP만으로 구분되지 않는, 한 호스트 안의 여러 소켓을 식별하는 계층입니다.

30초 답변

Google 검색을 예로 들면, 먼저 DNS로 IP를 얻고 443 포트로 TCP 3-way handshake를 맺습니다. 그 위에서 TLS handshake가 진행되어 ClientHello/ServerHello, 인증서 검증, ECDHE 키 교환으로 세션 키를 만들고, 이후 요청/응답은 그 세션 키로 암호화됩니다. 응답을 받으면 브라우저가 파싱해 렌더링합니다.

90초 답변

계층을 나눠 보면 IP는 목적지 호스트를 찾는 역할, MAC은 지금 링크에서 다음 장비로 넘기는 역할, 포트는 그 호스트 안의 어느 소켓인지 구분하는 역할로 나뉩니다. ARP는 이 세 계층을 잇는 역할을 합니다 — 목적지가 같은 네트워크가 아니면 브라우저는 최종 서버의 MAC을 찾지 않고 항상 기본 게이트웨이의 MAC만 ARP로 조회합니다. TCP 연결이 열리면 TLS handshake는 비대칭 키로 서버를 인증하고 키를 교환한 뒤 대칭 키로 전환합니다. 연결은 매 요청마다 새로 맺지 않고 HTTP Keep-Alive나 HTTP/2로 재사용되며, 더 필요 없거나 유휴 시간이 지나면 TCP 종료 과정으로 닫힙니다.

NET-02

Q. Connection Timeout과 Read Timeout은 왜 다르게 다뤄야 하나요?

핵심 개념

TCP Connection은 4-tuple로 식별되는 양방향 논리 경로이며, 연결 자체를 못 맺는 Connection Timeout과 연결 후 응답이 늦는 Read Timeout은 원인과 대응이 다른 별개의 실패입니다.

개념 해부

Connection Timeout은 서버 다운, 방화벽 차단, 네트워크 경로 문제로 SYN-ACK가 오지 않는 인프라성 실패이고, Read Timeout은 연결은 성공했지만 서버 내부 처리 지연으로 응답이 늦는 애플리케이션성 실패입니다. 둘 다 무한 대기를 막아 스레드·소켓·커넥션 풀 자원 고갈을 방지하는 목적은 같지만, 실패 원인을 진단할 때는 구분해야 합니다. TCP Keep Alive는 이 둘과 다른 개념으로, 유휴 연결이 살아있는지 운영체제가 주기적으로 확인하는 전송 계층 기능입니다.

30초 답변

Connection Timeout은 TCP 연결 자체를 맺는 단계의 최대 대기 시간이고, Read Timeout은 연결 이후 응답 데이터를 기다리는 최대 시간입니다. 전자는 서버·네트워크 장애를, 후자는 서버 내부 처리 지연을 의심하게 만듭니다. TCP Keep Alive는 유휴 상태의 좀비 연결을 정리하기 위한 별도의 probe 메커니즘입니다.

90초 답변

두 타임아웃을 하나로 뭉뚱그리면 장애 대응이 느려집니다. Connection Timeout이 자주 발생하면 서버 헬스, 네트워크 경로, 커넥션 풀 고갈을 먼저 봐야 하고, Read Timeout이 자주 발생하면 서버 내부의 느린 쿼리·외부 API·GC 정지를 봐야 합니다. TCP Connection은 출발지 IP·포트, 목적지 IP·포트로 이루어진 4-tuple로 식별되므로, 같은 서버·같은 포트라도 클라이언트 출발지 포트가 다르면 별개 연결로 관리됩니다. HTTP Keep-Alive(애플리케이션 계층의 연결 재사용)와 TCP Keep Alive(전송 계층의 생존 확인)는 이름이 비슷하지만 하는 일이 다릅니다.

“타임아웃이니까 같은 문제”라는 답은 얕습니다. 두 타임아웃은 발생 단계가 다르므로 원인 진단 경로도 달라야 합니다.

NET-03

Q. TCP 혼잡 제어와 UDP의 오류 처리는 어떻게 동작하나요?

핵심 개념

UDP는 checksum으로 오류를 검출만 하고 복구하지 않으며, TCP는 혼잡 윈도우(cwnd)를 조절해 네트워크가 감당할 수 있는 범위에서 송신량을 스스로 제어합니다.

개념 해부

UDP는 헤더의 checksum으로 손상된 데이터그램을 폐기하지만, 재전송이나 순서 보장은 하지 않으므로 신뢰성이 필요하면 애플리케이션 계층에서 메시지 번호·ACK·재전송을 직접 구현해야 합니다. TCP 혼잡 제어는 Slow Start로 cwnd를 빠르게 키우다가 임계점부터 Congestion Avoidance로 증가 폭을 줄이고, 손실 시 cwnd를 낮춥니다. 중복 ACK가 3번 오면 타임아웃을 기다리지 않고 즉시 재전송하는 Fast Retransmit, 그 후 Slow Start로 완전히 되돌아가지 않는 Fast Recovery가 있으며, 리눅스의 CUBIC이나 지연·대역폭을 함께 추정하는 BBR 같은 구현체가 있습니다.

30초 답변

UDP는 checksum으로 오류만 검출하고 복구는 하지 않으므로, 신뢰성이 필요하면 애플리케이션에서 직접 처리해야 합니다. TCP는 cwnd를 Slow Start로 키우다가 Congestion Avoidance로 넘어가고, 손실 감지 시 Fast Retransmit·Fast Recovery로 대응하며, CUBIC·BBR 같은 알고리즘으로 구체적인 증감 방식이 달라집니다.

90초 답변

TCP 혼잡 제어는 송신 호스트가 ACK, 손실, RTT 신호를 보고 스스로 전송량을 조절하는 엔드포인트 자율 메커니즘입니다. 이는 네트워크 장비가 트래픽 종류별로 우선순위를 부여하는 QoS와는 다른 층위입니다 — 예를 들어 음성·영상 같은 실시간 트래픽은 라우터·스위치가 우선순위 큐나 대역폭 보장으로 처리하는 정책 기반 제어이고, TCP 혼잡 제어는 각 연결의 송신 측이 손실·ACK를 보고 반응하는 자율 제어입니다. 둘 다 혼잡과 품질을 다루지만 책임 주체와 제어 위치가 다릅니다.

꼬리질문

질문답변 방향
UDP 위에서 신뢰성을 어떻게 구현하나요?메시지 번호를 붙이고 ACK를 받아 일정 시간 안에 응답이 없으면 재전송하는 방식으로 보완합니다.
Slow Start가 계속되면 어떻게 되나요?혼잡을 유발할 수 있어 임계점(ssthresh)부터 증가 폭을 줄이는 Congestion Avoidance로 전환합니다.
QoS만으로 혼잡 제어를 대체할 수 있나요?QoS는 네트워크 장비의 우선순위 정책일 뿐, 엔드포인트의 전송량 자체를 줄이지는 않습니다.

주의

“UDP는 오류 검출도 안 한다”는 틀린 답입니다. checksum으로 검출은 하되 복구를 하지 않는다는 점이 핵심입니다.

NET-04

Q. DNS TTL은 왜 변경 반영을 늦추고, DNS로 로드밸런싱이 가능한가요?

핵심 개념

TTL은 DNS 응답을 캐시에 보관하는 시간이며, 로컬 DNS와 클라이언트가 TTL 동안 캐시를 재사용하기 때문에 레코드를 바꿔도 모든 사용자에게 즉시 반영되지 않습니다.

개념 해부

흔히 말하는 DNS 전파 지연은 레코드가 전 세계로 복사되는 시간이 아니라, 여러 캐시가 만료되기를 기다리는 시간에 가깝습니다. 그래서 배포나 서버 이전 전에는 TTL을 미리 짧게 낮추고, 안정화되면 다시 올립니다. DNS Round-robin은 하나의 도메인에 여러 A/AAAA 레코드를 등록해 트래픽을 분산하는 가장 단순한 방법이지만, 캐시 때문에 변경이 느리게 반영되고 서버 장애를 감지하지 못해 죽은 IP가 캐시에 남아 있으면 일부 사용자가 계속 실패할 수 있습니다.

30초 답변

TTL 동안 로컬 DNS와 클라이언트가 이전 응답을 캐시해 재사용하므로, 레코드 변경은 TTL이 끝나야 모든 사용자에게 반영됩니다. DNS Round-robin으로 로드밸런싱은 가능하지만, 캐시로 인한 느린 반영과 장애 서버 미감지 문제가 있어 실무에서는 헬스체크 기반 DNS나 GeoDNS를 쓰거나 L4/L7 로드밸런서와 병행합니다.

90초 답변

TTL이 너무 길면 장애 대응이나 IP 변경 반영이 늦고, 너무 짧으면 DNS 질의가 늘어 권한 DNS와 로컬 DNS에 부담이 커지는 트레이드오프가 있습니다. DNS 로드밸런싱의 근본 한계는 DNS 자체가 헬스 상태를 실시간으로 반영하는 계층이 아니라는 점입니다. 그래서 가중치 기반 응답이나 지역 기반 라우팅(GeoDNS)으로 보완하더라도, 실제 요청 분산과 장애 감지의 정교한 제어는 L4/L7 로드밸런서가 맡고 DNS는 1차 트래픽 분산이나 지역 선택 용도로 쓰는 조합이 일반적입니다.

꼬리질문

질문답변 방향
TTL을 낮추면 무엇이 희생되나요?DNS 질의 빈도가 늘어 권한 DNS·로컬 DNS 부하가 커집니다.
DNS Round-robin이 실패를 못 막는 이유는?DNS는 응답 시점의 서버 상태를 확인하지 않고 등록된 레코드를 그대로 돌려주기 때문입니다.
배포 전 TTL을 낮추는 이유는?변경 사항이 캐시 만료를 기다리지 않고 더 빨리 반영되게 하기 위해서입니다.

오답/주의점

주의

“DNS를 바꾸면 즉시 반영된다”는 틀린 전제입니다. TTL이 남아있는 캐시는 그 시간만큼 이전 값을 계속 돌려줍니다.

NET-05

Q. HTTP 메시지는 어떻게 구성되고, HTTP/3는 왜 UDP 기반 QUIC을 쓰나요?

핵심 개념

HTTP 메시지는 시작줄·헤더·빈 줄·본문으로 구성되며 서버는 파싱→라우팅→인증/검증→로직→응답 순으로 처리하고, HTTP/3는 TCP의 Head-of-Line Blocking을 해결하기 위해 UDP 위에 QUIC이라는 별도의 신뢰성 계층을 직접 구현합니다.

개념 해부

요청 시작줄은 메서드·URI·버전, 응답 시작줄은 버전·상태코드·문구를 담습니다. HTTP/2는 하나의 TCP 연결에서 여러 요청을 멀티플렉싱하지만, 아래 TCP 계층에서 패킷 하나가 유실되면 순서 보장 때문에 뒤에 도착한 데이터도 애플리케이션에 전달되지 못하는 Head-of-Line Blocking이 있습니다. QUIC은 여러 스트림을 독립적으로 다뤄 한 스트림의 유실이 다른 스트림에 영향을 주지 않고, TLS 1.3을 통합해 핸드셰이크를 줄이며, IP·포트가 아닌 Connection ID로 연결을 식별해 네트워크가 바뀌어도 연결을 유지할 수 있습니다.

30초 답변

HTTP 메시지는 시작줄·헤더·본문으로 구성되고, 헤더는 Content-Type·Authorization·Cache-Control 같은 메타데이터를 담습니다. HTTP/3가 UDP 기반인 이유는 UDP가 빨라서가 아니라, QUIC이 스트림 단위 독립성으로 TCP의 Head-of-Line Blocking을 없애고 TLS 1.3 통합과 Connection ID로 빠른 재연결·연결 이동성을 제공하기 때문입니다.

90초 답변

서버 내부 처리는 연결 수신 → 메시지 파싱(메서드·경로·Host·쿠키·인증 헤더 확인) → 라우팅 → 인증/인가·검증 → 비즈니스 로직 → 상태 코드·헤더·본문 생성 순서를 따릅니다. PUT과 POST의 차이는 리소스 식별 주체와 멱등성입니다 — POST는 서버가 ID를 정하거나 작업을 실행해 반복 호출 시 여러 번 처리될 수 있고, PUT은 클라이언트가 정확한 URI에 전체 상태를 지정해 반복해도 결과가 같은 멱등 연산입니다. HEAD는 GET과 같지만 본문 없이 헤더만 받아 존재 확인·캐시 유효성 검사에 쓰고, OPTIONS는 지원 메서드 확인과 CORS Preflight에 쓰입니다.

꼬리질문

질문답변 방향
Head-of-Line Blocking은 어느 계층 문제인가요?TCP는 순서 보장을 위해 유실된 패킷 뒤 데이터를 계속 대기시키는 전송 계층 문제입니다.
QUIC의 0-RTT는 무엇인가요?이전에 연결한 적 있는 서버에는 핸드셰이크를 줄여 더 빠르게 재연결하는 기능입니다.
Accept와 Content-Type의 차이는?Accept는 클라이언트가 받을 수 있는 응답 형식, Content-Type은 보내는 본문의 실제 형식입니다.

오답/주의점

주의

“HTTP/3는 UDP라서 빠르다”는 얕은 답입니다. UDP 자체가 아니라 QUIC이 제공하는 스트림 독립성과 빠른 핸드셰이크가 핵심입니다.

NET-06

Q. TLS handshake는 왜 비대칭 키와 대칭 키를 함께 쓰고, 인증서는 무엇을 검증하나요?

핵심 개념

TLS는 비대칭 키로 서버를 인증하고 키를 교환한 뒤, 비용이 큰 비대칭 연산을 피하기 위해 실제 데이터는 대칭 키로 암호화하는 하이브리드 구조이며, 브라우저는 도메인 일치·CA 체인·유효기간·폐기 여부를 함께 검증합니다.

개념 해부

SSL은 초기 프로토콜이고 TLS가 이를 표준화·보완한 후속 프로토콜로, 현재 SSL 2.0/3.0은 취약점 때문에 쓰면 안 되고 HTTPS는 사실상 TLS 1.2/1.3 기반입니다. ECDHE 같은 키 교환으로 세션 키 자체를 네트워크에 노출하지 않고 양측이 같은 공유 비밀값을 만들 수 있고, 이후 AES-GCM이나 ChaCha20-Poly1305 같은 대칭 암호로 실제 트래픽을 암호화합니다. 인증서 검증은 SAN에 등록된 도메인이 접속 호스트와 일치하는지, 중간 CA를 거쳐 신뢰된 루트 CA로 체인이 이어지는지, 유효기간·용도·OCSP/CRL 기준 폐기 여부를 함께 봅니다.

30초 답변

TLS는 비대칭 키로 서버 신원을 확인하고 키 교환을 안전하게 합의한 뒤, 비용이 큰 비대칭 연산을 피하려고 이후 데이터는 대칭 키로 암호화하는 하이브리드 구조입니다. 브라우저는 인증서의 도메인 일치, CA 체인이 신뢰된 루트로 이어지는지, 유효기간과 폐기 여부를 확인해 신뢰 가능한 인증서인지 판단합니다.

90초 답변

왜 굳이 두 방식을 섞는가는 비용 문제로 설명할 수 있습니다. 비대칭 키는 공개키/개인키가 분리되어 서버 신원 확인에 적합하지만 연산 비용이 커서 매 요청 전체를 암호화하기엔 비효율적이므로, 핸드셰이크에서만 쓰고 이후 통신은 대칭 키로 전환합니다. 자가 서명 인증서는 스스로 서명한 것이라 신뢰 저장소의 루트 CA로 이어지는 객관적 체인이 없어 개발 환경에서는 쓸 수 있어도 운영 환경에서는 브라우저 경고가 발생합니다. TLS와 SSL을 혼용해 부르는 관행은 있지만(“SSL 인증서”), 실제 운영에서 쓰는 것은 TLS입니다.

꼬리질문

질문답변 방향
ECDHE는 왜 쓰나요?세션 키를 네트워크로 직접 전송하지 않고도 양측이 같은 공유 비밀을 계산할 수 있게 합니다.
중간 CA가 손상되면 어떻게 되나요?그 CA가 서명한 모든 인증서의 신뢰 체인이 무효화될 수 있습니다.
OCSP와 CRL의 차이는?OCSP는 개별 인증서 상태를 실시간 조회, CRL은 폐기 목록 전체를 내려받아 확인하는 방식입니다.

주의

“HTTPS면 SSL을 쓴다”는 부정확한 표현입니다. 현재 안전한 HTTPS 통신은 TLS 기반이고 SSL은 폐기된 구버전입니다.

NET-07

Q. REST 대신 GraphQL이나 gRPC를 고르는 기준은 무엇인가요?

핵심 개념

REST는 리소스·URI 기반으로 캐시 친화적이고, GraphQL은 클라이언트가 필요한 필드만 조회해 과다·과소 조회를 줄이지만 캐시가 어렵고, gRPC는 Protocol Buffers와 HTTP/2 기반으로 내부 서비스 간 고성능 통신에 적합합니다.

개념 해부

REST는 서버가 엔드포인트별 응답 구조를 정하고 클라이언트가 여러 엔드포인트를 호출하는 구조라 HTTP 캐시 활용이 쉽고 구조가 단순합니다. GraphQL은 화면마다 필요한 데이터가 다르거나 여러 리소스를 조합해야 할 때 유리하지만, 대부분 같은 URL로 요청이 들어와 캐시가 단순하지 않고 복잡한 쿼리가 서버 부하를 키울 수 있어 쿼리 복잡도·depth 제한이 필요합니다. gRPC는 HTTP/2 위에서 TLS로 전송을 보호하고 메타데이터로 JWT/OAuth 토큰을 전달하며, 서버 간 통신에는 양쪽 다 인증서를 검증하는 mTLS를 쓸 수 있습니다.

30초 답변

REST는 단순하고 캐시 친화적인 리소스 API에 적합하고, GraphQL은 클라이언트마다 필요한 데이터 모양이 다를 때 over/under-fetching을 줄여줍니다. gRPC는 내부 서비스 간 고성능 통신에 쓰며 Protocol Buffers로 이진 직렬화해 크기와 파싱 비용을 줄이는 대신 가독성과 디버깅 편의를 일부 포기합니다.

90초 답변

Protocol Buffers는 .proto 파일에 메시지·서비스를 정의해 여러 언어의 클라이언트/서버 코드를 생성할 수 있어 언어가 다른 서비스 간에도 같은 계약으로 통신할 수 있게 합니다. JSON보다 이진 포맷이라 크기가 작고 파싱이 빠르지만, 필드를 삭제하거나 번호를 재사용하면 하위 호환성이 깨질 수 있어 필드 번호 관리와 스키마 버전 관리가 중요합니다. 결국 REST/GraphQL/gRPC 선택은 “무엇이 더 좋은가”가 아니라 클라이언트 다양성, 캐시 필요성, 내부·외부 통신 여부, 성능 요구를 놓고 트레이드오프를 고르는 문제입니다.

NET-08

Q. 로그인 상태는 어디에 저장하고, API 인증 방식은 어떤 기준으로 고르나요?

핵심 개념

아이디·비밀번호를 로컬 스토리지나 쿠키에 직접 저장하면 안 되며, API 인증은 JWT·API Key·OAuth2.0·HMAC·mTLS 중 클라이언트 종류와 보안 요구에 맞는 방식을 골라야 합니다.

개념 해부

로컬 스토리지는 JavaScript로 접근 가능해 XSS에 취약하므로 로그인 이후에는 원본 비밀번호가 아니라 세션ID·토큰만 저장하고 쿠키라면 HttpOnly·Secure·SameSite로 보호해야 합니다. 쿠키를 암호화해도 유효한 문자열을 그대로 재전송하는 replay 공격이 가능하고 서버측 즉시 무효화가 어려우므로, 암호화만으로 세션보다 항상 안전해지는 것은 아닙니다. 세션은 서버 확장성(중앙 세션 저장소·Sticky Session), 저장소 비용(TTL·정책), CSRF 위험(SameSite·CSRF Token)을 함께 관리해야 합니다.

30초 답변

비밀번호는 검증 순간에만 쓰고 저장하지 않으며, 로그인 후에는 제한된 세션ID나 토큰만 HttpOnly/Secure/SameSite로 보호해 저장합니다. API 인증은 일반 웹·모바일은 JWT Bearer, 서버 간 단순 연동은 API Key, 외부 권한 위임은 OAuth2.0, 요청 위변조 방지는 HMAC 서명, 강한 상호 인증이 필요하면 mTLS를 씁니다.

90초 답변

이중 로그인 처리는 서비스 정책에 따라 달라집니다. 보안이 중요하면 새 로그인 성공 시 기존 세션·리프레시 토큰을 폐기하는 단일 세션 정책을, 여러 기기 사용을 허용하면 Redis 등에 사용자별 활성 세션 목록을 두고 초과 시 가장 오래된 세션을 만료시키는 방식을 씁니다. JWT처럼 무상태 토큰에서도 기기별 강제 로그아웃이 필요하면 deviceId나 jti를 토큰에 넣고 서버가 활성 목록·블랙리스트를 관리해야 하는데, 이는 순수 무상태 검증의 장점 일부를 포기하는 대신 제어력을 얻는 선택입니다.

NET-09

Q. 실시간 기능은 Polling·SSE·WebSocket 중 무엇을 고르고, 서버를 늘리면 무엇이 깨지나요?

핵심 개념

선택 기준은 이벤트 빈도와 양방향 필요 여부이며, 어떤 방식이든 서버를 여러 대로 늘리면 인스턴스별로 흩어진 연결 정보를 공용 브로커로 다시 묶어줘야 합니다.

개념 해부

이벤트가 드물면 구현이 단순한 Polling으로 충분하고, 서버에서 클라이언트로만 밀어주면 되면 SSE, 양방향·고빈도 통신이 필요하면 WebSocket이 적합합니다. WebSocket 서버를 늘리면 사용자 A와 B가 서로 다른 인스턴스에 연결되어, 한 인스턴스가 받은 메시지를 다른 인스턴스의 클라이언트에게 전달하지 못하는 문제가 생기므로 Redis Pub/Sub·Kafka 같은 공용 브로커로 인스턴스 간 메시지를 전파해야 합니다. Sticky Session은 연결 관리만 단순하게 할 뿐, 여러 서버에 걸친 구독자 문제 자체는 해결하지 못합니다.

30초 답변

이벤트가 드물면 Polling, 서버→클라이언트 단방향이면 SSE, 양방향·고빈도면 WebSocket을 씁니다. WebSocket·SSE 모두 서버가 여러 대면 인스턴스 밖의 공용 브로커(Redis Pub/Sub, Kafka)로 메시지를 전파해야 하고, 인증은 HTTP Upgrade 시점 쿠키나 첫 메시지의 토큰으로 처리하며 반드시 wss://를 씁니다.

90초 답변

SSE는 서버가 응답 스트림을 열어둔 채 연결 객체를 관리하는데, 단일 서버에서는 메모리에 두기 쉽지만 여러 대가 되면 이벤트를 발생시킨 인스턴스와 연결을 쥔 인스턴스가 달라 브로커가 필요하고, 재시작 시 연결이 끊기므로 Last-Event-ID 기반 재연결·누락 이벤트 복구를 설계해야 합니다. WebSocket 인증은 브라우저 WebSocket API로 임의 헤더를 붙이기 어려워 보통 쿠키 자동 전송이나 연결 직후 첫 메시지로 토큰을 보내는 방식을 쓰며, 토큰을 URL 쿼리에 넣는 방식은 로그에 남기 쉬워 피해야 합니다.

질문답변 방향

NET-10

Q. 웹 서버·WAS·프록시·API Gateway·로드밸런서는 각각 무슨 역할을 나눠 맡나요?

핵심 개념

웹 서버는 정적 리소스와 앞단 HTTP 처리를, WAS는 동적 로직 실행을 맡고, 리버스 프록시·API Gateway·로드밸런서는 그 앞에서 각각 대리·정책·분산이라는 다른 역할을 겹겹이 담당합니다.

개념 해부

웹 서버(Nginx/Apache/IIS/Caddy/LiteSpeed)는 정적 파일 제공과 TLS 종료·압축·접근 제어 같은 앞단 처리를 맡고, WAS(Tomcat 등)는 비즈니스 로직 실행을 맡습니다. 포워드 프록시는 클라이언트를 대신하고 리버스 프록시는 서버를 대신합니다. API Gateway는 단순 전달을 넘어 인증·인가·Rate Limiting·요청 변환·버전 관리를 API 단위로 중앙화한다는 점에서 로드밸런서·리버스프록시와 다릅니다. L4는 IP·포트·TCP/UDP 정보만 보고 분산해 빠르고, L7은 HTTP의 Host·Path·Header를 보고 세밀하게 라우팅합니다.

30초 답변

웹 서버는 정적 리소스와 TLS 종료 등 앞단을, WAS는 동적 로직 실행을 맡아 역할을 분리하고 보안·확장성을 얻습니다. 리버스 프록시는 서버를 대신해 요청을 받고, API Gateway는 여기에 인증·Rate Limiting 같은 API 정책을 더한 것이며, 로드밸런서는 L4(전송 계층)와 L7(애플리케이션 계층)로 나눠 트래픽을 분산하고 헬스체크로 장애 서버를 제외합니다.

90초 답변

이 구성 요소들을 겹겹이 두는 이유는 셋으로 요약됩니다 — 역할 분리(WAS는 로직에만 집중), 보안(WAS를 내부망에 두고 웹 서버만 노출), 확장성(여러 WAS 인스턴스로 분산·배포 유연성). 로드밸런싱 알고리즘은 Round Robin, Least Connections, Weighted Round Robin, 세션 친화성이 필요하면 IP Hash/Consistent Hashing을 쓰며, 헬스체크는 단순 TCP 포트 확인보다 /health 엔드포인트에서 애플리케이션·의존성 상태까지 확인하는 편이 정확하지만 너무 민감하면 일시적 지연에도 서버를 자주 빼내는 부작용이 있어 실패 횟수·복구 기준을 함께 설계해야 합니다.

NET-11

Q. CDN·캐시·Rate Limiting·WAF는 트래픽을 각각 어떻게 방어하나요?

핵심 개념

CDN·HTTP 캐시는 응답 속도와 원본 부하를, Rate Limiting은 과다 요청을, WAF는 애플리케이션 계층 공격 패턴을 각자 다른 층위에서 막는 방어선입니다.

개념 해부

CDN은 엣지 서버에 콘텐츠를 캐싱해 응답 속도를 높이고 원본 트래픽과 일부 DDoS를 흡수하지만, 캐시 무효화는 여러 지역 엣지에 즉시 반영되지 않아 파일명에 콘텐츠 해시를 넣는 방식이 가장 안정적입니다. HTTP 캐시는 Cache-Control(max-age/public/private/no-store/no-cache)과 ETag/Last-Modified 기반 304 재검증으로 동작하며, 사용자별 민감 정보나 인증 응답은 공유 캐시에 저장하면 안 됩니다. Rate Limiting은 Fixed Window(경계에서 순간적으로 2배 통과 가능)의 한계를 Sliding Window나 burst를 허용하는 Token Bucket, 평탄화하는 Leaky Bucket으로 보완하며, 분산 환경에서는 Redis 원자적 연산이나 Lua 스크립트로 카운터를 관리합니다. WAF는 URL·헤더·쿠키·본문 같은 애플리케이션 계층 정보를 검사해 OWASP Top 10 공격을 방어하는 계층이지만, Prepared Statement나 출력 인코딩 같은 애플리케이션 내부 방어를 대체하지 않습니다.

30초 답변

CDN과 HTTP 캐시는 응답 속도와 원본 부하를 줄이되 캐시 무효화 지연과 민감 정보 캐싱을 주의해야 합니다. Rate Limiting은 Fixed/Sliding Window, Token Bucket, Leaky Bucket 중 burst 허용 여부에 맞게 고르고 분산 환경에서는 Redis로 원자적으로 처리합니다. WAF는 애플리케이션 계층에서 XSS·SQLi 같은 패턴을 앞단에서 걸러내는 방어선이지 코드 내부 방어의 대체재가 아닙니다.

90초 답변

DDoS는 대역폭·연결 테이블을 고갈시키는 네트워크 계층 공격과, 정상 요청처럼 보이지만 비용이 큰 엔드포인트를 반복 호출하는 애플리케이션 계층 공격으로 나뉘어 후자는 트래픽 양만으로 판단하기 어렵습니다. 방어는 CDN·Anycast로 대량 트래픽을 흡수하고, WAF·Rate Limiting으로 비정상 패턴을 제한하고, 캐시·큐로 원본 부담을 줄이고, 애플리케이션에서는 타임아웃·백프레셔·서킷 브레이커로 장애 전파를 막는 다층 구조가 기본입니다. XSS·SQL Injection 자체의 방어(출력 인코딩·CSP, Prepared Statement)는 이미 다룬 별개 주제이므로, 여기서는 WAF가 그 방어들을 대체하지 않는 “앞단 계층”이라는 위치만 정확히 짚으면 됩니다.

꼬리질문

질문답변 방향
캐시 무효화가 느린 근본 이유는?여러 지역 엣지 서버에 TTL이 남아있는 캐시가 각각 만료되어야 하기 때문입니다.
fail-open과 fail-closed의 차이는?Rate Limiter 장애 시 요청을 허용할지(fail-open) 차단할지(fail-closed) 정하는 정책입니다.
WAF가 못 막는 것은?정상 요청과 공격의 경계가 모호한 경우 오탐·미탐이 생기고 우회 기법도 존재합니다.

오답/주의점

주의

“WAF만 있으면 애플리케이션 보안은 신경 안 써도 된다”는 위험한 답입니다. WAF는 앞단 방어선일 뿐 Prepared Statement·출력 인코딩 같은 내부 방어를 대체하지 않습니다.

네트워크 심화 면접은 “요청 하나가 계층을 통과하며 어떤 비용과 실패 지점을 만드는가”와 “트래픽이 커질 때 무엇이 먼저 무너지는가”를 묻습니다.

축핵심 질문확장 포인트
계층/주소IP·MAC·ARP·포트, 요청 흐름 전체 순서왜 MAC은 홉마다 바뀌고 IP는 유지되는가
TCP/UDPConnection·Timeout 구분, 혼잡 제어, UDP 신뢰성어떤 실패가 인프라 문제이고 어떤 실패가 애플리케이션 문제인가
DNSTTL·캐시, DNS 로드밸런싱의 한계왜 DNS 변경은 즉시 반영되지 않는가
HTTP/TLS메시지 구조, HTTP/3·QUIC, TLS handshake, 인증서 검증왜 비대칭 키와 대칭 키를 함께 쓰는가
API 프로토콜REST vs GraphQL vs gRPC 선택 기준캐시 친화성과 클라이언트 다양성의 트레이드오프
인증·실시간·인프라세션/토큰 설계, WebSocket 스케일아웃, 로드밸런싱·CDN·Rate Limiting서버가 여러 대일 때 무엇이 깨지는가

구체 질문 12선

번호구체 질문답변 방향
1다른 네트워크의 서버로 요청을 보낼 때 왜 서버의 MAC 주소를 직접 찾지 않나요?MAC은 링크 로컬이라 게이트웨이까지만 유효하다는 점을 설명합니다.
2Connection Timeout이 늘고 있다면 무엇을 먼저 의심하나요?서버 다운, 방화벽, 네트워크 경로, 커넥션 풀 고갈 같은 인프라 원인을 봅니다.
3UDP로 신뢰성 있는 통신을 만들려면 무엇을 직접 구현해야 하나요?메시지 번호, ACK, 재전송 로직을 애플리케이션 계층에서 구현해야 합니다.
4배포 직전에 DNS TTL을 낮추는 이유는 무엇인가요?레코드 변경이 캐시 만료를 기다리지 않고 더 빨리 반영되게 하기 위해서입니다.
5HTTP/2에서 멀티플렉싱을 지원하는데도 Head-of-Line Blocking이 생기는 이유는?아래 TCP 계층의 순서 보장 때문에 패킷 유실이 다른 스트림까지 지연시킨다고 설명합니다.
6자가 서명 인증서가 브라우저 경고를 띄우는 이유는 무엇인가요?신뢰 저장소의 루트 CA로 이어지는 체인이 없기 때문입니다.
7GraphQL을 도입했는데 캐시 히트율이 떨어졌다면 왜 그런가요?대부분의 요청이 같은 엔드포인트로 몰려 URL 기반 HTTP 캐시를 활용하기 어렵다는 점을 봅니다.
8로컬 스토리지에 로그인 토큰을 저장하면 안 되는 이유는?JavaScript로 접근 가능해 XSS 공격에 그대로 탈취될 수 있습니다.
9WebSocket 서버를 2대로 늘렸는데 일부 사용자에게 메시지가 전달되지 않는다면?인스턴스 간 메시지 전파를 위한 공용 브로커가 빠졌을 가능성을 봅니다.
10API Gateway 없이 로드밸런서만 있으면 무엇이 부족한가요?API 단위의 인증·Rate Limiting·버전 관리 같은 정책 중앙화가 빠집니다.
11CDN 캐시를 무효화했는데 일부 사용자가 여전히 예전 콘텐츠를 본다면?지역별 엣지 캐시의 TTL이 아직 남아있어 각자 만료를 기다려야 한다는 점을 설명합니다.
12Rate Limiter가 죽었을 때 fail-open과 fail-closed 중 무엇을 고르나요?서비스 가용성과 보안 요구 중 어느 쪽이 더 중요한 도메인인지로 판단합니다.
