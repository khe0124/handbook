프론트엔드 개발자 연결점

시작 증거상황

볼 증거 DevTools Network waterfall, console error, request id, frontend release version

학습 전환 화면 오류를 request path와 change path에 연결한다.

인프라에 넘길 것상황

볼 증거 실패 URL, status code, timing, region/browser, 재현 시각

학습 전환 인프라 담당자가 DNS, edge, LB, app log를 바로 대조할 수 있게 한다.

완료 산출물상황

볼 증거 browser-to-DB request path diagram, release marker, rollback condition

학습 전환 읽은 지식을 다음 장애 triage에서 재사용한다.

대상 독자와 학습 계약

대상 독자항목

내용 프론트엔드 실무 경험이 있고 API, 배포, 브라우저 디버깅은 익숙하지만 DNS, LB, VPC, SLO, DR을 한 시스템으로 설명하지 못하는 사람

완료 기준 화면 오류와 배포 이슈를 운영 계층별 증거로 좁히고, 인프라 담당자에게 넘길 evidence packet을 만들 수 있어야 한다.

선행 지식항목

내용 HTTP, TLS 기초, 브라우저 Network 탭, JavaScript error, API latency, CI/CD 기본

완료 기준 Linux, DB connection, container, cloud network는 문서 안의 실습 출력으로 보강한다.

학습 산출물항목

내용 browser-to-DB request path diagram, frontend release timeline, incident packet, rollback/restore drill report, service readiness score

완료 기준 읽은 양이 아니라 다른 담당자가 재현 가능한 문서와 증거로 완료를 판단한다.

학습 목표항목

내용 화면에서 보이는 오류를 DNS, edge, LB, runtime, DB, 배포, SLO 중 어느 계층의 문제인지 질문할 수 있게 한다.

완료 기준 서비스명 암기가 아니라 판단 순서, 증거, 완화, 후속 개선을 남긴다.

로드맵으로 읽는 순서

1주차 · 브라우저 요청 경로단계

읽을 문서 서비스 요청 경로 → DNS/TLS → CDN/WAF/LB → App/DB 경계

완료 산출물 DevTools waterfall, request path diagram, dig/curl/openssl 결과, target health 판독

2주차 · 프론트 배포와 런타임단계

읽을 문서 CI/CD·Artifact·Environment → 컨테이너·오케스트레이션·Health Check

완료 산출물 release note, asset hash/image digest, smoke test, health check gate, rollback 조건

3주차 · 네트워크와 보안 경계단계

읽을 문서 VPC·Subnet·Routing·NAT → 보안 경계 → VPN/Private Connectivity

완료 산출물 route table readback, flow log, SG/NACL 판정, private endpoint DNS 검증

4주차 · 관측·복구·클라우드 종합단계

읽을 문서 Observability·SLO → Incident Response·Rollback·DR → IaC·변경관리 → AWS·Azure 시나리오

완료 산출물 RUM/backend SLO dashboard, incident packet, rollback/restore drill, terraform plan review

60분 강연 흐름

0-5분시간

주제 왜 운영은 아키텍처 그림만으로 부족한가

핵심 메시지 요청 경로, 변경 경로, 복구 경로를 한 장으로 연결해야 함을 보여준다.

5-15분시간

주제 전체 운영 지도

핵심 메시지 DNS → Edge → LB → Runtime → Data store와 CI/CD → artifact → runtime → metric gate를 겹쳐 설명한다.

15-30분시간

주제 장애 triage 실전

핵심 메시지 5xx 증가 케이스로 사용자 영향, 최근 변경, 계층별 증거, rollback 판단을 연습한다.

30-42분시간

주제 네트워크·보안 경계

핵심 메시지 VPC, subnet, route, SG/NACL, Private Endpoint, DNS override의 대표 오판을 짚는다.

42-52분시간

주제 SLO·Incident·DR

핵심 메시지 burn rate, IC/scribe/comms, RPO/RTO, restore drill을 운영 성숙도 기준으로 연결한다.

52-60분시간

주제 체크리스트와 면접 답변

핵심 메시지 운영 인수 packet과 30초/90초 답변 구조로 마무리한다.

계층별 실패 모드

DNS/TLS계층

대표 실패 NXDOMAIN, wrong CNAME, SNI/SAN mismatch, chain 누락

첫 확인 증거 dig +trace, resolver 비교, openssl s_client, curl -v

Edge/CDN/WAF계층

대표 실패 WAF false positive, stale cache, origin policy mismatch

첫 확인 증거 edge request id, WAF log, cache policy, origin status

Load Balancer계층

대표 실패 502 upstream fail, 503 no healthy target, 504 timeout

첫 확인 증거 target health, listener rule, deregistration delay, idle timeout

Runtime계층

대표 실패 OOMKilled, readiness 실패, selector mismatch, graceful shutdown 누락

첫 확인 증거 kubectl describe/logs --previous, endpoints, rollout status

Data store계층

대표 실패 connection pool 고갈, lock wait, slow query, migration lock

첫 확인 증거 pool pending, DB wait event, slow query, migration version

Network policy계층

대표 실패 route miss, SG/NACL block, NAT saturation, private DNS 누락

첫 확인 증거 route table, flow log ACCEPT/REJECT, NAT metric, DNS query log

Change path계층

대표 실패 잘못된 artifact/config/secret/migration 배포

첫 확인 증거 commit SHA, image digest, config diff, secret version, deploy marker

Recovery path계층

대표 실패 rollback 불가, restore 미검증, failback 누락

첫 확인 증거 rollback command, backup age, restore duration, reconciliation result

AWS/Azure 증거 비교

DNS/Edge영역

AWS 증거 Route 53, CloudFront, AWS WAF, ACM, ALB access log

Azure 증거 Azure DNS, Front Door, WAF Policy, Managed Certificate, Application Gateway log

판단 기준 edge request id와 origin status를 분리해 WAF 차단과 origin 장애를 나눈다.

Network영역

AWS 증거 VPC, subnet route table, Security Group, NACL, NAT Gateway, VPC Flow Logs, PrivateLink

Azure 증거 VNet, subnet route table, NSG, NAT Gateway, Network Watcher flow log, Private Endpoint

판단 기준 route miss, policy reject, DNS public resolution, NAT saturation을 각각 다른 원인으로 본다.

Runtime영역

AWS 증거 ECS/EKS, target group health, CloudWatch Container Insights, ECR image digest

Azure 증거 AKS/App Service, backend health, Azure Monitor, ACR digest

판단 기준 readiness, rollout, image/config mismatch, connection draining을 배포 timeline에 연결한다.

Data/DR영역

AWS 증거 RDS/Aurora metrics, Performance Insights, snapshots, PITR, replica lag

Azure 증거 Azure SQL metrics, Query Performance Insight, backups, PITR, geo-replica lag

판단 기준 백업 존재가 아니라 restore duration, backup age, missing rows, failback 결과로 판단한다.

운영 의사결정 트리

1. 사용자가 실제로 영향을 받는가?질문

확인 증거 SLI, support ticket, synthetic check, region/device 분포

다음 선택 영향이 없으면 ticket으로 낮추고, 영향이 있으면 incident channel과 IC를 세운다.

2. 최근 변경과 같은 시간축인가?질문

확인 증거 deploy marker, image digest, config diff, migration version, feature flag audit

다음 선택 같은 시간축이면 rollback/flag off 후보를 먼저 준비한다. 아니면 요청 경로와 의존성 장애를 본다.

3. 요청이 어디까지 도달했는가?질문

확인 증거 DNS answer, WAF request id, LB target health, app access log, trace span, DB wait event

다음 선택 도달하지 못한 첫 계층이 현재의 가장 강한 원인 후보가 된다.

4. 원인 확정 전 완화가 가능한가?질문

확인 증거 rollback command, traffic shift, circuit breaker, rate limit, queue pause, read-only mode

다음 선택 사용자 영향을 줄이는 조치가 있으면 원인 분석과 병행한다.

5. 복구가 검증됐는가?질문

확인 증거 SLI 회복, error budget burn 정상화, data reconciliation, customer comms, runbook diff

다음 선택 지표 회복만으로 종료하지 말고 데이터·공지·문서 갱신까지 확인한다.

운영 준비도 점수표

0점점수

상태 문서 없음 또는 개인 기억에 의존

판정 런칭/인수 차단

1점점수

상태 다이어그램과 담당자만 있음

판정 장애 때 실행 불가. owner, dashboard, runbook 보강 필요

2점점수

상태 dashboard, alert, runbook, rollback plan이 있음

판정 기본 운영 가능. drill 증거가 없으면 위험

3점점수

상태 rollback/restore drill, SLO, incident packet, cost/access owner까지 있음

판정 독립 운영 가능

4점점수

상태 game day, failback, runbook diff, error budget policy가 반복 운영됨

판정 팀 표준화 가능

강연 데모 스크립트

데모 1데모

주제 정상 요청 경로 그리기

진행 방식 브라우저에서 DB까지 6개 hop을 그리고 각 hop의 증거를 하나씩 붙인다.

확인 질문 청중이 app log 이전 계층의 증거를 말할 수 있어야 한다.

데모 2데모

주제 5xx fast burn triage

진행 방식 incident snapshot을 보여주고 rollback, scale-out, DB restart 중 무엇을 먼저 할지 투표시킨다.

확인 질문 최근 변경과 DB baseline을 근거로 rollback 후보를 고르는지 확인한다.

데모 3데모

주제 private subnet egress 오판

진행 방식 flow log ACCEPT와 NAT bytes 4x를 함께 보여준다.

확인 질문 네트워크 차단이 아니라 retry storm/외부 API 지연을 의심하는지 본다.

데모 4데모

주제 restore drill 채점

진행 방식 backup_age, restore_duration, missing_rows를 보여주고 RPO/RTO 판정을 시킨다.

확인 질문 복구 성공과 목표 충족을 구분하는지 확인한다.

실습 채점 루브릭

초급수준

답변 특징 도구 이름과 서비스명을 나열한다.

증거 사용 장애 때 앱 로그나 콘솔 화면 하나에 의존한다.

판정 불합격. 운영 판단 순서와 증거 연결이 없다.

중급수준

답변 특징 요청 경로와 변경 경로를 그리고 주요 증거를 확인한다.

증거 사용 rollback 후보와 owner를 말하지만 drill 증거가 약하다.

판정 내부 운영 참여 가능. 공개 강연/출판용 설명으로는 보강 필요.

상급수준

답변 특징 사용자 영향, 최근 변경, 계층별 증거, 완화, 사후 개선을 incident packet으로 닫는다.

증거 사용 SLO burn, 비용, 보안, DR까지 같은 timeline에서 설명한다.

판정 강연/출판 사례의 기준점으로 삼을 수 있다.

리뷰어수준

답변 특징 청중/독자가 같은 결론에 도달하도록 출력 샘플, 오판 사례, 채점 기준을 제공한다.

증거 사용 클라우드별 차이와 조직 운영 체계의 한계를 명시한다.

판정 외부 공개 전 기술 리뷰를 맡길 수 있는 수준.

전문가 리뷰 질문

SRE 리뷰리뷰 영역

확인 질문 SLO, burn rate, incident role, postmortem action이 실제 운영 정책으로 이어지는가?

보강 기준 알림 피로, error budget 정책, paging 기준이 빠져 있으면 보강한다.

Cloud network 리뷰리뷰 영역

확인 질문 route table, SG/NACL/NSG, DNS override, private endpoint, NAT 비용 설명이 provider별로 정확한가?

보강 기준 AWS/Azure 차이를 서비스명 치환으로 처리한 부분을 수정한다.

Kubernetes/runtime 리뷰리뷰 영역

확인 질문 readiness/liveness/startup, graceful shutdown, rollout, target health가 정확히 분리되어 있는가?

보강 기준 무중단 배포와 health check를 섞어 설명한 부분을 수정한다.

DB/DR 리뷰리뷰 영역

확인 질문 connection pool, lock wait, migration lock, PITR, replica lag, failback 설명이 실제 복구 절차와 맞는가?

보강 기준 백업 존재와 복구 가능성을 혼동한 표현을 제거한다.

보안 리뷰리뷰 영역

확인 질문 IAM/Managed Identity, secret rotation, audit log, incident comms가 과도하게 단순화되지 않았는가?

보강 기준 장기 키, broad permission, secret leakage 대응을 명확히 한다.

공식 근거 맵

SLO/Burn rate영역

공식 문서 Google SRE Workbook · Alerting on SLOs

URL https://sre.google/workbook/alerting-on-slos/

반영 기준 burn rate, error budget, multi-window alert는 서비스별 baseline과 page load에 맞춰 조정해야 한다.

Kubernetes probes영역

공식 문서 Kubernetes Docs · Liveness, Readiness, and Startup Probes

URL https://kubernetes.io/docs/concepts/workloads/pods/probes/

반영 기준 liveness는 재시작, readiness는 traffic 수신 여부, startup은 느린 시작 보호로 분리한다.

AWS VPC Flow Logs영역

공식 문서 AWS Docs · Flow log records

URL https://docs.aws.amazon.com/vpc/latest/userguide/flow-log-records.html

반영 기준 ACCEPT/REJECT는 aggregation interval과 log-status를 함께 봐야 하며 delivery delay가 있을 수 있다.

AWS PrivateLink영역

공식 문서 AWS Docs · AWS PrivateLink concepts

URL https://docs.aws.amazon.com/vpc/latest/privatelink/concepts.html

반영 기준 endpoint 생성만으로 충분하지 않고 DNS, endpoint policy, route/security 경계를 함께 확인한다.

Azure Private Endpoint영역

공식 문서 Microsoft Learn · Private endpoint overview

URL https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview

반영 기준 private endpoint는 private IP로 Azure service에 연결하므로 Private DNS Zone 연결과 public access 정책을 같이 본다.

AWS ALB health영역

공식 문서 AWS Docs · Target group health checks

URL https://docs.aws.amazon.com/elasticloadbalancing/latest/application/target-group-health-checks.html

반영 기준 target health는 health check path, matcher, timeout, deregistration/draining과 함께 해석한다.

AWS RDS PITR영역

공식 문서 AWS Docs · Restoring a DB instance to a specified time

Flow log 판독영역

보안/IAM영역

OP-00

프론트엔드에서 시작하는 운영 지도

인프라·운영은 클라우드 서비스명을 외우는 영역이 아니라 사용자가 본 화면 오류를 어디까지 추적할 수 있는지의 문제다. 프론트엔드 개발자는 먼저 브라우저 증상, Network waterfall, status code, request id, release version을 잡고, 그 뒤 DNS → CDN/WAF → Load Balancer → Runtime → Data store로 경계를 넘겨야 한다.

OPERATIONS DECISION

운영 질문 브라우저에서 관찰한 증상이 어느 운영 계층으로 이어지는지 설명할 수 있는가?

확인할 증거 browser Network waterfall, request id, frontend release version, DNS answer, CDN/WAF request id, LB status, trace span

판단 기준 화면 오류를 프론트 코드 문제로 단정하지 않고 요청이 멈춘 첫 계층과 최근 변경을 함께 본다.

배제 확인 프론트엔드에서 시작하는 운영 지도를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 DevTools Network, curl -v, dig, CDN/WAF log, LB access log, app trace, SLO dashboard

명령 해석 프론트에서 수집 가능한 증거와 인프라/백엔드에 넘길 증거가 분리되어야 한다.

임시 완화와 영구 수정 특정 브라우저 또는 지역에서만 화면 오류가 나고 app log가 비어 있음 기준으로 영향 범위를 좁히고, request id와 release marker를 붙여 edge, LB, app 중 어디까지 도달했는지 먼저 좁힌다.

OP-01

4주 흡수 순서

빠르게 흡수하려면 네트워크부터 파고들기보다 본인 업무와 맞닿은 흐름에서 시작한다. 1주차에는 브라우저 요청과 DNS/TLS/CDN/LB를 연결하고, 2주차에는 CI/CD와 runtime health로 배포가 실제 사용자 경로에 들어가는 방식을 본다. 3주차에는 VPC, 보안 경계, private connectivity로 경계를 넓히고, 4주차에는 Observability, SLO, Incident, DR, cloud scenario로 운영 판단을 닫는다.

OPERATIONS DECISION

운영 질문 학습 순서가 실제 장애 triage와 운영 인수 순서로 이어지는가?

확인할 증거 request path diagram, VPC route table readback, deploy pipeline stage, SLO dashboard, rollback/restore drill record

판단 기준 개념 이름을 외운 순서가 아니라 장애 때 배제할 계층과 산출물 순서로 정리되어야 한다.

배제 확인 4주 흡수 순서를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 draw browser-to-DB request path, check deploy pipeline, inspect runtime health, list ingress/egress, review SLO burn alert

명령 해석 각 주차가 다이어그램, 명령 출력, runbook, drill packet 중 하나의 산출물로 끝나야 한다.

임시 완화와 영구 수정 DNS나 VPC 용어는 아는데 프론트 배포 실패와 사용자 영향으로 연결하지 못함 기준으로 영향 범위를 좁히고, 다음 학습 항목을 실제 화면 오류, 배포 marker, dashboard, rollback 조건에 연결한다.

OP-02

계층별 실패 모드

운영 실력은 장애 때 어떤 계층을 먼저 의심하고 어떤 증거로 배제하는지에서 드러난다. DNS/TLS, CDN/WAF, Load Balancer, runtime, DB, network policy, deploy pipeline, observability, incident process마다 대표 실패 모드와 첫 확인 증거가 다르다.

OPERATIONS DECISION

운영 질문 각 계층의 실패 모드와 첫 확인 증거를 구분할 수 있는가?

확인할 증거 DNS answer, TLS chain, WAF log, target health, trace waterfall, DB wait event, flow log, deploy marker, burn-rate alert

판단 기준 앱 로그만 보거나 클라우드 서비스명만 나열하면 운영 판단으로 부족하다.

배제 확인 계층별 실패 모드를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 dig/curl/openssl, LB target health, kubectl describe/logs, DB performance insight, flow log, CI release note

명령 해석 증거는 같은 timestamp, traceId, version, environment로 연결되어야 한다.

임시 완화와 영구 수정 프론트 화면 오류 하나를 보고 API 코드 문제로 단정 기준으로 영향 범위를 좁히고, 가장 앞단 계층부터 요청이 도달한 지점을 찾고, 최근 변경과 SLO burn을 함께 본다.

OP-03

운영 산출물과 답변 구조

운영 문서는 아키텍처 다이어그램만으로 끝나지 않는다. 프론트엔드 배포라면 asset hash, CDN invalidation, SPA fallback, API base URL, feature flag, rollback artifact가 함께 있어야 한다. 서비스 운영 전체로는 owner, escalation, SLO, dashboard, alert, runbook, rollback plan, RPO/RTO, 변경 이력, 비용 owner, access owner, 마지막 drill 날짜가 있어야 다음 사람이 같은 판단을 반복할 수 있다.

OPERATIONS DECISION

운영 질문 운영 산출물과 면접 답변이 실행 가능한 증거로 닫히는가?

확인할 증거 owner matrix, service catalog, SLO, dashboard, alert, runbook, rollback command, restore drill date, incident packet

판단 기준 담당자가 바뀌어도 같은 절차와 권한으로 대응할 수 있어야 한다.

배제 확인 운영 산출물과 답변 구조를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 service catalog, alert route, dashboard link, rollback command, restore drill report, postmortem, runbook diff

명령 해석 문서 링크만 있고 권한, owner, 마지막 drill 날짜가 없으면 운영 인수 미완료다.

임시 완화와 영구 수정 장애 중 dashboard, alert owner, rollback owner를 찾지 못함 기준으로 영향 범위를 좁히고, 인수 체크리스트에 owner, 권한, 마지막 drill, incident packet, runbook diff를 필수 항목으로 추가한다.

4 · 증거evidence

PRACTICE

출력 판독 훈련

인프라·운영 로드맵은 개념을 아는 것보다 실제 출력에서 정상과 비정상을 구분하는 훈련이 중요하다. 아래 lab은 명령, 출력, 판단, 완화, 영구 수정을 한 번에 연결한다.

PRACTICE LAB 01 · 운영 준비도 packet 판독

신규 서비스를 production에 올리기 전 운영 준비도 리뷰를 진행한다.

Command / Query

readiness packet
owner=team-payments
slo=checkout_success 99.9
rollback=artifact sha-prev
restore_drill=not_run
alert_owner=empty

목적 런칭 전 차단해야 할 운영 공백을 찾는다.

정상 출력

비정상 출력

판단 훈련 아키텍처는 있어도 복구 검증과 알림 owner가 없으면 운영 준비가 끝난 것이 아니다.

즉시 완화 런칭 gate를 보류하고 alert owner, rollback command, restore drill 일정을 확정한다.

검증 기준 readiness packet의 모든 owner와 마지막 drill 시간이 채워지고 smoke/rollback 검증이 통과한다.

TERM

용어사전

인프라·운영 로드맵에서 반복적으로 등장하는 운영 용어를 정의, 증거, 오해, 관련 항목 기준으로 정리한다. 장애 중에는 용어 자체보다 해당 용어가 어떤 로그, 지표, 설정, 책임 경계와 연결되는지를 확인한다.

request pathTERM
사용자 요청이 DNS에서 DB까지 통과하는 운영 경로. 운영에서는 DNS/CDN/WAF/LB/App/DB dependency map, traceId, app log로 확인한다. 흔한 오해는 "앱 로그가 없으면 앱 문제가 없다는 뜻이다."라고 보는 것이다. 관련해서 DNS, CDN/WAF, Load Balancer, DB pool를 함께 본다.
change pathTERM
코드 변경이 CI/CD에서 runtime과 incident response까지 검증되는 흐름. 운영에서는 CI run, artifact digest, deploy marker, SLO dashboard로 확인한다. 흔한 오해는 "CI green이면 운영 성공이다."라고 보는 것이다. 관련해서 artifact, environment, metric gate, rollback를 함께 본다.
SLOTERM
사용자 경험 기준의 내부 신뢰성 목표. 운영에서는 SLO dashboard, error budget, alert owner로 확인한다. 흔한 오해는 "모든 오류를 같은 우선순위로 처리하면 된다."라고 보는 것이다. 관련해서 SLI, error budget, paging를 함께 본다.
runbookTERM
장애나 변경 시 반복 실행 가능한 절차 문서. 운영에서는 runbook owner, rollback command, restore drill date로 확인한다. 흔한 오해는 "문서 링크만 있으면 운영 인수 완료다."라고 보는 것이다. 관련해서 owner, drill, incident packet를 함께 본다.
RPO/RTOTERM
허용 가능한 데이터 손실과 복구 시간 목표. 운영에서는 DR plan, restore drill, replica lag, failover result로 확인한다. 흔한 오해는 "백업이 있으면 DR 준비가 끝난다."라고 보는 것이다. 관련해서 backup, restore, DR를 함께 본다.
CASE

장애/운영 시나리오

신규 서비스를 런칭하기 전 운영 준비도 리뷰를 진행한다. 요청 경로는 DNS, CDN/WAF, Load Balancer, Runtime, DB로 그리고, 변경 경로는 CI/CD, artifact, config, environment, metric gate로 확인한다. 복구 경로는 rollback, feature flag off, traffic shift, restore, failback으로 분리한다. 빠진 항목은 런칭 후 장애가 아니라 런칭 전 차단 이슈로 다룬다.

Triage frame

인프라·운영 로드맵 장애는 프론트엔드에서 보인 증상 → 영향 범위 → 최근 변경 → 서비스 카탈로그 증거 → 완화책 → 복구 검증 → 재발 방지 순서로 기록한다.

INCIDENT FLOW

처음 10분 owner, tier, dependency map, SLO, cost owner, access owner 기준으로 영향 범위를 고정한다.

다음 30분 dashboard, alert, recent deploy, support ticket trend를 한 화면에서 확인 항목에서 증거를 모아 완화책을 실행한다.

종료 조건 회고가 시스템 변경으로 닫히지 않으면 반복된다.

T+15Incident packet

기록할 내용 완화책과 rollback 후보를 비교

판정 기준 원인 확정 전이라도 영향 완화가 가능하면 실행한다.

강연/출판용 실전 케이스

Case 1 · 배포 후 checkout 5xx fast burn

결제 API 신규 artifact 배포 8분 뒤 checkout_success SLO가 14x fast burn을 보이고 ALB 5xx와 app error가 동시에 증가한다.

T+00시점

판단/행동 burn alert 수신, incident channel 생성, IC/scribe 지정

해석 기준 사용자 영향과 의사결정권을 먼저 고정한다.

T+05시점

판단/행동 deploy marker, image digest, config diff, DB migration version 확인

해석 기준 최근 변경이 사용자 영향과 같은 시간축인지 확인한다.

T+10시점

판단/행동 target health, app log, DB wait event, feature flag 상태 확인

해석 기준 DB 압박이 아니라 새 runtime 오류와 연결되면 rollback 후보가 강해진다.

T+15시점

판단/행동 canary stop 또는 previous artifact rollback

해석 기준 원인 확정 전이라도 사용자 영향을 줄인다.

T+45시점

판단/행동 postmortem에 metric gate, rollback decision log, runbook diff 추가

해석 기준 재발 방지가 운영 산출물로 닫혀야 한다.

대표 오판 앱 로그 stack trace만 보고 디버깅을 계속하면서 rollback 결정을 늦추는 것.

종료 조건 burn rate가 baseline으로 회복되고 rollback artifact, config version, 의사결정 시간이 incident packet에 남으면 종료한다.

Case 2 · Private subnet egress와 NAT 비용 급증

private subnet batch가 외부 결제사 API timeout을 반복하고 NAT bytes가 4배 증가한다.

T+00시점

판단/행동 route table, SG/NACL, DNS resolution, flow log를 확인

해석 기준 네트워크가 막힌 것인지, 통신은 되지만 retry storm인지 분리한다.

T+10시점

판단/행동 provider 429/timeout, app retry rate, batch concurrency 확인

해석 기준 flow log ACCEPT와 NAT bytes 증가는 차단이 아니라 과도한 재시도일 수 있다.

T+20시점

판단/행동 batch concurrency 축소, retry backoff, circuit breaker 적용

해석 기준 비용과 장애 영향을 동시에 줄이는 완화책을 선택한다.

T+60시점

판단/행동 egress dependency map, retry budget, NAT cost anomaly alert 추가

해석 기준 비용 신호를 운영 incident 신호로 편입한다.

대표 오판 flow log ACCEPT만 보고 네트워크는 정상이라고 끝내거나, NAT 비용을 FinOps 문제로만 분리하는 것.

종료 조건 retry rate, NAT bytes, batch success, 외부 API 오류율이 baseline으로 돌아오면 종료한다.

Case 3 · Restore drill RPO/RTO 실패

DB restore drill에서 backup_age 17분, restore_duration 42분, missing_rows 128건으로 RPO 5분/RTO 30분을 모두 위반한다.

RISK

자주 틀리는 판단

인프라·운영 로드맵에서 자주 틀리는 판단은 프론트엔드에서 시작하는 운영 지도와 운영 산출물과 답변 구조의 책임 경계를 흐리는 데서 시작된다. 아래 신호가 보이면 설계, runbook, 답변 구조를 다시 점검한다.

  • 아키텍처 다이어그램은 있지만 알림 owner와 escalation 경로가 없다.
  • 배포 절차는 있지만 artifact digest, metric gate, rollback 검증이 없다.
  • SLO가 없어서 장애와 단순 오류를 같은 우선순위로 처리한다.
  • 운영 인수 문서가 사람 이름과 구두 설명에 의존한다.
  • 백업은 있지만 restore drill과 failback 절차가 없다.
  • NAT/egress 비용 급증을 운영 incident가 아니라 비용 이슈로만 본다.
