Q01

기술 SEO의 핵심은 무엇인가요?

검색 엔진이 URL을 발견, 크롤링, 렌더링, 색인, 이해할 수 있게 만드는 것입니다. sitemap, robots, canonical, status code, structured data, 성능이 함께 작동해야 합니다.

메타 태그만 수정하면 duplicate URL, blocked resource, JS rendering 실패, canonical 오류를 놓칩니다.

꼬리질문꼬리질문 답변
SEO와 성능은 어떻게 연결되나요?LCP, INP, CLS가 나쁘면 사용자가 이탈하고 Search Console의 Core Web Vitals 품질도 낮아집니다. SSR HTML, image priority, JS bundle, render blocking CSS를 줄이면 crawler rendering과 사용자 경험이 함께 좋아집니다.
CSR 페이지도 색인되나요?가능하지만 crawler가 JS를 렌더링해야 하므로 발견과 색인이 늦거나 실패할 수 있습니다. 중요한 title, canonical, 본문, internal links, structured data는 SSR이나 pre-rendered HTML에서 확인되게 두는 편이 안전합니다.
canonical은 언제 위험한가요?서로 다른 콘텐츠가 같은 canonical을 가리키거나, canonical URL이 noindex/blocked/redirect chain에 걸리면 ranking signal이 잘못 합쳐질 수 있습니다. 배포 전 rendered HTML과 Search Console 선택 canonical을 함께 확인해야 합니다.
TRAINING EVIDENCE technical SEO release packet, Search Console, crawl test, canonical audit
Q02

AEO/GEO는 SEO와 무엇이 다른가요?

SEO가 검색 결과 노출을 목표로 한다면 AEO/GEO는 답변 엔진과 생성형 검색이 인용·요약하기 쉬운 구조와 근거를 제공합니다.

키워드만 반복하면 AI 답변에서 신뢰 가능한 근거로 선택되기 어렵습니다.

꼬리질문꼬리질문 답변
FAQ schema만 넣으면 되나요?아닙니다. FAQ schema는 보조 신호일 뿐이고 실제 화면의 질문, 짧은 답, 근거, 최신성, 작성 주체가 일치해야 합니다. 보이지 않는 FAQ를 JSON-LD에만 넣으면 rich result와 답변 인용 모두에 불리합니다.
LLM이 좋아하는 문서 구조는?질문형 heading 아래에 직접 답을 먼저 쓰고, 조건, 예외, 근거 링크, 표를 이어 붙이는 구조가 유리합니다. entity 이름을 일관되게 쓰고 제품명, 조직, 기능 관계를 schema와 internal links로 보강합니다.
근거 출처는 어떻게 표시하나요?주장 옆에 공식 문서, 데이터 출처, 업데이트 날짜를 가까이 둡니다. AI 답변이 인용할 수 있도록 원문 URL, 저자/조직, 통계 기준 기간을 명확히 쓰고 오래된 수치는 갱신 기록을 남깁니다.
TRAINING EVIDENCE answer-first block, citation structure, entity schema, AI answer quality review
Q03

검색 의도는 어떻게 문서에 반영하나요?

informational, navigational, transactional, comparison 의도를 분리하고, 첫 화면과 heading에 답변 방향을 명확히 둡니다.

검색어만 보고 콘텐츠를 만들면 사용자가 실제로 해결하려는 질문과 CTA가 어긋납니다.

꼬리질문꼬리질문 답변
같은 키워드에 의도가 섞이면?SERP의 상위 결과와 Search Console query를 나눠 informational, comparison, transactional 블록을 분리합니다. 한 페이지에서 모두 다루면 heading과 CTA를 명확히 나누고, intent가 강하게 다르면 별도 landing URL과 canonical을 둡니다.
롱테일은?롱테일은 질문형 heading, FAQ, 비교 표, 사용 사례로 받습니다. 검색량이 작아도 전환 의도가 강할 수 있으므로 GA4 landing conversion과 Search Console impression/CTR을 같이 봅니다.
의도 변화는 어떻게 감지하나요?Search Console query, CTR, average position, SERP feature 변화, 내부 검색어, funnel drop을 release annotation과 함께 봅니다. 특정 query의 CTR이 떨어지면 title/description 문제가 아니라 SERP 의도 자체가 바뀌었는지 확인합니다.
TRAINING EVIDENCE query intent map, SERP review, content outline, CTR/engagement metric
Q04

canonical은 왜 중요한가요?

같은 콘텐츠가 여러 URL로 접근될 때 대표 URL을 알려 중복 색인과 ranking signal 분산을 줄입니다.

필터/정렬/추적 파라미터가 모두 색인되면 검색 품질과 crawl budget이 낭비됩니다.

꼬리질문꼬리질문 답변
canonical과 redirect 차이는?redirect는 사용자를 대표 URL로 실제 이동시키고, canonical은 접근 가능한 중복 URL에서 대표 색인 URL을 힌트로 알려줍니다. 영구 이동이나 통합은 301이 맞고, 정렬/UTM처럼 열어 둘 URL은 canonical로 대표를 지정합니다.
페이지네이션 canonical은?각 페이지에 고유 콘텐츠가 있으면 page=2가 자기 자신을 canonical로 가져야 합니다. 모두 1페이지로 canonical 처리하면 뒤쪽 상품이나 글이 색인과 internal link 신호에서 사라질 수 있습니다.
다국어 canonical은?각 locale URL은 자기 자신을 canonical로 두고 hreflang으로 대체 언어 관계를 연결합니다. 한국어 페이지가 영어 URL을 canonical로 가리키면 한국어 콘텐츠가 중복으로 처리되어 노출이 약해질 수 있습니다.
TRAINING EVIDENCE canonical tag audit, URL parameter policy, Search Console duplicate report, crawl sample
Q05

robots.txt와 noindex 차이는 무엇인가요?

robots.txt는 크롤링 접근을 제어하고, noindex는 색인 제외 신호입니다. 크롤링이 막히면 noindex를 보지 못할 수 있습니다.

민감 페이지를 robots.txt만으로 숨기면 URL 존재가 노출될 수 있고 보안 수단도 아닙니다.

꼬리질문꼬리질문 답변
robots로 보안이 되나요?안 됩니다. robots.txt는 협조적인 crawler에 대한 요청일 뿐 URL 노출을 막지 못합니다. 개인정보, admin, 결제 페이지는 인증/인가와 no-store cache가 필요하고 검색 제외는 noindex나 접근 차단 정책으로 따로 관리합니다.
nofollow는?nofollow는 링크 대상에 ranking signal을 전달하지 말라는 힌트입니다. 스팸성 사용자 생성 링크나 유료 링크에는 rel 속성을 쓰고, 내부 핵심 페이지 발견을 막는 용도로 남용하면 crawler discovery가 약해질 수 있습니다.
noarchive는 언제?검색 엔진의 저장된 사본 노출을 원하지 않을 때 씁니다. 가격, 재고, 법적 문구처럼 최신성이 민감한 페이지에서 검토하지만 색인 제외가 아니라 cache 표시 제한이라는 점을 구분해야 합니다.
TRAINING EVIDENCE robots test, meta robots audit, Search Console coverage, security review
Q06

structured data는 어떻게 검증하나요?

schema.org 타입, required/recommended fields, 실제 화면 콘텐츠와의 일치, validation error를 확인합니다.

보이지 않는 정보를 구조화 데이터에만 넣으면 검색 정책 위반과 rich result 누락이 생길 수 있습니다.

꼬리질문꼬리질문 답변
JSON-LD가 좋은 이유는?DOM 구조와 분리해 schema를 명확히 유지할 수 있고 SSR HTML에 넣기 쉽습니다. 다만 rendered HTML에서 실제 콘텐츠와 같은 값인지, product price나 availability가 hydration 후 바뀌지 않는지 검증해야 합니다.
FAQ schema 남용은?화면에 없는 질문이나 홍보성 답변을 넣으면 rich result 정책 위반이 될 수 있습니다. FAQ는 실제 사용자가 묻는 질문과 페이지 주제에 가까운 답만 두고, 반복 boilerplate는 줄이는 것이 좋습니다.
오류가 있으면 색인이 막히나요?대부분 structured data 오류만으로 색인이 막히지는 않습니다. 하지만 rich result 자격을 잃거나 entity 이해가 약해질 수 있으므로 Rich Results Test와 Search Console enhancement report에서 오류와 경고를 구분해 처리합니다.
TRAINING EVIDENCE Rich Results Test, schema validator, content parity check, release checklist
Q07

sitemap은 무엇을 담아야 하나요?

색인시키려는 canonical URL과 lastmod 등 discovery에 필요한 정보를 담고, blocked/noindex/중복 URL은 빼야 합니다.

모든 URL을 넣으면 crawler가 중요하지 않은 페이지에 예산을 씁니다.

꼬리질문꼬리질문 답변
lastmod는 정확해야 하나요?정확해야 합니다. 모든 URL의 lastmod를 매일 갱신하면 crawler가 신호를 신뢰하지 않을 수 있습니다. 본문, metadata, canonical, structured data처럼 색인 가치가 있는 변경에 맞춰 업데이트합니다.
동적 사이트맵은?대규모 서비스는 DB나 CMS 기준으로 canonical, indexable, status 200 URL만 동적으로 생성합니다. sitemap index로 분할하고 생성 시 robots/noindex/redirect URL이 섞이지 않도록 테스트합니다.
삭제 URL은?삭제된 URL은 sitemap에서 제거하고 404나 영구 삭제라면 410을 반환합니다. 대체 페이지가 있으면 관련성 높은 URL로 301 처리하고 internal link도 함께 정리해야 crawl error가 줄어듭니다.
TRAINING EVIDENCE sitemap diff, canonical match test, Search Console sitemap report, URL inventory
Q08

SSR이 SEO를 항상 해결하나요?

SSR은 초기 HTML 제공에 유리하지만 canonical, metadata, structured data, status code, content quality, performance가 함께 필요합니다.

SSR만 도입하고 hydration 오류나 빈 콘텐츠를 내보내면 검색 품질이 좋아지지 않습니다.

꼬리질문꼬리질문 답변
CSR도 검색될 수 있나요?검색될 수 있지만 JS rendering queue와 client error에 의존합니다. 핵심 landing, 상품, 문서 페이지는 SSR/pre-render로 본문과 internal links를 제공하고 CSR 전용 상태는 색인 대상에서 제외하는 편이 안정적입니다.
pre-render는?변경 빈도가 낮은 페이지를 build time이나 edge에서 HTML로 만들어 crawler와 사용자에게 빠르게 제공하는 방식입니다. 가격, 재고, 개인화처럼 자주 바뀌는 데이터는 ISR, cache revalidation, canonical consistency를 함께 설계해야 합니다.
status code는 왜 중요하나요?SSR 페이지가 오류 화면을 200으로 내보내면 soft 404나 잘못된 색인이 생깁니다. 삭제는 404/410, 영구 이동은 301, 권한 필요 페이지는 검색 색인 대상에서 제외되도록 HTTP status와 meta robots를 맞춰야 합니다.
TRAINING EVIDENCE rendered HTML snapshot, metadata audit, hydration log, crawl test
Q09

metadata는 어떻게 설계하나요?

title, description, Open Graph, Twitter card, canonical, hreflang을 페이지 목적과 검색 의도에 맞게 만듭니다.

모든 페이지가 같은 title/description이면 검색 결과에서 구분되지 않고 CTR이 떨어집니다.

꼬리질문꼬리질문 답변
description은 ranking 요소인가요?직접 ranking 요소로 보기보다는 검색 결과 snippet과 CTR에 영향을 주는 요소로 봅니다. query 의도에 맞는 요약과 차별점을 쓰고, 중복 description은 Search Console과 crawl report로 찾아 고칩니다.
OG와 SEO title은?SEO title은 검색 의도와 query 매칭에 맞추고, OG title은 공유 맥락에서 클릭을 설명하게 조정할 수 있습니다. 서로 완전히 다르면 브랜드와 canonical URL 인식이 흐려질 수 있어 핵심 entity와 페이지 목적은 맞춥니다.
동적 metadata는?route param이나 CMS 데이터로 생성하되 SSR HTML에 title, canonical, hreflang, OG가 완성되어 있어야 합니다. fallback title이 색인되지 않도록 loading/error 상태의 metadata와 404 status를 별도로 테스트합니다.
TRAINING EVIDENCE metadata snapshot, duplicate title report, SERP preview, social card test
Q10

hreflang은 언제 필요하고 무엇이 어렵나요?

다국어/다지역 동일 콘텐츠에서 언어와 지역 대체 URL을 알려줄 때 필요합니다.

상호 참조, canonical, locale URL이 어긋나면 검색 엔진이 잘못된 언어 페이지를 보여줄 수 있습니다.

꼬리질문꼬리질문 답변
x-default는?언어를 특정하기 어려운 글로벌 선택 페이지나 기본 landing을 지정할 때 씁니다. x-default도 hreflang set에 포함하고 canonical이 자기 자신을 가리키는지 확인해야 합니다.
자동 번역 페이지는?품질 낮은 자동 번역은 색인 품질과 브랜드 신뢰를 떨어뜨릴 수 있습니다. locale별로 사용자에게 보이는 번역 품질, currency/region 정보, local schema를 검수한 뒤 hreflang에 포함합니다.
canonical과 충돌하면?hreflang URL이 다른 언어 URL을 canonical로 가리키면 검색 엔진이 대체 언어 관계를 무시할 수 있습니다. 각 언어 페이지는 self-canonical을 두고 모든 locale이 reciprocal hreflang으로 서로를 참조해야 합니다.
TRAINING EVIDENCE hreflang matrix, reciprocal link test, locale URL audit, Search Console international report
Q11

애널리틱스 이벤트는 어떻게 정의하나요?

DOM 클릭이 아니라 사용자 의도, action, target, result, error, context를 담는 product event로 정의합니다.

button_text만 보내면 퍼널, 실패, 재시도, 권한 차단을 분석할 수 없습니다.

꼬리질문꼬리질문 답변
