마이그레이션과 호환성

큰 시스템에서 기술을 한 번에 바꾸지 못하는 이유와 안전한 전환의 언어를 익힙니다.

FORMAT : 개념 → 맥락 → 판단 기준 → 실패 신호 · UPDATED 2026-07
INDEX

이 문서의 위치

마이그레이션과 호환성 문서는 기술명을 외우기보다 이 주제에서 반복되는 압력, 책임 경계, 측정 기준을 읽는 데 초점을 둡니다. 아래 항목을 먼저 훑고 마지막의 수치 앵커와 사례로 판단 기준을 고정합니다.

MIG-01

마이그레이션은 변경 관리다

마이그레이션은 새 기술 적용이 아니라 기존 사용자를 깨뜨리지 않고 상태를 옮기는 과정이다. 코드, 데이터, API, 문서, 팀 습관까지 함께 이동해야 한다.

마이그레이션을 새 기술을 적용하는 일로만 생각하면 정작 어려운 부분을 놓친다. 진짜 어려운 건 기존 사용자를 깨뜨리지 않고 상태를 옮기는 것이다. code migration은 API, import, framework 변경을 다루는 대상이고, data migration은 schema, backfill, consistency를 다루는 대상이다. workflow migration은 팀의 작업 방식과 도구 변경을 다루는 대상이다. 코드만 옮기고 데이터나 팀 습관은 그대로 두면 마이그레이션이 절반만 끝난 상태로 오래 남는다.

MIG-02

호환성의 종류

Backward compatibility는 새 코드가 옛 입력을 받아들이는 능력이고, forward compatibility는 옛 코드가 새 데이터를 만나도 크게 깨지지 않는 능력이다. 배포 순서가 나뉘면 둘 다 중요해진다.

호환성은 방향에 따라 이름이 다르다. backward compatible은 새 버전이 기존 사용자를 깨지 않는다는 뜻이고, forward compatible은 구버전이 새로운 데이터를 만나도 크게 문제없이 동작한다는 뜻이다. wire compatibility는 서로 다른 프로세스 사이를 오가는 데이터 형식이 호환된다는 뜻이다. 배포가 한 번에 이루어지지 않고 여러 단계로 나뉘는 시스템이라면, 이 세 가지 호환성을 모두 챙겨야 배포 도중에도 서비스가 깨지지 않는다.

MIG-03

Expand-contract

DB와 API 변경은 보통 expand-contract로 간다. 먼저 새 필드/경로를 추가하고, 양쪽을 모두 지원하고, 트래픽을 옮긴 뒤, 마지막에 옛 것을 제거한다.

DB나 API를 바꿀 때 한 번에 밀어붙이면 되돌릴 방법이 없어진다. 그래서 세 단계로 나눈다. expand 단계는 새 구조를 추가하면서 기존 구조는 그대로 유지하는 단계다. migrate 단계는 읽기와 쓰기 경로를 새 구조로 전환하면서 기존 데이터를 backfill하는 단계다. contract 단계는 옛 구조의 사용량이 정말 0이 된 것을 확인한 뒤에야 그것을 제거하는 단계다. 이 순서를 지키면 어느 시점에서든 롤백할 수 있는 여지가 남는다.

MIG-04

점진적 롤아웃

한 번에 전환하면 실패 반경이 전체가 된다. feature flag, canary, shadow traffic, dual write, read fallback은 실패 반경을 줄이는 기술이다.

한 번에 전체를 전환하면 문제가 생겼을 때 실패 반경도 전체가 된다. feature flag는 사용자, 팀, 환경별로 노출을 세밀하게 제어하는 수단이고, canary는 일부 트래픽에만 먼저 새 버전을 적용해보는 수단이다. shadow traffic은 실제 요청을 새 경로로도 보내보되 그 응답은 사용자에게 반영하지 않는 수단이다. 이런 기술들의 공통점은 문제가 생겼을 때 영향받는 범위를 처음부터 작게 만든다는 것이다.

MIG-05

Deprecation

사용 중단은 공지문이 아니라 계약 변경 절차다. 대체 경로, 사용량 측정, 경고, deadline, owner, 제거 PR이 함께 있어야 한다.

사용 중단은 단순히 공지 하나 올리는 일이 아니라 사용자와의 계약을 바꾸는 절차다. usage inventory 절차는 지금 누가 이 기능을 쓰고 있는지 측정하는 단계이고, warning 절차는 로그, build warning, runtime warning으로 미리 알리는 단계다. deadline 절차는 실제로 제거할 시점과 예외를 인정할 기준을 정하는 단계다. 이 세 단계가 순서대로 진행돼야 어느 날 갑자기 기능이 사라져서 사용자가 당황하는 일이 없다.

MIG-06

읽히는 신호

마이그레이션 글은 새 기술의 장점보다 전환 전략이 중요하다. 호환성, 롤백, 사용량 측정, 단계별 제거가 있으면 큰 시스템에서 나온 글이다.

마이그레이션에 관한 글을 읽을 때는 새 기술이 얼마나 좋은지보다 전환 전략이 얼마나 치밀한지를 본다. dual support 신호는 신구 경로가 일정 기간 함께 동작하는지를 보여주고, rollback plan 신호는 문제가 생겼을 때 되돌아갈 지점이 있는지를 보여준다. adoption metric 신호는 전환률과 아직 남은 사용자 수를 계속 추적하고 있는지를 보여준다. 이 세 신호가 함께 있는 글이라면 그건 실제로 큰 시스템을 옮겨본 경험에서 나온 글이다.

CASE

실무 상황 예시

아래 수치는 이해를 위한 가상 운영 수치입니다. 목적은 특정 회사 사례를 베끼는 것이 아니라, 기술 글에 자주 등장하는 상황·숫자·판단 기준을 읽는 감각을 만드는 것입니다.

결제 API v1에서 v2로 이동

SITUATION

가상 운영 수치다. 결제 API v1 consumer는 68개이고, 모바일 앱은 4개 버전이 시장에 남아 있다. v2는 idempotency key와 상세 실패 코드를 추가하지만 v1 응답을 바로 없앨 수 없다.

NUMBERS

6주 dual support 기간을 둔다. v1 사용량은 100%에서 3주차 12%, 6주차 0.3%로 줄고, 마지막 0.3%는 오래된 앱 버전이라 강제 업데이트 정책과 연결한다.

LESSON

마이그레이션은 새 API 설계보다 남은 사용자를 처리하는 일이 더 어렵다. usage inventory, deadline, fallback이 없으면 제거 단계가 끝나지 않는다.

18M rows DB 컬럼 전환

SITUATION

주문 테이블 18M rows에 새 정규화 컬럼을 추가한다. 기존 컬럼을 바로 제거하면 구버전 서버와 배치 작업이 깨진다.

NUMBERS

nullable column 추가, dual write, 2,000 rows/sec backfill, 검증 쿼리, read path 전환, contract 순서로 진행한다. backfill은 약 2시간 30분이 걸리며 lock과 replica lag를 대시보드로 본다.

LESSON

DB 마이그레이션의 핵심은 SQL 한 줄이 아니라 배포 순서다. expand-contract를 지키면 롤백 가능한 지점을 유지하면서 데이터 구조를 바꿀 수 있다.

OUTPUT

실무 산출물 보강 기준

이 문서는 맥락 설명에서 끝내지 않고 실무자가 제출할 수 있는 산출물로 닫아야 한다. 짧은 글이라도 기준선, 입력 데이터, 판단 기준, 실패 시 조치를 한 표로 남긴다.

기준일·범위는 2026-07-09 기준으로 마이그레이션·호환성 문서에서 다루는 판단 범위와 제외 범위를 명시한다. 필수 산출물은 backfill 검증, dual-write/read 비교, rollback 불가 지점, cutover/abort 기준이다.

증거 예시는 old/new read diff, backfill count, lag, mismatch sample, abort trigger를 cutover checklist에 두는 것이다. 통과 기준은 숫자나 체크리스트가 의사결정, 승인자, rollback/abort 조건 중 하나와 연결되는 것이다. 나쁜 산출물은 개념 설명만 있고 기준선, 비교 대상, 책임자, 다음 조치가 없는 문서다.
