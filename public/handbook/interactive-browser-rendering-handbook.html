Browser & Rendering

CSS 속성을 외우는 대신, 코드의 변화가 어떤 브라우저 작업을 일으키고 언제 사용자에게 끊김으로 보이는지 이해합니다.

START

이 페이지를 읽고 할 수 있어야 하는 것

브라우저 렌더링을 공부하는 이유는 “transform이 빠르다” 같은 규칙을 암기하기 위해서가 아닙니다. 인터랙션이 버벅일 때 어떤 작업이 반복됐는지 확인하고, 가장 작은 변경으로 고칠 수 있어야 합니다.

카드를 오른쪽으로 움직일 때 left를 바꿀 수도 있고 transform: translateX()를 바꿀 수도 있습니다. 화면 결과는 비슷하지만 브라우저가 다시 해야 하는 일은 다를 수 있습니다. 전자는 요소의 위치와 주변 배치를 다시 계산하게 만들 수 있고, 후자는 이미 그려진 결과를 합성 단계에서 옮기는 것으로 끝날 수 있습니다.

이 장의 판단 순서

무엇이 바뀌었는지 확인하고, 그 변경이 Style·Layout·Paint·Composite 중 어느 단계까지 다시 실행시키는지 추적합니다. 그다음 작업 면적과 반복 횟수, 기기 성능, 주사율을 함께 보고 실제 병목인지 측정합니다. 마지막으로 성능을 위해 문서 흐름, 초점, 텍스트 선명도 같은 사용자 경험을 훼손하지 않았는지 확인합니다.

읽기 전 질문읽은 뒤 답할 수 있어야 하는 것
left보다 transform이 왜 자주 권장되는가?두 속성이 유발할 수 있는 pipeline 작업의 차이를 설명한다.
will-change를 붙이면 항상 빨라지는가?layer 준비의 이점과 메모리·관리 비용을 함께 설명한다.

BR-01

픽셀이 만들어지는 큰 흐름

브라우저는 HTML과 CSS를 그대로 화면에 붙이지 않습니다. 문서를 구조로 해석하고, 각 요소의 크기와 위치를 계산하고, 무엇을 그릴지 기록한 뒤 실제 픽셀로 만들어 합성합니다.

HTML→DOM+CSSOM→Style→Layout→Paint→Raster→Composite

DOM과 CSSOM은 서로 다른 질문에 답한다

DOM은 어떤 요소가 있고 서로 어떤 부모·자식 관계인지 표현합니다. CSSOM은 selector와 cascade를 적용했을 때 어떤 style 규칙이 유효한지 표현합니다. 브라우저는 둘을 함께 사용해 화면에 필요한 요소와 계산된 style을 결정합니다.

<article class="card"><h2>Rendering</h2></article>

.card {
  width: 320px;
  padding: 24px;
  background: white;
}

브라우저는 “article 안에 h2가 있다”는 구조와 “card는 너비 320px, 안쪽 여백 24px, 흰 배경이다”라는 style 정보를 결합합니다. 그 다음에야 화면에서 차지할 실제 크기와 위치를 계산할 수 있습니다.

React와 브라우저 render는 다르다

React render는 컴포넌트가 반환할 UI를 계산하는 과정입니다. 브라우저 render는 DOM과 style 결과를 픽셀로 만드는 과정입니다. React가 다시 실행돼도 DOM 변경이 없으면 layout이나 paint가 없을 수 있습니다. 반대로 React 없이 DOM style을 직접 바꿔도 브라우저 비용은 발생합니다.

BR-02

렌더링 파이프라인 단계별 이해

각 단계가 받는 입력과 만드는 결과를 알면 DevTools에 보이는 용어가 실제 코드와 연결됩니다.

1 Style Calculation

각 요소에 최종 적용될 style을 결정합니다. selector matching, cascade, inheritance, media query와 CSS variable 결과가 계산됩니다. class나 상위 custom property를 바꾸면 관련 요소의 style이 무효화되어 다시 계산될 수 있습니다.

확인할 것: 변경이 한 요소에 머무는지 많은 후손에게 퍼지는지 봅니다. 상위 custom property를 매 frame 바꾸면 예상보다 넓은 계산이 생길 수 있습니다.

2 Layout

각 box의 너비, 높이, x·y 위치를 계산합니다. 부모 크기는 자식에게, 자식 콘텐츠 크기는 다시 부모에게 영향을 줄 수 있어 한 변화가 주변 요소로 퍼질 수 있습니다. 이를 reflow라고도 부릅니다.

확인할 것: width, height, padding, font-size, top, left처럼 geometry나 흐름을 바꾸는 속성을 반복 변경하는지 봅니다. Layout은 잘못이 아닙니다. 실제 공간이 변해야 한다면 필요한 작업이며, 불필요하게 반복될 때가 문제입니다.

3 Paint

계산된 box를 어떤 순서와 모양으로 그릴지 명령을 만듭니다. 배경, 글자, border, shadow, image가 대상입니다. 작은 아이콘 색 변경과 viewport 전체 blur는 둘 다 Paint일 수 있지만 비용 규모는 다릅니다.

확인할 것: 발생 여부뿐 아니라 다시 그리는 영역의 크기와 빈도를 봅니다.

4 Rasterization

Paint 명령을 실제 pixel bitmap으로 바꿉니다. 페이지는 tile 단위로 raster될 수 있고, device pixel ratio가 높으면 같은 CSS 크기라도 실제 처리 픽셀이 늘어납니다. 큰 image, gradient, shadow, filter는 raster 비용과 texture memory를 키울 수 있습니다.

5 Compositing

여러 layer의 raster 결과를 올바른 위치와 순서로 조합해 최종 frame을 만듭니다. 요소가 별도 layer에 있고 transform이나 opacity만 바뀐다면 내용을 다시 그리지 않고 layer를 이동하거나 투명도를 바꾸는 것으로 처리할 수 있습니다.

핵심

목표는 무조건 Composite만 사용하는 것이 아닙니다. 필요한 시각 결과를 만들면서 매 frame 반복되는 Style, Layout, Paint의 범위와 횟수를 줄이는 것입니다. 한 번의 layout으로 끝날 UI 변경을 transform으로 흉내 내면 문서 흐름과 접근성이 더 나빠질 수 있습니다.

BR-03

CSS 변경 비용을 읽는 방법

속성을 빠르다·느리다로 외우지 말고, 변경 이후 브라우저가 어느 단계부터 다시 일해야 하는지 묻습니다.

변경가능한 작업이유와 사용 기준
width, height, padding, font-sizeStyle → Layout → Paint → Compositebox 크기와 주변 배치가 달라진다. 실제 문서 공간 변화에 사용한다.
top, leftStyle → Layout 또는 Paint → Compositepositioned box의 geometry가 변한다. 연속 animation은 측정한다.
background, color, borderStyle → Paint → Compositegeometry는 같아도 pixel 모양이 달라진다.
box-shadow, filterPaint 또는 GPU effect → Composite넓은 영역과 추가 연산이 필요할 수 있다.
transform, opacityStyle → 주로 Compositelayer가 준비돼 있으면 기존 pixel을 재배치할 수 있다.

같은 이동을 두 방식으로 비교하기

/* geometry를 바꾸는 방식 */
.card.is-moving { left: 240px; }

/* 그려진 결과를 이동하는 방식 */
.card.is-moving { transform: translateX(240px); }

left는 box의 위치 계산에 관여할 수 있습니다. transform은 layout상 원래 자리를 유지한 채 시각 결과를 이동합니다. 따라서 drag preview에는 transform이 잘 맞지만, 다른 콘텐츠가 빈자리를 채워야 하는 목록 재배치에는 layout 변경이나 FLIP 같은 전략이 필요합니다.

표는 출발점이다

브라우저 구현, 요소 크기, layer 상태와 반복 빈도에 따라 실제 비용은 달라집니다. 표는 측정 대상을 좁히는 도구이며 최종 판단은 대상 기기의 Performance trace로 합니다.

BR-04

레이어와 합성 이해

Compositing layer는 일부 콘텐츠를 별도 surface로 raster한 뒤 GPU에서 조합할 수 있도록 나눈 실행 단위에 가깝습니다.

별도 layer가 도움이 되는 경우

움직이는 요소가 독립 layer로 준비되면 내용이 바뀌지 않는 동안 매 frame 다시 paint하지 않고 위치나 opacity만 바꿀 수 있습니다. 큰 페이지 위를 이동하는 modal, fixed header, transform animation이 이점을 얻을 수 있습니다.

모든 요소를 layer로 만들면 안 되는 이유

각 layer는 raster 결과를 저장할 메모리와 관리 비용이 필요합니다. 큰 image나 고해상도 요소를 여러 layer로 만들면 texture memory, upload, 합성 비용이 증가합니다. 수백 개 요소에 will-change를 붙이면 오히려 느려질 수 있습니다.

.moving-card { will-change: transform; }
.moving-card.is-finished { will-change: auto; }

will-change곧 바뀔 속성을 알리는 hint최적화 명령이 아니며 상시 남발하지 않는다.
BR-05

프레임과 시간 예산

브라우저가 다음 화면을 제시간에 준비하지 못하면 같은 frame이 더 오래 남고 사용자는 이를 끊김 또는 jank로 느낍니다.

frame budget = 1000ms ÷ refresh rate
60Hz  ≈ 16.67ms
120Hz ≈  8.33ms
144Hz ≈  6.94ms

이 시간 전체를 JavaScript가 쓸 수 있는 것은 아닙니다. input, JavaScript, style, layout, paint, raster, composite가 함께 들어오므로 실제 안전 예산은 더 작습니다.

requestAnimationFrame timestamp 사용

let previousTime;
function tick(time) {
  const delta = previousTime == null ? 0 : time - previousTime;
  previousTime = time;
  position += velocity * (delta / 1000);
  node.style.transform = `translateX(${position}px)`;
  requestAnimationFrame(tick);
}
requestAnimationFrame(tick);

frame마다 2px씩 더하면 120Hz 화면에서 60Hz보다 훨씬 빠르게 이동할 수 있습니다. delta time으로 계산하면 refresh rate가 달라도 시간 기준 속도를 유지합니다.

BR-06

Layout Thrashing과 강제 동기 Layout

브라우저는 여러 style 변경을 모아 처리하려고 합니다. 그러나 style을 바꾼 직후 최신 geometry를 읽으면 정확한 값을 주기 위해 예정된 layout을 즉시 실행할 수 있습니다.

// write와 read가 반복되는 나쁜 예
items.forEach((item) => {
  item.style.width = `${nextWidth}px`; // write
  console.log(item.offsetWidth);       // read
});
// read → calculate → write로 묶는다.
const widths = items.map((item) => item.offsetWidth);
const nextWidths = widths.map((width) => width + 20);
items.forEach((item, index) => {
  item.style.width = `${nextWidths[index]}px`;
});

offsetWidth, getBoundingClientRect(), getComputedStyle() 등은 상황에 따라 pending style이나 layout을 확정시킬 수 있습니다. 사용 금지가 아니라 animation loop 안에서 read와 write를 교차시키지 말라는 뜻입니다.

실패 신호

한 frame 안에 작은 Layout block이 여러 번 반복되거나 JavaScript stack 아래 강제 layout 경고가 보이면 DOM read/write 순서를 먼저 확인합니다. React memo부터 추가하면 geometry 문제를 놓칠 수 있습니다.

BR-07

DevTools로 원인을 확인하는 순서

막연히 빨간색을 찾지 않습니다. 재현 조건을 고정하고 느린 frame의 작업을 찾은 뒤 코드와 연결합니다.

  1. 시나리오 고정: “카드를 1초간 드래그한다”처럼 시작과 끝을 정합니다.
  2. 조건 기록: viewport, CPU slowdown, 기기를 기록합니다.
  3. Recording: 정한 행동만 실행하고 바로 멈춥니다.
  4. 긴 frame 선택: Main track에서 JavaScript, Recalculate Style, Layout, Paint를 봅니다.
  5. Call stack 연결: 비싼 event가 어떤 함수와 DOM 변경에서 왔는지 찾습니다.
  6. 시각 보조: Paint flashing으로 영역을 보고 Layers로 합성 상태를 확인합니다.
  7. 한 원인만 수정: 같은 조건에서 다시 기록해 예상 단계가 줄었는지 비교합니다.

BR-08

단계별 실습

한 요소에서 pipeline을 확인한 뒤 개수를 늘려 차이가 드러나는 지점을 찾습니다.

Lab 1 한 요소 이동

  1. 같은 card를 두 개 만든다.
  2. 첫 번째는 left, 두 번째는 transform으로 이동시킨다.
  3. Performance trace에서 Layout, Paint, Composite 차이를 기록한다.
  4. Paint flashing으로 다시 그려지는 영역을 확인한다.

Lab 2 규모 늘리기

  1. card를 1, 10, 100, 1,000개로 늘린다.
  2. 각 수량의 frame time과 dropped frame을 기록한다.
  3. 비용이 급격히 나빠지는 지점을 찾는다.
  4. 화면 밖 요소도 update하는지 확인한다.

Lab 3 Thrashing 재현

  1. 반복문에서 style write 다음 offsetWidth를 읽는다.
  2. 강제 layout 횟수를 확인한다.
  3. read phase와 write phase를 분리한다.
  4. 같은 조건으로 다시 기록해 총 시간을 비교한다.

왜 transform이 자주 유리한가?layout상 자리를 유지하는 점, paint 생략 가능성, layer 조건과 메모리 비용을 설명한다.
Accordion 높이는 transform으로 바꿔야 하는가?주변 흐름이 실제 변해야 한다면 layout이 필요한 이유와 대안을 비교한다.
Trace에 Layout이 보이면 실패인가?필요 여부, 횟수, 면적, frame budget과 사용자 영향으로 판정한다.
will-change는 언제 제거하는가?animation lifecycle과 layer memory 비용을 설명한다.
React rerender와 repaint의 차이는?UI 계산, DOM commit, style/layout/paint 경계를 예로 설명한다.
최종 과제

느린 interaction 하나를 골라 “변경된 값 → 무효화된 단계 → trace 증거 → 수정한 코드 → 사용자 경험 변화”를 한 페이지로 기록합니다. FPS 하나로 끝내지 말고 입력 반응, frame time, paint 영역, 메모리와 접근성을 함께 판정합니다.
