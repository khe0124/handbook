문서 구조

프론트엔드 개발자가 Docker를 배워야 하는 이유는 “컨테이너를 띄운다”가 아니라 빌드 산출물, 런타임 환경, 네트워크 경계, 배포 재현성을 같은 언어로 설명하기 위해서입니다.

시작 증거FE bridge
로컬에서는 되지만 배포 컨테이너에서만 깨지는 env, file path, port, node version, native dependency 차이를 확인합니다.
자주 만나는 상황debug
이미지 빌드는 성공했지만 컨테이너가 즉시 종료되거나, 포트 매핑은 했는데 reverse proxy에서 502가 나는 경우를 다룹니다.
완료 산출물evidence
Dockerfile, image digest, docker inspect, container logs, health check, rollback 가능한 tag 정책을 남깁니다.
DCK-01

이미지와 컨테이너

이미지는 실행 가능한 파일시스템과 metadata를 담은 immutable artifact이고, 컨테이너는 그 이미지를 격리된 프로세스로 실행한 상태입니다. tag는 이름일 뿐이며 운영 증거는 digest로 고정해야 합니다.

INFRA DECISION

판단 질문 지금 실행 중인 컨테이너가 배포하려던 이미지와 같은가?

확인 증거 image tag, image digest, container id, created time, command, env readback

실패 신호 latest tag 재사용, registry에는 새 이미지가 있지만 host는 예전 digest 실행, rollback tag가 없음

docker image ls
docker inspect --format '{{.Id}} {{.Config.Image}} {{.Config.Cmd}}' app-container
docker logs --tail=100 app-container
DCK-02

Dockerfile

Dockerfile은 배포 환경을 문서화하는 코드입니다. dependency install layer와 source copy layer를 분리하면 cache hit가 안정되고, multi-stage build를 쓰면 빌드 도구와 런타임 파일을 분리할 수 있습니다.

DOCKERFILE REVIEW

볼 것 base image pinning, lockfile copy order, multi-stage boundary, non-root user, healthcheck, secret 미포함

프론트 연결 Vite/Next build output, public env, node_modules native dependency, static asset path가 이미지 안에서 일치하는지 확인합니다.

차단 기준 secret이 ARG/ENV/layer history에 남거나, runtime image에 dev dependency와 빌드 도구가 그대로 들어가면 리뷰를 멈춥니다.

docker build -t app:web-20260911 .
docker history app:web-20260911
docker run --rm -p 3000:3000 app:web-20260911
DCK-03

네트워크와 볼륨

컨테이너 내부 port와 host publish port는 다릅니다. 앱이 3000에서 listen해도 `-p 8080:3000`이면 외부 사용자는 8080으로 접근합니다. 데이터는 컨테이너 filesystem에 두면 재생성 시 사라지므로 volume이나 외부 저장소에 둡니다.

port mappingnetwork
host port와 container port를 연결합니다. nginx upstream, health check target, docker publish 설정이 같은 port를 가리켜야 합니다.
bridge networknetwork
컨테이너 간 통신을 위한 기본 네트워크입니다. 서비스 이름 해석은 Compose network 안에서만 기대해야 합니다.
volumestate
컨테이너 재생성 이후에도 남아야 하는 파일을 외부화합니다. 로그, DB, 업로드 파일의 보존 정책을 분리합니다.
DCK-04

런타임 제한

컨테이너는 VM이 아니라 host kernel 위의 제한된 프로세스입니다. CPU throttling, memory limit, file descriptor, ephemeral storage를 모르면 앱 장애를 코드 문제로 오판합니다.

RUNTIME EVIDENCE

확인 증거 memory limit, restart count, exit code, OOMKilled, CPU usage, log growth

운영 판단 container가 죽었는지, 앱 프로세스가 실패했는지, host resource가 부족한지 분리합니다.

완화 limit 조정은 임시 완화일 수 있습니다. leak, startup spike, cache size, log 폭증 원인을 별도로 닫아야 합니다.

docker stats
docker inspect --format '{{.State.ExitCode}} {{.State.OOMKilled}} {{.RestartCount}}' app-container
DCK-05

보안·배포 증거

Docker 배포의 핵심은 같은 입력으로 같은 이미지를 만들고, 취약점과 secret 노출을 확인하고, 어떤 digest가 어느 환경에 배포됐는지 추적하는 것입니다.

  • base image는 major tag가 아니라 digest 또는 명시 버전으로 고정합니다.
  • secret은 image에 넣지 않고 runtime secret manager나 orchestrator secret으로 주입합니다.
  • registry scan, SBOM, image signing, deploy approval, rollback tag를 release evidence packet에 묶습니다.
  • frontend bundle에 들어가도 되는 public env와 서버 secret을 분리합니다.
PRACTICE

출력 판독

Docker 실무는 명령을 외우는 것보다 출력에서 원인 후보를 줄이는 훈련이 중요합니다.

PRACTICE LAB

Command / Query `docker inspect`, `docker logs --previous`, `docker stats`로 실행 이미지, 종료 이유, 리소스 사용을 확인합니다.

정상 출력 배포 기록의 image digest와 실행 컨테이너 digest가 같고, health check가 통과하며 restart count가 증가하지 않습니다.

비정상 출력 OOMKilled true, exit code 127, required env 누락, port mismatch, latest tag drift가 보입니다.

판단 훈련 Dockerfile 문제, runtime env 문제, host resource 문제, network mapping 문제를 분리합니다.

즉시 완화 이전 digest로 rollback하거나 traffic을 빼고 env/port/resource 설정을 되돌립니다.

영구 수정 Dockerfile review checklist, digest pinning, health check, registry scan, release note를 추가합니다.

검증 기준 같은 commit을 clean build해도 같은 동작을 재현하고, smoke test와 로그에서 request id가 확인됩니다.
