프론트엔드 성능·진단 Q&A

Web Vitals, 번들, 렌더링, DevTools, React Profiler, RUM을 수치와 증거로 답합니다.

TRAINING : 30초 답변 → 90초 확장 → 꼬리질문 방어 → 증거 패킷 확인
GUIDE

훈련 방식

각 문항은 API 암기나 라이브러리 사용법이 아니라, 사용자 흐름, 브라우저 비용, 접근성, 성능, 보안, 운영 증거를 연결해 답하는 훈련용입니다.

frontend_answer_loop: 1_user_impact: "사용자가 겪는 변화와 실패 비용을 먼저 말한다" 2_runtime_boundary: "DOM, network, rendering, cache, browser policy 중 경계를 잡는다" 3_tradeoff: "선택 기준과 포기하는 것을 분리한다" 4_failure_mode: "race, stale data, accessibility, device variance, cache drift를 점검한다" 5_evidence: "trace, screenshot, test, metric, release log 중 하나를 증거로 든다"
Q01

프론트엔드 성능을 어디서부터 진단하나요?

사용자 영향 지표인 LCP, INP, CLS, error rate, route별 RUM을 먼저 보고 network, main thread, rendering, backend wait로 분해합니다.

Lighthouse 점수만 보면 실제 사용자 기기·네트워크·로그인 상태의 병목을 놓칩니다.

꼬리질문꼬리질문 답변
실험실 점수와 RUM이 다르면?lab은 고정 기기와 네트워크에서 회귀를 재현하는 데 좋고, RUM은 실제 브라우저·지역·로그인 상태의 p75를 보여줍니다. 차이가 나면 route, device tier, connection, release version으로 RUM을 나누고 같은 조건을 Lighthouse나 WebPageTest에 맞춰 재현합니다.
route별로 봐야 하는 이유는?홈, 검색, checkout, dashboard는 LCP element, API chain, JS chunk, third-party 의존성이 다릅니다. 전체 평균만 보면 핵심 route의 p75 LCP나 INP 악화를 내부 페이지의 좋은 수치가 가릴 수 있습니다.
성능 문제를 백엔드와 어떻게 나누나요?waterfall에서 DNS/TLS, TTFB, download, render-blocking, JS execution을 분리하고 Server-Timing header로 backend 처리 시간을 표시합니다. TTFB 이후 LCP resource 발견이나 hydration이 늦으면 프론트 병목이고, TTFB 자체가 route별로 높으면 API·SSR·edge cache를 같이 봅니다.
TRAINING EVIDENCE RUM dashboard, Web Vitals attribution, Performance trace, network waterfall
Q02

LCP가 느릴 때 무엇을 보나요?

TTFB, render-blocking resource, LCP element load priority, image size/format, client rendering delay를 나눠 봅니다.

이미지만 압축하면 서버 응답 지연이나 JS hydration 지연 때문에 개선이 안 될 수 있습니다.

꼬리질문꼬리질문 답변
LCP element가 바뀌면?viewport, 로그인 상태, A/B variant마다 LCP 후보가 hero image, 제목, skeleton, video poster로 바뀔 수 있습니다. Web Vitals attribution으로 실제 element selector를 기록하고 각 후보의 size, priority, cache hit, render delay를 따로 봅니다.
preload는 언제?초기 viewport의 LCP 이미지나 핵심 font처럼 브라우저가 늦게 발견하지만 반드시 필요한 resource에만 씁니다. preload 후 실제 사용되지 않거나 너무 많이 걸면 bandwidth 경쟁으로 JS/CSS와 LCP 이미지 우선순위가 꼬일 수 있습니다.
SSR이 항상 LCP에 좋은가요?항상 그렇지 않습니다. SSR은 초기 HTML 표시를 앞당길 수 있지만 서버 TTFB가 크거나 hydration JS가 무거우면 LCP와 INP가 같이 나빠집니다. SSR, SSG, CSR을 같은 route에서 TTFB, LCP render delay, hydration cost로 비교해야 합니다.
TRAINING EVIDENCE LCP attribution, server timing, priority hint, image audit
Q03

INP가 나쁠 때 어떻게 좁히나요?

느린 interaction을 찾고 event handler, long task, render cost, layout, third-party script를 분해합니다.

평균 입력 지연이 괜찮아도 특정 컴포넌트의 긴 작업이 p75/p98을 망칠 수 있습니다.

꼬리질문꼬리질문 답변
FID와 INP 차이는?FID는 첫 입력의 delay만 봤지만 INP는 페이지 생애 전체 interaction의 latency를 대표합니다. 그래서 최초 클릭은 빠르더라도 필터 변경, 검색 입력, 모달 열기에서 long task나 큰 commit이 있으면 INP가 나빠집니다.
debounce로 해결되나요?일부 입력 처리에는 도움이 되지만 클릭 후 화면 반응 자체가 늦거나 render commit이 길면 debounce만으로는 부족합니다. expensive calculation을 worker로 옮기거나 render 범위를 줄이고, immediate feedback을 먼저 보여 INP interaction delay와 presentation delay를 줄여야 합니다.
React rerender와 INP 연결은?interaction 뒤에 넓은 context 구독, 큰 list render, 불필요한 memo miss가 발생하면 main thread가 막혀 INP가 올라갑니다. React Profiler의 interaction commit과 DevTools Performance의 long task를 marker로 맞춰 어떤 component commit이 느린지 확인합니다.
TRAINING EVIDENCE INP attribution, long task trace, React Profiler, interaction marker
Q04

CLS는 왜 생기나요?

이미지/광고/폰트/동적 콘텐츠의 크기 예약 부족, late injection, hydration 차이로 layout shift가 생깁니다.

시각적으로 작은 이동도 사용자가 버튼을 잘못 누르게 만들 수 있습니다.

꼬리질문꼬리질문 답변
animation도 CLS인가요?transform과 opacity 기반 animation은 보통 layout shift로 잡히지 않지만 top, height, margin처럼 layout을 바꾸는 animation은 CLS를 만들 수 있습니다. Performance 패널의 layout shift rectangle로 움직인 요소와 입력 직후 shift 예외 여부를 확인합니다.
skeleton이 CLS를 줄이나요?skeleton이 최종 콘텐츠와 같은 높이, aspect-ratio, spacing을 예약하면 줄입니다. 반대로 skeleton 높이가 실제 카드나 광고보다 작거나 hydration 후 DOM 구조가 바뀌면 skeleton 자체가 CLS 원인이 됩니다.
font swap은?font-display swap은 텍스트를 빨리 보이게 하지만 fallback과 웹폰트 metrics가 다르면 글줄이 밀려 CLS가 생깁니다. size-adjust, ascent/descent override, subset, preload를 조합해 FOIT와 layout shift 사이를 조정합니다.
TRAINING EVIDENCE CLS attribution, layout shift rectangles, image dimension audit, font loading strategy
Q05

번들 크기는 어떻게 줄이나요?

route-level code splitting, dependency audit, tree shaking, dynamic import, polyfill 점검, asset 압축을 순서대로 봅니다.

무작정 minify만 하면 큰 dependency, 중복 polyfill, 초기 route에 묶인 admin code는 남아 있습니다.

꼬리질문꼬리질문 답변
dynamic import는 어디에?초기 route의 LCP와 interaction에 필요 없는 admin panel, editor, chart, modal, locale data, heavy validator에 우선 적용합니다. import boundary가 너무 잘게 쪼개져 request overhead가 커지지 않도록 route chunk map과 waterfall을 같이 봅니다.
tree shaking이 안 되는 이유는?package가 sideEffects를 과하게 선언했거나 CommonJS, namespace import, top-level side effect 때문에 bundler가 제거하지 못할 수 있습니다. bundle analyzer에서 남은 module을 확인하고 ESM entry, 직접 import, dependency 교체를 검토합니다.
gzip만 보면 충분한가요?충분하지 않습니다. gzip/brotli 전송량이 작아도 parse, compile, execute 비용은 남고 모바일 CPU에서는 JS 실행이 INP와 hydration readiness를 늦춥니다. compressed size와 uncompressed JS, coverage, main-thread execution time을 같이 봅니다.
TRAINING EVIDENCE bundle analyzer, coverage tab, route chunk map, dependency diff
Q06

React 렌더링 병목은 어떻게 찾나요?

Profiler로 commit duration, render count, why-did-render 원인, context 구독 범위, memoization 효과를 봅니다.

useMemo/useCallback을 무작정 넣으면 비용은 늘고 실제 rerender 원인은 그대로일 수 있습니다.

꼬리질문꼬리질문 답변
memo는 언제 효과가 있나요?같은 props로 자주 렌더되는 비싼 component가 있고 parent update가 잦을 때 효과가 있습니다. props identity가 매번 바뀌거나 render 비용이 작으면 비교 비용만 늘 수 있으므로 Profiler에서 commit duration과 render count 개선을 확인해야 합니다.
context가 왜 문제인가요?하나의 큰 context value가 바뀌면 그 값을 구독하는 넓은 subtree가 다시 렌더될 수 있습니다. state를 분리하거나 selector 기반 store를 쓰고, theme·auth·filter처럼 갱신 빈도가 다른 값은 provider를 나눠 commit 범위를 줄입니다.
key 변경은 어떤 영향을 주나요?key가 바뀌면 React는 기존 subtree를 재사용하지 않고 unmount/remount합니다. list reorder나 route param 처리에서 key를 잘못 주면 state 손실, effect 재실행, image/font 재로드, 큰 commit으로 INP 악화가 생길 수 있습니다.
TRAINING EVIDENCE React Profiler export, render count, flamegraph, memoization benchmark
Q07

list virtualization은 언제 필요한가요?

DOM node 수와 render cost가 사용자 기기에서 frame budget을 넘을 때 사용합니다.

무조건 virtualization을 넣으면 accessibility, find-in-page, dynamic height, scroll restoration이 어려워집니다.

꼬리질문꼬리질문 답변
동적 높이는?동적 높이는 측정 cache, estimated size, ResizeObserver, overscan 조정이 필요합니다. 높이 추정이 틀리면 scroll jump와 CLS처럼 보이는 이동이 생기므로 row measurement invalidation과 scroll restoration fixture를 둡니다.
SEO 콘텐츠에도 쓰나요?검색 노출이 중요한 본문이나 상품 목록의 핵심 콘텐츠에는 조심해야 합니다. crawler와 no-JS 환경에서 콘텐츠가 사라질 수 있으므로 SSR/SSG로 의미 있는 초기 목록을 제공하거나 페이지네이션을 우선 검토합니다.
가상 리스트에서 focus는?focus된 row가 unmount되지 않게 overscan과 active item 보존을 설계해야 합니다. keyboard 이동, screen reader announce, scroll restoration을 테스트하고, DOM에 없는 항목 수와 위치는 aria-setsize나 별도 상태로 설명합니다.
TRAINING EVIDENCE DOM node count, scroll FPS, virtualization fixture, a11y fallback
Q08

image optimization은 무엇을 포함하나요?

format, responsive srcset, intrinsic size, lazy loading, priority, CDN caching, decoding 전략을 포함합니다.

모든 이미지를 lazy로 두면 hero LCP가 늦어지고, 원본 해상도를 그대로 쓰면 네트워크 비용이 큽니다.

꼬리질문꼬리질문 답변
WebP/AVIF 선택은?AVIF는 압축률이 좋지만 인코딩 비용과 decode 지연이 있을 수 있고, WebP는 호환성과 decode 안정성이 좋습니다. 사진, 투명 이미지, 썸네일별로 byte size와 decode time을 비교하고 picture/source fallback을 둡니다.
lazy loading의 함정은?초기 viewport의 hero나 LCP 이미지를 lazy로 두면 브라우저가 요청을 늦게 시작합니다. fold 근처 이미지는 적절한 rootMargin이나 eager loading을 쓰고, below-the-fold만 lazy로 두어 waterfall에서 LCP request가 앞에 있는지 확인합니다.
priority는 언제 높이나요?초기 viewport에서 LCP 후보인 이미지나 poster처럼 사용자에게 첫 화면을 만드는 resource에만 높입니다. 여러 이미지에 fetchpriority high를 주면 CSS, font, JS와 경쟁해 전체 LCP가 느려질 수 있습니다.
TRAINING EVIDENCE image waterfall, LCP element audit, srcset test, CDN cache header
Q09

font가 성능에 미치는 영향은?

font file size, preload, display strategy, subset, fallback metric이 LCP와 CLS에 영향을 줍니다.

웹폰트를 늦게 로드하거나 fallback metrics가 다르면 텍스트가 밀리고 CLS가 생깁니다.

꼬리질문꼬리질문 답변
font-display swap은 항상 좋은가요?읽기 시작을 빠르게 하지만 fallback과 실제 font의 폭·높이가 다르면 텍스트 재배치가 생깁니다. 브랜드 font가 필수인 hero는 preload와 metric override를 쓰고, 본문은 system font fallback으로 LCP와 CLS를 안정화할 수 있습니다.
variable font는?여러 weight/style 파일을 하나로 줄이면 request와 cache 관리가 좋아질 수 있지만, 필요한 축보다 파일이 크면 오히려 손해입니다. 실제 사용하는 weight, unicode-range, compression 후 size를 비교하고 unused axis를 제거합니다.
한글 폰트 최적화는?한글은 glyph 수가 많아 subset과 unicode-range 전략이 중요합니다. 핵심 화면에 필요한 글자만 preload하고 나머지는 지연 로드하거나 system fallback을 쓰며, font waterfall과 CLS attribution으로 효과를 확인합니다.
TRAINING EVIDENCE font waterfall, font-display audit, CLS attribution, subset diff
Q10

third-party script는 어떻게 관리하나요?

비즈니스 가치, load timing, async/defer, sandbox, consent, long task 영향, 장애 격리를 봅니다.

analytics/chat script가 main thread를 막거나 개인정보 동의 전에 실행될 수 있습니다.

꼬리질문꼬리질문 답변
defer와 async 차이는?defer는 HTML parsing을 막지 않고 실행 순서를 보존하며 DOMContentLoaded 전에 실행됩니다. async는 다운로드 완료 즉시 실행되어 순서가 보장되지 않아 tag 간 의존성이 있거나 hydration 중 main thread를 빼앗으면 INP와 초기 렌더를 흔들 수 있습니다.
태그 매니저 위험은?코드 리뷰 밖에서 script가 추가되고 consent, CSP, performance budget을 우회할 수 있습니다. tag inventory, owner, trigger 조건, long task attribution, 개인정보 동의 상태를 정기적으로 점검해야 합니다.
서드파티 장애는 어떻게 격리하나요?timeout, async loading, iframe sandbox, consent gate, circuit breaker를 두고 핵심 UI render path와 분리합니다. third-party가 느리거나 실패해도 LCP element, checkout action, analytics queue flush가 멈추지 않는 fixture를 둡니다.
TRAINING EVIDENCE third-party inventory, long task attribution, consent test, script loading policy
Q11

Network waterfall에서 무엇을 읽나요?

DNS, TCP/TLS, TTFB, download, priority, blocking, request chain, cache hit/miss를 봅니다.

총 시간만 보면 우선순위 문제, render-blocking chain, cache 미스 원인을 놓칩니다.

꼬리질문꼬리질문 답변
TTFB가 크면 무조건 백엔드인가요?아닙니다. DNS/TLS, edge miss, redirect, server queue, SSR data fetch, auth middleware가 모두 TTFB에 포함될 수 있습니다. Server-Timing, CDN cache status, redirect chain을 같이 봐야 API 처리와 네트워크·edge 문제를 나눌 수 있습니다.
HTTP/2면 waterfall이 사라지나요?사라지지 않습니다. multiplexing으로 connection 병목은 줄지만 priority, request discovery, server push 오용, 큰 JS download 경쟁은 여전히 보입니다. waterfall에서는 resource가 언제 발견됐고 어떤 요청이 LCP resource를 밀었는지 봅니다.
cache hit은 어디서 보나요?DevTools size column의 memory/disk cache, response header의 Age, x-cache, cf-cache-status 같은 CDN header, RUM resource timing의 transferSize로 확인합니다. cache hit인데 느리면 main thread decode나 render delay도 같이 봐야 합니다.
TRAINING EVIDENCE HAR, DevTools waterfall, cache header, priority column

성능 budget 예외는?접근성 요구를 충족하기 위해 추가 DOM이나 text가 필요하다면 예외를 줄 수 있습니다. 대신 route별 Web Vitals 영향, 대체 최적화, keyboard/screen reader 증거를 남겨 품질 기준이 임의로 흔들리지 않게 합니다.
TRAINING EVIDENCE a11y/performance decision note, DOM count, keyboard test, RUM metric

대시보드 성능은 어떤 지표가 중요한가요?

initial load, filter interaction latency, chart render time, data refresh cost, memory growth를 봅니다.

첫 로드만 빠르고 필터 변경마다 전체 chart를 다시 그리면 업무 도구로는 느립니다.

꼬리질문꼬리질문 답변
차트가 많으면?초기 viewport chart만 먼저 렌더하고 나머지는 lazy render나 virtualization, canvas/WebGL batch rendering을 검토합니다. chart library bundle size, data transform cost, tooltip interaction INP, memory growth를 함께 측정합니다.
필터 변경 최적화는?filter input에는 immediate feedback을 주고 비싼 aggregation은 debounce, memoized selector, worker, server aggregation으로 분리합니다. 이전 결과 cache와 optimistic loading state를 쓰되 stale data 표시와 cancelation을 명확히 합니다.
자동 refresh는?polling 간격, tab visibility, user activity, network 상태에 맞춰 조절해야 합니다. refresh가 chart rerender와 API waterfall을 계속 만들면 INP와 memory가 나빠지므로 incremental update와 backoff, pause control을 둡니다.

한 번 최적화하고 끝내면 새 dependency나 UI 변경으로 금방 회귀합니다.

꼬리질문꼬리질문 답변

Q30

성능 최적화가 기능 회귀를 만들지 않게 하려면?

꼬리질문꼬리질문 답변
