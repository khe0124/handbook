프론트엔드 웹 서버 배포와
Nginx 설정·보안

빌드가 성공한 뒤 실제 사용자 요청이 안전하게 도착하기까지의 경계를 다룹니다. 정적 파일 서빙, SPA fallback, 캐시, 압축, API proxy, TLS, 보안 헤더, 권한, 로그와 rollback을 하나의 운영 흐름으로 연결합니다.

AUDIENCE : FRONTEND · PRODUCT ENGINEER · RELEASE OWNER · UPDATED 2026-09
WEB-01

배포 경계와 요청 흐름

프론트엔드 배포는 dist 폴더를 복사하는 작업이 아닙니다. DNS와 TLS를 거친 요청이 CDN 또는 Nginx에 도착하고, HTML·해시 자산·API 요청이 서로 다른 정책으로 처리되는 전체 경로를 설계하는 일입니다.

REQUEST PATHBrowser → DNS → CDN/LB → Nginx → HTML or hashed asset
Browser → Nginx /api/ → application upstream → database/external API
경계책임대표 실패
DNS·TLS올바른 endpoint와 인증서 제공인증서 만료, 잘못된 레코드, redirect loop
CDN·Nginx정적 파일, 캐시, 압축, route fallback오래된 HTML, chunk 404, 잘못된 MIME
API proxyupstream 연결, timeout, header 전달CORS, 무한 retry, client IP 유실
브라우저HTML과 chunk 조합 실행구 HTML이 삭제된 새 chunk를 요청
WEB-02

빌드 산출물과 서버 구조

빌드 산출물은 immutable artifact로 만들고, 서버에서 다시 빌드하지 않습니다. 같은 artifact를 환경별로 승격해야 재현과 rollback이 가능합니다.

항목기준증거
artifactcommit SHA와 build ID로 식별checksum, release manifest
환경값secret을 번들에 넣지 않음번들 문자열 검사, runtime config 정책
배포 디렉터리release별 디렉터리와 atomic symlink 전환current → releases/20260930-...
소유권Nginx worker는 읽기만 가능owner/group/mode 점검
중요

Vite의 VITE_* 같은 값은 빌드 시 JavaScript에 포함되어 사용자에게 공개됩니다. API key나 private token을 환경변수라는 이유만으로 넣으면 안 됩니다.

WEB-03

Nginx 정적 서빙 기본 설정

가장 작은 설정에서 시작해 server name, document root, index, MIME, access log를 명시합니다. 배포 전에는 반드시 nginx -t로 구문과 참조 파일을 검증합니다.

server {
    listen 80;
    server_name app.example.com;
    root /srv/frontend/current;
    index index.html;

    access_log /var/log/nginx/frontend.access.log;
    error_log  /var/log/nginx/frontend.error.log warn;

    location / {
        try_files $uri $uri/ /index.html;
    }
}
지시어의미주의
rootURI를 파일 경로에 결합업로드 경로와 섞지 않음
try_files파일 존재 여부 순서대로 확인API까지 index.html로 fallback하지 않음
server_name가상 호스트 선택default server의 의도치 않은 응답 차단
include mime.types확장자별 Content-TypeJS/CSS MIME 오류 확인
WEB-04

SPA 라우팅과 오류 처리

클라이언트 라우터의 URL은 서버 파일이 아닙니다. 존재하지 않는 실제 asset과 SPA route를 구분하지 않으면 누락된 JavaScript 요청에도 HTML이 200으로 반환되어 진단이 어려워집니다.

location /assets/ {
    try_files $uri =404;
    expires 1y;
    add_header Cache-Control "public, max-age=31536000, immutable";
}

location / {
    try_files $uri $uri/ /index.html;
}

location = /index.html {
    add_header Cache-Control "no-cache";
}
요청기대 응답이유
/orders/42index.html클라이언트 router가 해석
/assets/app.hash.js파일 또는 404HTML fallback 금지
/api/ordersupstream 응답SPA fallback과 분리
없는 일반 URL앱의 Not Found 화면HTTP status 전략은 SSR/SEO 요구와 별도 검토
WEB-05

캐시·압축·성능

HTML은 최신 배포를 가리켜야 하고, content hash가 있는 자산은 오래 캐시해야 합니다. 둘을 같은 정책으로 캐시하면 새 배포가 보이지 않거나 매 요청마다 자산을 다시 받습니다.

대상권장 방향검증
HTMLno-cache 또는 짧은 TTL재검증 후 최신 build ID 확인
해시 JS/CSS1년 + immutable같은 URL의 내용이 절대 바뀌지 않음
이미지·폰트해시 여부에 따라 장기 캐시CORS와 font MIME 확인
압축Brotli 또는 gzip, text 계열만Content-Encoding, Vary: Accept-Encoding
gzip on;
gzip_vary on;
gzip_min_length 1024;
gzip_types text/css application/javascript application/json image/svg+xml;
배포 호환성

새 release가 올라간 직후에도 이전 HTML을 가진 사용자가 있을 수 있습니다. 최근 release의 해시 asset을 일정 시간 보존하거나 CDN invalidation과 service worker 갱신 전략을 함께 설계합니다.

WEB-06

리버스 프록시와 API 경계

같은 origin의 /api/를 upstream으로 전달하면 브라우저 CORS 구성이 단순해집니다. 대신 path rewrite, timeout, 실제 client IP, protocol header의 책임이 Nginx로 이동합니다.

location /api/ {
    proxy_pass http://app_upstream;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_connect_timeout 3s;
    proxy_read_timeout 30s;
}
판단확인 질문실패 신호
pathproxy_pass의 trailing slash가 URI를 어떻게 바꾸는가upstream 404
timeout사용자 요청의 최대 정상 시간은 얼마인가무제한 대기 또는 성급한 504
retrymutation을 자동 재시도해도 멱등한가중복 주문·저장
WebSocket/SSEupgrade·buffering 정책이 필요한가연결 즉시 종료, 이벤트 지연
WEB-07

TLS와 보안 헤더

TLS 종료 지점과 보안 헤더의 소유자를 명확히 합니다. CDN과 Nginx가 동시에 같은 헤더를 덧붙이면 중복·충돌할 수 있으므로 실제 최종 응답을 기준으로 검증합니다.

add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
add_header Content-Security-Policy "default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'" always;
통제목적도입 방법
HTTPS redirect평문 전송 차단LB/CDN의 원본 protocol 인지 후 loop 확인
HSTS브라우저가 HTTPS만 사용전체 subdomain 준비 후 점진 적용
CSP스크립트·연결·frame 출처 제한Report-Only로 위반 수집 후 강제
frame-ancestorsclickjacking 방지실제 embed 요구와 함께 결정
server tokens불필요한 버전 노출 축소server_tokens off, 패치 대체 불가
CSP

'unsafe-inline'과 넓은 wildcard로 경고만 없애면 CSP의 방어력이 사라집니다. nonce/hash 또는 자체 호스팅으로 실제 실행 출처를 좁히고, 외부 analytics가 전송하는 데이터도 검토합니다.

WEB-08

서버 권한과 공격 표면

Nginx 설정만 안전해도 서버가 안전한 것은 아닙니다. worker 권한, 파일 쓰기 권한, directory listing, 숨김 파일, 관리 endpoint, 로그의 민감정보를 함께 제한합니다.

항목안전 기준검증
프로세스비특권 worker, 필요한 port만 노출process owner와 listening socket 확인
파일artifact read-only, Nginx가 배포 디렉터리에 쓰지 못함권한과 mount mode 확인
숨김 파일.git, .env, backup 파일 차단대표 경로에 404/403 확인
autoindex기본 비활성화디렉터리 URL에서 목록 미노출
로그token, cookie, 개인정보, query secret 제거샘플 로그 privacy review
rate limit로그인·고비용 endpoint 중심, 사용자 영향 측정429와 정상 burst 시나리오
