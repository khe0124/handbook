풀스택 개발 과정에
AI Agent와 AI Loop 적용하기

이 문서는 AI가 들어간 제품을 만드는 법이 아닙니다. 일반 풀스택 개발자가 요구사항 정의, 기획, 디자인, 개발, 테스트, 배포를 AI Native하게 수행하는 법을 다룹니다.

PERSONA : Full-Stack Developer using AI agents as work partners
ZERO

무엇을 AI Native하게 바꾸는가

핵심은 제품 안에 AI 기능을 넣는 것이 아닙니다. 내가 풀스택 기능을 만드는 과정 자체에 AI agent를 배치하고, 매 단계마다 AI Loop로 결과를 검증하는 것입니다.

단계기존 방식AI Native 방식
요구사항 정의요청을 읽고 바로 기능 목록을 만든다AI와 요구사항을 쪼개고 모호함, 누락, 엣지케이스를 뽑는다
기획대략적인 사용자 흐름을 정한다AI와 사용자 시나리오, 상태, 실패 흐름, 정책을 만든다
디자인화면을 보고 구현한다AI에게 UX 리스크, 빈 상태, 오류 상태, 접근성 누락을 검토시킨다
프론트엔드컴포넌트와 상태를 구현한다AI agent에게 초안을 맡기고 사람이 상태, 반응형, 접근성을 검증한다
백엔드API와 DB를 구현한다AI와 API 계약, 권한, 트랜잭션, 예외 케이스를 먼저 고정한다
테스트주요 성공 케이스를 테스트한다AI가 만든 테스트 후보 중 위험 케이스를 골라 회귀 테스트로 고정한다
릴리스빌드가 되면 배포한다AI와 릴리스 노트, 롤백 조건, 운영 체크리스트를 작성한다
한 문장 정의 AI Native 풀스택 개발자는 AI를 “코드 생성기”로만 쓰지 않고, 요구사항 분석가, UX 리뷰어, 구현 보조자, 테스트 설계자, 코드 리뷰어, 릴리스 서기 역할로 나누어 배치한다.
LOOP

AI Loop 기본형

AI Loop는 AI에게 한 번 물어보고 끝내는 것이 아닙니다. 매 단계에서 같은 루프를 반복합니다.

AI LOOP 목표 고정 → 맥락 제공 → AI 초안 생성 → 사람 검토 → 누락/위험 보강 → 실행 → 검증 → 기록
Loop 단계내가 하는 일AI agent에게 맡기는 일남기는 증거
목표 고정이번 단계의 완료 기준을 한 문장으로 정한다목표가 모호한지 질문 목록을 만든다task-brief.md
맥락 제공요구사항, 제약, 기존 코드, 금지 행동을 준다필요한 추가 맥락을 요청한다context-package.yaml
초안 생성작업 범위를 작게 나눈다요구사항, 화면 흐름, 코드, 테스트 초안을 만든다draft.md, diff
사람 검토정책, UX, 보안, 기존 계약 위반을 판단한다자체 체크리스트로 빠진 항목을 찾는다review-note.md
실행채택한 변경만 적용한다반복 작업, 보일러플레이트, 테스트 작성 보조commit diff
검증테스트, 빌드, 수동 확인을 실행한다실패 원인 후보와 수정안을 제안한다verification-log.md
기록거절한 제안과 남은 위험을 남긴다episode log 초안을 정리한다agent-episode-log.md
AGENT

풀스택 업무의 AI Agent 역할

하나의 만능 AI에게 “다 해줘”라고 시키면 결과가 흐려집니다. 역할을 나누면 위임과 검토가 쉬워집니다.

Agent 역할맡길 일맡기면 안 되는 일사람의 검토 기준
Requirements Analyst요구사항 분해, 질문 목록, 엣지케이스 후보비즈니스 우선순위 최종 결정진짜 사용자 문제와 비목표가 분리됐는가
Product Planner사용자 시나리오, 상태 전이, 실패 흐름스코프 확대 결정MVP와 후속 범위가 분리됐는가
UX Reviewer빈 상태, 오류 상태, 접근성, 모바일 흐름 점검브랜드/최종 디자인 결정사용자가 다음 행동을 이해하는가
Frontend Builder컴포넌트 초안, 상태 분기, 테스트 후보기존 디자인 시스템 무시반응형, 접근성, 로딩/에러가 맞는가
Backend BuilderAPI 계약, DB migration 초안, validation 후보권한 모델 변경을 임의 수행권한, 트랜잭션, idempotency가 안전한가
Test Critic테스트 케이스, 회귀 조건, 수동 QA 목록테스트 통과를 대신 보증실패 케이스와 경계값이 포함됐는가
Release Scribe릴리스 노트, 롤백 플랜, 변경 요약출시 승인위험, 검증, 롤백 조건이 명확한가
CASE

예시 기능: 백오피스 환불 승인 기능 만들기

AI 제품이 아니라 일반 백오피스 풀스택 기능을 예로 듭니다. 목표는 CS 운영자가 환불 요청을 검색하고, 주문/결제/고객 정보를 확인한 뒤 승인 또는 반려하며, 모든 판단이 감사 로그로 남는 기능입니다.

feature_request:
  title: "백오피스 환불 승인 기능"
  user:
    - "CS 운영자"
    - "정산 관리자"
    - "운영 리더"
  happy_path:
    - "운영자가 환불 요청 목록에서 상태와 기간으로 검색한다"
    - "주문 상세, 결제 내역, 고객 문의 사유를 확인한다"
    - "환불 가능 금액과 정책 위반 여부를 확인한다"
    - "승인 또는 반려 사유를 입력한다"
    - "상태 변경과 감사 로그가 저장된다"
  constraints:
    - "refund_manager 권한만 승인 가능"
    - "이미 처리된 요청은 재승인 불가"
    - "부분 환불은 결제 금액 이하만 가능"
    - "승인/반려에는 사유 입력 필수"
    - "모든 결정은 actor, target, before/after, reason으로 audit log 기록"
개발 산출물AI Loop 적용
요구사항 정의서AI가 누락 질문을 만들고 사람이 범위를 확정한다
사용자 흐름AI가 happy path와 실패 path를 나누고 사람이 MVP를 고른다
화면 설계AI가 테이블, 필터, 상세 drawer, 승인 confirm, 권한 없음 상태를 점검한다
API 계약AI가 endpoint와 에러 코드를 초안화하고 사람이 권한과 멱등성을 검토한다
DB 모델AI가 refund_requests, refund_decisions, audit_logs 후보를 만들고 사람이 상태 전이와 제약을 확정한다
테스트AI가 테스트 후보를 만들고 사람은 high-risk 케이스를 고정한다
릴리스AI가 릴리스 노트 초안을 만들고 사람은 롤백 조건을 확정한다

EX

구체 업무 예시

1. 요구사항 정의에 AI Loop 적용

prompt_to_requirements_agent:
  role: "Requirements Analyst"
  task: "백오피스 환불 승인 기능 요구사항에서 모호한 점과 누락된 엣지케이스를 찾아줘"
  context:
    - "CS 운영자가 환불 요청을 검색하고 상세를 확인한다"
    - "refund_manager 권한자가 승인 또는 반려한다"
    - "모든 결정은 감사 로그로 남긴다"
  output_format:
    - "clarifying_questions"
    - "edge_cases"
    - "non_goals"
    - "acceptance_criteria"
AI가 찾은 질문사람의 결정
이미 처리된 환불 요청을 다시 승인하면?409 already_processed
부분 환불 금액이 결제 금액보다 크면?400 invalid_refund_amount
권한 없는 운영자가 승인 버튼을 누르면?UI에서는 disabled, API에서는 403 forbidden
환불 승인 후 결제사 호출 실패가 나면?상태를 processing_failed로 남기고 재시도 큐와 운영 알림 생성

2. API 설계에 AI Loop 적용

api_contract:
  POST /api/admin/refund-requests/:requestId/approve
    auth: "refund_manager only"
    body:
      amount: number
      reason: string
    responses:
      200: refund_approved
      400: invalid_refund_amount_or_reason
      401: unauthenticated
      403: not_refund_manager
      409: already_processed

  POST /api/admin/refund-requests/:requestId/reject
    auth: "refund_manager only"
    body:
      reason: string
    responses:
      200: refund_rejected
      400: missing_reject_reason
      403: not_refund_manager
      409: already_processed

3. 디자인 검토에 AI Loop 적용

화면 상태AI가 점검할 질문사람이 확정할 기준
목록 기본 상태필터, 검색, 상태 badge, 금액/요청일이 스캔 가능한가상태/기간/담당자 필터 제공
상세 확인주문, 결제, 고객 사유, 이전 처리 이력이 한 화면에 연결되는가상세 drawer와 audit log panel 제공
승인 중중복 클릭과 실수 승인을 막는가confirm modal + button disabled
오류운영자가 조치할 수 있는 메시지인가already_processed와 payment_provider_failed 분리
권한 없음버튼만 숨기지 않고 이유가 보이는가읽기 전용 화면 + 권한 요청 안내

4. 테스트 설계에 AI Loop 적용

test_cases_selected_by_human:

BEST

나쁜 적용과 좋은 적용

Bad practice왜 문제인가Best practice
AI에게 “환불 승인 기능 만들어줘”라고 한다요구사항, 권한, 화면 상태, 테스트 기준이 섞인다요구사항 agent, UX agent, frontend/backend agent, test critic으로 나눈다
AI가 만든 코드를 바로 붙인다기존 디자인 시스템, API 계약, 권한 모델을 깨뜨릴 수 있다context package로 기존 규칙과 금지 행동을 먼저 준다
AI가 만든 테스트 목록을 전부 믿는다위험도 판단은 제품 맥락을 알아야 한다사람이 high-risk 케이스를 고르고 회귀 테스트로 고정한다
작업이 끝나면 대화창을 닫는다다음 기능에서 배운 점을 재사용할 수 없다accepted/rejected suggestion과 검증 명령을 episode log로 남긴다

항목기록 기준통과 기준
기준일평가 실행일, 사용 모델·도구 버전, 주요 정책·프롬프트 해시, 대상 코드 브랜치를 함께 남긴다.2026-07-09 기준으로 재실행자가 같은 입력과 버전을 확인할 수 있다.
평가셋/fixture정상 케이스, 경계값, 실패 유도 케이스, 보안·개인정보 케이스를 최소 3:1:1:1 비율로 둔다.fixture 이름, 입력, 기대 출력, 금지 출력, 소유자가 표로 연결된다.
metric threshold정확도, 누락률, hallucination, latency, cost, human override율 중 문서 목적에 맞는 지표를 고른다.핵심 경로 pass 95% 이상, 치명 실패 0건, p95 latency와 비용이 사전 budget 안에 있다.
승인 기준제품 책임자, 엔지니어, 보안/운영 검토자가 보는 evidence packet을 분리한다.각 승인자가 pass/fail 사유와 남은 예외를 한 줄로 남긴다.
rollback 기준오답 누적, 비용 초과, 개인정보 노출, 권한 없는 자동 실행을 즉시 중단 조건으로 둔다.feature flag, 이전 prompt/model, 수동 처리 루트, 사용자 공지 문안이 준비되어 있다.
