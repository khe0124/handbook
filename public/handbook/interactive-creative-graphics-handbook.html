Creative Graphics

표현 요구를 가장 작은 충분한 렌더링 모델로 바꾸는 법

INTERACTIVE WEB MASTERY · UPDATED 2026-10
START

렌더러를 선택한다는 것

Creative Graphics의 핵심은 가장 강력한 API를 고르는 일이 아니다. 표현 요구, 다뤄야 할 객체와 픽셀의 양, 상호작용과 접근성, 기기별 비용을 만족하는 가장 작은 충분한 모델을 고르는 일이다.

제품 제목과 버튼을 WebGL texture로 그릴 수도 있고, 수천 개 입자를 DOM element로 만들 수도 있다. 둘 다 기술적으로 가능하지만 좋은 선택은 아니다. 전자는 의미·선택·검색·focus를 다시 구현하게 만들고, 후자는 각 element의 style·layout·paint 관리 비용을 늘린다. 렌더러는 결과 이미지뿐 아니라 브라우저와 팀이 떠안는 책임의 형태를 결정한다.

CORE MODEL

요구 → 장면 모델 → 렌더러 → 자원 → 프레임 → 지각 가능한 결과로 생각한다. 먼저 텍스트·도형·픽셀·3D 공간 중 무엇을 표현하는지, 객체가 개별 의미와 focus를 가져야 하는지, 매 프레임 얼마나 많이 바뀌는지 적는다. 그다음 CPU가 객체를 관리할지 GPU가 정점을 병렬 처리할지 정하고, 메모리·draw call·fill rate·접근성 비용을 측정한다. Three.js와 shader는 이 판단을 대신하지 않고 GPU 경로가 필요한 문제를 더 높은 추상화와 직접적인 픽셀 규칙으로 확장한다.

먼저 묻는 질문선택에 미치는 영향
콘텐츠가 읽고 선택하고 검색해야 하는 정보인가?DOM 또는 DOM overlay를 우선한다.
각 도형을 개별 선택·focus·event 대상으로 다뤄야 하는가?작은 수라면 SVG가 자연스럽다.
수천 개 2D sprite가 매 프레임 바뀌는가?Canvas 2D의 한 bitmap surface가 유리할 수 있다.
3D projection, 대량 정점, texture sampling, custom effect가 필요한가?WebGL과 shader가 후보가 된다.
대규모 compute와 명시적 GPU pipeline 관리가 핵심인가?지원 환경과 fallback을 확인한 뒤 WebGPU를 검토한다.
01

다섯 렌더링 모델은 무엇이 다른가

DOM→SVG→Canvas→WebGL→WebGPU는 단순한 상위·하위 기술 순서가 아니다. 화면을 기억하고 갱신하는 주체와 개발자가 책임지는 범위가 다르다.

DOM + CSS브라우저가 의미 있는 element, layout, style과 접근성 tree를 관리한다.
SVG브라우저가 vector shape와 path를 retained scene처럼 기억한다.
Canvas 2D명령을 실행해 bitmap에 즉시 그린다. 그린 객체는 앱이 기억한다.
WebGLbuffer, texture, shader와 draw call로 GPU raster pipeline을 제어한다.
WebGPUrender·compute pipeline, bind group, command encoding을 더 명시적으로 구성한다.
모델화면의 기본 단위브라우저가 보존하는 것개발자가 추가로 책임지는 것
DOMsemantic element와 boxtree, layout, event, accessibility합리적인 구조와 style 변화
SVGvector shape/path각 shape의 속성·hit target복잡한 path와 node 수 관리
Canvas 2Dpixel buffer최종 bitmapscene state, redraw, hit testing, semantics
WebGLvertex와 fragmentGPU context와 저수준 자원pipeline state, shader, 자원 생명주기
WebGPUbuffer·texture·pipeline·commandGPU device 인터페이스명시적 pipeline, binding, synchronization 구조
Retained와 Immediate

DOM과 SVG는 “이 객체가 존재한다”는 모델을 브라우저가 보존하는 retained mode다. Canvas는 그리기 명령 뒤 객체를 기억하지 않는 immediate mode이므로 위치, z-order, hover 대상, 다시 그릴 방법을 앱이 별도로 보존한다. WebGL과 WebGPU도 GPU에 데이터를 올리지만 제품의 의미 있는 scene과 상호작용 모델은 애플리케이션 또는 engine이 소유한다.

02

DOM과 CSS: 의미 있는 인터페이스의 기본값

DOM은 “그래픽이 약한 렌더러”가 아니라 텍스트, 문서 흐름, control, 반응형 layout과 접근성을 함께 다루는 고수준 UI 모델이다.

브라우저는 element tree를 바탕으로 style을 계산하고 box geometry를 배치한 뒤 paint와 compositing을 수행한다. 모든 style 변경이 같은 비용을 내지는 않는다. width 변경은 주변 layout을 다시 계산할 수 있지만 transform과 opacity는 이미 그려진 layer를 합성하는 경로를 탈 수 있다. 다만 layer 승격도 texture memory를 쓰므로 will-change를 무제한 붙이는 것은 해결책이 아니다.

DOM이 맞는 사례

스크롤 기반 editorial 페이지의 제목, 본문, 링크, CTA는 DOM에 둔다. CSS transform과 clip-path로 충분한 reveal을 만들면 텍스트 선택, 반응형 줄바꿈, screen reader와 검색을 그대로 얻는다.

DOM이 무거워지는 사례

별빛 배경을 위해 8,000개의 div를 생성하고 매 frame 각각 style을 갱신한다. 의미 없는 node가 style·memory·event 관리 대상이 되어 표현보다 객체 관리 비용이 커진다.

DOM을 우선할 때다른 모델을 검토할 신호
텍스트·폼·navigation·focus가 핵심의미 없는 동종 객체가 수천 개
콘텐츠 크기에 따른 자연스러운 layout 필요모든 pixel을 매 frame 직접 갱신
개별 element의 semantics와 event 필요3D projection이나 per-pixel effect가 핵심
03

SVG: 도형이 곧 객체인 벡터 장면

SVG는 선, 원, path, text를 해상도와 독립적인 vector 객체로 보존한다. 각 도형이 DOM node이므로 style, event, focus와 접근성 정보를 연결할 수 있다.

viewBox는 SVG 내부 좌표계를 viewport에 mapping한다. path의 d는 선과 곡선의 geometry이며, fill은 내부를, stroke는 윤곽을 그린다. 확대해도 기하를 다시 rasterize하므로 로고, 아이콘, diagram처럼 선명한 모양에 적합하다. 반면 수천 개 node나 매우 복잡한 path를 계속 morph하면 DOM 관리와 path 계산 비용이 늘어난다.

좋은 사례 · 지하철 노선도역과 노선은 개별 path와 circle이다. 역 focus, 이름 label, 선택 상태를 객체에 연결하고 확대해도 선명하다.
좋은 사례 · 데이터 차트막대 수가 제한적이고 각 값에 tooltip·keyboard 탐색·label이 필요하면 SVG의 객체성이 유용하다.
경계 사례 · 대량 scatter plot점이 수만 개가 되면 node 하나씩 관리하기보다 Canvas 또는 GPU에서 점을 batch하고 별도 접근 가능한 요약을 제공한다.

SVG morph가 가능한 조건

두 path 사이를 자연스럽게 보간하려면 command 구조와 점의 대응이 호환되어야 한다. 단순히 모양이 비슷하다고 중간 path가 의미 있게 만들어지는 것은 아니다. shape normalization이나 동일 topology가 필요한 이유다.

04

Canvas 2D: 한 표면을 다시 그리는 모델

Canvas 2D는 element를 쌓는 대신 하나의 bitmap에 선, 도형, 이미지와 text를 그린다. 객체 수가 많아도 DOM node 수는 늘지 않지만 scene과 interaction은 직접 관리해야 한다.

State입자 위치·속도·색을 JS 배열에 보존
Clear이전 frame의 pixel을 지우거나 trail을 남김
Update시간과 입력으로 state 계산
Drawcontext 명령으로 전체 또는 dirty region 그림
RepeatrequestAnimationFrame으로 다음 frame 예약

CSS size와 backing-store size를 구분해야 한다. 화면에서 500×300 CSS pixel인 canvas를 device pixel ratio 2에서 선명하게 만들려면 내부 buffer를 1000×600으로 만들고 좌표계를 보정한다. 그러나 DPR을 그대로 무제한 적용하면 면적 비용은 비율의 제곱으로 커진다.

bufferWidth = cssWidth × cappedDPR bufferHeight = cssHeight × cappedDPR pixelCount = cssWidth × cssHeight × cappedDPR²
Canvas가 잘하는 것직접 해결해야 하는 것
particle, brush, game sprite, dense chart의 대량 2D draw각 객체의 hit testing과 z-order
image pixel 조작과 합성 모드keyboard focus와 screen reader용 의미 구조
한 surface로 빠르게 다시 그리는 장면resize, DPR, pause/resume, state 보존
흔한 오해

Canvas가 항상 DOM보다 빠른 것은 아니다. 정적인 버튼 열 개는 DOM이 더 단순하고, 매 frame 전체 화면을 다시 칠하는 고해상도 Canvas는 fill 비용이 클 수 있다. “객체가 많다”뿐 아니라 얼마나 자주, 얼마나 넓은 pixel이 바뀌는지 측정한다.

05

GPU 파이프라인을 한 장으로 이해하기

WebGL과 WebGPU를 이해하려면 “3D 라이브러리”보다 CPU가 데이터를 준비하고 GPU가 많은 정점과 pixel을 병렬 계산한다는 경계를 먼저 이해해야 한다.

CPU statescene, camera, animation, input 결정
Buffersposition, normal, UV, index를 GPU로 전달
Vertex stage각 정점을 clip space 위치로 변환
Rasterizationtriangle이 덮는 fragment 후보 생성
Fragment stagetexture·빛·효과로 최종 색 계산
Outputdepth, blend를 거쳐 framebuffer에 기록

GPU는 “객체 하나”를 이해하지 않는다. vertex buffer와 pipeline state를 이용해 primitive를 그리고 fragment를 계산한다. 3D model이 화면에 보이는 과정은 보통 local 좌표를 world, view, clip 공간으로 변환하는 행렬 곱을 거친다. clip 좌표는 perspective divide 후 normalized device coordinates가 되고 viewport에 mapping된다.

clipPosition = projectionMatrix × viewMatrix × modelMatrix × localPosition screen ← perspective divide(clipPosition)
데이터의미예
Attribute / vertex buffer정점마다 다른 입력position, normal, UV, instance offset
Uniform한 draw 동안 공유되는 값time, camera matrix, mouse, color
Texture좌표로 조회하는 2D/3D 데이터image, normal map, previous render result
Varying / interpolantvertex 결과가 triangle 내부에서 보간되어 fragment로 전달UV, color, transformed normal
06

WebGL: 브라우저의 raster GPU API

WebGL은 JavaScript에서 GPU raster pipeline을 사용하게 하지만 scene, camera, light나 object라는 개념을 기본 제공하지 않는다. buffer, shader program, texture와 상태를 묶어 draw call을 만드는 API다.

하나의 mesh를 그리려면 geometry 데이터를 buffer에 올리고, vertex/fragment shader를 compile·link하고, attribute와 uniform을 연결하고, texture와 blend/depth 상태를 정한 뒤 draw를 요청한다. 이 저수준 구성이 반복되기 때문에 일반 제품은 Three.js 같은 engine을 사용한다. 그래도 WebGL의 비용 모델을 알아야 engine 사용 중 병목을 설명할 수 있다.

CPU 병목

객체마다 material과 상태를 바꾸며 수천 번 draw call을 보낸다. GPU가 빠르더라도 JavaScript→driver 명령 제출과 scene update가 frame budget을 소모한다.

대안: batching, instancing, shared material, culling.

GPU 병목

전체 화면 transparent layer를 여러 번 그리고 복잡한 fragment shader와 고해상도 texture를 사용한다.

대안: DPR cap, pass 축소, shader 단순화, texture 압축·해상도 조절.

Context loss는 예외가 아니라 복구 경로다

GPU context가 사라지면 buffer, texture, program 같은 자원을 다시 만들어야 한다. 애플리케이션의 원본 state와 asset을 GPU 자원과 분리해 두고, context loss 동안 fallback을 보여주며 restore 시 재업로드할 수 있어야 한다.

07

WebGPU: 더 명시적인 render와 compute

WebGPU는 WebGL의 단순한 “더 빠른 버전”이 아니다. modern GPU의 render·compute 능력을 명시적인 pipeline과 command 구조로 노출하는 다른 프로그래밍 모델이다.

개념역할WebGL 사고에서 달라지는 점
Adapter / DeviceGPU 기능을 요청하고 자원을 생성하는 진입점지원 기능과 limit을 명시적으로 협상
Render pipelineshader, vertex layout, blend, depth 형식을 미리 묶음draw 도중 암묵적으로 상태를 계속 바꾸기보다 pipeline을 준비
Bind groupshader가 읽을 buffer, texture, sampler의 묶음resource binding 구조가 선언적이고 검증 가능
Command encoderrender/compute 작업을 기록해 queue에 제출명령 생성과 GPU 실행의 경계가 더 명확
Compute pass화면 triangle과 무관한 병렬 계산particle simulation, image processing, data transform을 GPU에서 수행

WebGPU를 선택할 기준은 로고에 gradient를 넣고 싶어서가 아니다. 대규모 simulation, compute와 render의 결합, 자원과 pipeline 제어가 프로젝트의 핵심일 때 복잡성 비용을 지불할 가치가 생긴다. 도입 전에는 feature detection, secure context, 대상 브라우저와 기기, adapter/device 요청 실패, device loss, WebGL 또는 정적 fallback을 실제 배포 환경에서 검증한다.

Progressive enhancement

필수 콘텐츠와 구매·탐색 흐름을 WebGPU 초기화 성공에 묶지 않는다. GPU 장면은 능력이 확인된 뒤 강화하고, 실패하면 DOM 이미지·video·Canvas·WebGL 등 제품에 맞는 낮은 단계로 내려간다.

08

객체 수만 세면 안 되는 이유

성능은 “WebGL이 빠르다” 같은 기술 이름이 아니라 CPU 작업, 명령 수, geometry, pixel, 메모리와 전송량의 조합이다.

비용무엇을 뜻하나증상대표 대응
DOM/SVG nodestyle·layout·event·접근성 객체 관리많은 개별 element 갱신 시 CPU frame 증가node 축소, 변화 격리, Canvas/GPU batch 검토
Draw callCPU가 GPU에 한 묶음의 그리기 명령 제출작은 mesh가 많고 material 전환이 잦을 때 CPU 병목instancing, batching, material 공유
Triangle / vertexvertex stage와 rasterization 입력량고밀도 mesh, 화면 밖 객체도 처리LOD, culling, geometry 단순화
Fill rate / overdraw실제로 계산·기록하는 fragment의 양과 중복고DPR, fullscreen effect, transparency에서 GPU 병목DPR cap, 영역 축소, pass·투명 layer 축소
Texture memoryGPU에 상주하는 image/render target 용량모바일 crash, upload hitch, device loss크기·format·mipmap 검토, 압축, dispose
Shader complexityfragment/vertex마다 수행하는 연산과 sampling해상도 증가 시 급격한 frame 저하분기·sample·loop 축소, 계산 단계 이동
rawTextureBytes ≈ width × height × bytesPerPixel × mip/face/layer count frameBudget at 60fps ≈ 16.7ms (JavaScript + style/layout + raster + GPU + presentation)

FPS 하나만 보지 않는다. CPU main-thread time, GPU frame time, draw call, triangle, texture memory, 긴 frame의 빈도와 저성능 기기 온도·전력까지 함께 본다. 평균 60fps여도 첫 interaction에서 shader compile 때문에 멈추거나 scroll 중 간헐적으로 50ms frame이 생기면 사용 경험은 불안정하다.

09

Three.js는 WebGL 위에서 무엇을 하는가

Three.js는 GPU를 없애지 않는다. WebGL/WebGPU의 buffer와 shader 자원을 scene graph, geometry, material, camera, light, renderer라는 작업 단위로 조직한다.

Scene그릴 object hierarchy의 root
Cameraworld를 어느 위치·projection으로 볼지 정의
Geometryposition, normal, UV, index buffer 데이터
Material어떻게 표면을 그릴지 정하는 shader·state 묶음
Meshgeometry와 material을 transform에 결합
Rendererscene을 순회해 GPU 명령과 자원을 관리

scene graph의 parent transform은 child에 누적된다. camera도 object이지만 화면을 그리는 관점으로 사용한다. geometry를 여러 mesh가 공유할 수 있고, material도 공유하면 자원과 상태 전환을 줄일 수 있다. 반대로 component가 unmount될 때 texture·geometry·material을 무조건 따로 만들고 dispose하지 않으면 GPU memory leak이 생긴다.

기능내부 의미비용 질문
Raycasterpointer를 NDC ray로 바꾸고 geometry와 교차 검사매 frame 모든 mesh를 검사하는가? spatial partition이 필요한가?
InstancedMesh같은 geometry/material을 transform만 달리해 적은 draw로 반복개별 material 차이가 정말 필요한가?
RenderTarget화면 대신 texture에 장면을 렌더링해상도와 format만큼 추가 memory·fill을 쓰는가?
Post-processing이전 pass 결과를 fullscreen shader로 다시 처리pass마다 화면을 다시 읽고 쓰는 비용을 감당하는가?
Loading managerasset 요청의 진행과 오류를 집계장면 초기화 전 콘텐츠를 막는가? 실패 fallback이 있는가?
React와 Three.js

React state가 바뀔 때마다 geometry와 material을 새로 만드는 구조를 피한다. 선언적 scene library를 쓰더라도 매 frame 값은 render loop와 ref/uniform 경계에서 관리하고, 제품 state와 GPU resource lifetime을 구분한다.

10

Shader 사고법: 픽셀을 그리는 규칙

Shader는 “멋있는 효과 코드”가 아니라 수많은 정점 또는 fragment에 같은 작은 함수를 병렬 적용하는 프로그램이다. 먼저 입력 공간과 출력 의미를 정한다.

Vertex shader: 모양과 위치를 바꾼다

vertex shader는 각 정점의 최종 clip position을 계산한다. 시간과 UV에 sine을 적용해 plane을 물결치게 하거나, instance별 offset으로 수천 객체를 배치할 수 있다. 단, 정점 사이 표면은 보간되므로 geometry subdivision이 부족하면 부드러운 displacement가 나오지 않는다.

// 개념 예시: local position을 변형한 뒤 화면 좌표로 보낸다.
vec3 displaced = position;
displaced.z += sin(displaced.x * frequency + uTime) * amplitude;
gl_Position = projectionMatrix * modelViewMatrix * vec4(displaced, 1.0);

Fragment shader: 각 fragment의 색을 결정한다

fragment shader는 보간된 UV·normal·position과 texture/uniform을 이용해 색과 alpha를 계산한다. image distortion은 보통 geometry를 움직이는 대신 UV를 변형한 뒤 texture를 다른 위치에서 sampling한다.

// 개념 예시: pointer 근처에서 UV를 밀어 이미지를 왜곡한다.
float influence = smoothstep(radius, 0.0, distance(vUv, uPointer));
vec2 warpedUv = vUv + uDirection * influence * strength;
vec4 color = texture2D(uTexture, warpedUv);
gl_FragColor = color;
도구무엇을 표현하나사례
UVgeometry 표면의 0–1 texture 좌표image crop, distortion, atlas sampling
Normal + dot product표면 방향과 빛/시선 방향의 정렬 정도diffuse light, rim light, facing mask
sin/cos반복과 진동wave, orbit, pulse
Noise연속적이지만 규칙적이지 않은 fieldflow, dissolve edge, terrain displacement
SDF점에서 경계까지의 signed distance해상도 독립 shape, outline, smooth union
Render feedback이전 frame을 다음 frame의 입력으로 사용trail, fluid-like persistence
Shader 디버깅 순서

검은 화면이면 효과를 더 붙이지 않는다. geometry와 camera가 보이는지 → UV를 색으로 출력할 수 있는지 → texture가 읽히는지 → uniform이 갱신되는지 → 한 연산씩 추가했을 때 NaN·범위·precision 문제가 없는지 확인한다.

11

접근성과 혼합 구성

GPU scene이 있다고 페이지 전체를 canvas 안에 넣을 이유는 없다. 의미와 조작은 DOM에, 대량 시각 표현은 적합한 surface에 두는 혼합 구성이 흔한 정답이다.

층책임예
Semantic DOM제목, 설명, form, link, focus, 상태 알림제품 configurator의 option과 가격
Graphics surface제품 preview, particle, 3D model, 장식선택에 따라 변하는 신발 3D scene
Interaction adapterpointer/keyboard 입력을 제품 state로 정규화canvas drag와 회전 버튼이 같은 camera target 변경
FallbackGPU 실패·저전력·motion 축소에서도 핵심 목표 유지정적 이미지 gallery와 동일한 구매 option

Canvas 자체에 대체 설명 한 줄을 붙이는 것만으로 복잡한 interactive chart가 접근 가능해지지는 않는다. 핵심 insight 요약, 데이터 table, keyboard로 가능한 filter, 현재 선택 상태를 DOM으로 제공한다. 장식 그래픽은 보조 기술에서 숨기고 콘텐츠를 중복 낭독하지 않는다.

Canvas가 제품 전체를 소유

제목, 버튼, 가격까지 texture로 그린다. 텍스트 선택, 확대 reflow, focus, screen reader, 번역과 자동화 테스트를 모두 다시 구현해야 한다.

의미와 표현의 책임 분리

DOM이 정보와 control의 source of truth이고 GPU scene은 같은 state를 시각화한다. 그래픽이 꺼져도 구매 흐름과 상태 이해가 남는다.

요구선택이유

사례 B · 캠페인 hero

한 줄의 kinetic headline과 몇 개 shape라면 DOM+CSS 또는 SVG로 시작한다. 이미지 표면이 pointer에 따라 유동적으로 왜곡되고 여러 layer가 빛·depth와 결합된다면 WebGL shader의 가치가 생긴다. 그래도 headline과 CTA는 DOM에 남기고, reduced motion에서는 distortion을 멈춘 정적 composition을 제공한다.

사례 C · 제품 3D configurator

Three.js scene에 model, camera, environment light와 material variant를 구성한다. UI option은 DOM button이며 선택 state가 material uniform/texture를 바꾼다. 초기 model이 크면 poster image를 먼저 보여주고, progress와 실패 fallback을 제공한다. 보이지 않는 variant texture를 모두 최고 해상도로 선로드하지 않고 사용 흐름에 맞춰 요청한다.

사례 D · 10,000개 particle

각 particle이 semantic object가 아니므로 DOM 10,000개는 피한다. 단순 2D이면 Canvas batch가 충분할 수 있다. 3D depth, per-particle GPU animation, post effect가 필요하면 WebGL instancing 또는 point rendering으로 이동한다. WebGPU compute는 particle 간 simulation과 대규모 병렬 갱신이 실제 병목일 때 비교한다.

DECIDE

렌더러 의사결정 절차

  1. 의미를 분리한다. 읽고 선택하고 focus할 콘텐츠와 순수 시각 표현을 구분한다.
  2. 장면 단위를 정한다. box, vector shape, 2D pixel/sprite, vertex/triangle, compute data 중 무엇인가?
  3. 규모와 변화율을 센다. 객체 수뿐 아니라 매 frame 변경 수, 덮는 pixel 면적, 해상도와 pass 수를 적는다.
  4. 최소 후보를 prototype한다. DOM/SVG로 충분하면 거기서 멈춘다. 부족한 요구가 명확할 때 Canvas/GPU로 이동한다.
  5. 의미와 입력 fallback을 설계한다. keyboard, screen reader, reduced motion, GPU 실패 경로를 먼저 적는다.
  6. 대상 기기에서 측정한다. CPU/GPU frame, draw call, memory, load/compile hitch, 전력과 열을 비교한다.
