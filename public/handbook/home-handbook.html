STANDARD — 하은

판단이 흔들릴 때 돌아와 대조하는 좌표. 2026.08 / 2~7월 관찰 기록 기반

깊이 본 것을 여러 매체로 옮기는 사람.
감지가 먼저 오고, 구조가 따라오고, 만들면서 확신이 생긴다.

이 문서의 구조 — 아래는 병렬 목록이 아니라 인과 사슬이다. 배선 → 방향 → 결과 → 실패 동역학 → 규칙 → 순서. 어떤 항목이 이상하면 한 층 위로 올라가서 원인을 확인할 것.

2. 방향 — 무엇이 움직이게 하는가

파생되는 성질
D1 authorship회사 이름이 아니라 내 이름결과물에 자기를 투영한다
D2 공공적 의미의료→공유경제→재생에너지→기후의미가 없으면 착수 자체가 안 된다
D3 안정목적이 아니라 토대회사에서 얻는 건 도메인·근육·월급·시간
구조적 미스매치 (가장 중요한 한 줄)

D1은 인정을 연료로 쓰는데, 선택한 길(1인 브랜드)은 인정이 가장 늦게 오는 길이다.
→ 임계점 도달 전에 방전될 위험이 상시 존재한다. D2를 보조 연료로 의식적으로 쓸 것.
→ 요시무라 히로시식 "조용히 오래 쌓기"는 인정 없이 견디는 체질을 전제한다. 태도는 동경하되 연료 설계는 다르게.

3. 결과 — 강점과 약점은 같은 뿌리에서 나온다

뿌리강점으로약점으로
W1 해상도품질의 마지노선끝을 못 정함 · 위임 불가
W2 구조화어떤 도메인이든 진입 가능—
W3 새로움5중 교집합의 희소성트랙 과다 · 깊이 미달
W4 무확신 실행확신이 깨져도 엔진이 안 멈춤—
W5 재정의 회복슬럼프가 짧다혼자면 회복이 안 된다
W6 정확도 선호빠른 자기 교정자기비판 루프
W7 손의 확신사변에 안 갇힌다착수 전 설계가 약함
D1 authorship만든 것의 밀도공개 지연 · 비판 과잉반응
D2 의미방향의 일관성의미 없으면 아무것도 못 함
그래서 제1원칙: 고치지 말고 배치한다.

교정은 강점까지 같이 죽인다. 약점이 발현되는 환경을 안 만드는 쪽이 잘 작동한다.

4. 축적된 자산

산업디자인 · 콘텐츠 에디팅 · 프론트 7년 · 백엔드 실구현 · 탄소 도메인
각각은 흔하다. 다섯이 한 사람 안에서 현역으로 도는 건 드물다.
W3(새로움에 끌림)이 보통은 산만함으로 끝나는데, 여기서는 전환이 리셋이 아니라 적층이었다.

  • 언어 정밀도 — 기획·개발 실패의 대부분은 코드가 아니라 정의의 부정확에서 온다
  • 자기 명제 — 기술은 따라잡히지만 자기 언어는 안 따라잡힌다
  • 정합성 책임 경험 — VRC 원장, 락, 단일 트랜잭션
  • 심미 기준선 — 훈련으로 안 생긴다
  • 도메인 일관성 + 규제 타이밍(2027~28)
비대칭 진단

T(기술)가 A(비주얼 결과물)를 한참 앞서 있다. 반대보다 희소한 형태지만, 방치하면 도달점이 툴 엔지니어가 된다.

전부 안 보인다는 게 진짜 문제. 위축의 원인은 실력 차가 아니라 공개 여부였다.
지금은 늘리는 단계가 아니라 꺼내는 단계.

5. 실패 동역학

루프

비교 → 확신 하락 → 착수 지연 → 결과물 없음 → 자기비판 → 확신 더 하락
→ 그리고 여기서 새 트랙을 연다 (통제감이 돌아와 회복처럼 느껴지지만 실제로는 부채 증가)

약해질 때 나는 멈추는 게 아니라 벌린다. 이게 유일하게 자가 진단이 안 되는 실패 모드다.

트리거 — 내가 하려던 자리에 이미 선 사람의 완성작(최강) / 새 영역 진입 직후 / 트랙 3개 초과 / 종료 경험 없이 오래 / 몰입 직후(저항력 최저)
→ 첫 번째를 마지막 상태에서 만나면 위력이 몇 배.

경보 (둘 이상이면 이미 방전)
  • 우선순위에 "전부"라고 답한다
  • 남의 작업물을 자주 본다
  • 새 커리큘럼을 짜고 싶다
  • 식사·수면을 미룬다
  • "정리해줘" 요청이 잦다
  • 사람들이 답답하다 ← 관계 신호 아님, 컨디션 신호

회복

  • 에너지 낮을 때 떠오른 계획은 실행 금지. 메모하고 2주 뒤에 다시 본다 → 5장 루프 차단

7. 순서 — 무엇을 먼저 하는가

2층 구조를 혼동하지 않는다.

층내용조건
바닥검증 가능한 작업 케이스지금 여기
지붕취향·기록·에세이 아카이브바닥이 생긴 뒤

동경하는 형태(취향만 올려도 읽히는 아카이브)는 커리어를 만든 방법이 아니라 만들어진 뒤의 결과물이다. 지붕부터 올리면 그냥 개인 블로그가 되고, 케이스 위에 올리면 작가의 목소리가 된다.

케이스 하나 = 2~4주 = 검증된 완주 단위. 이 형식은 W1·D1을 동시에 우회한다. 완료 조건이 형식에 있고, 받는 사람이 바깥에 있기 때문.

무대 선택

비핸스의 통화는 비주얼이다. 가장 약한 축으로 가장 경쟁 심한 시장에 들어가는 것.
팔 수 있는 건 "이 화면이 예쁘다"가 아니라 "이 복잡한 도메인이 이해 가능한 형태가 됐다".
→ 케이스 스터디 · 인터랙티브 설명 · 개인 사이트. (Appleton / Wattenberger 좌표)

취향을 인프라로 바꾼다

1px을 매번 손으로 고치는 건 아티스트의 일이고, 다시는 어긋날 수 없게 만드는 것(토큰·린트·계약·검증기)이 내 일이다.
→ 시스템은 완결 조건이 명확해서 W1 문제도 같이 해결된다.

9. 검증

이건 진단서가 아니라 가설 묶음이다. 근거는 전부 "목표 앞에 섰을 때의 나"에서 나왔고, 일과 무관한 영역의 나는 다르게 움직일 수 있다. (특히 W5·W6은 표본이 적다)

  • 분기마다 열어서 틀린 항목을 지우고 실제로 관찰된 걸 적는다
  • 지울 때는 근거를 같이 적는다 — "이 분기에 X를 했는데 예측과 달랐다"
  • 1층(배선)은 잘 안 바뀐다. 자주 바뀌는 건 3층 이하다. 1층이 자주 바뀌면 관찰이 틀린 것.

기준선은 발견하는 게 아니라 쌓는 것.

AI Native 개발자 역량 지도

이 핸드북의 큰그림은 많은 기술을 나열하는 것이 아니라, 기능 하나를 끝까지 책임지는 개발자를 만드는 것입니다. 기본기, 제품 구현, 운영 책임, AI Native 실행, 사용자 경험, 반복 작업 자동화, 커리어 증거가 서로 끊기지 않아야 합니다.

역량 층담당하는 질문이 핸드북에서 확인할 문서남겨야 할 증거
기본기왜 이 구조가 맞고 어디서 깨지는가CS 기초, 컴퓨터 시스템, 언어 런타임, 응용 수학·측정복잡도 판단, resource trace, benchmark evidence, 불변식 설명
제품 구현사용자 흐름이 UI, API, DB 상태로 안전하게 닫히는가프론트엔드 데이터·상태·폼, TypeScript·JavaScript 런타임, 백엔드 핵심, 데이터 계층UI state model, schema boundary, API contract, transaction boundary, 테스트 결과
운영 책임배포 후 문제가 생기면 어떻게 감지하고 되돌리는가인프라·운영, 런타임 품질, 플랫폼 도구runbook, log/metric/trace, rollback plan, incident note

완료 산출물 지도 보강

각 트랙은 읽은 분량이 아니라 제출 가능한 산출물로 완료를 판단한다. 모든 완료 산출물은 빈 템플릿, 채워진 예시, 자가검수 기준 중 최소 2개 이상으로 연결되어야 한다.

자가검수

트랙 완료 전 “이 산출물을 다른 사람이 보고 재현·검토·승인할 수 있는가?”를 확인한다. 이름만 있는 checklist나 packet은 완료로 보지 않고, 최소 한 개의 완성 예시와 빈 템플릿을 연결한다.
