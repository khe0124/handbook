CLD-00

웹 서비스 기본 구성

AWS와 Azure 서비스는 이름을 1:1로 외우면 안 된다. CloudFront와 Azure Front Door는 edge 계층에서 캐시, WAF, 전역 라우팅을 담당하고, Application Load Balancer와 Application Gateway는 regional L7 진입점 역할을 한다. 런타임, 데이터, identity, observability는 각 클라우드의 책임 경계와 장애 신호를 따로 확인한다.

OPERATIONS DECISION

운영 질문 AWS와 Azure 구성 요소를 서비스명이 아니라 책임 경계로 설명할 수 있는가?

확인할 증거 Route 53/Azure DNS, CloudFront/Azure Front Door, ALB/Application Gateway, ECS/EKS/AKS/App Service, RDS/Azure SQL

판단 기준 edge, regional ingress, runtime, data, identity, observability를 분리해 그릴 수 있어야 한다.

배제 확인 웹 서비스 기본 구성을 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 CloudFront/Front Door request log, ALB/App Gateway target health, runtime health, DB metrics

명령 해석 edge 403, regional 5xx, runtime failure, DB pressure를 같은 오류로 묶지 않는다.

임시 완화와 영구 수정 CloudFront 또는 Front Door 403 증가와 origin 5xx가 동시에 관찰됨 기준으로 영향 범위를 좁히고, WAF/edge 차단과 origin 연결 실패를 분리해 완화책을 선택한다.

CLD-01

사설 네트워크와 데이터 경계

AWS는 VPC, public/private subnet, NAT Gateway, Security Group, VPC Endpoint, AWS PrivateLink로 경계를 만든다. Azure는 VNet, subnet, NAT Gateway, Network Security Group, Private Endpoint, Private Link, Private DNS Zone을 조합한다. 핵심은 DB와 관리형 서비스가 인터넷을 거치지 않게 하는 것이다.

OPERATIONS DECISION

운영 질문 DB와 관리형 서비스가 인터넷을 거치지 않는다는 것을 어떤 증거로 확인하는가?

확인할 증거 route table, private endpoint, Private DNS, Security Group/NSG, flow log, public access disabled

판단 기준 DNS가 private endpoint를 가리키고 route/policy/flow log가 사설 경로를 증명해야 한다.

배제 확인 사설 네트워크와 데이터 경계를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 route table readback, private DNS resolution, flow log ACCEPT/REJECT, DB public access setting

명령 해석 private endpoint를 만들었어도 DNS가 public endpoint를 가리키면 사설 경로가 아니다.

임시 완화와 영구 수정 private subnet 앱이 DB 또는 storage 접근 실패, 또는 public egress 비용 급증 기준으로 영향 범위를 좁히고, DNS override, endpoint policy, route table, NSG/Security Group, egress path를 순서대로 본다.

정상예시 신호

관찰값 Private DNS가 사설 IP를 반환하고 flow log가 private endpoint 경로를 기록

해석 인터넷을 거치지 않는 경로로 판단한다.

비정상예시 신호

관찰값 Private Endpoint는 있지만 DNS가 public endpoint를 반환

해석 DNS override 또는 resolver rule을 먼저 수정한다.

CLD-02

Secret과 배포

AWS에서는 IAM role, Secrets Manager, Parameter Store, ECR, CodePipeline 또는 GitHub Actions를 사용한다. Azure에서는 Microsoft Entra ID, Managed Identity, Key Vault, Azure Container Registry, Azure DevOps 또는 GitHub Actions를 연결한다. secret은 build artifact에 넣지 않고 runtime 주입과 rotation 절차를 둔다.

OPERATIONS DECISION

운영 질문 secret과 배포 권한이 artifact와 runtime 경계에서 분리되어 있는가?

확인할 증거 IAM/Managed Identity, Secrets Manager/Key Vault, runtime injection, rotation record, deploy approval

판단 기준 secret이 build artifact, image, frontend bundle, log에 남으면 운영 경계 실패로 본다.

배제 확인 Secret과 배포를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 role assignment, secret version, deployment environment, audit log, image/config diff

명령 해석 배포 주체와 런타임 주체의 권한이 분리되어야 영향 범위를 줄일 수 있다.

임시 완화와 영구 수정 secret rotation 직후 app 인증 실패 또는 배포 pipeline 권한 오류 기준으로 영향 범위를 좁히고, revoke, 재발급, runtime 재시작, 영향 범위 확인을 절차로 나눈다.

CLD-03

장애와 비용 사례

CloudFront나 Azure Front Door 캐시 설정 오류는 stale content를 만들고, NAT Gateway 비용 폭증은 private subnet egress 설계가 잘못됐다는 신호일 수 있다. RDS/Azure SQL connection pool 고갈, ALB/Application Gateway health probe 실패, AKS/EKS rollout 실패는 지표와 로그를 같은 릴리스 단위로 묶어야 빠르게 좁힌다.

OPERATIONS DECISION

운영 질문 장애 신호와 비용 신호를 같은 운영 timeline에서 설명할 수 있는가?

확인할 증거 WAF rule change, cache policy, target health, DB pressure, NAT bytes, retry storm, log ingestion

판단 기준 비용 급증도 retry, egress route, cross-AZ traffic 같은 운영 장애 신호일 수 있다.

배제 확인 장애와 비용 사례를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 edge log, target health, DB metric, NAT/egress cost, retry rate, deployment marker

명령 해석 최근 변경과 비용/장애 신호를 같은 시간축에 놓고 원인 후보를 줄인다.

임시 완화와 영구 수정 NAT 비용 4배 증가와 외부 API timeout/retry 증가 기준으로 영향 범위를 좁히고, retry 제한, egress allowlist, route 수정, cost anomaly alert를 함께 남긴다.

CHECK

실무 체크리스트

AWS·Azure 실전 시나리오 체크리스트는 웹 서비스 기본 구성, 사설 네트워크와 데이터 경계, Secret과 배포, 장애와 비용 사례에서 놓치기 쉬운 운영 증거를 작업 전후로 고정하기 위한 검토표다. 각 항목은 프론트엔드 증상, 배포 승인, 운영 인수에서 같은 기준으로 다시 확인한다.

  • AWS와 Azure에서 같은 역할을 하는 서비스를 1:1로 외우지 말고 edge, network, runtime, data, identity, observability 책임으로 매핑한다.
  • Route 53/Azure DNS, CloudFront/Azure Front Door, ALB/Application Gateway, ECS Fargate·EKS/AKS·App Service, RDS/Azure SQL 조합을 요청 경로로 그린다.
  • Secrets Manager 또는 Key Vault, IAM role 또는 Managed Identity, PrivateLink 또는 Private Endpoint를 보안 경계에 포함한다.
  • CloudWatch 또는 Azure Monitor에서 RED 지표, DB connection, health probe, deployment version을 같은 대시보드에 둔다.
설계작업 단계

필수 산출물 목적, 영향 범위, 비목표, owner

차단 기준 영향 범위가 사용자·시스템·비용 기준으로 설명되지 않음

변경작업 단계

필수 산출물 diff, 승인 기록, 검증 명령

차단 기준 production 변경과 staging 검증의 차이가 설명되지 않음

복구작업 단계

필수 산출물 rollback 또는 forward fix, 담당자, 예상 시간

차단 기준 실패 시 되돌릴 수 없는데 사전 승인과 공지가 없음

PLAYBOOK

실무 플레이북

AWS·Azure 실전 시나리오 플레이북은 AWS AZURE OPERATIONS PLAYBOOK 기준으로 증상, 범위, 최근 변경, 계층별 증거를 연결한다. 목표는 명령어를 많이 아는 것이 아니라 어느 가설을 버리고 어떤 완화책을 선택할지 설명하는 것이다.

AWS AZURE OPERATIONS PLAYBOOK 1 symptom → 2 scope → 3 recent change → 4 evidence
→ 5 mitigation → 6 verification → 7 runbook diff
1 · 증상symptom
무엇이 안 되는가를 사용자 관점 한 문장으로. "느리다"가 아니라 어떤 요청이 언제부터 어떻게 실패하는지 적는다
2 · 영향 범위scope
전체인가 일부인가. region·tenant·경로·클라이언트 중 무엇으로 갈리는지가 가설의 절반을 지운다
3 · 최근 변경recent change
직전 배포, 설정·권한 변경, 인증서·route 교체를 같은 시간축에 올린다. 대부분의 장애는 최근 변경에서 온다
4 · 증거evidence
provider, region, account/subscription 전제를 먼저 고정하고 그 조건의 콘솔·CLI 출력을 남긴다. 이름이 같은 기능도 provider마다 동작이 다르다
5 · 완화mitigation
provider가 제공하는 되돌리기 수단(이전 버전, snapshot, traffic shift)이 지금 쓸 수 있는지부터 확인한다
6 · 복구 검증verification
완화가 실제로 먹혔는지 같은 증거로 다시 확인한다. 사용자 경로를 한 번 통과시켜야 끝난 것이다
7 · 런북 갱신runbook diff
이번에 내린 판단을 문서에 되돌린다. 다음 사람이 같은 순서를 다시 발명하지 않게 하는 단계
Edge / Ingress운영 표면

볼 증거 Route 53/Azure DNS, CloudFront/Front Door, WAF, ALB/App Gateway

판단 기준 edge와 origin의 장애를 분리한다.

Runtime / Data운영 표면

볼 증거 ECS/EKS/AKS/App Service, RDS/Azure SQL, Redis, storage

판단 기준 runtime health와 data dependency를 같은 release 단위로 본다.

Identity / Cost운영 표면

볼 증거 IAM/Managed Identity, Secrets Manager/Key Vault, NAT/egress, monitor cost

판단 기준 보안과 비용도 운영 장애 신호다.

AWS 경로확인 단계

명령·확인 위치 Route 53 answer, CloudFront cache/WAF log, ALB target health, ECS task/RDS metrics

해석 기준 CloudFront 403과 ALB 5xx를 분리한다.

Azure 경로확인 단계

명령·확인 위치 Azure DNS, Front Door health, Application Gateway probe, AKS/App Service, Azure SQL metrics

해석 기준 Front Door와 App Gateway의 책임 경계를 본다.

비용/egress확인 단계

명령·확인 위치 NAT Gateway bytes, data transfer, log ingestion, managed service autoscale

해석 기준 비용 급증도 최근 변경과 같은 timeline에 놓는다.

CloudFront / Front Door 403심화 장애 패턴

관찰 신호 WAF rule, origin policy, signed URL/cookie, geo rule

판정 기준 edge 차단과 origin 차단을 분리한다.

ALB / App Gateway 502심화 장애 패턴

관찰 신호 target health, backend protocol, TLS to origin, idle timeout

판정 기준 edge가 정상이어도 origin 연결이 실패할 수 있다.

RDS / Azure SQL pressure심화 장애 패턴

관찰 신호 connection count, CPU, lock wait, storage IOPS, replica lag

판정 기준 DB 병목과 app pool 설정을 같이 본다.

NAT / Egress cost spike심화 장애 패턴

관찰 신호 NAT bytes, retry storm, log export, cross-AZ traffic

판정 기준 비용 급증을 운영 incident로 취급한다.

PRACTICE

출력 판독 훈련

AWS·Azure 실전 시나리오는 개념을 아는 것보다 실제 출력에서 정상과 비정상을 구분하는 훈련이 중요하다. 아래 lab은 명령, 출력, 판단, 완화, 영구 수정을 한 번에 연결한다.

PRACTICE LAB 01 · Azure private connectivity 판독

Azure App Service가 Azure SQL Private Endpoint에 간헐적으로 연결하지 못한다.

Command / Query

az network watcher test-connectivity --source-resource app-service-id --dest-address db.privatelink.database.windows.net --dest-port 1433

목적 DNS, NSG, Private Endpoint 경로가 실제로 연결 가능한지 확인한다.

정상 출력

ConnectionStatus: Reachable
AvgLatencyInMs: 12
Hops: PrivateEndpoint

비정상 출력

ConnectionStatus: Unreachable
Hops: Internet
Issue: DNS resolved public endpoint

판단 훈련 Private Endpoint는 있어도 DNS가 public endpoint를 반환하면 사설 경로가 아니다.

즉시 완화 Private DNS zone link와 resolver rule을 수정한다.

영구 수정 Private Endpoint 생성 runbook에 DNS resolution 검증과 public access disabled 확인을 추가한다.

검증 기준 test-connectivity Reachable, nslookup 사설 IP 반환, Azure SQL public access disabled.

TERM

용어사전

AWS·Azure 실전 시나리오에서 반복적으로 등장하는 운영 용어를 정의, 증거, 오해, 관련 항목 기준으로 정리한다. 장애 중에는 용어 자체보다 해당 용어가 어떤 로그, 지표, 설정, 책임 경계와 연결되는지를 확인한다.

edge layerTERM
DNS, CDN, WAF처럼 사용자와 가장 가까운 공개 계층. 운영에서는 Route 53/Azure DNS, CloudFront/Front Door log, WAF rule로 확인한다. 흔한 오해는 "edge 403과 origin 5xx는 같은 문제다."라고 보는 것이다. 관련해서 origin, cache policy, regional ingress를 함께 본다.
regional L7 ingressTERM
ALB/Application Gateway처럼 region 내부 HTTP 진입을 처리하는 계층. 운영에서는 target health, backend protocol, idle timeout로 확인한다. 흔한 오해는 "CDN이 정상이면 ALB/App Gateway도 정상이다."라고 보는 것이다. 관련해서 ALB, Application Gateway, health probe를 함께 본다.
managed identityTERM
Azure workload가 secret 없이 리소스 권한을 얻는 identity. 운영에서는 role assignment, audit log, Key Vault access로 확인한다. 흔한 오해는 "배포 권한과 런타임 권한은 같아도 된다."라고 보는 것이다. 관련해서 IAM role, Secrets Manager, Key Vault를 함께 본다.
PrivateLink/Private EndpointTERM
AWS/Azure 관리형 서비스 접근을 사설 경로로 제한하는 구성. 운영에서는 Private DNS, endpoint policy, flow log, public access disabled로 확인한다. 흔한 오해는 "endpoint만 만들면 public egress가 사라진다."라고 보는 것이다. 관련해서 VPC Endpoint, Private DNS Zone, NSG를 함께 본다.
NAT GatewayTERM
private subnet의 outbound internet 경로가 되는 관리형 NAT. 운영에서는 NAT bytes, retry storm, egress cost, deployment marker로 확인한다. 흔한 오해는 "비용 급증은 FinOps 문제지 incident가 아니다."라고 보는 것이다. 관련해서 egress allowlist, retry rate, cost anomaly alert를 함께 본다.
CASE

장애/운영 시나리오

B2B SaaS 관리자 서비스를 클라우드에 배포한다. AWS안은 Route 53 → CloudFront/WAF → Application Load Balancer → ECS Fargate → RDS Multi-AZ와 ElastiCache로 구성하고, secret은 Secrets Manager, 이미지는 ECR, 로그와 알림은 CloudWatch로 둔다. Azure안은 Azure DNS → Azure Front Door/WAF → Application Gateway → AKS 또는 App Service → Azure SQL zone redundant 구성과 Azure Cache for Redis로 구성하고, secret은 Key Vault, 이미지는 ACR, 로그와 알림은 Azure Monitor로 둔다.

Triage frame

AWS·Azure 실전 시나리오 장애는 프론트엔드에서 보인 증상 → 영향 범위 → 최근 변경 → Edge / Ingress 증거 → 완화책 → 복구 검증 → 재발 방지 순서로 기록한다.

RISK

자주 틀리는 판단

AWS·Azure 실전 시나리오에서 자주 틀리는 판단은 웹 서비스 기본 구성와 장애와 비용 사례의 책임 경계를 흐리는 데서 시작된다. 아래 신호가 보이면 설계, runbook, 답변 구조를 다시 점검한다.

  • AWS 서비스명과 Azure 서비스명을 단순 번역해서 같은 장애 특성을 가진다고 가정한다.
  • CloudFront나 Azure Front Door 뒤에 origin timeout, cache policy, WAF rule 변경 이력을 남기지 않는다.
  • NAT Gateway 또는 egress 비용을 보지 않아 private subnet의 외부 호출 비용이 폭증한다.
  • RDS/Azure SQL 백업은 켜져 있지만 restore drill과 connection pool 장애 대응이 없다.
