서비스명이 아니라 책임 경계로

CloudFront와 Front Door, ALB와 Application Gateway, RDS와 Azure SQL을 1:1로 외우는 순간부터 장애 판단은 틀리기 시작한다. 이름이 비슷하다고 장애 특성까지 같지는 않다. 필요한 건 서비스명이 아니라 edge, network, runtime, data, identity, cost라는 책임 경계로 두 클라우드를 동시에 읽는 눈이다.

edge 계층에서는 403(edge 차단)과 5xx(origin 장애)를 같은 오류로 묶지 않는 게 출발점이다. 그 안쪽 네트워크 경계로 들어가면 AWS의 VPC·PrivateLink와 Azure의 VNet·Private Endpoint가 같은 역할을 하는데, 가장 흔한 함정은 endpoint를 만든 것과 실제로 사설 경로가 된 것을 혼동하는 것이다 — DNS가 여전히 public endpoint를 반환하면 endpoint는 있으나 마나다. identity 쪽 경계도 마찬가지 원리다. IAM role이든 Managed Identity든, secret이 build artifact나 이미지, 프런트엔드 번들, 로그에 남는 순간 그 경계는 이미 깨진 것이다.

이 모든 경계가 실제로 무너지는 지점은 장애와 비용이 겹치는 순간에 드러난다. CDN 캐시 설정 오류는 stale content를 만들고, NAT Gateway 비용 폭증은 종종 private subnet의 egress 설계 문제라는 신호다 — 비용 급증도 retry storm 같은 운영 장애로 다뤄야지 FinOps 문제로만 넘기면 안 된다. AWS AZURE OPERATIONS PLAYBOOK은 이 판단을 symptom → scope → evidence 순서로 굳히고, Azure private connectivity 판독 실습은 App Service가 Azure SQL Private Endpoint에 간헐적으로 연결하지 못하는 상황에서 test-connectivity 출력이 Reachable과 Unreachable(DNS resolved public endpoint)로 갈리는 걸 직접 비교시킨다.

여기서 자주 틀리는 판단은 서비스명을 단순 번역해서 같은 장애 특성을 가정하는 것, WAF·cache policy 변경 이력을 남기지 않는 것, 백업은 켜져 있지만 restore drill은 해본 적 없는 것이다. region, quota, managed service 제약은 시점마다 바뀌므로, 기준일과 확인 출처 없는 서비스 매핑이나 비용 판단은 여전히 초안일 뿐이다. 결국 매번 돌아가는 질문은 하나다 — 이 판단을 서비스명이 아니라 책임 경계로 설명할 수 있는가.

CLD-00

웹 서비스 기본 구성

AWS와 Azure 서비스는 이름을 1:1로 외우면 안 된다. CloudFront와 Azure Front Door는 edge 계층에서 캐시, WAF, 전역 라우팅을 담당하고, Application Load Balancer와 Application Gateway는 regional L7 진입점 역할을 한다. 런타임, 데이터, identity, observability는 각 클라우드의 책임 경계와 장애 신호를 따로 확인한다.

이직하고 처음 맡은 서비스가 AWS에서 Azure로 옮겨가는 프로젝트였다. 처음엔 "CloudFront는 Front Door, ALB는 App Gateway"처럼 1:1로 표를 만들어 외우려고 했다. 그런데 실제로 장애가 나니까 이 표가 하나도 도움이 안 됐다. edge 403이 뜨는 상황과 origin 5xx가 뜨는 상황은 겉보기엔 비슷해 보여도 원인이 완전히 다른 계층에 있었기 때문이다.

실제로 이런 일이 있었다. Front Door 403이 늘면서 동시에 origin 쪽 5xx도 관찰됐다. 서비스명 매핑만 외워온 팀원은 "Front Door 문제니까 WAF 룰만 보면 된다"고 판단했는데, 그렇게 하니 절반만 맞았다. WAF 룰 오탐으로 403이 늘어난 것과, 별개로 backend가 배포 직후 잠깐 죽어 있었던 것, 이 두 사건이 우연히 겹쳐 있었다. edge 문제를 고치고 나서 "이제 다 됐겠지" 하고 넘어갔다면 origin이 여전히 죽어 있는 걸 놓칠 뻔했다. 이후로는 서비스 이름이 아니라 edge, regional ingress, runtime, data, identity, observability라는 책임 경계로 항상 나눠서 본다. 이름이 다른 두 클라우드라도 이 틀로 보면 같은 방식으로 비교할 수 있다.

CLD-01

사설 네트워크와 데이터 경계

AWS는 VPC, public/private subnet, NAT Gateway, Security Group, VPC Endpoint, AWS PrivateLink로 경계를 만든다. Azure는 VNet, subnet, NAT Gateway, Network Security Group, Private Endpoint, Private Link, Private DNS Zone을 조합한다. 핵심은 DB와 관리형 서비스가 인터넷을 거치지 않게 하는 것이다.

Private Endpoint를 만들어놓고 비용 대시보드에서 public egress가 하나도 안 줄어서 당황한 적이 있다. 콘솔에는 분명히 endpoint가 떠 있는데, 실제 트래픽은 여전히 인터넷을 거쳐 나가고 있었다. 원인은 DNS였다 — endpoint는 만들어졌지만 그 이름을 조회하면 여전히 public IP가 나오고 있었던 것이다. route, policy, flow log가 다 사설 경로를 가리켜야 진짜 "사설화됐다"고 말할 수 있는데, DNS 하나가 빠지면 나머지가 다 맞아도 소용없다.

private subnet 앱이 DB나 storage 접근에 실패하거나 public egress 비용이 급증하는 상황을 겪으면, 다음 순서로 하나씩 확인한다.

  1. DNS override — 그 이름이 사설 IP로 응답하는지 먼저 본다. 원인의 대부분이 여기다.
  2. endpoint policy — 경로는 맞는데 정책이 요청만 거부하고 있지는 않은지 본다.
  3. route table — 해당 대역이 의도한 target으로 향하는지 확인한다.
  4. NSG / Security Group — 양방향 허용 규칙이 실제 요청의 port와 맞는지 본다.
  5. egress path — 최종적으로 트래픽이 인터넷을 거치는지 사설 경로로 흐르는지 확인한다.

순서를 뒤섞어서 route table부터 뒤지면, 정작 원인이었던 DNS는 한참 뒤에나 들여다보게 된다.

정상적인 경우라면 Private DNS가 사설 IP를 반환하고 flow log가 private endpoint 경로를 기록한다. 이럴 때는 인터넷을 거치지 않는 경로로 판단해도 된다. 비정상적인 경우에는 Private Endpoint는 있지만 DNS가 public endpoint를 반환한다. 이때는 endpoint 자체보다 DNS override나 resolver rule을 먼저 의심하고 수정해야 한다.

CLD-02

Secret과 배포

AWS에서는 IAM role, Secrets Manager, Parameter Store, ECR, CodePipeline 또는 GitHub Actions를 사용한다. Azure에서는 Microsoft Entra ID, Managed Identity, Key Vault, Azure Container Registry, Azure DevOps 또는 GitHub Actions를 연결한다. secret은 build artifact에 넣지 않고 runtime 주입과 rotation 절차를 둔다.

배포 파이프라인이 쓰는 권한과 런타임에서 앱이 쓰는 권한을 하나로 합쳐서 관리하는 팀을 종종 본다. 편하긴 한데, 둘 중 하나가 뚫리면 나머지 하나까지 같이 위험해진다는 게 문제다. IAM/Managed Identity, Secrets Manager/Key Vault, runtime injection, rotation record, deploy approval을 하나씩 대조해보면 이 둘이 실제로 분리돼 있는지 드러난다. secret이 build artifact나 image, frontend bundle, log 어디에라도 남아 있다면, 그 자체로 이미 운영 경계가 뚫린 것이다.

secret rotation을 돌린 직후 app 인증이 실패하거나 배포 pipeline에서 권한 오류가 나는 걸 본 적이 있다. 순서가 문제였다. revoke하고 재발급까지는 했는데 runtime 재시작을 깜빡한 것이다. 예전 secret을 여전히 메모리에 물고 있던 프로세스들은 재시작 전까지 계속 같은 인증 실패를 뱉었다. revoke, 재발급, runtime 재시작, 영향 범위 확인 — 이 순서를 하나라도 건너뛰면 꼭 이런 식으로 뒤늦게 사고가 터진다.

CLD-03

장애와 비용 사례

CloudFront나 Azure Front Door 캐시 설정 오류는 stale content를 만들고, NAT Gateway 비용 폭증은 private subnet egress 설계가 잘못됐다는 신호일 수 있다. RDS/Azure SQL connection pool 고갈, ALB/Application Gateway health probe 실패, AKS/EKS rollout 실패는 지표와 로그를 같은 릴리스 단위로 묶어야 빠르게 좁힌다.

NAT 비용이 갑자기 4배로 뛴 걸 FinOps 팀이 먼저 발견하고 우리한테 물어온 적이 있다. 처음엔 "그냥 트래픽이 늘었나 보다" 하고 넘길 뻔했는데, 같은 시점에 외부 결제 API timeout도 같이 늘고 있었다는 걸 뒤늦게 알아챘다. 두 신호를 따로 보고 있었다면 하나는 FinOps가, 하나는 운영팀이 각자 다른 티켓으로 다루고 끝났을 것이다. 실제로는 하나의 사건이었다 — 외부 API가 느려지자 우리 애플리케이션이 계속 재시도를 날리고 있었고, 그 재시도량 자체가 NAT bytes를 밀어올려서 비용으로 드러난 것이었다.

이 사건 이후로는 비용 급증을 절대 회계 이슈로만 넘기지 않는다. WAF rule change, cache policy, target health, DB pressure, NAT bytes, retry storm을 최근 배포 marker와 같은 시간축에 놓고 본다. 이때 즉시 할 수 있는 건 retry를 제한하고 egress allowlist를 점검하는 것이고, cost anomaly alert도 같이 남겨둔다. 비용만 줄이고 retry storm을 일으킨 근본 원인을 안 고치면, 다음 배포에서 외부 API가 또 느려지는 순간 똑같은 패턴이 반복된다.

CHECK

실무 체크리스트

AWS·Azure 실전 시나리오 체크리스트는 웹 서비스 기본 구성, 사설 네트워크와 데이터 경계, Secret과 배포, 장애와 비용 사례의 변경 위험을 사전에 드러내기 위한 검토표다. 각 항목은 리뷰, 배포 승인, 운영 인수에서 같은 증거로 다시 확인되어야 한다.

  • AWS와 Azure에서 같은 역할을 하는 서비스를 1:1로 외우지 말고 edge, network, runtime, data, identity, observability 책임으로 매핑한다.
  • Route 53/Azure DNS, CloudFront/Azure Front Door, ALB/Application Gateway, ECS Fargate·EKS/AKS·App Service, RDS/Azure SQL 조합을 요청 경로로 그린다.
  • Secrets Manager 또는 Key Vault, IAM role 또는 Managed Identity, PrivateLink 또는 Private Endpoint를 보안 경계에 포함한다.
  • CloudWatch 또는 Azure Monitor에서 RED 지표, DB connection, health probe, deployment version을 같은 대시보드에 둔다.

이 체크리스트의 세 관문은 AWS·Azure 구성 변경에서도 똑같이 적용된다.

  1. 설계 — 목적, 영향 범위, 비목표, owner가 산출물로 남아 있어야 한다. 영향 범위가 사용자·시스템·비용 기준으로 설명되지 않는다면, 이 단계에서 진행을 막아야 한다.
  2. 변경 — diff, 승인 기록, 검증 명령이 함께 있어야 한다. WAF rule이나 cache policy처럼 눈에 잘 안 띄는 조건이 다를 수 있으니, production 변경과 staging 검증의 차이가 설명되지 않으면 배포해서는 안 된다.
  3. 복구 — rollback 또는 forward fix, 담당자, 예상 시간이 미리 정해져 있어야 한다. 실패 시 되돌릴 수 없는데 사전 승인과 공지가 없다면 배포를 보류해야 한다.

실무 플레이북

AWS·Azure 실전 시나리오 플레이북은 AWS AZURE OPERATIONS PLAYBOOK 기준으로 증상, 범위, 최근 변경, 계층별 증거를 연결한다. 목표는 명령어 암기가 아니라 어떤 가설을 버리고 어떤 완화책을 실행할지 결정하는 것이다.

AWS AZURE OPERATIONS PLAYBOOK 1 symptom → 2 scope → 3 recent change → 4 evidence
→ 5 mitigation → 6 verification → 7 runbook diff
1 · 증상symptom
무엇이 안 되는가를 사용자 관점 한 문장으로. "느리다"가 아니라 어떤 요청이 언제부터 어떻게 실패하는지 적는다
2 · 영향 범위scope
전체인가 일부인가. region·tenant·경로·클라이언트 중 무엇으로 갈리는지가 가설의 절반을 지운다
3 · 최근 변경recent change
직전 배포, 설정·권한 변경, 인증서·route 교체를 같은 시간축에 올린다. 대부분의 장애는 최근 변경에서 온다
4 · 증거evidence
provider, region, account/subscription 전제를 먼저 고정하고 그 조건의 콘솔·CLI 출력을 남긴다. 이름이 같은 기능도 provider마다 동작이 다르다
5 · 완화mitigation
provider가 제공하는 되돌리기 수단(이전 버전, snapshot, traffic shift)이 지금 쓸 수 있는지부터 확인한다
6 · 복구 검증verification
완화가 실제로 먹혔는지 같은 증거로 다시 확인한다. 사용자 경로를 한 번 통과시켜야 끝난 것이다
7 · 런북 갱신runbook diff
이번에 내린 판단을 문서에 되돌린다. 다음 사람이 같은 순서를 다시 발명하지 않게 하는 단계

AWS·Azure 장애를 다룰 때도 클라우드 이름은 잠시 잊고 "이게 어느 책임 경계의 문제인가"로 표면을 나눠서 본다. Edge/Ingress 표면은 "사용자와 가장 가까운 곳에서 걸러졌는가"를 Route 53/Azure DNS, CloudFront/Front Door, WAF, ALB/App Gateway로 본다. edge와 origin의 장애를 분리하는 게 이 표면의 핵심이다. Runtime/Data 표면은 "요청을 받은 뒤 처리 과정에서 무너졌는가"를 ECS/EKS/AKS/App Service, RDS/Azure SQL, Redis, storage로 본다. runtime health와 data dependency를 같은 release 단위로 묶어서 봐야 한다. Identity/Cost 표면은 "겉으로는 안 보이지만 권한이나 비용으로 새고 있는가"를 IAM/Managed Identity, Secrets Manager/Key Vault, NAT/egress, monitor cost로 본다. 보안과 비용도 그 자체로 운영 장애 신호라는 걸 여기서 다시 확인한다.

이 세 표면은 조사하는 순서까지 정해져 있다.

  1. AWS 경로 — Route 53 answer, CloudFront cache/WAF log, ALB target health, ECS task/RDS metrics를 보고 CloudFront 403과 ALB 5xx를 분리한다.
  2. Azure 경로 — Azure DNS, Front Door health, Application Gateway probe, AKS/App Service, Azure SQL metrics를 보고 Front Door와 App Gateway의 책임 경계를 확인한다.
  3. 비용/egress 확인 — NAT Gateway bytes, data transfer, log ingestion, managed service autoscale을 보고 비용 급증도 최근 변경과 같은 timeline에 놓는다.

같은 계층이라도 장애 패턴에 따라 판정 기준이 달라진다. CloudFront / Front Door 403은 WAF rule, origin policy, signed URL/cookie, geo rule로 나타나는데, edge 차단과 origin 차단을 분리해서 봐야 한다. ALB/App Gateway 502는 target health, backend protocol, TLS to origin, idle timeout으로 나타나므로, edge가 정상이어도 origin 연결이 실패할 수 있다는 걸 염두에 둔다. RDS/Azure SQL pressure는 connection count, CPU, lock wait, storage IOPS, replica lag로 나타나는데, DB 병목과 app pool 설정을 함께 봐야 한다. NAT/Egress cost spike는 NAT bytes, retry storm, log export, cross-AZ traffic으로 나타나므로, 비용 급증을 그 자체로 운영 incident로 취급해야 한다.

PRACTICE

출력 판독 훈련

AWS·Azure 실전 시나리오는 개념을 아는 것보다 실제 출력에서 정상과 비정상을 구분하는 훈련이 중요하다. 아래 lab은 명령, 출력, 판단, 완화, 영구 수정을 한 번에 연결한다.

PRACTICE LAB 01 · Azure private connectivity 판독

Azure App Service가 Azure SQL Private Endpoint에 간헐적으로 연결하지 못한다.

DNS, NSG, Private Endpoint 경로가 실제로 연결 가능한지 확인하려면 다음을 실행한다.

az network watcher test-connectivity --source-resource app-service-id --dest-address db.privatelink.database.windows.net --dest-port 1433

정상적인 경우라면 Private Endpoint 경로로 연결에 성공한다.

ConnectionStatus: Reachable
AvgLatencyInMs: 12
Hops: PrivateEndpoint

비정상적인 경우에는 인터넷 경로를 거쳐 연결에 실패한다.

ConnectionStatus: Unreachable
Hops: Internet
Issue: DNS resolved public endpoint

Private Endpoint는 만들어져 있어도 DNS가 public endpoint를 반환하면 사설 경로가 아니라는 뜻이다. 즉시 완화는 Private DNS zone link와 resolver rule을 수정하는 것이다. 영구 수정은 Private Endpoint 생성 runbook에 DNS resolution 검증과 public access disabled 확인을 추가하는 것이다. test-connectivity가 Reachable로 나오고 nslookup이 사설 IP를 반환하며 Azure SQL의 public access가 disabled로 확인되면 이 조치가 끝난 것이다.

TERM

용어사전

AWS·Azure 실전 시나리오에서 반복적으로 등장하는 운영 용어를 정의, 증거, 오해, 관련 항목 기준으로 정리한다. 장애 중에는 용어 자체보다 해당 용어가 어떤 로그, 지표, 설정, 책임 경계와 연결되는지를 확인한다.

edge layer
DNS, CDN, WAF처럼 사용자와 가장 가까운 곳에서 요청을 맞이하는 공개 계층이다. Route 53/Azure DNS, CloudFront/Front Door log, WAF rule로 확인한다. edge 403과 origin 5xx를 같은 문제로 묶어보기 쉬운데, 하나는 요청이 edge에서 걸러진 것이고 다른 하나는 origin까지 도달한 뒤에야 실패한 것이라 원인이 있는 위치 자체가 다르다.
regional L7 ingress
ALB/Application Gateway처럼 region 안쪽에서 HTTP 요청을 받는 계층이다. target health, backend protocol, idle timeout으로 확인한다. CDN이 멀쩡하면 ALB/App Gateway도 당연히 괜찮을 거라 넘겨짚기 쉬운데, CDN은 edge 계층이고 ALB/App Gateway는 그 안쪽 regional 계층이라 서로 독립적으로 장애가 날 수 있다.
managed identity
Azure workload가 secret 없이도 리소스 권한을 받을 수 있게 해주는 identity다. role assignment, audit log, Key Vault access로 확인한다. 배포할 때 쓰는 권한과 런타임에서 쓰는 권한을 굳이 나눌 필요 있나 싶겠지만, 나눠두지 않으면 한쪽이 뚫렸을 때 영향이 다른 쪽까지 그대로 번진다.
PrivateLink/Private Endpoint
AWS/Azure 관리형 서비스로의 접근을 사설 경로로만 제한하는 구성이다. Private DNS, endpoint policy, flow log, public access disabled로 확인한다. endpoint를 만드는 순간 public egress가 사라질 거라 기대하기 쉬운데, DNS가 여전히 public endpoint를 돌려주고 있다면 트래픽은 그대로 인터넷을 거쳐 나간다.
NAT Gateway
private subnet이 인터넷으로 나갈 때 거치는 관리형 NAT다. NAT bytes, retry storm, egress cost, deployment marker로 확인한다. 비용이 갑자기 튀면 FinOps가 알아서 처리할 회계 이슈라고 넘기기 쉬운데, retry storm이나 잘못된 egress route 같은 운영 장애가 비용이라는 형태로 먼저 드러나는 경우가 많다.
책임 경계
서비스명 대신 edge, network, runtime, data, identity, cost로 나눠 보는 틀이다. 각 경계가 남기는 증거가 무엇인지로 확인한다. 두 클라우드를 1:1 서비스 매핑으로 외우기 쉬운데, 이름이 대응한다고 장애 특성까지 같지는 않아서 매핑표는 장애 때 도움이 되지 않는다.
origin
edge 뒤에서 실제 응답을 만드는 서버다. edge 응답 코드와 origin 상태 코드를 나눠 확인한다. edge에서 오류가 보이면 edge 문제라고 단정하기 쉬운데, edge 403과 origin 5xx가 우연히 겹치면 한쪽만 고치고 끝낼 위험이 있다.
403 vs 5xx
403은 edge나 정책이 요청을 막은 것이고 5xx는 뒤쪽이 응답을 못 만든 것이다. 어느 계층의 로그에 남았는지로 가른다. 둘 다 접속 실패로 보기 쉬운데, 막은 주체가 다르므로 볼 로그도 되돌릴 대상도 다르다.
cache policy
edge가 무엇을 얼마나 캐시할지 정한 규칙이다. 응답 헤더의 cache 상태와 정책 변경 이력으로 확인한다. 배포했는데 예전 화면이 보이면 배포 실패로 의심하기 쉬운데, 대부분은 캐시 정책과 무효화 누락이 원인이다.
stale content
무효화되지 않아 낡은 채로 계속 서빙되는 응답이다. 자산 해시, 응답 헤더, 무효화 기록으로 확인한다. 일부 사용자만 겪으니 단말 문제로 보기 쉬운데, edge 지점마다 캐시 상태가 달라 생기는 전형적인 증상이다.
VPC / VNet
클라우드 안에 만드는 사설 네트워크 단위이고 provider마다 이름이 다르다. 대역, subnet 구성, 연결 상태로 확인한다. 이름이 다르니 개념도 다를 거라 보기 쉬운데, 경계를 만드는 역할은 같고 세부 기본값과 제약이 다르다.
NSG / Security Group
인스턴스나 subnet에 붙는 허용 규칙 묶음이다. 규칙과 실제 요청의 source·port를 대조해 확인한다. 같은 개념이니 설정을 그대로 옮기면 된다고 보기 쉬운데, 적용 범위와 기본 허용 정책이 provider마다 달라 그대로 옮기면 구멍이 생긴다.
Private DNS Zone
private endpoint 이름을 사설 IP로 응답하게 하는 전용 zone이다. zone과 네트워크 link, 실제 조회 결과로 확인한다. endpoint를 만들면 이름도 따라올 거라 생각하기 쉬운데, 이 연결이 빠지면 트래픽은 계속 인터넷으로 나간다.
resolver rule
특정 이름의 조회를 지정한 resolver로 보내는 규칙이다. 규칙 대상과 실제 조회 경로로 확인한다. DNS는 하나뿐이라 생각하기 쉬운데, 어느 규칙을 타느냐에 따라 같은 이름이 사설과 공인 중 다른 답을 돌려준다.
Secrets Manager / Key Vault
비밀 값을 보관하고 접근을 통제하는 관리형 저장소다. 접근 로그와 버전, 교체 이력으로 확인한다. 저장소에 넣었으니 안전하다고 보기 쉬운데, 값을 꺼내 build artifact나 이미지에 넣는 순간 경계는 이미 깨진 것이다.
runtime injection
비밀과 설정을 빌드가 아니라 실행 시점에 넣는 방식이다. 이미지 안에 값이 없는지와 주입 경로로 확인한다. 편의상 빌드에 넣기 쉬운데, 이미지 레이어에 박힌 값은 나중에 덮어써도 이전 레이어에 남는다.
배포 권한 vs 런타임 권한
파이프라인이 쓰는 권한과 앱이 실행 중에 쓰는 권한이다. 각 주체의 policy와 사용 기록으로 확인한다. 하나로 합치면 편하다고 보기 쉬운데, 둘 중 하나가 뚫리면 나머지까지 함께 위험해진다.
egress 비용
내부에서 인터넷으로 나가는 트래픽에 붙는 요금이다. NAT metric과 비용 대시보드를 함께 확인한다. 비용은 FinOps가 볼 문제로 넘기기 쉬운데, 급증은 대개 사설 경로 누락이나 재시도 폭주라는 운영 신호다.
retry storm
실패한 요청을 여러 클라이언트가 동시에 재시도하며 부하가 증폭되는 상태다. 재시도 횟수와 트래픽·비용 급증 시점으로 확인한다. 재시도는 안전장치라 보기 쉬운데, 백오프와 상한이 없으면 죽어가는 상대를 더 때리고 요금까지 밀어올린다.
restore drill
백업에서 실제로 복구해 보는 훈련이다. 마지막 성공 시각과 소요 시간, 복구된 데이터 시점으로 확인한다. 백업이 켜져 있으니 복구도 될 거라 보기 쉬운데, 해본 적 없는 복구 절차는 검증되지 않은 가정일 뿐이다.
quota / region 제약
계정과 region마다 걸린 자원 상한과 기능 차이다. 콘솔의 한도와 provider 문서를 기준일과 함께 확인한다. 문서에 있으니 어디서나 될 거라 보기 쉬운데, region마다 지원 여부와 상한이 달라 그대로 옮기면 배포 당일에 막힌다.
CASE

장애/운영 시나리오

B2B SaaS 관리자 서비스를 클라우드에 배포한다. AWS안은 Route 53 → CloudFront/WAF → Application Load Balancer → ECS Fargate → RDS Multi-AZ와 ElastiCache로 구성하고, secret은 Secrets Manager, 이미지는 ECR, 로그와 알림은 CloudWatch로 둔다. Azure안은 Azure DNS → Azure Front Door/WAF → Application Gateway → AKS 또는 App Service → Azure SQL zone redundant 구성과 Azure Cache for Redis로 구성하고, secret은 Key Vault, 이미지는 ACR, 로그와 알림은 Azure Monitor로 둔다.

Triage frame

AWS·Azure 실전 시나리오 장애는 증상 → 영향 범위 → 최근 변경 → Edge / Ingress 증거 → 완화책 → 복구 검증 → 재발 방지 순서로 기록한다. 이 흐름이 있어야 담당자가 바뀌어도 같은 결론에 도달한다.

처음 10분은 원인을 찾기보다 영향 범위부터 좁힌다. Route 53/Azure DNS, CloudFront/Front Door, WAF, ALB/App Gateway 기준으로 어느 계층이 관련됐는지부터 고정한다. 다음 30분은 Route 53 answer, CloudFront cache/WAF log, ALB target health, ECS task/RDS metrics 항목에서 증거를 모아 완화책을 실행한다. 서비스명 암기가 아니라 책임 경계로 정리하는 게 종료 조건이다.

장애가 종료된 뒤에는 세 항목을 incident packet에 남긴다. 증상은 edge 403 증가나 NAT 비용 4배 증가이고, WAF rule, origin policy, egress route, retry storm을 순서대로 봐서 판정한다. 완화는 WAF rule rollback, cache policy rollback, retry 제한, egress allowlist 중에서 고르는데, 보안과 가용성의 trade-off를 항상 함께 기록해야 한다. 사후에는 cloud-specific runbook과 cost anomaly alert를 추가해서, 다음에도 서비스명 암기가 아니라 책임 경계로 판단할 수 있게 정리한다.

RISK

자주 틀리는 판단

AWS·Azure 실전 시나리오에서 자주 틀리는 판단은 웹 서비스 기본 구성와 장애와 비용 사례의 책임 경계를 흐리는 데서 시작된다. 아래 신호가 보이면 설계, runbook, 답변 구조를 다시 점검한다.

  • AWS 서비스명과 Azure 서비스명을 단순 번역해서 같은 장애 특성을 가진다고 가정한다.
  • CloudFront나 Azure Front Door 뒤에 origin timeout, cache policy, WAF rule 변경 이력을 남기지 않는다.
  • NAT Gateway 또는 egress 비용을 보지 않아 private subnet의 외부 호출 비용이 폭증한다.
  • RDS/Azure SQL 백업은 켜져 있지만 restore drill과 connection pool 장애 대응이 없다.
EVIDENCE

검증 기준·증거 패킷

AWS·Azure 실전 시나리오는 region, quota, managed service 제약이 바뀌면 답이 달라진다. 아래 패킷을 채우기 전까지 서비스명 매핑이나 비용 판단은 확정하지 않는다.

기준일은 2026-07-09 감사를 기준으로 삼고, 신규 region이나 service가 출시되거나 quota가 바뀔 때 재확인한다. AWS What's New, Azure Updates, 공식 service quota 페이지, 변경 티켓을 남겨서 문서·Q&A·incident packet의 기준일과 확인 출처가 일치하는지 본다.

AWS/Azure region 전제도 명시해야 한다. AWS ap-northeast-2/us-east-1, Azure Korea Central/East US처럼 실제 후보 region을 적고 AZ/zone 지원을 확인한 뒤, region별 ALB/App Gateway, NAT Gateway, RDS/Azure SQL, PrivateLink/Private Endpoint 지원 표를 남긴다. latency, data residency, zone redundancy, service availability를 같은 기준으로 비교해야 한다.

quota와 capacity ceiling은 LB target 수, public IP, NAT gateway, route table, vCPU, managed DB connection/storage/IOPS quota를 변경 전에 확인한다. AWS Service Quotas, Azure Quotas, provider CLI 출력, quota increase request id를 남겨서 현재 사용량, 한도, 증설 소요 시간, fallback 설계가 모두 기록되게 한다.

managed service 제약은 RDS/Azure SQL, ECS/AKS/EKS, App Gateway/Front Door 등 서비스별 failover, maintenance, patch, backup, network 제한을 확인한다. engine version, maintenance window, backup retention, failover event, connection reset metric을 남기면 self-managed와 managed 선택의 책임 경계, 운영 불가능한 영역이 명확해진다.

명령 출력 예시는 region 지원, quota, LB health, DNS/TLS, cost anomaly, audit log를 캡처한다. dig, openssl s_client, ALB/App Gateway health, Azure Resource Graph, AWS CLI quota 출력, cost explorer/export를 남기면 정상/비정상 출력과 공식 문서 링크가 incident packet에 함께 들어간다.

공식 문서 확인 절차는 서비스 설계 전에 provider 공식 문서의 region availability, limits/quotas, SLA, managed service limitations, pricing을 순서대로 확인하는 것이다. 확인 URL, 확인자, 확인일, 적용하지 않은 제약과 이유를 남겨서, 답변에 "현재 기준 확인 필요"라는 말 대신 확인한 기준과 남은 불확실성이 적히게 한다.
