FLOW

여섯 개 hop으로 쪼개 읽기

브라우저에서 발생한 요청이 서버 응답으로 돌아오기까지는 DNS, TLS, CDN/WAF, Load Balancer, App, DB라는 여섯 개 hop을 지난다. 장애가 났을 때 가장 먼저 할 일은 이 중 어느 hop에서 요청이 멈췄는지 좁히는 것이다 — 그 앞단은 원인 후보고, 그 뒷단은 로그가 비어 있어도 무죄다.

DNS가 잘못되면 애플리케이션 로그 자체가 비어 있을 수 있다. 요청이 서버에 도달하지도 못했기 때문이다. TLS는 한 단계 더 미묘한데, 인증서 만료나 SNI 불일치, intermediate chain 누락은 네트워크 연결은 되면서 HTTPS만 실패하는 패턴을 만든다. dig와 openssl s_client 결과를 함께 남겨야 권한 DNS와 public resolver, SAN과 SNI를 분리해서 볼 수 있다. 다음 hop인 Load Balancer는 단순 분산 장치가 아니라 장애 격리 장치다 — health check path가 의존성을 너무 깊이 보면 정상 서버까지 빠지고, 너무 얕게 보면 죽은 서버가 계속 트래픽을 받는다. 502는 upstream 연결 실패, 503은 capacity, 504는 timeout으로 먼저 나눠야 다음 조사가 헛돌지 않는다. 마지막 App-DB 구간은 connection pool과 lock, migration이 얽히는데, 프론트 증상만 보고 API 코드부터 고치기 전에 traceId로 request log와 DB wait event를 반드시 이어봐야 한다.

이 판단 순서를 실제 명령으로 옮긴 게 REQUEST PATH TRIAGE PLAYBOOK이고, ALB target health 502 판독이나 DNS NXDOMAIN vs cache 판독 같은 실습은 정상 출력과 비정상 출력을 나란히 놓고 그 차이를 손으로 확인시킨다. 로그인 API가 간헐적으로 504를 반환하는 사례에서는 DNS와 TLS부터 배제하고 나서야 Load Balancer와 DB로 넘어가는 순서 자체가 진단이 된다.

그래서 이 영역에서 가장 자주 틀리는 판단도 결국 순서를 건너뛰는 데서 나온다. 프론트 화면 오류만 보고 API부터 고치거나, health check가 통과했다고 애플리케이션도 정상이라 단정하거나, TLS 인증서 문제를 네트워크 장애로 오해하는 것. hop을 하나씩 배제해나가는 습관이 이 여섯 구간을 읽는 유일한 방법이다.

REQ-00

기준 경로

대표 경로는 DNS → CDN/WAF → Load Balancer → App → DB다. 장애가 나면 사용자의 증상, DNS 해석, TLS handshake, CDN cache, WAF 차단, Load Balancer target health, 애플리케이션 로그, DB connection pool을 같은 시간축에 올린다.

장애가 나면 다들 본능적으로 앱 로그부터 연다. 익숙한 화면이기 때문이다. 그런데 그 로그가 텅 비어 있으면 그때부터 당황하기 시작한다 — 앱이 죽은 건가, 배포가 잘못된 건가. 사실 앱 로그가 비어 있다는 것 자체가 하나의 단서다. 요청이 앱까지 오지도 못했다는 뜻이니까. DNS는 응답으로, edge는 request id로, LB는 target health로 "나는 이 요청을 받았다"는 흔적을 남긴다. 이 흔적을 hop 순서대로 하나씩 따라가면, 어디서 흔적이 뚝 끊기는지 보인다. 그 지점 바로 앞이 범인이다.

여기서 다들 한 번씩은 걸리는 함정이 있다. "뒤쪽 계층 로그가 비어 있으니 그 계층이 문제겠지"라는 추론이다. 실제로는 정반대인 경우가 훨씬 많다. 앞단에서 이미 막혀서 뒤쪽까지 요청이 갈 일 자체가 없었던 것뿐인데, 로그가 비었다는 이유로 뒤쪽 계층을 의심하고 시간을 낭비한다.

몇 년 전 특정 지역 사용자만 로그인이 안 된다는 신고가 들어온 적이 있다. 처음엔 다들 로그인 API 코드부터 열어봤다. DB도 찔러보고, 세션 로직도 다시 읽어봤다. 그런데 정작 그 지역 사용자의 요청은 앱 로그에 단 한 줄도 없었다. DNS 응답을 찍어보니 그 지역에서만 옛날 IP가 나오고 있었다 — 요청이 아예 우리 서버 문턱도 밟지 못하고 있었던 것이다. 이후로는 순서를 지킨다. dig로 이름 해석부터, openssl로 TLS handshake, 그 다음에야 WAF·LB·app·DB 로그를 순서대로 연다. 그리고 이 모든 증거를 같은 timestamp와 traceId로 묶어서 본다. DNS 응답 시각과 앱 로그 시각이 어긋나 있으면, 사실은 서로 다른 두 사건을 하나로 착각하고 있는 것일 수 있다.

REQ-01

DNS와 TLS

DNS가 잘못되면 애플리케이션 로그가 비어 있을 수 있다. TLS 인증서 만료, SNI 불일치, intermediate chain 누락은 네트워크 연결은 되지만 HTTPS에서 실패하는 전형적인 원인이다. curl -v, openssl s_client, dig 결과를 함께 남긴다.

DNS 문제와 TLS 문제는 사용자 입장에선 똑같이 "사이트 접속 안 됨"이다. 하지만 운영자 입장에서 이 둘은 완전히 다른 층위의 사고다. DNS가 틀렸다면 요청은 서버 문턱도 밟지 못한 것이고, TLS가 틀렸다면 문 앞까지는 왔는데 신원 확인에서 걸려 돌아간 것이다. 그래서 앱 로그가 텅 비어 있거나 브라우저가 handshake 단계에서 멈춘다면, 코드를 뒤지기 전에 이 요청이 애초에 우리 서버에 도착이나 했는지부터 물어야 한다.

이 둘을 가르는 방법은 단순하다. dig로 이름이 제대로 풀리는지 보고, openssl s_client로 그 이름의 인증서가 신뢰되는지 본다. 이름과 인증서는 완전히 독립적인 두 실패 지점이라, 하나가 맞다고 다른 하나도 맞다는 보장이 없다.

실제로 이런 일이 있었다. 새 도메인으로 넘어간 지 며칠 지났는데, 특정 지역 사용자들만 계속 예전 IP로 붙는다는 신고가 들어왔다. 처음엔 "아직 전파가 안 끝났나 보다" 하고 넘겼는데, TTL을 확인해보니 이미 만료 시점이 한참 지나 있었다. 원인은 그 지역 ISP의 resolver가 예전 레코드를 필요 이상으로 오래 캐싱하고 있었던 것 — 우리 쪽에서 아무리 새 레코드를 내려도 그 resolver를 거치는 사용자에게는 절대 반영되지 않았다. 이럴 때 TTL을 지금 낮춰봐야 소용없다. 이미 캐시에 박힌 값에는 새 TTL이 소급 적용되지 않기 때문이다. 그래서 도메인을 옮기기로 했다면 최소 하루이틀 전에 TTL부터 낮춰두는 습관이 필요하다. CDN binding이나 certificate chain 갱신도 마찬가지로, 전 세계 모든 사용자에게 동시에 퍼지지 않는다는 걸 전제하고 복구 절차를 짜야 한다.

REQ-02

Load Balancer와 health check

Load Balancer는 단순 분산 장치가 아니라 장애 격리 장치다. health check path가 실제 의존성을 너무 깊게 보거나 너무 얕게 보면 정상 pod가 빠지거나 죽은 앱이 살아 있는 것처럼 보인다. 502는 upstream 연결 실패, 504는 timeout으로 우선 분리한다.

Load Balancer를 그냥 트래픽 나눠주는 장치로 생각하면 곤란하다. health check가 잘못 설정돼 있으면, LB가 스스로 멀쩡한 서버를 걸러내고 있어도 아무도 눈치채지 못한다. 502, 503, 504를 그냥 "5xx 에러"로 뭉뚱그려 보는 습관도 위험하긴 마찬가지다. 502는 애초에 연결 자체가 안 된 것이고, 503은 받을 여력이 없다는 뜻이고, 504는 연결은 됐는데 응답이 너무 늦어 포기한 것이다. 셋 다 "못 받았다"는 결과는 같아도 원인은 전혀 다른 곳에 있다.

배포 직후에 502·503이 늘고 target 몇 개가 unhealthy로 빠지는 건 사실 흔한 그림이다. 언젠가 이런 일이 있었다. 새 버전을 배포했더니 ALB가 target 절반을 unhealthy로 판정하고 트래픽을 안 보내기 시작했다. 처음엔 "새 버전에 버그가 있나" 하고 코드를 의심했는데, 알고 보니 새 버전의 애플리케이션이 뜨는 데 예전보다 3~4초 더 걸렸을 뿐이었다. health check가 그 3~4초를 못 기다리고 곧바로 unhealthy 판정을 내려버린 것이다. LB가 뭐라고 판단했는지(target health, listener rule, target group metric)와 앱이 실제로 어떻게 응답했는지(app access log, trace waterfall)를 나란히 놓고 보고 나서야 이걸 알아챘다. 이 상황에서 즉시 할 수 있는 건 문제의 target을 빼고(drain), rollout을 멈추는 것이다. readiness 지연 자체를 고칠지, health check 타이밍을 늘릴지는 그 다음에 천천히 판단해도 된다.

REQ-03

앱과 DB 경계

App → DB 구간은 connection pool, timeout, transaction lock, migration, secret rotation이 얽힌다. 프론트 증상만 보고 API 문제로 단정하지 말고, traceId로 request log, slow query, DB wait event를 이어 본다.

DB가 바쁘다고 항상 사용자가 피해를 보는 건 아니다. 그래서 "DB가 눌려 있다"는 신호(connection pool pending, lock wait, slow query)와 "그게 실제로 사용자에게 영향을 줬다"는 신호(request timeout, secret rotation event)를 따로 봐야 한다. 앞쪽만 보고 장애라고 단정하면, 사실 DB는 잠깐 바빴을 뿐이고 사용자 요청은 멀쩡히 처리된 경우까지 소동을 일으키게 된다. 판단 기준은 시간이다. trace waterfall에서 요청이 늘어지기 시작한 시점과 DB wait event가 튄 시점이 같아야 DB 경계 문제로 본다. 이 둘이 어긋나 있으면 진짜 범인은 다른 곳에 있다.

결제 서비스에서 이런 일이 있었다. 로그인 API가 504를 뱉기 시작했는데, 동시에 DB connection pool 대기도 치솟고 있었다. 처음엔 그냥 "DB가 느려졌다"로 결론 내리고 DB 서버 스펙을 올릴 뻔했다. 그런데 trace waterfall을 자세히 보니 늘어진 구간과 pool 대기가 튄 시점이 정확히 겹쳤고, 그 직전에 배포된 migration이 테이블 하나에 lock을 오래 잡고 있었다는 게 drill down 끝에 드러났다. 이럴 때 당장 할 수 있는 건 pool을 보호하고 slow query를 차단하는 것이고, 진짜 고쳐야 할 건 그 migration lock을 풀고 pool 크기와 timeout 값을 다시 잡는 것이다. 이 둘을 구분해서 기록해두지 않으면, 다음에 같은 증상이 나타났을 때 담당자가 또 DB 서버 스펙부터 의심하게 된다.

이 판단을 실제 지표로 옮기면 정상과 비정상이 뚜렷하게 갈린다. 정상일 때는 pool pending 낮음, slow query 없음, lock wait 없음이라는 조합으로 나타난다 — 이럴 때 API가 느리다면 DB보다는 upstream이나 app 로직을 먼저 의심해야 한다. 반대로 비정상일 때는 pool pending 급증, lock wait 증가, API timeout 동시 발생이라는 조합으로 나타난다. 이 조합이 보이면 DB 병목 또는 connection pool 설정 문제로 우선 좁혀서 조사한다.

CHECK

실무 체크리스트

서비스 요청 경로 체크리스트는 기준 경로, DNS와 TLS, Load Balancer와 health check, 앱과 DB 경계의 변경 위험을 사전에 드러내기 위한 검토표다. 각 항목은 리뷰, 배포 승인, 운영 인수에서 같은 증거로 다시 확인되어야 한다.

  • 사용자 증상, 지역, 시간, 브라우저 조건을 먼저 기록한다.
  • DNS, TLS, CDN/WAF, Load Balancer, App, DB 로그를 같은 시간축에 맞춘다.
  • 502, 503, 504, timeout, TLS error를 분리한다.
  • traceId로 프론트, API, DB 관측 신호를 연결한다.

이 체크리스트의 세 관문은 서비스 요청 경로 변경에서도 똑같이 적용된다. 설계 단계에서는 목적, 영향 범위, 비목표, owner가 산출물로 남아 있어야 한다. 영향 범위가 사용자·시스템·비용 기준으로 설명되지 않는다면, 이 단계에서 진행을 막아야 한다.

변경 단계에서는 diff, 승인 기록, 검증 명령이 함께 있어야 한다. DNS TTL이나 health check 설정처럼 눈에 잘 안 띄는 조건이 다를 수 있으니, production 변경과 staging 검증의 차이가 설명되지 않으면 배포해서는 안 된다.

복구 단계에서는 rollback 또는 forward fix, 담당자, 예상 시간이 미리 정해져 있어야 한다. 실패 시 되돌릴 수 없는데 사전 승인과 공지가 없다면 배포를 보류해야 한다.

무엇이 안 되는가를 사용자 관점 한 문장으로. "느리다"가 아니라 어떤 요청이 언제부터 어떻게 실패하는지 적는다
2 · 영향 범위scope
전체인가 일부인가. region·tenant·경로·클라이언트 중 무엇으로 갈리는지가 가설의 절반을 지운다
3 · 최근 변경recent change
직전 배포, 설정·권한 변경, 인증서·route 교체를 같은 시간축에 올린다. 대부분의 장애는 최근 변경에서 온다
4 · 증거evidence
hop 순서로 배제한다 — DNS 응답 → CDN/WAF 차단 로그 → LB target health → app latency → DB pool 대기
5 · 완화mitigation
문제 hop을 우회하거나 끊는다. 캐시 우회, LB에서 비정상 target 제외, 직전 배포 rollback이 먼저다
6 · 복구 검증verification
완화가 실제로 먹혔는지 같은 증거로 다시 확인한다. 사용자 경로를 한 번 통과시켜야 끝난 것이다
7 · 런북 갱신runbook diff
이번에 내린 판단을 문서에 되돌린다. 다음 사람이 같은 순서를 다시 발명하지 않게 하는 단계

실제로 장애가 터지면 앞서 나눈 세 hop 묶음을 그대로 따라가면 된다. 먼저 이름이 제대로 풀렸는지부터 본다 — authoritative answer와 resolver 차이, TTL·CNAME/ALIAS chain 같은 전파 조건이다. 앱 로그가 비어 있으면 여기서부터 의심해야 한다. 이름이 맞았다면 다음은 그 이름으로의 연결을 신뢰할 수 있는지다. SNI·SAN·expiry·intermediate chain 같은 인증서 조건과 WAF/CDN request id를 본다. HTTPS 실패와 WAF 차단을 앱 장애로 오판하지 않는 게 이 단계의 핵심이다. 이름도, 연결도 문제없다면 마지막으로 받은 요청을 제대로 처리했는지를 본다. target health와 502/503/504, traceId로 시작해서 pool pending·slow query까지 이어서 확인한다. timeout이 어느 hop에서 시작됐는지를 시간축으로 연결하는 게 이 마지막 단계의 목표다.

이 세 표면을 실제로 조사하는 순서도 있다. DNS 확인 단계에서는 dig +trace app.example.com, dig app.example.com @8.8.8.8을 실행해서 권한 서버 응답과 public resolver cache 차이를 구분한다. TLS 확인 단계에서는 curl -v https://app.example.com/health, openssl s_client -servername app.example.com -connect app.example.com:443으로 SNI, certificate chain, expiry, ALPN, handshake error를 본다. 경로 확인 단계에서는 LB target health, WAF log, app access log, trace waterfall, DB pool metric을 확인해 502는 upstream 연결, 504는 timeout, 503은 capacity/health 후보로 나눈다.

같은 "접속 실패"라도 계층마다 실패의 결이 다르다. DNS fail은 이름 자체가 잘못 풀리는 문제라 NXDOMAIN, wrong CNAME, resolver cache, split-horizon mismatch로 나타나는데, app log가 비어 있으면 DNS/edge에서 요청이 멈췄을 가능성이 높다. TLS fail은 이름은 맞았는데 그 연결을 신뢰할 수 없는 문제라 certificate expired, SAN mismatch, missing intermediate, SNI mismatch로 나타나므로 curl과 openssl 결과를 같이 보고 브라우저 오류 문구만 믿어서는 안 된다. LB fail은 연결까지는 됐는데 받아줄 곳이 없거나 늦는 문제라 unhealthy target, no healthy upstream, idle timeout, deregistration delay로 나타나는데, 502/503/504를 같은 서버 오류로 묶으면 원인을 놓친다. App/DB fail은 받기는 받았는데 처리가 밀리는 문제라 pool pending, lock wait, slow query, downstream timeout으로 나타나므로 trace waterfall에서 가장 먼저 늘어난 구간을 찾는 것이 우선이다.

PRACTICE

출력 판독 훈련

서비스 요청 경로는 개념을 아는 것보다 실제 출력에서 정상과 비정상을 구분하는 훈련이 중요하다. 아래 lab은 명령, 출력, 판단, 완화, 영구 수정을 한 번에 연결한다.

PRACTICE LAB 01 · ALB target health 502 판독

배포 직후 로그인 API에서 502가 증가한다. 앱 로그는 일부 요청만 남고 ALB target health가 흔들린다.

ALB가 upstream target을 정상으로 보고 있는지 확인하려면 다음을 실행한다.

aws elbv2 describe-target-health --target-group-arn arn:aws:elasticloadbalancing:region:acct:targetgroup/app-login/abc

정상적인 경우라면 target이 healthy로 표시되고 응답 코드도 정상이다.

TargetHealth.State: healthy
HealthCheckPort: traffic-port
Target.ResponseCode: 200

비정상적인 경우에는 target이 unhealthy로 표시되고 health check 자체가 실패한 이유가 함께 나온다.

TargetHealth.State: unhealthy
TargetHealth.Reason: Target.ResponseCodeMismatch
Description: Health checks failed with these codes: [500]

이 결과는 ALB 502가 앱 코드 전체의 문제가 아니라 target health check path 또는 새 버전의 readiness 문제일 수 있다는 걸 보여준다. 즉시 완화는 신규 target drain, rollout pause, 이전 artifact rollback이다. 영구 수정은 health check path를 실제 readiness와 분리하고 배포 smoke test에 target health gate를 추가하는 것이다. unhealthy target이 0이 되고 ALB 5xx가 정상화되며 app access log와 traceId가 다시 연결되면 이 조치가 제대로 된 것이다.

PRACTICE LAB 02 · DNS NXDOMAIN vs cache 판독

일부 지역 사용자만 app.example.com 접속 실패를 보고한다.

권한 DNS와 public resolver cache 차이를 분리하려면 다음을 실행한다.

dig +trace app.example.com

dig app.example.com @8.8.8.8

정상적인 경우라면 권한 DNS가 정상 응답한다.

app.example.com. 60 IN A 203.0.113.10
status: NOERROR

비정상적인 경우에는 레코드 자체가 사라져 있다.

status: NXDOMAIN
;; no servers could be reached from delegated zone

같은 도메인을 조회했는데 결과가 다르다면 이건 앱 장애가 아니라 record 삭제, zone delegation, resolver cache 문제일 수 있다. 즉시 완화는 이전 record 복구, TTL 전파 모니터링, CDN origin fallback 확인이다. 영구 수정은 DNS change ticket에 TTL 사전 조정, rollback record, 권한 DNS 검증을 필수 항목으로 넣는 것이다. authoritative resolver와 public resolver가 모두 NOERROR를 반환하고 CDN/WAF request id가 다시 등장하면 이 조치가 끝난 것이다.

TERM

용어사전

서비스 요청 경로에서 반복적으로 등장하는 운영 용어를 정의, 증거, 오해, 관련 항목 기준으로 정리한다. 장애 중에는 용어 자체보다 해당 용어가 어떤 로그, 지표, 설정, 책임 경계와 연결되는지를 확인한다.

DNS
도메인을 IP나 CNAME으로 바꿔주는 이름 해석 체계다. dig +trace나 public resolver 결과, TTL로 확인한다. "앱 로그가 비었으니 DNS는 멀쩡하겠지"라고 넘기기 쉬운데, 요청이 DNS 단계에서 막히면 애플리케이션은 애초에 그 요청을 받아본 적조차 없다.
TLS
HTTPS로 연결하기 전에 인증서와 암호화 조건을 서버와 합의하는 단계다. curl -v나 openssl s_client로 SAN/SNI/chain을 확인한다. 인증서를 무사히 발급받았다고 해서 모든 사용자의 접속이 성공하는 건 아니다 — SNI가 어긋나거나 intermediate chain이 빠지면 발급은 됐어도 handshake에서 걸린다.
CDN/WAF request id
edge 계층을 지나간 요청 하나하나에 붙는 추적 번호다. CDN log, WAF log, edge 403 여부로 확인한다. 403이 뜨면 반사적으로 앱 권한 문제라고 단정하기 쉬운데, WAF가 정상 요청을 오탐으로 걸러서 애플리케이션 근처에도 못 가고 돌아온 경우도 겉보기엔 똑같은 403이다.
target health
Load Balancer가 이 backend에 트래픽을 보내도 되는지 스스로 내리는 판정이다. LB target health, health check status, 502/503/504로 확인한다. pod가 Running이라고 LB도 그렇게 보는 건 아니다 — health check path가 실제 readiness 조건과 어긋나 있으면, 멀쩡히 살아 있는 pod도 unhealthy로 찍혀 트래픽을 못 받는다.
connection pool
App이 DB 연결을 매번 새로 맺지 않고 재사용하려고 관리하는 연결 묶음이다. pool pending, DB wait event, request timeout으로 확인한다. DB CPU가 한가하다고 DB 병목이 아니라고 단정하면 안 된다. CPU와 무관하게 pool 크기 자체가 작거나 lock wait가 늘면 똑같은 timeout이 난다.
CASE

장애/운영 시나리오

특정 시간대에 로그인 API가 간헐적으로 504를 반환한다. 먼저 DNS와 TLS가 정상인지 배제하고, CDN/WAF 차단 로그와 Load Balancer target health를 본다. 그 다음 App의 request latency와 DB connection pool 대기를 확인해 timeout이 어디에서 시작됐는지 좁힌다.

Triage frame

서비스 요청 경로 장애는 증상 → 영향 범위 → 최근 변경 → DNS 증거 → 완화책 → 복구 검증 → 재발 방지 순서로 기록한다. 이 흐름이 있어야 담당자가 바뀌어도 같은 결론에 도달한다.

처음 10분은 원인을 찾기보다 영향 범위부터 좁힌다. 이름 해석 증거(authoritative answer, resolver 차이, TTL, CNAME/ALIAS chain)를 기준으로 지금 문제가 특정 지역·특정 사용자에 국한되는지부터 고정한다. 다음 30분은 dig +trace app.example.com, dig app.example.com @8.8.8.8로 그 증거를 모아 완화책을 실행한다. 같은 탐색이 다음 장애에서 반복되지 않는 게 종료 조건이다.

장애가 종료된 뒤에는 세 항목을 incident packet에 남긴다. 증상은 특정 지역 로그인 504와 app log 일부 누락이고, DNS/edge/LB/app 중 어디까지 요청이 도달했는지를 먼저 확인해서 판정한다. 완화는 WAF rule rollback, bad target drain, feature flag off, DB pool 보호 중에서 고르는데, 사용자 영향이 줄어드는 조치를 원인 분석과 병행하는 게 원칙이다. 사후에는 missing traceId, weak health check, timeout mismatch를 runbook에 반영해서 다음 장애에서 같은 탐색을 반복하지 않게 한다.

RISK

자주 틀리는 판단

서비스 요청 경로에서 자주 틀리는 판단은 기준 경로와 앱과 DB 경계의 책임 경계를 흐리는 데서 시작된다. 아래 신호가 보이면 설계, runbook, 답변 구조를 다시 점검한다.

  • 프론트 화면 오류만 보고 API 코드부터 수정한다.
  • Load Balancer health check가 통과하면 애플리케이션도 정상이라고 단정한다.
  • TLS 인증서 문제를 네트워크 장애로 오해한다.
  • DB lock wait와 API timeout을 별개 사건으로 본다.
EVIDENCE

검증 기준·증거 패킷

서비스 요청 경로는 브라우저 증상부터 DB 경계까지 같은 traceId와 시간창으로 묶어야 한다. 각 증거는 기준일, provider, region, runtime version을 함께 남긴다.

기준일은 2026-07-09 감사를 기준으로 삼고, 장애 drill이나 구조 변경이 있을 때마다 재확인한다. incident 시작/종료 시각, deploy id, runbook revision을 남겨서 DNS, TLS, LB, app, DB 증거의 시간대와 기준일이 일치하는지 확인해야 한다.

provider/region/version 전제도 명시해야 한다. AWS ALB/NLB 또는 Azure Application Gateway/Load Balancer, 운영 region, app runtime, DB engine version을 적어두고 listener rule, target group/backend pool, health probe 설정, connection pool 설정을 함께 남긴다. 이래야 edge, regional LB, app, DB 중 어느 계층의 책임인지가 나중에도 분리된다.

명령 출력 예시는 DNS, TLS, LB health, app log, DB pool 지표를 한 요청 단위로 캡처한다. dig, openssl s_client, curl -w, ALB/App Gateway access log, target health, DB lock/pool metric을 남기면 traceId 또는 5-tuple로 hop별 정상/비정상 판정이 이어진다.

완료 기준은 증상, 첫 실패 hop, 완화, rollback, 재검증 명령이 incident packet에 모두 포함되는 것이다. before/after latency, 5xx, target health, DB wait event를 근거로 앱 배포 rollback과 인프라 rollback 중 어느 조치가 필요한지 결정한다.
