이력서·LinkedIn 문안

공개 프로필과 지원용 이력서에 옮길 문장. 사실은 이력 원장을 기준으로, 강조 순서는 지원 포지션에 맞춰 조정한다.

01

문안 편집의 입력과 결과

기간·프로젝트·기여의 근거는 개인 이력·기여 증거에서 먼저 확인한다. 지원 역할을 고른 뒤 여기의 문안을 수정한다. 전체 이력 원장을 제출 문서에 그대로 복제하지 않는다.

LinkedIn 공개 헤드라인은 일관된 주력 포지션을 유지한다. 공고별로 조정하는 것은 제출 이력서의 소개·사례 순서다. 아래 경력·교육은 공개용 요약 문안이며 원장의 사실과 다르면 원자료 확인 후 양쪽을 갱신한다.

02

소개

산업디자인에서 출발해 UI/UX를 거쳐 7년간 프론트엔드를 해왔습니다. 에너지·핀테크처럼 규칙이 복잡한 도메인의 B2B/SaaS 제품에서 화면·폼·권한·상태 전이·리포트를 프론트엔드 전 범위로 책임졌습니다. 최근 광명시 거래 플랫폼에서는 Spring Boot 백엔드의 배출권 거래 원장과 정산 트랜잭션까지 직접 구현하며 풀스택으로 넓혔습니다.

화면을 예쁘게 만드는 것보다, 사용자가 어떤 업무를 끝내야 하고 어떤 오류를 회복해야 하며 어떤 API 계약에 의존하는지를 먼저 정리합니다.

04

경력 문장 규칙

경력 bullet은 기술 스택 나열이 아니라 문제, 행동, 판단, 결과의 압축이어야 한다. 내부 수치가 공개 불가하면 측정 방식이나 재현 가능한 변화로 대신한다.

규칙좋은 문장피할 문장
문제부터 쓴다대량 공정 데이터 입력에서 사용자가 오류를 회복할 수 있도록 검증·편집 흐름을 재설계했다.React Flow와 MUI로 화면을 구현했다.
내 책임을 분리한다서버 산식은 도메인 정책을 따르고, 프론트에서는 거래내역 조회·필터·세액 표시와 검증 흐름을 담당했다.세금 신고 시스템을 전부 만들었다.
증거를 붙인다3.5년간 운영한 Next.js 기업 웹사이트에서 SEO/AEO, 성능, 문의 흐름을 반복 개선했다.웹사이트를 오래 운영했다.
공고에 맞춘다FE 공고에는 렌더링·상태·성능을, 풀스택 공고에는 API 계약·트랜잭션·도메인 경계를 앞에 둔다.모든 공고에 같은 소개문을 보낸다.
05

공개 전 검수

LinkedIn은 공개 문서이므로 강한 표현보다 검증 가능한 표현이 중요하다. 아래 기준을 통과하지 못한 문장은 공개 전 줄인다.

검수 항목통과 기준수정 방향
수치기간, 범위, 산정 기준을 함께 말할 수 있다.정확한 수치를 못 밝히면 “반복 개선”, “장기 운영”, “재현 조건”으로 바꾼다.
역할단독 구현, 공동 구현, 협업, 학습 확장을 구분했다.“리드”, “주도”, “전체”는 책임 범위가 명확할 때만 쓴다.
보안·고객 정보내부 URL, 고객명, secret, 매출·계약 수치가 없다.도메인은 익명화하고 구조와 판단만 남긴다.
타깃 적합도첫 화면에서 지원 포지션과 연결되는 키워드가 보인다.제출 이력서의 소개와 최근 경력 첫 bullet을 조정한다. 공개 프로필은 주력 포지션의 일관성을 유지한다.
