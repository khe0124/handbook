개인 작품·포트폴리오

한 작품에서 미감·도메인 이해·실제 동작을 보여준다. 업무 사례와 개인 작품을 구분하고, AI 검증은 실제 사용 범위에 맞춰 덧붙인다.

01

개인 작품·포트폴리오

이 문서는 무엇을 만들고, 어떻게 검증하고, 어떤 형태로 공개할지를 관리한다. 지원 포지션은 역할·팀 선택, 일정은 두 트랙 실행 계획, 말로 설명하는 훈련은 면접 답변에서 다룬다.

산출물목적섞지 않을 것
개인 인터랙티브 작품 하나나의 시각적 판단과 구현 기준을 직접 경험하게 한다.가상 데이터·새 작업을 과거 업무 성과로 포장하지 않는다.
업무 사례 하나이미 한 결정의 맥락·기여·한계·검증을 설명한다.팀 결과를 개인 성과로 바꾸거나 비공개 자료를 공개하지 않는다.
AI 활용 기록AI 초안 중 무엇을 채택·수정·거절했는지 보여준다.개발 보조 사용과 제품 내 모델 운영을 같은 경험으로 취급하지 않는다.
02

첫 작품 — LCA를 이해하는 하나의 인터랙션

제안하는 출발점은 “같은 제품에서 무엇이 배출량 차이를 만드는가?”를 조작으로 이해하는 작은 설명형 웹이다. 기존 제품환경평가 도메인 이해와 디자인·프론트엔드 경험을 연결하되, 회사 제품이나 데이터는 복제하지 않는다.

설계 항목이번 범위완료 조건
사용자와 질문비전문가가 재료 또는 운송 조건 하나를 바꿔 차이를 이해한다.사용자가 바뀐 결과의 이유와 가정을 자기 말로 설명할 수 있다.
핵심 흐름조건 선택 → 가상 결과 변화 → 원인·가정 보기한 경로가 처음부터 끝까지 작동하고 초기화·잘못된 입력을 다룬다.
도메인 경계단순화한 가상 계수와 데이터. 검증된 산정 도구가 아닌 설명용 데모라고 표시한다.단위·가정·한계를 결과 옆에 공개한다. 실제 환경 성과를 주장하지 않는다.
시각 기준타이포그래피, 정보 위계, 결과 변화 피드백, 절제된 모션모바일·키보드·저감 모션에서도 질문과 결과를 이해할 수 있다.
제외 범위로그인, 관리자, 결제, 범용 공정 에디터, 실제 고객 데이터기능을 추가하고 싶으면 지금의 질문을 이해하는 데 필수인지 먼저 판단한다.
AI의 역할초안 구현·테스트 후보·리뷰 보조최종 미감·도메인 가정·검증·출시 판단은 직접 한다. RAG 기능을 넣는 것이 목표가 아니다.

도메인 공개 제약이 크면 같은 원칙으로 가상 에너지 사용량 설명 UI를 택한다. 두 후보를 동시에 만들지는 않는다.

03

작품과 사례를 묶는 최소 구조

보여줄 것포함할 내용
동작하는 결과데모 또는 재현 가능한 실행 방법, 핵심 조작 안내, 현재 한계.
한 장의 사례 글문제·대상 → 범위 → 내 결정 → 대안 → 검증 → 한계. 업무 작업이라면 기여 원장을 기준으로 작성한다.
시각적 판단전후 화면과 위계·간격·타이포·모션을 바꾼 이유. 예쁜 화면만 모으지 않는다.
검증 결과주요 흐름 테스트, 모바일·키보드 확인, 필요한 성능 측정의 조건과 결과. 확인하지 않은 것은 미확인으로 남긴다.
공개 범위공개 가능 여부, 데이터 출처·권한, 가상 예시 표시, 비공개 정보 제거.

한 장의 기록에서 시작한다. 아래 파일명은 내용을 찾기 위한 선택지이며 문서 수를 채우는 필수 목록이 아니다. 글·영상은 이 기록을 재사용하고 새로운 주제를 병렬로 열지 않는다.

04

산출물 지도 — 이력을 증거로 바꾸기

아래는 전부 만들어야 할 목록이 아니라, 지원할 공고의 갭에 맞춰 하나만 고를 사례 후보입니다. 산출물은 검증 가능한 증거입니다. 하나의 프로젝트에서 PM, 개발자, UX 관점의 산출물이 동시에 나올 수 있지만, 역할을 부풀리면 안 됩니다.

후보산출물소스완료 기준
1성능 개선 회고제품환경평가 대형 폼, Greenery 웹사이트, 코드 스플리팅증상, 측정, 원인, 조치, 전후 증거가 있다.
2트랜잭션·원장 ADRgks-car-be VRC 원장, 비관락, 상태 전이맥락, 결정, 대안, trade-off, 테스트 증거가 있다.
3스펙 갭 분석 + 사용자 여정 맵제품환경평가 실패 회복, 광명 도메인 시장 라이프사이클요구, 발견한 갭, 제안, 구현, 결과가 한 장에 있다.
4디버깅 회고상태·동시성·성능 버그 중 하나재현, 가설, 기각, 근본원인, 재발방지가 있다.
5AI Native 검증 루프 공개물task spec, generated diff, test output, rejected suggestionAI가 한 일과 사람이 승인한 판단이 분리된다.
파일명 규칙career/artifacts/{pm|dev|ux}-{project}-{topic}.md 로 저장한다. 공개 가능, 익명화 필요, 구두 설명만 가능, 비공개를 머리말에 표시한다.
05

미감과 구현을 함께 검수

기준확인할 질문남길 증거
위계·밀도첫 화면에서 무엇을 읽고 무엇을 조작해야 하는가? 여백과 카드가 내용보다 앞서지 않는가?핵심 화면 전후와 바꾼 이유.
타이포·정렬수치·단위·설명·조작의 관계가 일관되는가?같은 내용의 모바일·데스크톱 화면.
인터랙션조작 결과가 보이고 잘못된 입력에서 회복할 수 있는가?핵심 경로와 오류 경로 테스트.
접근성·성능키보드·작은 화면·모션 감소에서도 쓸 수 있는가?확인한 환경과 결과. 측정했다면 장치·조건·기준선을 함께 남긴다.
도메인 설명단순화한 가정과 사실을 혼동시키지 않는가?사용자 피드백과 설명을 바꾼 기록.
06

2016–2019 시각 작업 아카이브 전략

2016년부터 2019년 사이의 ai, psd, png 작업은 대표작처럼 포장할 대상이 아닙니다. 대신 지금의 미감이 어디서 시작됐고, 어떤 실패를 지나 기준이 생겼는지를 보여주는 시각적 여정의 원본 자료로 다룹니다.

분류판단 기준자산화 방식
visual sense seed완성도는 낮아도 지금의 취향과 연결되는 색, 여백, 질감, 구도, 타이포그래피가 보인다.“이미 있던 감각”의 증거로 보드에 남긴다.
bad but useful후지지만 문제의식, 주제 선택, 실험 의도가 읽힌다.실패한 판단과 지금의 해석을 나란히 적는다.
craft gap왜 어설픈지 설명할 수 있다. 정렬, 위계, 밀도, 폰트, 이미지 처리 중 하나가 깨져 있다.지금이라면 고칠 기준을 critique note로 남긴다.
theme repeat반복되는 관심사, 분위기, 소재, 화면 구성 방식이 있다.현재 브랜드와 이어지는 패턴으로 묶는다.
discard지금의 방향과 연결되지 않고 설명할 기준도 없다.보관만 하고 공개 자산에서는 제외한다.
ARCHIVE PRINCIPLE오래된 작업은 “잘 만든 작품”으로 살리는 것이 아니라 “지금의 기준이 형성되기 전의 원본 자료”로 살린다. 목표는 미화가 아니라 해석이다.
단계할 일완료 기준
1. 수집ai, psd, png, jpg, pdf를 연도별 폴더로 모은다.2016, 2017, 2018, 2019 폴더가 생긴다.
2. 미리보기파일을 전부 열지 말고 썸네일과 빠른 export로 훑는다.각 연도별 후보 10개 이하가 남는다.
3. 30개 선별좋고 나쁨이 아니라 “지금의 나와 연결되는가”로 고른다.전체 후보 30개 안팎의 visual journey set이 생긴다.
4. reading 작성각 작업에 당시 의도, 지금 보이는 문제, 남아 있는 감각, 지금이라면 고칠 기준을 쓴다.이미지당 3~5문장 critique note가 붙는다.
5. 보드화연도별로 5~8개 이미지를 배치하고 흐름을 만든다.visual-journey-2016-2019.pdf 또는 웹 페이지가 생긴다.
6. 재가공가치 있는 3~5개만 remake 또는 before/reading 콘텐츠로 만든다.포트폴리오, 글, 영상에 쓸 수 있는 사례가 생긴다.
공개 문장

2016–2019 Visual Archive는 완성작 모음이 아니라, 지금의 미감과 작업 기준이 형성되기 전의 원본 자료다. 조악한 결과물 안에서도 반복되는 관심사, 실패한 비례, 어설픈 타이포그래피, 지금까지 이어지는 시각적 집착을 읽어내기 위한 아카이브다.

저장 구조역할
originals/2016–2019원본 ai, psd, png를 연도별로 보관한다.
exports/원본을 열지 않아도 볼 수 있는 jpg/png 미리보기를 저장한다.
notes/연도별 reading note와 개별 critique note를 저장한다.
boards/visual journey PDF, 웹 페이지, 발표용 보드를 저장한다.
remake-candidates.md다시 만들 가치가 있는 작업과 이유를 남긴다.
첫 실행현재 작품을 먼저 진행한다. 아카이브가 그 판단을 설명하는 데 필요할 때만 작은 묶음을 골라, 각 이미지에 “당시 좋았던 감각 / 지금 보이는 문제 / 지금이라면 고칠 기준” 세 줄만 붙인다.
07

AI 작업 루프

AI Native 경험은 “AI에게 시켰다”가 아니라 루프를 운영한 기록입니다. 작업 루프는 입력, 생성, 검증, 수정, 기록으로 남아야 합니다.

단계내가 한 일AI에게 맡긴 일남길 증거
Frame문제, 범위, 금지 범위, 성공 기준을 정의누락 요구사항과 위험 후보 제안task-spec.md
Context기존 코드, API, 상태, 권한, 데이터 규칙을 정리맥락을 구현 단위로 재구성context-package.md
Generate작은 변경 단위로 요청하고 diff를 검토초안 코드, 테스트, 문서 생성generated-diff-review.md
Verify테스트·빌드·수동 QA·보안 fixture를 실행누락 테스트와 edge case 제안test-build-results.md
Decide채택, 수정, 거절, 후속 과제를 확정릴리스 노트와 위험 요약 초안release-packet.md
작업 루프 한 문장AI는 빠른 초안 작성자이고, 저는 요구사항 분해자·리뷰어·검증 책임자입니다. 그래서 제 포트폴리오는 최종 화면뿐 아니라 AI 출력이 어떤 기준으로 채택되거나 거절됐는지까지 보여줍니다.
08

AI 활용 EVIDENCE PACKET

적용 대상남길 최소 기록확장할 때
AI로 개발을 보조한 모든 작업목표·제외 범위·통과 기준, 제공한 맥락, 채택/수정/거절한 제안과 이유, 실제 실행한 테스트 결과.task-spec.md, context-package.md, generated-diff-review.md, test-build-results.md 등으로 분리할 수 있다.
제품이 실제 모델을 호출하는 작업만평가셋·기준선·실패 유형·권한 경계·민감정보 처리·지연·비용·fallback.eval-report.md, security-fixtures.md, ops-trace.md. 아래 AI 기능 검증 장부를 사용한다.

AI가 쓴 코드량이나 프롬프트 개수 대신, 사람이 어떤 위험을 발견하고 최종 판단했는지 한 사례로 증명한다. 비공개 코드·고객 데이터·키가 포함된 입력과 로그는 공개하지 않는다.

09

제품 내 AI가 있을 때만 — Eval·Security·Ops

적용 조건: 제품 자체가 모델을 호출하거나 검색·생성 결과를 제공할 때 사용한다. AI로 코드를 작성했을 뿐인 일반 UI 작품에는 이 평가 장부를 요구하지 않는다. 아래 수치는 형식을 보여주는 가상 예시이며 개인 성과나 권장 임계값이 아니다.

AI 기능은 데모가 쉬운 만큼 과장도 쉽습니다. 아래 기준을 준비해야 “실제로 품질을 어떻게 보장했나요?”라는 질문에 버틸 수 있습니다.

축준비할 증거면접 답변
Evaluationgolden question, baseline/candidate report, pass/fail threshold프롬프트 감이 아니라 평가셋과 기준선으로 변경을 판단했습니다.
Groundingcitation trace, no-answer policy, unsupported claim rejection근거 없는 답은 답변하지 않거나 사람 검토로 넘기도록 설계했습니다.
Securityprompt injection fixture, permission boundary, PII redaction사용자 입력과 검색 문서는 instruction이 아니라 untrusted data로 취급했습니다.
Operationsp95 latency, token cost, cache hit, fallback plan품질뿐 아니라 비용과 지연시간도 릴리스 판단에 포함했습니다.
Human Reviewreview queue, confidence threshold, audit trail고위험 판단은 자동화하지 않고 사람 검토 경로를 둡니다.

순서작성 내용
1. 결과와 문제데모 링크·대표 화면·사용자가 이해하거나 해결할 질문.
2. 범위와 역할개인 작업/업무 사례 여부, 데이터 출처, 본인·팀·AI가 한 일.
3. 결정과 대안선택한 UI·상태·API 구조와 제외한 대안, 시각적 판단.
4. 검증재현 방법, 확인 환경, 테스트·피드백 결과. 실제 AI 기능이면 평가·보안·운영 근거를 추가한다.
5. 한계와 다음 판단아직 확인하지 못한 것, 단순화한 가정, 공개할 수 없는 범위, 개선할 한 가지.

공개 전 점검

질문완료 기준
직접 경험할 수 있는가?링크 또는 실행 방법으로 핵심 흐름이 동작한다.
나의 판단이 보이는가?중요한 선택 하나와 제외한 대안 하나를 이유로 설명한다.
사실과 가상이 분리되는가?샘플 데이터·예시 수치·학습 구현을 실제 업무 결과처럼 말하지 않는다.
검증과 권한을 확인했는가?주요 경로와 접근성을 확인하고 자료 공개 범위를 지켰다.
다음에도 재사용할 수 있는가?작업에서 배운 기준을 짧은 글로 남겼다. 책·영상 제작은 그 다음 선택이다.
