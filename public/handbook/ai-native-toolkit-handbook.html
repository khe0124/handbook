UX/UI 디자인 검토와
화면 설계

이 문서는 AI를 디자이너 대체물이 아니라 화면 상태, 오류 흐름, 접근성, 반응형 누락을 찾는 리뷰어로 사용하는 방법을 다룹니다.

읽기 전에

이 문서에서 AI Agent는 스스로 도구를 실행하는 runtime agent가 아니라, 역할을 분리한 역할 프롬프트(Requirements Analyst, UX Reviewer 등)를 뜻한다. 실제 tool-use·자율 실행 agent 런타임은 08–10 practice-AX 트랙에서 다룬다.

이 트랙의 모든 단계는 하나의 canonical loop를 공유한다: Plan → Act → Verify → Reflect를 stop condition에 도달할 때까지 반복한다. 아래 단계별 화살표는 이 loop를 한 단계에 한 번 통과시킨 단면이다.

UX-00

왜 디자인 단계에 AI를 쓰는가

풀스택 개발자는 디자인을 그대로 구현하는 데서 멈추면 안 됩니다. 실제 제품은 로딩, 빈 상태, 오류, 권한 없음, 모바일, 키보드 접근성에서 깨집니다. AI Reviewer는 이 누락을 빠르게 훑는 역할을 합니다.

검토 영역AI가 찾는 것사람이 결정하는 것
화면 상태empty/loading/success/error/disabled 상태 누락실제 구현할 상태와 문구
사용자 행동다음 행동이 모호한 지점CTA 우선순위
접근성label, focus, keyboard, contrast 위험디자인 시스템 기준 적용
반응형좁은 화면에서 깨지는 레이아웃모바일 배치와 숨김 기준

USE

실제로 이렇게 사용한다

디자인 검토에서 AI는 시각적 취향을 결정하는 사람이 아니라 누락 탐지자입니다. 사용자 흐름과 현재 화면 상태를 주고, 빠진 상태와 접근성 위험을 찾게 합니다.

내 입력:
백오피스 환불 승인 화면을 구현하려고 해.
현재 화면에는 환불 요청 테이블, 상태 필터, 상세 drawer,
승인 버튼, 반려 버튼만 있어.

너는 UX Reviewer야.
아래 관점으로 빠진 것을 찾아줘.
1. 화면 상태
2. 오류 메시지
3. 접근성
4. 모바일 레이아웃
5. 사용자가 다음 행동을 모르는 지점
AI 출력 예사람의 결정
already_processed와 payment_provider_failed 오류를 분리해야 함둘 다 별도 banner/inline message로 구현
승인 버튼이 너무 쉽게 눌림금액과 사유를 다시 보여주는 confirm modal 추가
상세 drawer가 키보드 focus를 가두지 않음focus trap, escape close, aria-labelledby를 구현 체크리스트에 추가
screen-state-checklist.md:
screen_states:
  idle: "filter, table, selected refund request"
  reviewing: "detail drawer with order/payment/customer reason"
  submitting: "approve/reject buttons disabled, loading text"
  success: "updated status + audit log refresh"
  error:
    - already_processed
    - invalid_refund_amount
    - payment_provider_failed
    - forbidden
accessibility:
  - "filter inputs have labels"
  - "detail drawer has aria-labelledby"
  - "confirm modal traps focus"
  - "keyboard approval flow works"
개념

AI에게 “예쁜 화면”을 요청하면 산출물이 흐려집니다. 대신 “사용자가 막히는 상태를 찾아라”라고 요청해야 구현 체크리스트가 나옵니다.

UX-02

백오피스 환불 승인 화면 상태

상태화면 요구검토 질문
기본필터, 검색, 환불 요청 테이블상태, 금액, 요청일, 담당자가 스캔 가능한가
빈 목록조건에 맞는 요청 없음 안내필터 초기화 행동이 보이는가
상세 검토주문/결제/문의/감사 로그 drawer승인 판단에 필요한 정보가 한 곳에 있는가
승인/반려 중button disabled, progress 표시중복 처리와 실수 클릭이 막히는가
이미 처리됨already_processed 메시지일반 실패로 뭉개지지 않는가
권한 없음승인/반려 버튼 대신 읽기 전용 안내권한 요청 경로가 있는가
UX-03

검수 기준

Bad practiceBest practice
AI에게 화면을 예쁘게 만들어달라고만 한다상태, 오류, 접근성, 모바일 체크리스트를 요청한다
성공 화면만 구현한다권한 없음, 이미 처리됨, 결제사 실패, 중복 제출 상태을 함께 설계한다
AI가 제안한 UI를 그대로 따른다기존 디자인 시스템과 제품 톤에 맞춰 사람이 조정한다

DONE

완료 가능성 패킷 (dev workflow)

이 단계 산출물은 제품에 배포된 AI 시스템이 아니라 개발 과정에 AI를 쓴 기록이다. 그래서 완료 기준은 hallucination률·p95 latency·cost가 아니라, 사람의 결정이 분리·검증·추적되는가이다. 런타임 AI 품질 지표가 필요한 작업은 LLM 로드맵과 AI Native 작업 표준을 따른다.

항목기록 기준통과 기준
검증일·환경작업일, 사용한 AI 도구/모델, 대상 코드 브랜치를 남긴다.재실행자가 같은 입력과 도구로 결과를 다시 만들 수 있다.
결정 분리AI가 만든 질문·제안과 사람이 확정한 결정을 나눠서 남긴다.채택/거절한 AI 제안과 그 근거가 로그로 남는다.
범위 고정non-goal과 acceptance criteria를 작업 전에 적는다.MVP와 후속 범위가 분리되고 수용 기준이 테스트 가능한 문장이다.
구현 연결각 결정이 UI/API/DB 중 어디에 영향을 주는지 연결한다.결정이 코드 변경 지점으로 추적된다.
검증 증거실행한 검증 명령(test/build/수동 QA)과 결과를 남긴다.테스트·빌드가 통과했고 실패 케이스가 회귀로 고정됐다.
중단·롤백배포 후 되돌릴 조건을 정량으로 적는다. 에러율은 분모·측정 시간창·최소 트래픽을 함께 명시한다.feature flag·이전 버전·수동 처리 루트가 준비돼 있다.
