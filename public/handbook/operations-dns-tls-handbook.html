FLOW

이름과 신뢰는 별개 문제다

이름이 IP로 바뀌는 순간과 그 연결이 안전하다고 증명되는 순간은 서로 다른 문제다. DNS는 A, AAAA, CNAME, ALIAS, CAA 같은 record로 이름을 해석하고, TTL은 장애 대응 속도와 resolver 부하 사이의 트레이드오프다 — 그래서 작업 전에는 TTL을 낮추고 안정화 후에 다시 올린다. 같은 이름이 내부와 외부에서 다른 IP로 해석되는 split-horizon 구성도 흔한데, 이때는 장애 분석보다 먼저 사용자가 어느 resolver를 쓰는지부터 확인해야 한다.

TLS는 발급 성공과 handshake 성공이 다르다는 게 핵심이다. 인증서가 발급됐어도 SAN 범위, wildcard, SNI, intermediate chain, OCSP, 자동 갱신이 함께 맞지 않으면 브라우저에서는 여전히 실패한다. 그래서 도메인을 바꾸는 작업은 하나의 절차로 묶인다 — 사전 TTL 조정, record diff, 인증서 준비, smoke test, 전파 모니터링, rollback record까지, 새 경로와 이전 경로가 전파되는 동안 둘 다 안전해야 한다.

DNS TLS CHANGE PLAYBOOK은 권한 DNS(dig +trace), 인증서(openssl s_client -showcerts), 사용자 경로(curl -v --resolve)를 이 순서로 확인하게 하고, TLS chain/SNI 판독 실습은 모바일 브라우저 일부에서만 인증서 오류가 나는 상황을 놓고 정상 응답(Verify return code: 0)과 비정상 응답(unable to verify the first certificate)을 나란히 대조시킨다. 도메인을 새 CDN으로 옮기는 실전 사례도 같은 원칙을 따른다 — 24~48시간 전에 TTL을 낮추고, 인증서를 미리 붙이고, 일부 트래픽으로 먼저 검증한 뒤에야 전체를 전환한다.

이 영역에서 가장 자주 나오는 실수는 TTL을 작업 직전에 낮추는 것, 인증서가 발급됐다는 이유로 SNI와 chain 검증을 생략하는 것, 내부와 외부 resolver 결과 차이를 놓치는 것이다. 결국 모든 판단은 두 질문으로 좁혀진다 — 이 이름은 지금 어느 resolver 기준으로 어떤 IP로 해석되는가, 그리고 이 연결은 handshake까지 실제로 신뢰할 수 있는가. 브라우저에서 한 번 성공했다고 이 두 질문에 답한 것은 아니다.

DNS-00

DNS record와 TTL

A, AAAA, CNAME, ALIAS, TXT, CAA record의 목적을 구분한다. TTL은 장애 대응 속도와 resolver 부하 사이의 선택이다. 이전 작업 전 TTL을 낮추고, 작업 후 안정화되면 다시 올린다.

TTL을 다들 "짧을수록 안전하다"고만 생각하는데, 짧으면 그만큼 모든 resolver가 우리 권한 서버에 더 자주 물어본다는 뜻이기도 하다. 그래서 평소엔 적당히 길게 두고, 변경 작업 직전에만 짧게 낮추는 식으로 운영한다. 문제는 이 타이밍을 놓쳤을 때 벌어진다.

도메인을 옮기던 날, 일부 사용자만 간헐적으로 예전 IP로 계속 붙는다는 신고가 들어왔다. dig NS와 dig +trace로 권한 서버 응답을 보니 이미 새 값을 정확히 돌려주고 있었다. 그런데 그 사용자들이 쓰는 public resolver만 여전히 예전 값을 캐시하고 있었다. 이때 반사적으로 나오는 생각이 "그럼 지금이라도 TTL을 낮추면 금방 퍼지지 않을까"인데, 이건 틀렸다. 이미 캐시에 박힌 값에는 새 TTL이 소급 적용되지 않는다. TTL은 반드시 작업 전에 미리 낮춰둬야 의미가 있고, 이미 벌어진 일이라면 이전 record를 되돌리면서 전파 상황을 지켜보는 수밖에 없다.

DNS-01

split-horizon DNS

같은 이름이 내부와 외부에서 다른 IP로 해석되는 split-horizon DNS는 VPN, 사내망, Private Endpoint에서 자주 필요하다. 장애 분석 시 사용자가 어느 resolver를 쓰는지 먼저 확인한다.

split-horizon DNS 자체는 이상한 설정이 아니다. VPN이나 사내망 사용자에게는 사설 IP를, 일반 인터넷 사용자에게는 public IP를 돌려주는 건 흔히 필요한 구성이다. 문제는 이게 "왜 이렇게 설계됐는지"가 문서에 안 남아 있을 때다. 그러면 장애가 날 때마다 담당자가 처음부터 다시 원리를 재구성해야 한다.

VPN으로 접속한 사용자만 내부 API를 못 쓴다는 신고를 받은 적이 있다. dig로 한 번 조회해봤더니 멀쩡했다 — 그런데 알고 보니 내가 개인 노트북에서 조회한 건 public resolver를 거친 결과였다. VPN 사용자는 그 이름을 internal resolver로 조회하고 있었고, 거기서는 다른 답이 나오고 있었다. "한 resolver로 조회한 결과가 모든 사용자에게 똑같이 적용된다"는 가정이 얼마나 위험한지 이때 체감했다. 결국 resolver rule과 Private DNS zone link 설정이 어긋나 있었다는 걸 internal과 public 양쪽을 나란히 조회하고 나서야 알아챘다. 한쪽만 확인하고 "정상"이라고 결론 냈다면, VPN 사용자 쪽 문제는 계속 미해결로 남았을 것이다.

DNS-02

TLS 인증서

TLS 운영은 인증서 발급만이 아니다. SAN, wildcard 범위, SNI, intermediate chain, OCSP, 자동 갱신, 만료 알림, CAA 정책을 함께 본다. 인증서 교체는 rollback 가능한 변경으로 관리한다.

인증서 발급 알림에 초록불이 뜨면 다들 안심하고 넘어간다. 하지만 발급 성공과 사용자 브라우저에서의 handshake 성공은 완전히 다른 이야기다. 그 사이에서 SNI가 어긋나거나 intermediate chain이 빠지면, 발급은 멀쩡히 됐어도 접속은 계속 실패한다.

실제로 겪은 일인데, 데스크탑 브라우저에서는 다 잘 되는데 모바일 브라우저 일부에서만 인증서 오류가 난다는 신고가 들어왔다. 처음엔 "모바일 쪽 캐시 문제겠지" 하고 넘길 뻔했다. openssl s_client로 chain을 직접 까보고 나서야 원인을 알았다 — intermediate 인증서 하나가 서버에서 빠져 있었는데, 대부분의 데스크탑 브라우저는 자체적으로 이 intermediate를 캐싱하고 있어서 문제가 안 드러났을 뿐이었다. 모바일 브라우저는 그런 캐시가 없어서 곧바로 걸렸다. SNI, chain, SAN 이 셋은 꼭 따로 확인해야 한다. 하나만 놓쳐도 특정 클라이언트에서만 재현되는, 잡기 까다로운 실패가 생긴다. 즉시 완화는 빠진 중간 인증서를 다시 연결하는 것이었고, 영구 수정은 renewal alert를 다시 살려서 다음번엔 이런 게 조용히 빠지지 않게 만드는 것이었다.

DNS-03

도메인 변경 절차

도메인 변경에는 사전 TTL 조정, record diff, 인증서 준비, CDN/WAF 연결, smoke test, 전파 모니터링, rollback record가 필요하다. dig, curl -v, openssl s_client 결과를 변경 티켓에 남긴다.

도메인 변경은 항상 "새 경로가 잘 되는가"만 확인하고 끝내기 쉬운데, 진짜 위험한 건 전파되는 그 며칠 동안이다. 새 경로만 완벽하게 준비하고 이전 경로를 방치하면, 아직 전파가 안 끝난 사용자들이 그 사이에서 계속 피해를 본다.

새 CDN으로 옮긴 다음 날, 특정 지역에서만 403이 뜬다는 신고가 들어왔다. dig로 그 지역 resolver 결과를 찍어보니 이미 새 CDN을 가리키고 있었다. 문제는 CDN 쪽이었다 — 새 CDN의 WAF 설정이 아직 그 지역 트래픽 패턴에 맞게 튜닝되지 않아서 정상 요청을 막고 있었던 것이다. 여기서 중요한 교훈은, 전파가 진행되는 동안에는 어떤 사용자는 이전 endpoint를, 어떤 사용자는 새 endpoint를 동시에 보고 있다는 걸 항상 전제해야 한다는 점이다. 이 상황에서는 CDN rule을 rollback하면서 동시에 전파 상태를 계속 추적해야 했다. rollback만 하고 전파 상태를 놓쳤다면, 되돌린 게 정말 모든 지역에 반영됐는지 확인할 방법이 없었을 것이다.

CHECK

실무 체크리스트

DNS·TLS·도메인 운영 체크리스트는 DNS record와 TTL, split-horizon DNS, TLS 인증서, 도메인 변경 절차의 변경 위험을 사전에 드러내기 위한 검토표다. 각 항목은 리뷰, 배포 승인, 운영 인수에서 같은 증거로 다시 확인되어야 한다.

  • record 종류와 TTL 변경 계획을 사전에 작성한다.
  • CAA, SAN, wildcard, SNI, intermediate chain을 확인한다.
  • 인증서 만료 알림과 자동 갱신 실패 알림을 둔다.
  • 도메인 변경 전후 dig, curl, openssl 결과를 기록한다.

이 체크리스트의 세 관문은 DNS·TLS 변경에서도 똑같이 적용된다. 설계 단계에서는 목적, 영향 범위, 비목표, owner가 산출물로 남아 있어야 한다. 영향 범위가 사용자·시스템·비용 기준으로 설명되지 않는다면, 이 단계에서 진행을 막아야 한다.

변경 단계에서는 diff, 승인 기록, 검증 명령이 함께 있어야 한다. TTL이나 인증서 chain처럼 눈에 잘 안 띄는 조건이 다를 수 있으니, production 변경과 staging 검증의 차이가 설명되지 않으면 배포해서는 안 된다.

복구 단계에서는 rollback 또는 forward fix, 담당자, 예상 시간이 미리 정해져 있어야 한다. 실패 시 되돌릴 수 없는데 사전 승인과 공지가 없다면 배포를 보류해야 한다.

PLAYBOOK

실무 플레이북

DNS·TLS·도메인 운영 플레이북은 DNS TLS CHANGE PLAYBOOK 기준으로 증상, 범위, 최근 변경, 계층별 증거를 연결한다. 목표는 명령어 암기가 아니라 어떤 가설을 버리고 어떤 완화책을 실행할지 결정하는 것이다.

DNS TLS CHANGE PLAYBOOK symptom → scope → recent change → evidence
→ mitigation → verification → runbook diff

DNS·TLS 장애를 다룰 때도 "왜 연결이 안 되는가"를 이름 문제인지 신뢰 문제인지 되돌릴 수 있는 문제인지로 나눠서 본다. DNS record 표면은 "이름이 아직 안 퍼진 것인지, 애초에 틀린 것인지"를 record type, authoritative answer, TTL, resolver cache, CAA로 구분한다. 전파 지연 때문에 아직 안 퍼진 것과 권한 서버가 처음부터 잘못된 값을 돌려주는 것은 완전히 다른 문제이므로 여기서 갈라야 한다. TLS chain 표면은 "이름은 맞았는데 그 연결을 신뢰할 수 있는가"를 SAN, issuer, expiry, intermediate, SNI, OCSP로 확인한다. 인증서 발급 성공과 사용자 handshake 성공이 다르다는 걸 여기서도 다시 확인한다. Rollback 표면은 "지금 조치를 되돌릴 수 있는가"를 previous record, previous certificate, CDN/WAF binding, smoke result로 확인한다. 도메인 변경도 언제든 되돌릴 수 있는 변경으로 다뤄야 한다.

이 세 표면을 실제로 조사하는 순서도 있다. 권한 DNS 확인 단계에서는 dig +trace app.example.com, dig NS example.com, dig CAA example.com을 실행해서 권한 서버와 resolver cache를 분리한다. 인증서 확인 단계에서는 openssl s_client -servername app.example.com -connect app.example.com:443 -showcerts로 SNI와 chain 누락을 확인한다. 사용자 경로 확인 단계에서는 curl -v --resolve app.example.com:443:IP https://app.example.com/health로 DNS 변경 전후 edge와 origin을 분리해서 테스트한다.

PRACTICE

출력 판독 훈련

DNS·TLS·도메인 운영은 개념을 아는 것보다 실제 출력에서 정상과 비정상을 구분하는 훈련이 중요하다. 아래 lab은 명령, 출력, 판단, 완화, 영구 수정을 한 번에 연결한다.

PRACTICE LAB 01 · TLS chain/SNI 판독

모바일 브라우저 일부에서만 인증서 오류가 발생한다.

SNI, SAN, 만료일, intermediate chain 누락을 확인하려면 다음을 실행한다.

openssl s_client -servername app.example.com -connect app.example.com:443 -showcerts

정상적인 경우라면 chain 검증이 통과하고 SAN도 현재 도메인과 일치한다.

Verify return code: 0 (ok)
subjectAltName = DNS:app.example.com
notAfter=Sep 20 12:00:00 2026 GMT

비정상 출력, 즉 비정상적인 경우에는 chain 검증에 실패하고 SAN도 예전 도메인을 가리킨다.

Verify return code: 21 (unable to verify the first certificate)
subjectAltName = DNS:old.example.com

서버 연결 자체는 되지만 인증서 체인 또는 SNI binding이 잘못된 상태라는 뜻이다. 즉시 완화는 CDN/LB 인증서 binding을 rollback하거나 올바른 certificate chain을 재배포하는 것이다. 영구 수정은 certificate inventory, renewal alert, SNI smoke test를 배포 gate에 추가하는 것이다. openssl verify가 ok로 나오고 curl -v handshake가 성공하며 브라우저 오류 재현이 멈추면 이 조치가 끝난 것이다.

용어사전

DNS·TLS·도메인 운영에서 반복적으로 등장하는 운영 용어를 정의, 증거, 오해, 관련 항목 기준으로 정리한다. 장애 중에는 용어 자체보다 해당 용어가 어떤 로그, 지표, 설정, 책임 경계와 연결되는지를 확인한다.

TTL
resolver가 DNS 응답을 얼마나 오래 캐시할지 정하는 값이다. authoritative answer, resolver cache, provider change history로 확인한다. 작업 직전에 TTL을 낮추면 곧바로 퍼질 거라 기대하기 쉬운데, 이미 캐시에 박힌 값에는 새 TTL이 소급 적용되지 않는다. 그래서 TTL 조정은 늘 작업 전에 미리 해둬야 한다.
CNAME/ALIAS
한 이름을 다른 이름이나 provider의 alias 대상으로 연결하는 record다. CNAME/ALIAS chain, dig result로 확인한다. 어느 provider든 ALIAS는 다 똑같이 동작할 거라 생각하고 설정을 그대로 옮기는 경우가 있는데, flattening 방식과 apex domain 지원 여부가 provider마다 달라서 예상과 다르게 동작하는 일이 흔하다.
CAA
어떤 CA가 이 도메인의 인증서를 발급할 수 있는지 제한하는 DNS record다. dig CAA, certificate issuance log로 확인한다. 인증서 발급과는 별 상관없는 설정처럼 보이지만, CAA가 새로 쓰려는 CA를 허용하지 않으면 발급 자체가 거부된다. 그래서 인증서를 교체하기 전에 CAA부터 확인해야 헛수고를 안 한다.
split-horizon DNS
같은 이름이 내부와 외부에서 서로 다른 IP로 풀리는 구성이다. internal resolver, public resolver, Private DNS zone으로 확인한다. 한 번 조회해본 결과가 모든 사용자에게 똑같이 적용될 거라 넘겨짚기 쉬운데, VPN 사용자와 일반 인터넷 사용자는 애초에 서로 다른 resolver를 거치므로 같은 이름이라도 다른 답을 받는다.
SNI
TLS handshake 초반에 접속하려는 hostname을 서버에 미리 알려주는 값이다. openssl s_client -servername, SAN mismatch로 확인한다. IP만 맞으면 인증서도 알아서 맞을 거라 생각하기 쉬운데, 같은 IP에 여러 도메인이 함께 물려 있는 경우 SNI가 어떤 인증서를 내줄지를 실질적으로 결정한다.
CASE

장애/운영 시나리오

도메인을 새 CDN으로 이전한다. 24~48시간 전에 TTL을 낮추고, 새 CDN에 인증서를 미리 붙인다. CAA와 DNS record diff를 리뷰하고, 일부 트래픽으로 smoke test를 수행한 뒤 문제가 생기면 이전 record로 rollback한다.

Triage frame

DNS·TLS·도메인 운영 장애는 증상 → 영향 범위 → 최근 변경 → DNS record 증거 → 완화책 → 복구 검증 → 재발 방지 순서로 기록한다. 이 흐름이 있어야 담당자가 바뀌어도 같은 결론에 도달한다.

처음 10분은 원인을 찾기보다 영향 범위부터 좁힌다. record type, authoritative answer, TTL, resolver cache, CAA 기준으로 지금 문제가 특정 resolver나 특정 클라이언트에 국한되는지부터 고정한다. 다음 30분은 dig +trace app.example.com, dig NS example.com, dig CAA example.com 항목에서 증거를 모아 완화책을 실행한다. 갱신 실패가 실제 장애로 번지기 전에 알림이 오는 게 종료 조건이다.

초기 대응 시간표와 별도로, 사후 리뷰에서는 세 항목을 incident packet에 남긴다. 증상은 일부 고객만 인증서 오류를 보거나 구버전 IP로 접속되는 것이고, resolver, TTL, chain, CDN binding을 순서대로 확인해서 판정한다. 완화는 이전 record 복구, 인증서 재연결, CDN cache purge 중에서 고르는데, 전파가 진행 중일 때는 이전 경로와 새 경로 양쪽 endpoint가 모두 안전해야 한다는 원칙을 지킨다. 사후에는 TTL 사전 변경, CAA/renewal alert, certificate inventory를 추가해서 갱신 실패가 장애로 번지기 전에 알림이 오게 만든다.

RISK

자주 틀리는 판단

DNS·TLS·도메인 운영에서 자주 틀리는 판단은 DNS record와 TTL와 도메인 변경 절차의 책임 경계를 흐리는 데서 시작된다. 아래 신호가 보이면 설계, runbook, 답변 구조를 다시 점검한다.

  • TTL을 작업 직전에 낮추면 이미 늦다.
  • 인증서가 발급됐다는 이유로 SNI와 chain 검증을 생략한다.
  • 내부 resolver와 외부 resolver 결과 차이를 놓친다.
  • CNAME flattening이나 ALIAS 동작을 provider마다 같다고 가정한다.
EVIDENCE

검증 기준·증거 패킷

DNS와 TLS는 전파 지연, resolver cache, client 호환성 때문에 기준일과 관측 위치를 분리해 기록해야 한다. 브라우저 성공만으로 배포 완료를 선언하지 않는다.

기준일은 2026-07-09 감사를 기준으로 삼고, DNS cutover나 인증서 갱신 전후로 재확인한다. zone serial, record change id, certificate notBefore/notAfter, issuer를 남겨서 권한 DNS, recursive resolver, 실제 client 관측값의 시각이 함께 있는지 확인한다.

provider/region/version 전제도 명시해야 한다. Route 53/Azure DNS, ACM/Key Vault/App Gateway/Front Door 등 실제 provider와 region, TLS policy version을 적어두고 hosted zone/private zone id, certificate ARN 또는 secret id, listener TLS policy를 함께 남긴다. public DNS와 private DNS view, edge TLS와 origin TLS는 서로 다른 계층이므로 구분해서 다뤄야 한다.

명령 출력 예시는 DNS answer, TTL, chain, SAN, protocol/cipher를 캡처한다. dig +trace, dig @resolver, openssl s_client -servername, curl -v --resolve, LB listener log를 남기면 정상/비정상 client matrix와 rollback record가 같은 기록 안에 있게 된다.

완료 기준은 cutover, certificate rotation, cache propagation을 재현 가능하게 설명하는 것이다. old/new answer 비교, expiry alert, OCSP/chain 확인, rollback TTL을 근거로, 변경 전 낮춘 TTL이 실제로 반영됐고 변경 후 기대한 answer와 TLS chain이 모든 필수 client에서 통과하는지 확인한다.
