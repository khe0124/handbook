DNS-00

DNS record와 TTL

A, AAAA, CNAME, ALIAS, TXT, CAA record의 목적을 구분한다. TTL은 장애 대응 속도와 resolver 부하 사이의 선택이다. 이전 작업 전 TTL을 낮추고, 작업 후 안정화되면 다시 올린다.

OPERATIONS DECISION

운영 질문 DNS record와 TTL이 변경/복구 시간에 맞게 설계되었는가?

확인할 증거 A/AAAA/CNAME/ALIAS/TXT/CAA, authoritative answer, TTL, resolver cache

판단 기준 record 목적과 TTL 전파 지연을 작업 전부터 고려해야 한다.

배제 확인 DNS record와 TTL를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 dig NS, dig +trace, dig CAA, provider DNS change history

명령 해석 권한 서버 응답과 public resolver cache를 분리한다.

임시 완화와 영구 수정 이전 IP가 일부 resolver에 남아 사용자만 간헐 실패 기준으로 영향 범위를 좁히고, TTL 사전 조정, 이전 record rollback, 전파 모니터링을 실행한다.

DNS-01

split-horizon DNS

같은 이름이 내부와 외부에서 다른 IP로 해석되는 split-horizon DNS는 VPN, 사내망, Private Endpoint에서 자주 필요하다. 장애 분석 시 사용자가 어느 resolver를 쓰는지 먼저 확인한다.

OPERATIONS DECISION

운영 질문 split-horizon DNS가 사용자 위치별로 의도한 IP를 반환하는가?

확인할 증거 internal resolver, public resolver, VPN resolver, Private DNS zone, conditional forwarder

판단 기준 같은 이름이 내부/외부에서 다르게 해석되는 이유가 문서화되어야 한다.

배제 확인 split-horizon DNS를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 dig @internal, dig @public, resolver rule, Private DNS zone link

명령 해석 잘못된 resolver를 쓰면 사설 서비스가 public endpoint로 흐를 수 있다.

임시 완화와 영구 수정 VPN 사용자만 내부 API 접속 실패 기준으로 영향 범위를 좁히고, resolver rule과 Private DNS link를 수정하고 양쪽 결과를 기록한다.

DNS-02

TLS 인증서

TLS 운영은 인증서 발급만이 아니다. SAN, wildcard 범위, SNI, intermediate chain, OCSP, 자동 갱신, 만료 알림, CAA 정책을 함께 본다. 인증서 교체는 rollback 가능한 변경으로 관리한다.

OPERATIONS DECISION

운영 질문 TLS 인증서가 발급뿐 아니라 실제 handshake에서 유효한가?

확인할 증거 SAN, wildcard scope, SNI, issuer, expiry, intermediate chain, OCSP, renewal alert

판단 기준 인증서 발급 성공과 사용자 handshake 성공은 다르다.

배제 확인 TLS 인증서를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 openssl s_client -showcerts, curl -v, certificate inventory, renewal job log

명령 해석 SNI와 chain 누락, SAN mismatch를 반드시 확인한다.

임시 완화와 영구 수정 일부 브라우저에서 certificate chain 오류 기준으로 영향 범위를 좁히고, 중간 인증서 연결, CDN binding, renewal alert를 복구한다.

DNS-03

도메인 변경 절차

도메인 변경에는 사전 TTL 조정, record diff, 인증서 준비, CDN/WAF 연결, smoke test, 전파 모니터링, rollback record가 필요하다. dig, curl -v, openssl s_client 결과를 변경 티켓에 남긴다.

OPERATIONS DECISION

운영 질문 도메인 변경이 rollback 가능한 변경으로 관리되는가?

확인할 증거 TTL pre-change, record diff, certificate binding, CDN/WAF config, smoke test, rollback record

판단 기준 새 경로와 이전 경로가 전파 기간 동안 모두 안전해야 한다.

배제 확인 도메인 변경 절차를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 dig before/after, curl --resolve, openssl s_client, CDN request log

명령 해석 전파 중 일부 사용자는 이전/새 endpoint를 모두 볼 수 있다.

임시 완화와 영구 수정 새 CDN 전환 후 일부 지역 403 기준으로 영향 범위를 좁히고, 이전 record 복구 또는 CDN rule rollback을 실행하고 전파 상태를 추적한다.

CHECK

실무 체크리스트

DNS·TLS·도메인 운영 체크리스트는 DNS record와 TTL, split-horizon DNS, TLS 인증서, 도메인 변경 절차에서 놓치기 쉬운 운영 증거를 작업 전후로 고정하기 위한 검토표다. 각 항목은 프론트엔드 증상, 배포 승인, 운영 인수에서 같은 기준으로 다시 확인한다.

  • record 종류와 TTL 변경 계획을 사전에 작성한다.
  • CAA, SAN, wildcard, SNI, intermediate chain을 확인한다.
  • 인증서 만료 알림과 자동 갱신 실패 알림을 둔다.
  • 도메인 변경 전후 dig, curl, openssl 결과를 기록한다.
설계작업 단계

필수 산출물 목적, 영향 범위, 비목표, owner

차단 기준 영향 범위가 사용자·시스템·비용 기준으로 설명되지 않음

변경작업 단계

필수 산출물 diff, 승인 기록, 검증 명령

차단 기준 production 변경과 staging 검증의 차이가 설명되지 않음

복구작업 단계

필수 산출물 rollback 또는 forward fix, 담당자, 예상 시간

차단 기준 실패 시 되돌릴 수 없는데 사전 승인과 공지가 없음

PLAYBOOK

실무 플레이북

DNS·TLS·도메인 운영 플레이북은 DNS TLS CHANGE PLAYBOOK 기준으로 증상, 범위, 최근 변경, 계층별 증거를 연결한다. 목표는 명령어를 많이 아는 것이 아니라 어느 가설을 버리고 어떤 완화책을 선택할지 설명하는 것이다.

DNS TLS CHANGE PLAYBOOK 1 symptom → 2 scope → 3 recent change → 4 evidence
→ 5 mitigation → 6 verification → 7 runbook diff
1 · 증상symptom
무엇이 안 되는가를 사용자 관점 한 문장으로. "느리다"가 아니라 어떤 요청이 언제부터 어떻게 실패하는지 적는다
2 · 영향 범위scope
전체인가 일부인가. region·tenant·경로·클라이언트 중 무엇으로 갈리는지가 가설의 절반을 지운다
3 · 최근 변경recent change
직전 배포, 설정·권한 변경, 인증서·route 교체를 같은 시간축에 올린다. 대부분의 장애는 최근 변경에서 온다
4 · 증거evidence
권한 DNS(dig +trace), 인증서 체인과 SNI(openssl s_client -showcerts), 사용자 경로(curl -v --resolve)를 이 순서로 확인한다
5 · 완화mitigation
이전 record와 이전 인증서로 되돌린다. TTL이 높으면 되돌려도 즉시 반영되지 않는다는 것을 전제로 공지한다
6 · 복구 검증verification
완화가 실제로 먹혔는지 같은 증거로 다시 확인한다. 사용자 경로를 한 번 통과시켜야 끝난 것이다
7 · 런북 갱신runbook diff
이번에 내린 판단을 문서에 되돌린다. 다음 사람이 같은 순서를 다시 발명하지 않게 하는 단계
DNS record운영 표면

볼 증거 record type, authoritative answer, TTL, resolver cache, CAA

판단 기준 전파 지연과 잘못된 권한 서버를 구분한다.

TLS chain운영 표면

볼 증거 SAN, issuer, expiry, intermediate, SNI, OCSP

판단 기준 인증서 발급 성공과 사용자 handshake 성공은 다르다.

Rollback운영 표면

볼 증거 previous record, previous certificate, CDN/WAF binding, smoke result

판단 기준 도메인 변경도 되돌릴 수 있는 변경으로 다룬다.

권한 DNS확인 단계

명령·확인 위치 dig +trace app.example.com, dig NS example.com, dig CAA example.com

해석 기준 권한 서버와 resolver cache를 분리한다.

인증서확인 단계

명령·확인 위치 openssl s_client -servername app.example.com -connect app.example.com:443 -showcerts

해석 기준 SNI와 chain 누락을 확인한다.

사용자 경로확인 단계

명령·확인 위치 curl -v --resolve app.example.com:443:IP https://app.example.com/health

해석 기준 DNS 변경 전후 edge와 origin을 분리 테스트한다.

PRACTICE

출력 판독 훈련

DNS·TLS·도메인 운영은 개념을 아는 것보다 실제 출력에서 정상과 비정상을 구분하는 훈련이 중요하다. 아래 lab은 명령, 출력, 판단, 완화, 영구 수정을 한 번에 연결한다.

PRACTICE LAB 01 · TLS chain/SNI 판독

모바일 브라우저 일부에서만 인증서 오류가 발생한다.

Command / Query

openssl s_client -servername app.example.com -connect app.example.com:443 -showcerts

목적 SNI, SAN, 만료일, intermediate chain 누락을 확인한다.

정상 출력

Verify return code: 0 (ok)
subjectAltName = DNS:app.example.com
notAfter=Sep 20 12:00:00 2026 GMT

비정상 출력

Verify return code: 21 (unable to verify the first certificate)
subjectAltName = DNS:old.example.com

판단 훈련 서버 연결은 되지만 인증서 체인 또는 SNI binding이 잘못된 상태다.

즉시 완화 CDN/LB 인증서 binding rollback 또는 올바른 certificate chain 재배포.

영구 수정 certificate inventory, renewal alert, SNI smoke test를 배포 gate에 추가한다.

검증 기준 openssl verify ok, curl -v handshake 성공, 브라우저 오류 재현 중단.

TERM

용어사전

DNS·TLS·도메인 운영에서 반복적으로 등장하는 운영 용어를 정의, 증거, 오해, 관련 항목 기준으로 정리한다. 장애 중에는 용어 자체보다 해당 용어가 어떤 로그, 지표, 설정, 책임 경계와 연결되는지를 확인한다.

TTLTERM
resolver가 DNS 응답을 캐시하는 시간. 운영에서는 authoritative answer, resolver cache, provider change history로 확인한다. 흔한 오해는 "작업 직전에 낮추면 즉시 전파된다."라고 보는 것이다. 관련해서 record rollback, resolver, propagation를 함께 본다.
CNAME/ALIASTERM
이름을 다른 이름이나 provider alias 대상으로 연결하는 record. 운영에서는 CNAME/ALIAS chain, dig result로 확인한다. 흔한 오해는 "모든 DNS provider의 ALIAS 동작은 같다."라고 보는 것이다. 관련해서 A record, flattening, CDN binding를 함께 본다.
CAATERM
어떤 CA가 인증서를 발급할 수 있는지 제한하는 DNS record. 운영에서는 dig CAA, certificate issuance log로 확인한다. 흔한 오해는 "CAA는 인증서 운영과 무관하다."라고 보는 것이다. 관련해서 TLS, issuer, renewal를 함께 본다.
split-horizon DNSTERM
같은 이름이 내부와 외부에서 다른 IP로 해석되는 구성. 운영에서는 internal resolver, public resolver, Private DNS zone로 확인한다. 흔한 오해는 "한 resolver 결과가 모든 사용자 결과다."라고 보는 것이다. 관련해서 VPN resolver, conditional forwarder, Private Endpoint를 함께 본다.
SNITERM
TLS handshake에서 접속하려는 hostname을 서버에 전달하는 값. 운영에서는 openssl s_client -servername, SAN mismatch로 확인한다. 흔한 오해는 "IP만 맞으면 인증서도 맞는다."라고 보는 것이다. 관련해서 SAN, certificate binding, handshake를 함께 본다.
CASE

장애/운영 시나리오

도메인을 새 CDN으로 이전한다. 24~48시간 전에 TTL을 낮추고, 새 CDN에 인증서를 미리 붙인다. CAA와 DNS record diff를 리뷰하고, 일부 트래픽으로 smoke test를 수행한 뒤 문제가 생기면 이전 record로 rollback한다.

Triage frame

DNS·TLS·도메인 운영 장애는 프론트엔드에서 보인 증상 → 영향 범위 → 최근 변경 → DNS record 증거 → 완화책 → 복구 검증 → 재발 방지 순서로 기록한다.

INCIDENT FLOW

다음 30분 dig +trace app.example.com, dig NS example.com, dig CAA example.com 항목에서 증거를 모아 완화책을 실행한다.

자주 틀리는 판단

DNS·TLS·도메인 운영에서 자주 틀리는 판단은 DNS record와 TTL와 도메인 변경 절차의 책임 경계를 흐리는 데서 시작된다. 아래 신호가 보이면 설계, runbook, 답변 구조를 다시 점검한다.

  • TTL을 작업 직전에 낮추면 이미 늦다.
  • 인증서가 발급됐다는 이유로 SNI와 chain 검증을 생략한다.
  • 내부 resolver와 외부 resolver 결과 차이를 놓친다.
  • CNAME flattening이나 ALIAS 동작을 provider마다 같다고 가정한다.
SUMMARY

총정리

DNS·TLS·도메인 운영의 핵심은 프론트엔드에서 보이는 증상을 운영 계층의 증거와 연결해, 원인 후보를 줄이고 복구 기준을 명확히 말하는 것이다. 아래 표는 리뷰나 면접 직전에 마지막으로 훑는 압축본이다.

주제확인할 증거판단 기준
DNS record와 TTLA/AAAA/CNAME/ALIAS/TXT/CAA, authoritative answer, TTL, resolver cacherecord 목적과 TTL 전파 지연을 작업 전부터 고려해야 한다.
split-horizon DNSinternal resolver, public resolver, VPN resolver, Private DNS zone, conditional forwarder같은 이름이 내부/외부에서 다르게 해석되는 이유가 문서화되어야 한다.
TLS 인증서SAN, wildcard scope, SNI, issuer, expiry, intermediate chain, OCSP, renewal alert인증서 발급 성공과 사용자 handshake 성공은 다르다.
도메인 변경 절차TTL pre-change, record diff, certificate binding, CDN/WAF config, smoke test, rollback record새 경로와 이전 경로가 전파 기간 동안 모두 안전해야 한다.
실무 플레이북DNS record → TLS chain → Rollbackdig +trace app.example.com, dig NS example.com, dig CAA example.com; openssl s_client -servername app.example.com -connect app.example.com:443 -showcerts; curl -v --resolve app.example.com:443:IP https://app.example.com/health
복구 기준일부 고객만 인증서 오류 또는 구버전 IP 접속갱신 실패가 장애가 되기 전에 알림이 와야 한다.
