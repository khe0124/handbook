학습 전환 성능/장애 판단을 사용자 영향 기준으로 설명한다.

OBS-00

세 신호

로그는 사건의 세부 맥락, 메트릭은 시간에 따른 수치, 트레이스는 요청 경로를 보여준다. 세 신호가 traceId, service, environment, version으로 연결되어야 장애 시 요청 단위로 원인을 좁힐 수 있다.

OPERATIONS DECISION

운영 질문 로그, 메트릭, 트레이스가 같은 요청을 설명할 수 있는가?

확인할 증거 timestamp, service, env, version, trace_id, request id, deployment marker

판단 기준 세 신호가 traceId와 version으로 연결되지 않으면 원인 후보를 좁히기 어렵다.

배제 확인 세 신호를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 log query, RED dashboard, trace waterfall, deploy marker comparison

명령 해석 동일 요청의 로그와 trace, 같은 시간대의 metric 변화를 연결한다.

임시 완화와 영구 수정 로그는 있으나 traceId가 없어 특정 사용자 요청을 추적할 수 없음 기준으로 영향 범위를 좁히고, schema 보강과 trace propagation 수정을 영구 개선으로 남긴다.

OBS-01

RED와 USE

HTTP 서비스는 RED(rate, error, duration)를 먼저 본다. 인프라 리소스는 USE(utilization, saturation, errors)를 본다. p95/p99 latency, error rate, saturation은 평균보다 사용자 영향을 잘 드러낸다.

OPERATIONS DECISION

운영 질문 서비스 지표와 리소스 지표 중 어떤 신호가 사용자 영향을 더 잘 설명하는가?

확인할 증거 request rate, error rate, duration p95/p99, utilization, saturation, errors

판단 기준 HTTP 서비스는 RED, 인프라 리소스는 USE로 보되 평균보다 tail과 saturation을 우선한다.

배제 확인 RED와 USE를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 RED/USE dashboard, p95/p99 latency, saturation panel, high-cardinality label review

명령 해석 CPU 평균이 정상이어도 queue, pool, p99가 나쁘면 사용자 영향 후보로 본다.

임시 완화와 영구 수정 평균 latency는 정상이나 p99와 queue saturation만 증가 기준으로 영향 범위를 좁히고, tail latency와 saturation을 기준으로 완화 우선순위를 잡는다.

OBS-02

SLO

SLO는 사용자 경험을 기준으로 잡는 내부 신뢰성 목표다. SLA처럼 외부 보상 약속 자체는 아니지만, 제품 약속과 운영 우선순위의 근거가 된다. SLI를 정의하고 error budget을 계산하면 모든 경고를 paging하지 않고 사용자 영향이 큰 실패에 집중할 수 있다.

OPERATIONS DECISION

운영 질문 이 SLO가 실제 사용자 경험을 대표하는지 어떻게 확인하는가?

확인할 증거 SLI definition, request success rate, latency percentile, freshness, durability, business success

판단 기준 사용자 여정의 성공·지연·신선도와 연결되지 않으면 paging 기준으로 쓰지 않는다.

배제 확인 SLO를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 SLO dashboard, error budget remaining, release freeze policy, alert owner

명령 해석 SLO 위반 시 사람이 취할 행동과 owner가 없으면 운영 기준으로 부족하다.

임시 완화와 영구 수정 checkout success SLO burn이 fast-burn 기준을 넘음 기준으로 영향 범위를 좁히고, 원인 확정 전에도 rollback, feature degrade, traffic shed 같은 영향 완화를 검토한다.

OBS-03

SLO burn rate

SLO burn rate는 error budget이 얼마나 빠르게 소진되는지 보는 방식이다. 짧은 창과 긴 창을 함께 사용하면 급격한 장애와 느린 품질 저하를 모두 잡을 수 있다. 알림에는 owner, dashboard, runbook 링크가 있어야 한다.

OPERATIONS DECISION

운영 질문 error budget이 얼마나 빠르게 소진되는지 어떤 창으로 판단하는가?

확인할 증거 fast burn 5m/1h, slow burn 30m/6h, error budget remaining, paging policy

판단 기준 짧은 창과 긴 창이 함께 나빠질 때 즉시 paging하고, 느린 소진은 ticket과 release freeze로 관리한다.

배제 확인 SLO burn rate를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?

확인 위치 SLO burn dashboard, alert rule, silence policy, incident runbook

명령 해석 알림에는 owner, dashboard, runbook, 완화 선택지가 있어야 한다.

임시 완화와 영구 수정 error rate는 낮아 보이지만 checkout_success_rate burn이 급증 기준으로 영향 범위를 좁히고, 평균 지표보다 사용자 성공률과 error budget 소진 속도를 우선한다.

Fast burn예시 신호

관찰값 5m와 1h 창 모두 error budget 소진 속도 급증

해석 즉시 paging하고 완화 조치를 검토한다.

Slow burn예시 신호

관찰값 30m와 6h 창에서 완만한 품질 저하

해석 근무 시간 ticket, release freeze, owner 조치로 관리한다.

CHECK

실무 체크리스트

Observability·SLO 체크리스트는 세 신호, RED와 USE, SLO, SLO burn rate에서 놓치기 쉬운 운영 증거를 작업 전후로 고정하기 위한 검토표다. 각 항목은 프론트엔드 증상, 배포 승인, 운영 인수에서 같은 기준으로 다시 확인한다.

  • SLI를 사용자 행동과 연결해 정의한다.
  • RED, USE, p95/p99, error rate, saturation을 구분한다.
  • log, metric, trace를 traceId와 version으로 연결한다.
  • SLO burn rate와 error budget 기준으로 알림 우선순위를 나눈다.
설계작업 단계

필수 산출물 목적, 영향 범위, 비목표, owner

차단 기준 영향 범위가 사용자·시스템·비용 기준으로 설명되지 않음

변경작업 단계

필수 산출물 diff, 승인 기록, 검증 명령

차단 기준 production 변경과 staging 검증의 차이가 설명되지 않음

복구작업 단계

필수 산출물 rollback 또는 forward fix, 담당자, 예상 시간

차단 기준 실패 시 되돌릴 수 없는데 사전 승인과 공지가 없음

PLAYBOOK

실무 플레이북

Observability·SLO 플레이북은 SLO OBSERVABILITY DESIGN PLAYBOOK 기준으로 증상, 범위, 최근 변경, 계층별 증거를 연결한다. 목표는 명령어를 많이 아는 것이 아니라 어느 가설을 버리고 어떤 완화책을 선택할지 설명하는 것이다.

SLO OBSERVABILITY DESIGN PLAYBOOK 1 symptom → 2 scope → 3 recent change → 4 evidence
→ 5 mitigation → 6 verification → 7 runbook diff
1 · 증상symptom
무엇이 안 되는가를 사용자 관점 한 문장으로. "느리다"가 아니라 어떤 요청이 언제부터 어떻게 실패하는지 적는다
2 · 영향 범위scope
전체인가 일부인가. region·tenant·경로·클라이언트 중 무엇으로 갈리는지가 가설의 절반을 지운다
3 · 최근 변경recent change
직전 배포, 설정·권한 변경, 인증서·route 교체를 같은 시간축에 올린다. 대부분의 장애는 최근 변경에서 온다
4 · 증거evidence
사용자 영향을 SLI로 먼저 읽는다 — 성공률, latency, freshness. 그다음 trace_id로 로그와 트레이스를 잇고 deploy marker와 같은 시간축에 올린다
5 · 완화mitigation
burn rate가 빠른 구간을 먼저 끊는다. 배포 rollback, 트래픽 축소, 기능 차단 중 error budget을 덜 태우는 쪽을 고른다
6 · 복구 검증verification
완화가 실제로 먹혔는지 같은 증거로 다시 확인한다. 사용자 경로를 한 번 통과시켜야 끝난 것이다
7 · 런북 갱신runbook diff
이번에 내린 판단을 문서에 되돌린다. 다음 사람이 같은 순서를 다시 발명하지 않게 하는 단계
SLI운영 표면

볼 증거 request success, latency, freshness, durability, business success

판단 기준 사용자 여정과 연결되지 않은 지표는 paging 기준이 아니다.

Telemetry운영 표면

볼 증거 log schema, metric label, trace sampling, deploy marker

판단 기준 traceId와 version이 없으면 원인 연결이 약해진다.

Alert운영 표면

볼 증거 multi-window burn rate, runbook, owner, silence policy

판단 기준 알림은 사람이 취할 행동과 연결되어야 한다.

로그확인 단계

명령·확인 위치 timestamp, level, service, env, version, trace_id, user/tenant scope

해석 기준 PII와 secret은 redaction하고 검색 가능한 필드를 남긴다.

메트릭확인 단계

명령·확인 위치 RED/USE dashboard, p95/p99, saturation, high-cardinality label review

해석 기준 label 폭증은 비용과 성능 장애가 된다.

SLO확인 단계

명령·확인 위치 5m/1h fast burn, 30m/6h slow burn, error budget remaining

해석 기준 빠른 장애와 느린 품질 저하의 대응을 분리한다.

Good SLI심화 장애 패턴

관찰 신호 checkout_success_rate, payment_authorized_latency_p95, report_freshness

판정 기준 사용자 여정의 성공/지연/신선도와 연결된다.

Bad SLI심화 장애 패턴

관찰 신호 CPU average, pod restart count only, raw request count

판정 기준 원인 지표일 수는 있지만 사용자 영향 기준으로는 약하다.

Alert rule심화 장애 패턴

관찰 신호 fast burn은 즉시 paging, slow burn은 근무 시간 처리

판정 기준 모든 알림이 사람을 깨우면 중요한 장애를 놓친다.

Cardinality guard심화 장애 패턴

관찰 신호 user_id, request_id, raw URL을 metric label로 쓰지 않음

판정 기준 관측 시스템 자체가 비용/성능 장애가 될 수 있다.

PRACTICE

출력 판독 훈련

Observability·SLO는 개념을 아는 것보다 실제 출력에서 정상과 비정상을 구분하는 훈련이 중요하다. 아래 lab은 명령, 출력, 판단, 완화, 영구 수정을 한 번에 연결한다.

PRACTICE LAB 01 · Fast burn alert 판독

checkout 성공률이 급격히 떨어졌지만 CPU와 memory는 정상이다.

Command / Query

sum(rate(http_requests_total{route="/checkout",status=~"5.."}[5m])) / sum(rate(http_requests_total{route="/checkout"}[5m]))

목적 리소스 지표가 아니라 사용자 성공률 기준으로 SLO burn을 판단한다.

정상 출력

5m burn: 0.4x
1h burn: 0.7x
error budget remaining: 82%

비정상 출력

5m burn: 18x
1h burn: 9x
error budget remaining: 42%

판단 훈련 5m와 1h 창이 동시에 나빠져 즉시 paging해야 하는 fast burn이다.

즉시 완화 checkout feature flag off, payment dependency timeout 축소, rollback 후보 검토.

영구 수정 checkout_success SLI와 alert-to-action runbook을 분리하고 dependency timeout budget을 재조정한다.

검증 기준 5m burn 1x 이하, checkout success 회복, incident runbook action 완료.

PRACTICE LAB 02 · Slow burn freshness 판독

리포트 생성은 실패하지 않지만 데이터 freshness가 계속 늦어진다.

Command / Query

sum_over_time(report_freshness_violation_total[6h])

목적 즉시 장애가 아닌 느린 품질 저하를 SLO로 관리한다.

정상 출력

violations_6h: 0
freshness_p95: 4m

비정상 출력

violations_6h: 37
freshness_p95: 48m

판단 훈련 사용자 요청 실패가 없어도 freshness SLO를 태우는 slow burn이다.

즉시 완화 batch concurrency 조정, low-priority job pause, customer comms 준비.

영구 수정 queue lag 기반 autoscaling과 freshness dashboard를 추가한다.

검증 기준 freshness_p95 목표 이하, 6h violation 0, backlog 정상화.

TERM

용어사전

Observability·SLO에서 반복적으로 등장하는 운영 용어를 정의, 증거, 오해, 관련 항목 기준으로 정리한다. 장애 중에는 용어 자체보다 해당 용어가 어떤 로그, 지표, 설정, 책임 경계와 연결되는지를 확인한다.

logTERM
사건의 세부 맥락을 남기는 관측 신호. 운영에서는 timestamp, level, service, env, trace_id로 확인한다. 흔한 오해는 "로그 양이 많으면 관측 가능성이 높다."라고 보는 것이다. 관련해서 traceId, redaction, schema를 함께 본다.
metricTERM
시간에 따른 수치 변화를 보는 관측 신호. 운영에서는 RED/USE dashboard, p95/p99, saturation로 확인한다. 흔한 오해는 "CPU 평균이 정상이면 사용자 영향도 없다."라고 보는 것이다. 관련해서 label, cardinality, alert를 함께 본다.
traceTERM
요청이 여러 서비스와 dependency를 지나는 경로. 운영에서는 trace waterfall, deployment marker, request id로 확인한다. 흔한 오해는 "trace는 디버깅 부가 기능일 뿐이다."라고 보는 것이다. 관련해서 span, downstream, latency를 함께 본다.
SLITERM
SLO를 계산하는 사용자 영향 지표. 운영에서는 request success, latency, freshness, durability로 확인한다. 흔한 오해는 "모든 내부 지표는 SLI가 될 수 있다."라고 보는 것이다. 관련해서 SLO, error budget, business success를 함께 본다.
burn rateTERM
error budget이 얼마나 빠르게 소진되는지 보는 비율. 운영에서는 5m/1h fast burn, 30m/6h slow burn로 확인한다. 흔한 오해는 "error rate가 낮으면 paging할 필요가 없다."라고 보는 것이다. 관련해서 error budget, paging, release freeze를 함께 본다.
CASE

장애/운영 시나리오

새 릴리스 후 p99 latency만 증가하고 error rate는 안정적이다. 평균 latency가 아니라 tail latency를 보고, trace에서 특정 downstream 호출이 느려졌는지 확인한다. SLO burn rate가 빠르게 증가하면 paging하고, 느린 소진이면 ticket으로 관리한다.

RISK

자주 틀리는 판단

Observability·SLO에서 자주 틀리는 판단은 세 신호와 SLO burn rate의 책임 경계를 흐리는 데서 시작된다. 아래 신호가 보이면 설계, runbook, 답변 구조를 다시 점검한다.

  • CPU 알림만 많고 사용자 영향 알림이 없다.
  • 로그는 있지만 traceId가 없어 요청 단위 분석이 안 된다.
  • high-cardinality label을 무분별하게 추가해 비용과 성능을 망친다.
  • SLO 없이 모든 경고를 같은 심각도로 보낸다.
SUMMARY

총정리

Observability·SLO의 핵심은 프론트엔드에서 보이는 증상을 운영 계층의 증거와 연결해, 원인 후보를 줄이고 복구 기준을 명확히 말하는 것이다. 아래 표는 리뷰나 면접 직전에 마지막으로 훑는 압축본이다.
