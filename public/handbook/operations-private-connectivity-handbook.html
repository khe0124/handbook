터널 UP과 통신 성공은 다르다

터널이 UP이라는 상태값과 실제 업무 트래픽이 목적지 포트까지 도달했다는 사실은 전혀 다른 명제다. 이 둘을 같다고 보는 순간부터 사설 연결 장애는 미궁에 빠진다. Site-to-Site VPN은 인터넷 품질과 IPsec 협상에 기대는 만큼 빠르게 구축할 수 있지만, 전용선이나 Direct Connect, Private Endpoint는 비용과 리드타임이 큰 대신 예측 가능성을 산다 — 이 trade-off를 먼저 정해야 한다.

연결 방식이 정해지면 IPsec 협상이 시작된다. Phase 1에서 IKE SA를 세우고 Phase 2에서 실제 데이터 트래픽용 SA를 세우는데, encryption, DH group, PFS, lifetime, traffic selector가 양쪽에서 정확히 일치해야 한다. 터널이 반복적으로 flap한다면 여기서 proposal mismatch나 rekey 문제부터 의심한다. 그런데 터널이 멀쩡히 UP이어도 아직 아무것도 증명된 게 아니다. local CIDR, peer CIDR, route table, security group, 고객사 방화벽, return path가 전부 맞아야 앱 통신이 이뤄지고, CIDR overlap은 협상이 아니라 설계 단계에서 이미 없어야 하는 문제다.

그래서 장애가 나면 터널 상태와 실제 패킷 카운터를 분리해서 봐야 한다. PRIVATE CONNECTIVITY DEBUG PLAYBOOK은 Tunnel, Routing/Firewall, Application path 세 표면을 나눠 보게 하고, "VPN tunnel UP but API timeout" 판독 실습은 phase1·phase2가 모두 UP인데 packet_in이 0이고 고객사 방화벽이 deny인 출력을 보여준다 — VPN 자체가 아니라 고객사 방화벽과 return path를 의심해야 하는 전형적인 신호다. 고객사에 협업을 요청할 때도 마찬가지다. source IP, destination IP, port, timestamp, packet 증거를 함께 넘겨야 상대가 같은 시간대, 같은 5-tuple로 확인할 수 있다.

이 영역에서 반복되는 실수는 VPN 터널 UP을 서비스 연동 완료로 착각하는 것, 고객사 방화벽 담당자와 시간을 맞추지 않는 것, Phase 2 traffic selector가 실제 CIDR과 어긋나는 것이다. 결국 장애 때마다 되돌아가는 질문은 셋이다 — 터널은 UP인가, 애플리케이션 통신은 성공했는가, 이 증거는 양쪽이 같은 시간대·같은 5-tuple로 확인 가능한가.

VPN-00

연결 방식

Site-to-Site VPN은 빠르게 구축할 수 있지만 인터넷 품질과 IPsec 협상에 의존한다. 전용선, Direct Connect, Interconnect, ExpressRoute, Private Endpoint는 비용과 리드타임이 크지만 예측 가능성과 격리가 좋다.

연동 초기엔 다들 Site-to-Site VPN을 고른다. 며칠이면 뚫리고, 전용선처럼 리드타임이 몇 주씩 걸리지도 않으니까. 문제는 이 선택의 이유가 어디에도 안 적혀 있을 때다. 몇 달 뒤 그 VPN 품질이 흔들리기 시작하면, 그때 가서야 "왜 처음부터 전용선으로 안 갔지"라는 질문이 나온다.

실제로 겪은 사례다. 야간 배치로 고객사 ERP와 데이터를 주고받는 연동이었는데, 어느 날부터 배치가 예정 시간을 자꾸 넘기기 시작했다. circuit/tunnel status를 보니 인터넷 품질 자체가 들쭉날쭉했다 — VPN은 결국 인터넷 위에 얹은 암호화 터널이라, 인터넷이 흔들리면 같이 흔들린다. 이때 당장 할 수 있는 건 재시도 로직을 손보고 batch window를 좀 여유 있게 잡는 정도였다. 하지만 이건 임시방편이라는 걸 분명히 해뒀다. 그 업무가 정말 중요하고 복구 목표(RTO/RPO)가 엄격하다면, 장기적으로는 전용선이나 Private Endpoint로 옮기는 계획을 별도로 잡아야 한다. 임시 조치만 계속 반복하면서 전환 계획을 안 세우면, 같은 지연이 다음 분기에도 똑같이 재발한다.

VPN-01

IPsec 협상

IPsec은 Phase 1에서 IKE SA를 만들고 Phase 2에서 데이터 트래픽용 SA를 만든다. encryption, integrity, DH group, PFS, lifetime, PSK, NAT-T, traffic selector가 양쪽에서 일치해야 한다.

IPsec은 양쪽이 encryption, DH group, lifetime 같은 값을 토씨 하나 안 틀리고 합의해야만 터널이 선다. 그래서 터널이 DOWN이라면 다른 거 다 제쳐두고 proposal mismatch나 rekey 문제부터 의심하는 게 맞다.

rekey 시점마다 터널이 몇 초씩 flap하는 걸 겪은 적이 있다. 터널이 UP으로 떠 있으니 다들 "협상은 문제없다"고 넘어갔는데, 그게 착각이었다. 터널 UP은 그저 협상이 끝났다는 표시일 뿐이지, 실제로 패킷이 흐르고 있다는 보장은 아니다. IKE log를 뒤져보니 rekey 주기마다 lifetime 값이 양쪽에서 미묘하게 다르게 설정돼 있었고, 그 순간마다 재협상이 일어나면서 짧게 끊기고 있었던 것이다. lifetime과 PFS, proposal 값을 양쪽에서 다시 맞추고, rekey 로그를 계속 남겨서 다음에도 같은 패턴이 나타나는지 지켜보기로 했다.

VPN-02

라우팅과 방화벽

터널 UP은 충분하지 않다. local CIDR, peer CIDR, route table, security group, 고객사 방화벽, return path가 맞아야 앱 통신이 된다. CIDR overlap은 설계 단계에서 제거해야 한다.

터널이 UP이라는 이유로 "네트워크는 다 됐다"고 결론 내리면 꼭 한 번 당한다. 흔한 실수가 ping(ICMP)이 되니까 API도 될 거라 믿는 것이다. ICMP는 열려 있어도 실제 업무가 쓰는 포트는 firewall이나 traffic selector 설정 때문에 따로 막혀 있을 수 있다.

터널은 UP인데 고객사 ERP API 호출만 계속 timeout 나는 걸 겪은 적이 있다. ping은 잘 됐다. 그래서 처음엔 애플리케이션 코드를 의심했는데, 시간만 날렸다. traffic selector부터 route, firewall, DNS 순서로 하나씩 짚어보니 원인은 firewall이었다 — 우리 쪽 route와 firewall은 그 API 포트를 허용하고 있었지만, 고객사 쪽 firewall이 그 포트에 대한 return path를 막고 있었다. 한쪽만 열려 있으면 요청은 나가도 응답이 못 돌아온다는 걸 이때 제대로 배웠다. 순서를 지키지 않고 아무거나 먼저 의심했다면, 막힌 계층을 찾는 데 훨씬 더 오래 걸렸을 것이다.

VPN-03

운영 증거

장애 시 터널 상태, rekey 로그, packet counter, tcpdump, nc, curl 결과를 분리해 본다. 고객사에 요청할 때는 source IP, destination IP, port, timestamp, packet evidence를 제공한다.

고객사 네트워크 담당자와 통화할 때 "그쪽 방화벽이 막고 있는 것 같다"고만 말하면 대화가 거의 안 풀린다. 상대도 자기 쪽 로그를 보면서 "우리는 문제없다"고 맞선다. 이렇게 되면 누가 맞는지가 아니라 누가 더 확신에 차서 말하는지로 논쟁이 흘러간다.

실제로 이런 지루한 핑퐁을 몇 번 겪은 뒤로는 방식을 바꿨다. timestamp, source IP, destination IP, port, packet counter를 캡처해서 먼저 보낸다. "네트워크가 이상한 것 같다"가 아니라 "10:04:12에 42개를 보냈는데 0개가 들어왔다"고 구체적으로 말하면, 상대방도 같은 시간대·같은 5-tuple로 자기 쪽 로그를 찾아볼 수 있다. 증거 없이 협업을 요청하면 방화벽·라우팅 담당자와의 대화가 추측 대 추측으로 흘러가지만, 이렇게 구체적인 증거를 먼저 던지면 대화가 훨씬 빨리 풀린다. 그래서 이제는 아예 공유 evidence template과 escalation owner를 runbook에 미리 정해뒀다. 다음 장애에서는 같은 논쟁을 처음부터 다시 하지 않아도 된다.

CHECK

실무 체크리스트

VPN·Private Connectivity 체크리스트는 연결 방식, IPsec 협상, 라우팅과 방화벽, 운영 증거의 변경 위험을 사전에 드러내기 위한 검토표다. 각 항목은 리뷰, 배포 승인, 운영 인수에서 같은 증거로 다시 확인되어야 한다.

  • local/peer CIDR, tunnel endpoint, Phase 1/2 값을 표로 합의한다.
  • 터널 UP과 애플리케이션 통신 성공을 분리해 검증한다.
  • route table, 방화벽, return path, DNS를 양쪽에서 확인한다.
  • 장애 시 전달할 packet evidence 양식을 미리 정한다.

이 체크리스트의 세 관문은 사설 연결 변경에서도 똑같이 적용된다.

  1. 설계 — 목적, 영향 범위, 비목표, owner가 산출물로 남아 있어야 한다. 영향 범위가 사용자·시스템·비용 기준으로 설명되지 않는다면, 이 단계에서 진행을 막아야 한다.
  2. 변경 — diff, 승인 기록, 검증 명령이 함께 있어야 한다. Phase 1/2 proposal 값처럼 눈에 잘 안 띄는 조건이 다를 수 있으니, production 변경과 staging 검증의 차이가 설명되지 않으면 배포해서는 안 된다.
  3. 복구 — rollback 또는 forward fix, 담당자, 예상 시간이 미리 정해져 있어야 한다. 실패 시 되돌릴 수 없는데 사전 승인과 공지가 없다면 배포를 보류해야 한다.

사설 연결 장애를 다룰 때도 "터널은 살아 있는데 왜 통신이 안 되는가"를 세 단계로 나눠서 좁힌다. Tunnel 표면은 "협상 자체가 살아 있는가"를 IKE/Phase 2 status, lifetime, proposal, rekey log, packet counter로 확인한다. 터널 UP과 서비스 통신 성공은 서로 다른 명제이므로 분리해서 확인해야 한다. Routing/Firewall 표면은 "협상된 터널 위로 실제 경로가 열려 있는가"를 local CIDR, peer CIDR, route table, firewall, return path로 확인한다. 이 표면의 핵심은 양쪽 네트워크가 같은 증거를 보고 있는지 확인하는 것이다. Application path 표면은 "경로가 열려 있어도 업무 포트까지 응답이 오는가"를 source IP, destination IP, port, DNS, tcpdump, nc/curl result로 확인한다. ICMP 성공만으로 API 성공을 판단하면 안 된다는 원칙이 여기서도 적용된다.

이 세 표면은 조사하는 순서까지 정해져 있다.

  1. 협상 — VPN tunnel status, IKE log, Phase 1/2 proposal을 비교해서 encryption, DH group, PFS, lifetime mismatch를 찾는다.
  2. 포트 — nc -vz host port, curl -v internal-api, tcpdump host peer-ip로 터널이 아니라 실제 업무 포트를 직접 검증한다.
  3. 증거 공유 — timestamp, src/dst, port, packet capture, firewall decision을 정리해서 고객사와 같은 시간대 증거를 맞춘다.
PRACTICE

출력 판독 훈련

VPN·Private Connectivity는 개념을 아는 것보다 실제 출력에서 정상과 비정상을 구분하는 훈련이 중요하다. 아래 lab은 명령, 출력, 판단, 완화, 영구 수정을 한 번에 연결한다.

PRACTICE LAB 01 · VPN tunnel UP but API timeout 판독

Site-to-Site VPN 터널은 UP이지만 고객사 ERP API 호출이 timeout 된다.

터널 상태와 실제 애플리케이션 포트 통신을 분리해서 확인하려면 다음 packet evidence를 본다.

vpn packet evidence
src=10.12.4.18 dst=172.20.8.10 port=443
phase1=UP phase2=UP
packet_out=42 packet_in=0
customer_firewall=deny

정상적인 경우라면 나간 패킷만큼 들어온 패킷도 있고 firewall도 allow다.

phase2=UP
packet_out=42
packet_in=42
firewall=allow
curl_status=200

비정상 출력, 즉 비정상적인 경우에는 나간 패킷은 있는데 들어온 패킷이 0이고 고객사 firewall이 deny다.

phase2=UP
packet_out=42
packet_in=0
customer_firewall=deny
curl_status=timeout

이 패턴은 VPN 자체보다 고객사 방화벽, return path, traffic selector 문제일 가능성이 높다는 걸 보여준다. 즉시 완화는 고객사에 timestamp, src/dst, port, packet counter를 전달하고 임시 allow rule을 요청하는 것이다. 영구 수정은 연동 runbook에 packet evidence template과 방화벽 변경 승인 절차를 포함하는 것이다. packet_in이 늘고 curl이 200을 반환하고 고객사 firewall allow log와 애플리케이션 health check가 모두 성공하면 이 조치가 끝난 것이다.

TERM

용어사전

VPN·Private Connectivity에서 반복적으로 등장하는 운영 용어를 정의, 증거, 오해, 관련 항목 기준으로 정리한다. 장애 중에는 용어 자체보다 해당 용어가 어떤 로그, 지표, 설정, 책임 경계와 연결되는지를 확인한다.

Site-to-Site VPN
인터넷 위에 암호화 터널을 얹어서 사설망끼리 연결하는 방식이다. tunnel status, latency, SLA, cost로 확인한다. 터널이 UP이면 서비스 통신도 당연히 될 거라 생각하기 쉬운데, UP은 그저 협상이 끝났다는 표시일 뿐이고 실제로 데이터가 흐르는지는 packet counter로 따로 확인해야 안다.
IPsec Phase 1
IKE SA를 세워서 터널 협상의 기반을 만드는 단계다. IKE log, encryption, integrity, DH group으로 확인한다. Phase 1만 성공하면 데이터도 곧바로 흐를 거라 넘겨짚기 쉬운데, 실제 데이터 트래픽은 이 뒤에 별도로 협상되는 Phase 2의 IPsec SA를 통해서만 흐른다.
IPsec Phase 2
실제 데이터 트래픽이 쓸 IPsec SA를 협상하는 단계다. IPsec SA, PFS, lifetime, traffic selector로 확인한다. traffic selector는 대충 비슷하게만 맞춰도 될 거라 생각하기 쉬운데, 실제 CIDR과 정확히 일치하지 않으면 터널은 멀쩡히 UP이어도 특정 대역의 트래픽만 아무도 모르게 누락된다.
CIDR overlap
양쪽 네트워크의 주소 대역이 겹쳐서 라우팅이 불가능하거나 애매해지는 상태다. local CIDR, peer CIDR, route readback으로 확인한다. NAT로 대충 우회하면 그만이라 생각하기 쉬운데, NAT 자체가 나중에 디버깅을 훨씬 복잡하게 만들기 때문에 애초에 설계 단계에서 overlap을 없애는 쪽이 항상 낫다.
return path
응답 패킷이 원래 요청한 쪽으로 되돌아오는 경로다. route table, firewall log, tcpdump로 확인한다. 요청이 나가는 경로만 열어두면 통신이 될 거라 생각하기 쉬운데, 응답이 다른 경로로 돌아오거나 그 경로가 firewall에 막혀 있으면 요청은 분명히 나갔는데 결과는 영영 돌아오지 않는다.
Direct Connect / ExpressRoute / Interconnect
클라우드와 사내망을 인터넷을 거치지 않고 잇는 전용 연결 서비스다. circuit 상태, 대역폭, SLA로 확인한다. 비싸니 나중에 검토하자고 미루기 쉬운데, 인터넷 품질에 흔들리면 안 되는 업무라면 이 예측 가능성을 사는 것이 곧 요구사항이다.
IKE SA
Phase 1에서 만들어지는 협상용 보안 연결이다. IKE 로그의 협상 결과와 제안 값으로 확인한다. 터널이 떴으면 협상은 끝났다고 보기 쉬운데, Phase 1만 성공하고 Phase 2가 안 서면 데이터는 한 바이트도 흐르지 않는다.
IPsec SA
Phase 2에서 만들어지는 실제 데이터 트래픽용 보안 연결이다. SA 목록과 packet counter로 확인한다. 두 Phase를 한 덩어리로 보기 쉬운데, 장애 지점을 가르려면 어느 단계까지 성립했는지 따로 확인해야 한다.
proposal mismatch
양쪽이 제안한 암호화·무결성·DH group 값이 달라 협상이 실패한 상태다. IKE 로그의 거절 사유로 확인한다. 설정을 비슷하게 맞췄으니 되겠지 생각하기 쉬운데, 값 하나만 달라도 터널은 서지 않는다.
DH group
키 교환에 쓰는 수학적 그룹의 강도 설정이다. 양쪽 proposal 값으로 확인한다. 높을수록 좋다고 보기 쉬운데, 상대 장비가 지원하지 않으면 협상 자체가 실패한다.
PFS
세션 키가 유출돼도 과거 트래픽까지는 풀리지 않게 하는 설정이다. Phase 2 proposal과 rekey 로그로 확인한다. 켜기만 하면 되는 옵션으로 보기 쉬운데, 양쪽 설정이 어긋나면 rekey 시점마다 터널이 끊긴다.
lifetime / rekey
보안 연결의 유효 시간과 만료 시 다시 협상하는 동작이다. rekey 주기의 로그와 그 시각의 끊김으로 확인한다. 터널이 UP이면 안정적이라 보기 쉬운데, 양쪽 lifetime이 미묘하게 다르면 주기마다 짧게 끊기는 flap이 생긴다.
PSK
양쪽이 미리 나눠 가진 공유 비밀 값이다. 설정 값과 교체 이력으로 확인한다. 한 번 맞추면 끝이라 보기 쉬운데, 교체 절차와 담당자가 없으면 만료나 유출 시 즉시 대응할 수 없다.
NAT-T
중간에 NAT가 있을 때 IPsec이 통과할 수 있게 감싸 주는 방식이다. 협상 결과에 NAT 감지 여부로 확인한다. 없어도 되는 옵션으로 보기 쉬운데, 경로에 NAT가 끼면 이것 없이는 터널이 서지 않는다.
traffic selector
이 터널로 흘려보낼 출발지·목적지 대역을 정한 조건이다. 양쪽 설정 값과 실제 CIDR을 대조해 확인한다. 대충 넓게 잡으면 되겠지 생각하기 쉬운데, 양쪽 selector가 정확히 대응하지 않으면 특정 대역만 조용히 빠진다.
tunnel flap
터널이 짧게 끊겼다 다시 붙기를 반복하는 상태다. 상태 변화 로그와 rekey 시각으로 확인한다. 지금 UP이니 괜찮다고 보기 쉬운데, 반복되는 flap은 그때마다 진행 중이던 연결을 끊어 배치와 API를 실패시킨다.
packet counter
터널을 실제로 지난 패킷 수다. packet_in과 packet_out을 나눠 확인한다. 상태값만 보고 통신이 된다고 결론 내기 쉬운데, UP인데 packet_in이 0이면 문제는 터널이 아니라 상대 쪽 방화벽이나 return path다.
ICMP
ping이 쓰는 프로토콜이다. 도달 여부를 빠르게 보는 용도로 쓴다. ping이 되니 API도 될 거라 믿기 쉬운데, 업무가 쓰는 포트는 방화벽이나 traffic selector에서 따로 막혀 있을 수 있다.
MTU / MSS
한 번에 보낼 수 있는 패킷 크기의 상한과 TCP가 협상하는 조각 크기다. 큰 요청만 실패하는 패턴과 조각화 여부로 확인한다. 연결되면 크기는 상관없다고 보기 쉬운데, 터널로 감싸면서 여유가 줄어 큰 응답만 끊기는 장애가 생긴다.
BGP / ASN
경로 정보를 서로 알려 주는 라우팅 프로토콜과 그 참여자 식별 번호다. BGP 세션 상태와 광고·수신된 경로로 확인한다. 세션이 붙었으니 경로도 다 왔다고 보기 쉬운데, 광고 필터에 걸린 대역은 조용히 빠진 채로 남는다.
5-tuple
출발지 IP·포트, 목적지 IP·포트, 프로토콜 다섯 값의 조합이다. 양쪽이 같은 사건을 볼 때의 공통 좌표로 쓴다. 네트워크가 이상하다고만 전하기 쉬운데, 시각과 5-tuple을 함께 넘겨야 상대도 자기 로그에서 같은 요청을 찾을 수 있다.
RTO / RPO
복구까지 허용되는 시간과 잃어도 되는 데이터의 양이다. 업무별로 정한 목표값과 실제 훈련 결과로 확인한다. 임시 우회로 급한 불을 껐으면 됐다고 보기 쉬운데, 이 목표가 엄격하면 임시방편이 아니라 연결 방식 자체를 바꿔야 한다.
CASE

장애/운영 시나리오

고객사 ERP와 Site-to-Site VPN을 연결한다. CIDR overlap을 먼저 확인하고, IPsec proposal을 양쪽 문서로 맞춘다. 터널이 올라온 뒤에는 ICMP가 아니라 실제 API port와 DB port를 nc, tcpdump, 애플리케이션 health check로 검증한다.

Triage frame

VPN·Private Connectivity 장애는 증상 → 영향 범위 → 최근 변경 → Tunnel 증거 → 완화책 → 복구 검증 → 재발 방지 순서로 기록한다. 이 흐름이 있어야 담당자가 바뀌어도 같은 결론에 도달한다.

처음 10분은 원인을 찾기보다 영향 범위부터 좁힌다. IKE/Phase 2 status, lifetime, proposal, rekey log, packet counter 기준으로 터널이 문제인지 그 뒤 단계가 문제인지부터 고정한다. 다음 30분은 VPN tunnel status, IKE log, Phase 1/2 proposal 비교 항목에서 증거를 모아 완화책을 실행한다. 다음 연동 때 같은 합의 누락이 반복되지 않는 게 종료 조건이다.

사고 기록에는 세 항목을 incident packet 형식으로 남긴다. 증상은 터널은 UP인데 ERP API가 timeout 나는 것이고, route, firewall, return path, DNS, app port를 순서대로 봐서 판정한다. 완화는 backup tunnel, traffic selector 수정, 방화벽 임시 rule 중에서 고르는데, 임시 rule은 만료 시점과 승인자를 반드시 함께 둬야 한다. 사후에는 CIDR registry, proposal baseline, packet evidence template을 추가해서 다음 연동 때 같은 합의 누락이 반복되지 않게 한다.

RISK

자주 틀리는 판단

VPN·Private Connectivity에서 자주 틀리는 판단은 연결 방식와 운영 증거의 책임 경계를 흐리는 데서 시작된다. 아래 신호가 보이면 설계, runbook, 답변 구조를 다시 점검한다.

  • VPN 터널 UP을 서비스 연동 완료로 착각한다.
  • 고객사 방화벽 변경 담당자와 시간을 맞추지 않는다.
  • Phase 2 traffic selector가 실제 CIDR과 다르다.
  • DNS forwarder가 없어 IP로만 임시 테스트하고 끝낸다.
EVIDENCE

검증 기준·증거 패킷

사설 연결은 cloud와 고객망 양쪽의 물리/논리/BGP/방화벽 증거가 맞아야 완료된다. 한쪽 콘솔의 connected 상태만으로 업무 트래픽 성공을 보장하지 않는다.

기준일은 2026-07-09 감사를 기준으로 삼고, VPN/DX/ExpressRoute 변경이나 failover drill이 있을 때마다 재확인한다. maintenance ticket, tunnel event, BGP session change, firewall rule change를 남겨서 cloud와 고객망 담당자가 같은 시간창과 prefix 목록을 확인하는지 본다.

provider/region/version 전제도 명시해야 한다. AWS Site-to-Site VPN/Direct Connect/Transit Gateway 또는 Azure VPN Gateway/ExpressRoute/Virtual WAN, region, gateway SKU, device firmware를 적어두고 tunnel outside IP, ASN, BGP peer, advertised/received prefix, gateway SKU를 함께 남긴다. provider 제한과 고객 장비 제한은 서로 다른 원인이므로 분리해서 좁혀야 한다.

명령 출력 예시는 IKE/IPsec, BGP, route, packet capture, DNS forwarding을 캡처한다. tunnel status, BGP neighbor summary, route propagation, firewall hit/drop, pcap filter, dig forwarding 결과를 남기면 5-tuple이 source, tunnel, destination 중 어디까지 보였는지 기록된다.

완료 기준은 primary/secondary 경로와 failover 기준이 검증되는 것이다. failover drill 로그, asymmetric routing 여부, MTU/MSS 테스트, rollback route를 근거로, 장애 시 전환 조건과 되돌림 조건, 고객망 승인자가 명확한지 확인한다.
