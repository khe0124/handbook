VPN·Private Connectivity

사설 연결을 터널 상태가 아니라 서비스 통신 성공 기준으로 검증한다

FLOW

이 문서를 관통하는 흐름

이 문서는 VPN·Private Connectivity를 "터널이 UP이다"라는 상태값이 아니라 실제 업무 트래픽이 목적지 포트까지 도달했다는 증거로 검증하도록 짜여 있다. 사설 연결 하나가 살아있다고 말하려면 연결 방식 선택, IPsec 협상, 라우팅과 방화벽, 그리고 양쪽이 공유할 수 있는 운영 증거라는 네 겹이 순서대로 맞아야 한다. 아래 절들은 이 네 겹을 개념에서 판단 기준으로, 판단 기준에서 실행 가능한 플레이북으로 좁혀가는 순서로 이어진다.

맨 앞 INDEX 절은 본문이 아니라 이 문서를 읽는 방식을 정하는 계약서다. 이 문서는 개념 요약이 아니라 운영 판단 연습용 플레이북이라고 못 박고, 각 항목을 "무엇을 아는가"가 아니라 "장애 때 어떤 증거를 보고 어떤 가설을 버리는가" 기준으로 읽으라고 지시한다. 그 아래 핵심 개념, 주제별 운영 증거, 실무 플레이북, 용어사전, Incident packet, 주제별 답변 구조라는 여섯 항목이 이후 절의 순서를 그대로 예고한다.

본문은 VPN-00 연결 방식에서 시작한다. Site-to-Site VPN은 인터넷 품질과 IPsec 협상에 기대는 만큼 빠르게 구축할 수 있지만, 전용선·Direct Connect·Interconnect·ExpressRoute·Private Endpoint는 비용과 리드타임이 큰 대신 예측 가능성과 격리를 산다는 trade-off를 먼저 세운다. 연결 방식이 정해지면 VPN-01 IPsec 협상으로 넘어가, Phase 1에서 IKE SA를 세우고 Phase 2에서 데이터 트래픽용 IPsec SA를 세우는 과정에서 encryption, integrity, DH group, PFS, lifetime, PSK, NAT-T, traffic selector가 양쪽에서 정확히 일치해야 한다는 점을 짚는다. 터널 DOWN이나 반복적인 flap은 여기서 proposal mismatch와 rekey 문제를 먼저 의심하라는 것이 이 장의 결론이다.

터널이 UP이라고 끝나는 게 아니다. VPN-02 라우팅과 방화벽은 local CIDR, peer CIDR, route table, security group, 고객사 방화벽, return path가 전부 맞아야 애플리케이션 통신이 이뤄진다는 것을 보여주고, CIDR overlap은 협상이 아니라 설계 단계에서 이미 제거돼야 하는 문제라고 선을 긋는다. 이어지는 VPN-03 운영 증거는 터널 상태, rekey 로그, packet counter, tcpdump, nc, curl 결과를 서로 분리해서 봐야 한다는 원칙을 세우고, 고객사에 협업을 요청할 때 넘길 최소 단위 — source IP, destination IP, port, timestamp, packet evidence — 를 정의한다. VPN-00부터 VPN-03까지는 결국 "터널 UP"과 "서비스 통신 성공"이 서로 다른 명제라는 것을 계층별로 증명하는 흐름이다.

CHECK 실무 체크리스트는 이 네 장의 판단 기준을 변경 위험 검토표로 압축한다. local/peer CIDR과 Phase 1/2 값을 표로 합의하고, 터널 UP과 애플리케이션 통신 성공을 분리해 검증하고, route table·방화벽·return path·DNS를 양쪽에서 확인하고, 장애 시 넘길 packet evidence 양식을 미리 정해두라는 네 항목이 설계·변경·복구 단계별 산출물과 차단 기준 표로 다시 정리된다.

PLAYBOOK 실무 플레이북은 PRIVATE CONNECTIVITY DEBUG PLAYBOOK이라는 serial-card로 이 체크리스트를 실행 순서로 바꾼다. symptom → scope → recent change → evidence → mitigation → verification → runbook diff라는 한 줄 흐름 아래, Tunnel·Routing/Firewall·Application path 세 개의 운영 표면마다 볼 증거와 판단 기준을 나눠 배치하고, 협상·포트·증거 공유 세 확인 단계에서 실제로 칠 명령과 그 해석 기준까지 이어붙인다. 이 장의 핵심은 명령어 암기가 아니라 어떤 가설을 버리고 어떤 완화책을 실행할지 결정하는 순서 자체다.

PRACTICE 출력 판독 훈련은 그 순서를 실제 출력으로 손에 익힌다. "VPN tunnel UP but API timeout 판독" 랩 하나가 Site-to-Site VPN 터널은 UP인데 고객사 ERP API 호출은 timeout인 상황을 packet evidence로 재현하고, packet_in이 0이고 customer_firewall이 deny인 비정상 출력과 정상 출력을 나란히 놓아 VPN 자체가 아니라 고객사 방화벽과 return path를 의심해야 한다는 판단을 훈련시킨 뒤, 즉시 완화(임시 allow rule 요청)와 영구 수정(packet evidence template과 방화벽 변경 승인 절차를 runbook에 추가)을 분리해 실행하게 한다.

TERM 용어사전은 Site-to-Site VPN, IPsec Phase 1, IPsec Phase 2, CIDR overlap, return path 다섯 용어를 정의·운영 증거·자주 하는 오해·관련 항목으로 정리해 앞선 장들에서 흩어져 쓰인 개념을 한곳에 모은다. CASE 장애/운영 시나리오는 고객사 ERP와 Site-to-Site VPN을 새로 연결하는 실제 사례를 따라가며, CIDR overlap을 먼저 확인하고 IPsec proposal을 양쪽 문서로 맞춘 다음 ICMP가 아니라 실제 API/DB 포트를 nc·tcpdump·health check로 검증하라는 흐름을 Triage frame 콜아웃과 Incident packet 표로 못 박는다.

RISK 자주 틀리는 판단은 VPN 터널 UP을 서비스 연동 완료로 착각하거나, 고객사 방화벽 변경 담당자와 시간을 맞추지 않거나, Phase 2 traffic selector가 실제 CIDR과 다르거나, DNS forwarder 없이 IP로만 임시 테스트하고 끝내는 네 가지 반복 실수를 짚는다. EVIDENCE 검증 기준·증거 패킷은 이 모든 판단이 결국 cloud와 고객망 양쪽의 물리·논리·BGP·방화벽 증거가 같은 시간창과 prefix 목록에서 일치해야 완료된다고 선언하며 문서를 닫는다.

그러니 이 문서는 위에서 아래로 한 번 읽고 끝낼 자료가 아니라, 장애가 발생했을 때 "터널은 UP인가, 애플리케이션 통신은 성공했는가", "이 증거는 양쪽이 같은 시간대·같은 5-tuple로 확인 가능한가", "지금 취할 조치는 임시 완화인가 영구 수정인가"라는 세 질문으로 되돌아가 참조하는 자료다.

VPN-00

연결 방식

Site-to-Site VPN은 빠르게 구축할 수 있지만 인터넷 품질과 IPsec 협상에 의존한다. 전용선, Direct Connect, Interconnect, ExpressRoute, Private Endpoint는 비용과 리드타임이 크지만 예측 가능성과 격리가 좋다.

운영 질문확인할 증거판단 기준
사설 연결 방식이 요구되는 격리와 예측 가능성에 맞는가?VPN/Direct Connect/ExpressRoute/Private Endpoint option, latency, SLA, cost, lead time빠른 구축과 안정적 전용 연결의 trade-off를 명시해야 한다.
연결 방식을 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?connectivity design, circuit/tunnel status, provider SLA, cost estimate연결 방식 선택이 업무 중요도와 복구 목표에 맞아야 한다.
연결 방식 장애에서 임시 완화와 영구 수정은 어떻게 나누는가?VPN 품질 변동으로 배치 연동 지연임시 VPN과 장기 전용선/Private Endpoint 전환 계획을 분리한다.
VPN-01

IPsec 협상

IPsec은 Phase 1에서 IKE SA를 만들고 Phase 2에서 데이터 트래픽용 SA를 만든다. encryption, integrity, DH group, PFS, lifetime, PSK, NAT-T, traffic selector가 양쪽에서 일치해야 한다.

운영 질문확인할 증거판단 기준
IPsec Phase 1/2 협상이 양쪽에서 같은 값으로 합의되었는가?IKE SA, IPsec SA, encryption, integrity, DH group, PFS, lifetime, PSK, NAT-T터널 DOWN은 proposal mismatch와 rekey 문제를 먼저 본다.
IPsec 협상을 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?VPN tunnel status, IKE log, Phase 1/2 proposal sheet, packet counter터널 UP과 데이터 패킷 흐름은 별개로 검증한다.
IPsec 협상 장애에서 임시 완화와 영구 수정은 어떻게 나누는가?rekey 시점마다 터널 flap 발생lifetime/PFS/proposal 값을 맞추고 rekey 로그를 보관한다.
VPN-02

라우팅과 방화벽

터널 UP은 충분하지 않다. local CIDR, peer CIDR, route table, security group, 고객사 방화벽, return path가 맞아야 앱 통신이 된다. CIDR overlap은 설계 단계에서 제거해야 한다.

운영 질문확인할 증거판단 기준
터널 UP 이후 실제 서비스 통신 경로가 열려 있는가?local CIDR, peer CIDR, route table, customer firewall, return path, DNSICMP 성공만으로 API/DB 포트 성공을 판단하지 않는다.
라우팅과 방화벽을 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?route readback, firewall log, nc -vz, curl internal API, tcpdump양쪽 route와 firewall이 같은 src/dst/port를 허용해야 한다.
라우팅과 방화벽 장애에서 임시 완화와 영구 수정은 어떻게 나누는가?터널은 UP이나 ERP API timeouttraffic selector, route, firewall, DNS를 순서대로 좁힌다.
VPN-03

운영 증거

장애 시 터널 상태, rekey 로그, packet counter, tcpdump, nc, curl 결과를 분리해 본다. 고객사에 요청할 때는 source IP, destination IP, port, timestamp, packet evidence를 제공한다.

운영 질문확인할 증거판단 기준
고객사와 공유 가능한 packet evidence가 준비되어 있는가?timestamp, source IP, destination IP, port, tunnel id, packet counter, tcpdump sample상대방이 같은 시간대와 같은 5-tuple로 확인할 수 있어야 한다.
운영 증거를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?tcpdump, nc/curl output, firewall decision, tunnel byte counter증거가 없으면 고객사 방화벽/라우팅 협업이 추측이 된다.
운영 증거 장애에서 임시 완화와 영구 수정은 어떻게 나누는가?양쪽 모두 상대 네트워크 문제라고 주장공유 evidence template과 escalation owner를 runbook에 추가한다.
CHECK

실무 체크리스트

VPN·Private Connectivity 체크리스트는 연결 방식, IPsec 협상, 라우팅과 방화벽, 운영 증거의 변경 위험을 사전에 드러내기 위한 검토표다. 각 항목은 리뷰, 배포 승인, 운영 인수에서 같은 증거로 다시 확인되어야 한다.

  • local/peer CIDR, tunnel endpoint, Phase 1/2 값을 표로 합의한다.
  • 터널 UP과 애플리케이션 통신 성공을 분리해 검증한다.
  • route table, 방화벽, return path, DNS를 양쪽에서 확인한다.
  • 장애 시 전달할 packet evidence 양식을 미리 정한다.

PRACTICE

출력 판독 훈련

VPN·Private Connectivity는 개념을 아는 것보다 실제 출력에서 정상과 비정상을 구분하는 훈련이 중요하다. 아래 lab은 명령, 출력, 판단, 완화, 영구 수정을 한 번에 연결한다.

PRACTICE LAB 01 · VPN tunnel UP but API timeout 판독

Site-to-Site VPN 터널은 UP이지만 고객사 ERP API 호출이 timeout 된다.

Command / Query목적
vpn packet evidence
src=10.12.4.18 dst=172.20.8.10 port=443
phase1=UP phase2=UP
packet_out=42 packet_in=0
customer_firewall=deny
터널 상태와 실제 애플리케이션 포트 통신을 분리한다.

위 명령을 실행했을 때 정상 출력과 비정상 출력이 어떻게 다른지 비교한다.

정상 출력비정상 출력판단 훈련
phase2=UP
packet_out=42
packet_in=42
firewall=allow
curl_status=200
phase2=UP
packet_out=42
packet_in=0
customer_firewall=deny
curl_status=timeout
VPN 자체보다 고객사 방화벽, return path, traffic selector 문제일 가능성이 높다.

CASE

장애/운영 시나리오

고객사 ERP와 Site-to-Site VPN을 연결한다. CIDR overlap을 먼저 확인하고, IPsec proposal을 양쪽 문서로 맞춘다. 터널이 올라온 뒤에는 ICMP가 아니라 실제 API port와 DB port를 nc, tcpdump, 애플리케이션 health check로 검증한다.

Triage frame

VPN·Private Connectivity 장애는 증상 → 영향 범위 → 최근 변경 → Tunnel 증거 → 완화책 → 복구 검증 → 재발 방지 순서로 기록한다. 이 흐름이 있어야 담당자가 바뀌어도 같은 결론에 도달한다.

RISK

자주 틀리는 판단

VPN·Private Connectivity에서 자주 틀리는 판단은 연결 방식와 운영 증거의 책임 경계를 흐리는 데서 시작된다. 아래 신호가 보이면 설계, runbook, 답변 구조를 다시 점검한다.

  • VPN 터널 UP을 서비스 연동 완료로 착각한다.
  • 고객사 방화벽 변경 담당자와 시간을 맞추지 않는다.
  • Phase 2 traffic selector가 실제 CIDR과 다르다.
  • DNS forwarder가 없어 IP로만 임시 테스트하고 끝낸다.
