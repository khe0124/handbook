백엔드·DB·API
설계 루프

AI agent는 API와 DB 초안을 빠르게 만들 수 있지만, 풀스택 개발자는 권한, 데이터 무결성, 트랜잭션, 기존 계약을 직접 검증해야 합니다.

BE-00

백엔드 단계에서 AI를 쓰는 방식

백엔드에서 AI를 쓸 때의 목표는 코드를 빨리 받는 것이 아니라 API 계약과 데이터 판단을 먼저 명확히 하는 것입니다. 권한과 중복 처리처럼 위험한 결정은 AI 제안이 아니라 사람의 결정으로 고정해야 합니다.

AI에게 맡길 일사람이 검토할 일
endpoint 후보와 error code 초안권한 모델과 기존 API 스타일
DB table과 index 후보unique 제약, 데이터 보존, migration 위험
validation rule 후보보안과 비즈니스 정책
테스트 후보트랜잭션과 race condition 위험
BE-01

백엔드 AI Loop

BACKEND LOOP 기획 산출물 입력 -> API 계약 초안 -> DB 제약 검토 -> 권한/트랜잭션 검토 -> 테스트 후보 -> 구현 
prompt:
  role: "Backend Builder"
  task: "백오피스 환불 승인 기능의 API 계약과 DB 모델 초안을 작성해줘"
  constraints:
    - "refund_manager만 승인/반려 가능"
    - "이미 처리된 요청은 재처리 불가"
    - "승인/반려 시 audit log 필수"
  output:
    - endpoints
    - error_codes
    - tables
    - indexes
    - backend_tests
USE

실제로 이렇게 사용한다

백엔드 단계에서는 AI가 만든 endpoint나 table을 그대로 쓰지 않습니다. 먼저 API 계약과 DB 제약을 초안으로 받고, 권한·중복·만료·트랜잭션을 사람이 검토합니다.

내 입력:
백오피스 환불 승인 기능의 백엔드 설계를 해줘.

이미 결정된 것:
- refund_manager만 승인/반려 가능
- CS 운영자는 조회만 가능
- 이미 처리된 요청이면 409
- 환불 금액은 결제 금액 이하
- 승인/반려 사유 필수
- 모든 결정은 audit log로 남겨야 함

너는 Backend Builder야.
출력:
1. API endpoint
2. error code
3. DB table
4. index/constraint
5. 꼭 필요한 backend test
AI 출력 예사람이 검토할 점
POST /refund-requests/:id/approve는 로그인 사용자면 가능refund_manager만 가능하도록 403 조건 수정
감사 로그 없이 상태만 변경refund_decision과 audit_log를 같은 transaction에서 저장하도록 수정
상태 변경만 updatestatus가 requested/reviewing일 때만 처리되도록 조건부 update와 locking 검토
api-contract.md:
POST /api/admin/refund-requests/:requestId/approve
  auth: refund_manager
  body: { amount, reason }
  errors:
    400: invalid_refund_amount_or_reason
    403: not_refund_manager
    409: already_processed

db-plan.md:
refund_requests:
  id
  order_id
  customer_id
  requested_amount
  status
  decided_at
constraints:
  - "only requested/reviewing requests can be approved or rejected"
  - "refund_decisions and audit_logs are inserted in the same transaction"
개념

백엔드에서 AI Loop는 코드를 받는 과정이 아니라 계약을 먼저 고정하는 과정입니다. 계약이 고정되면 프론트, 백엔드, 테스트가 같은 기준으로 움직입니다.

BE-02

API 계약 예시

POST /api/admin/refund-requests/:requestId/approve
  auth: refund_manager
  body:
    amount: number
    reason: string
  responses:
    200: refund_approved
    400: invalid_refund_amount_or_reason
    403: not_refund_manager
    409: already_processed

POST /api/admin/refund-requests/:requestId/reject
  auth: refund_manager
  body:
    reason: string
  responses:
    200: refund_rejected
    400: missing_reject_reason
    403: not_refund_manager
    409: already_processed

DB 설계 예시

필드/제약판단

EVAL

평가 가능성 보강 패킷

AI Native와 AX 산출물은 좋은 의도보다 재현 가능한 평가 기록으로 닫는다. 아래 패킷이 없으면 데모는 가능해도 운영 승인이나 다음 반복 학습으로 넘기지 않는다.

항목기록 기준통과 기준
기준일평가 실행일, 사용 모델·도구 버전, 주요 정책·프롬프트 해시, 대상 코드 브랜치를 함께 남긴다.2026-07-09 기준으로 재실행자가 같은 입력과 버전을 확인할 수 있다.
평가셋/fixture정상 케이스, 경계값, 실패 유도 케이스, 보안·개인정보 케이스를 최소 3:1:1:1 비율로 둔다.fixture 이름, 입력, 기대 출력, 금지 출력, 소유자가 표로 연결된다.
metric threshold정확도, 누락률, hallucination, latency, cost, human override율 중 문서 목적에 맞는 지표를 고른다.핵심 경로 pass 95% 이상, 치명 실패 0건, p95 latency와 비용이 사전 budget 안에 있다.
승인 기준제품 책임자, 엔지니어, 보안/운영 검토자가 보는 evidence packet을 분리한다.각 승인자가 pass/fail 사유와 남은 예외를 한 줄로 남긴다.
rollback 기준오답 누적, 비용 초과, 개인정보 노출, 권한 없는 자동 실행을 즉시 중단 조건으로 둔다.feature flag, 이전 prompt/model, 수동 처리 루트, 사용자 공지 문안이 준비되어 있다.
제출물

eval-packet.md에는 기준일, fixture 링크, metric threshold, 승인자, rollback 절차를 채운 완성 예시와 빈 템플릿을 함께 둔다. 수치가 없는 평가는 학습 기록으로만 보관하고 운영 판단에 쓰지 않는다.
