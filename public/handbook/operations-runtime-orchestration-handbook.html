RUN-00

컨테이너 런타임

컨테이너는 프로세스, filesystem, network namespace, cgroup 제한을 묶은 실행 단위다. CPU, memory, file descriptor, ephemeral storage 제한을 모르고 운영하면 OOM, throttling, log 폭증을 놓친다.

컨테이너를 그냥 "작은 서버" 정도로 생각하면 CPU와 memory 제한이 왜 중요한지 놓치기 쉽다. 실제로 컨테이너는 cgroup으로 리소스가 강하게 제한된 프로세스이고, 이 제한을 넘는 순간 OOMKilled나 throttling 같은 형태로 즉시 대가를 치른다. 그래서 컨테이너 제한이 실제 장애 신호와 연결되어 있는지 확인하려면 CPU throttling, memory working set, OOMKilled, file descriptor, ephemeral storage, restart reason을 함께 봐야 한다. 컨테이너를 이미지가 아니라 제한된 프로세스로 보는 관점이 여기서부터 시작된다.

이 관점이 맞는지 검증하려면 kubectl describe, logs --previous, cgroup metric, container exit code를 확인한다. 여기서 중요한 것은 재시작 자체가 아니라 재시작의 이유다. 같은 "재시작 8번"이라도 정상적으로 종료 후 재기동한 것인지, 계속 OOMKilled로 죽어나가는 것인지는 exit reason으로만 구분할 수 있다.

트래픽이 늘어난 뒤 OOMKilled가 반복되는 상황을 생각해보자. 이때 먼저 해야 할 것은 request/limit 값이 실제 사용량과 맞는지, memory leak이 있는지, 부하가 몰릴 때 graceful degradation이 동작하는지를 나눠서 보는 것이다. 이 세 가지를 뭉뚱그려서 "메모리가 부족하니 limit을 올리자"고만 하면, 진짜 원인이 leak이었을 경우 문제는 조금 늦게 다시 터질 뿐이다.

RUN-01

오케스트레이션 객체

Kubernetes 기준으로 Deployment는 desired state, ReplicaSet은 replica 유지, Pod는 실행 단위, Service는 안정된 discovery, Ingress는 외부 HTTP 진입점이다. label과 selector가 어긋나면 정상 pod도 traffic을 받지 못한다.

Kubernetes에서 Deployment, ReplicaSet, Pod, Service, Ingress는 각자 다른 역할을 하지만, 실제 장애는 이 객체들이 서로 정확히 연결되지 않을 때 생긴다. 오케스트레이션 객체 연결이 traffic routing까지 일치하는지는 Deployment, ReplicaSet, Pod, Service, selector, endpoint, Ingress rule, target group을 하나씩 따라가며 확인한다. 특히 label과 selector가 어긋나면 pod 자체는 정상으로 떠 있어도 Service가 그 pod를 찾지 못해 트래픽을 아예 받지 못하는 상황이 생긴다.

이걸 원인 후보에서 배제하려면 kubectl get endpoints, describe service/ingress, target health, event log를 본다. 핵심은 desired state, 즉 내가 의도한 상태와 실제 traffic이 흐르는 endpoint를 나란히 놓고 비교하는 것이다. Deployment가 정상이라고 나와도 그게 실제로 트래픽을 받고 있다는 뜻은 아니다.

pod는 분명 Running 상태인데 서비스는 503을 반환하는 상황이 대표적인 예다. 이럴 때는 코드를 의심하기 전에 selector, endpoint, ingress rule부터 확인해야 한다. 문제가 selector 설정에 있었다면 그걸 고치고 smoke test로 실제 트래픽이 다시 흐르는지 확인하는 것이 영구적인 해결책이다.

RUN-02

health check

readiness는 트래픽을 받아도 되는지, liveness는 재시작이 필요한지, startup probe는 느린 부팅을 보호하는지 판단한다. health check가 DB까지 강하게 묶이면 DB 지연 때 전체 pod가 빠질 수 있다.

readiness, liveness, startup probe는 이름은 비슷하지만 완전히 다른 질문에 답한다. readiness는 지금 이 pod가 트래픽을 받아도 되는가, liveness는 이 pod를 재시작해야 하는가, startup probe는 아직 부팅 중이니 좀 더 기다려줘야 하는가를 묻는다. 이 셋이 각자 목적에 맞게 분리되어 있는지는 readiness status, liveness restart, startup probe, probe path dependency, failure threshold로 확인한다. 특히 liveness가 DB 상태까지 검사하도록 설계하면, DB가 잠깐 느려졌을 뿐인데 멀쩡한 pod까지 전부 재시작시켜서 장애를 오히려 키울 수 있다.

이 설계가 잘못됐는지 확인하려면 kubectl describe pod, probe event, readiness endpoint, dependency status를 본다. 여기서 나누어야 할 질문은 두 가지다. 지금 트래픽을 받아도 되는가, 그리고 재시작이 필요한가. 이 둘을 같은 probe로 뭉쳐서 판단하면 안 된다.

실제로 DB 지연이 발생했을 때 모든 pod가 liveness 실패로 동시에 재시작되는 사고가 일어난다. 이걸 막으려면 liveness probe의 검사 범위를 얕게, 프로세스가 살아있는지 정도로 좁히고, dependency 상태는 readiness나 별도 metric으로 분리해서 봐야 한다. 그래야 DB가 느려져도 pod는 살아있으면서 readiness만 내려가고, DB가 회복되면 자연스럽게 다시 트래픽을 받는다.

RUN-03

배포 안정성

rolling update는 maxUnavailable, maxSurge, pod disruption budget, connection draining, graceful shutdown이 함께 맞아야 무중단에 가까워진다. HPA는 CPU만이 아니라 queue lag, request rate 같은 업무 지표도 후보가 된다.

무중단 배포는 replica를 여러 개 띄운다고 저절로 되는 게 아니다. rolling update가 실제로 안전하려면 maxUnavailable, maxSurge, PDB, terminationGracePeriod, preStop, target deregistration delay가 모두 맞물려야 한다. 새 pod가 준비되는 타이밍과 기존 pod가 종료되는 타이밍이 실제 traffic 흐름과 맞아야 사용자가 끊김을 느끼지 않는다.

이게 실제로 지켜지는지는 rollout status, pod events, LB target draining, connection error rate로 확인한다. 여기서 흔한 오해가 "replica가 3개 있으니 무중단이겠지"라는 생각이다. 하지만 무중단 여부를 결정하는 건 replica 개수가 아니라 연결이 정리되는 타이밍과 readiness가 맞아떨어지는지다.

배포 도중 일부 요청이 502로 실패하는 상황을 만나면 순서대로 확인한다. 먼저 rollout을 pause하거나 undo해서 확산을 막고, drain 설정을 조정하고, graceful shutdown 로직을 보강한다. 이 세 가지를 순서 없이 아무거나 먼저 건드리면 원인 파악이 더 늦어진다.

CHECK

실무 체크리스트

컨테이너·오케스트레이션·Health Check 체크리스트는 컨테이너 런타임, 오케스트레이션 객체, health check, 배포 안정성의 변경 위험을 사전에 드러내기 위한 검토표다. 각 항목은 리뷰, 배포 승인, 운영 인수에서 같은 증거로 다시 확인되어야 한다.

  • readiness, liveness, startup probe의 목적을 분리한다.
  • resource request/limit과 실제 사용량을 비교한다.
  • service selector, ingress rule, connection draining을 점검한다.
  • graceful shutdown과 rolling update 조건을 부하 상황에서 검증한다.

이 체크리스트에서 특히 자주 놓치는 지점이 세 군데다. 설계 단계에서는 readiness/liveness 목적 분리나 resource 설정처럼 눈에 보이는 것만 챙기고, 정작 이 변경이 다른 서비스나 비용에 어떤 영향을 주는지는 문서로 남기지 않는 경우가 많다. 목적, 영향 범위, 비목표, owner가 산출물로 남아 있지 않고 영향 범위가 사용자·시스템·비용 기준으로 설명되지 않는다면, 이 단계에서 진행을 막아야 한다.

변경 단계에서는 diff와 승인 기록, 검증 명령이 함께 있어야 한다. probe 설정이나 rollout 전략처럼 부하 상황에서만 문제가 드러나는 변경은 특히, production 변경과 staging 검증이 어떻게 다른지 설명하지 못하면 배포해서는 안 된다.

복구 단계는 배포가 끝난 뒤에야 신경 쓰기 쉬운데 사실 배포 전에 정해둬야 한다. rollback 또는 forward fix 중 무엇을 쓸지, 담당자가 누구인지, 얼마나 걸릴지가 미리 정해져 있지 않고 실패 시 되돌릴 수도 없는데 사전 승인과 공지가 없다면, 배포를 보류해야 한다.

장애가 컨테이너·오케스트레이션 계층에서 터졌을 때는 세 가지 표면을 순서대로 훑는다. 먼저 Pod / Task health 표면에서 readiness, liveness, startup probe, restart reason, exit code를 본다. 여기서 판단할 것은 재시작이 회복 과정인지, 아니면 증상이 계속 악화되고 있다는 신호인지다. 다음으로 Traffic 표면에서 service selector, target group, ingress rule, connection draining을 본다. 목적은 정상적으로 떠 있는 pod가 실제로 traffic을 받는 경로에 있는지 확인하는 것이다. 마지막으로 Capacity 표면에서 request/limit, throttling, OOM, HPA signal, queue lag를 본다. CPU 평균만 보면 정상처럼 보이는 경우가 많으니, saturation과 tail latency를 함께 봐야 진짜 압박 상황을 잡아낼 수 있다.

이 세 표면을 실제로 조사하는 순서도 있다. 먼저 상태 확인 단계에서 kubectl get pods, describe pod, logs --previous, rollout status로 CrashLoop, OOMKilled, probe failure 중 무엇인지 분리한다. 그다음 네트워크 확인 단계에서 service endpoints, ingress events, target health, connection draining을 보면서 selector mismatch나 readiness 누락을 찾는다. 마지막으로 리소스 확인 단계에서 CPU throttling, memory working set, ephemeral storage, file descriptor를 본다. limit부터 무작정 올리기 전에 원인 지표를 먼저 확인해야, 같은 문제가 limit을 올린 뒤에도 반복되는 걸 막을 수 있다.

PRACTICE

출력 판독 훈련

컨테이너·오케스트레이션·Health Check는 개념을 아는 것보다 실제 출력에서 정상과 비정상을 구분하는 훈련이 중요하다. 아래 lab은 명령, 출력, 판단, 완화, 영구 수정을 한 번에 연결한다.

PRACTICE LAB 01 · OOMKilled 판독

배포 후 일부 pod가 재시작되고 p99 latency가 증가한다.

재시작 원인이 liveness 실패인지 OOMKilled인지는 겉보기 증상만으로는 구분되지 않는다. 이걸 가려내려면 다음 명령으로 pod의 종료 이력을 직접 확인해야 한다.

kubectl describe pod api-7d9f -n production

kubectl logs api-7d9f -n production --previous

정상적인 경우라면 pod가 Completed 상태로 종료되고 재시작 횟수가 0이다.

Last State: Terminated
Reason: Completed
Restart Count: 0

비정상적인 경우에는 다음처럼 OOMKilled와 반복 재시작이 나타난다.

Last State: Terminated
Reason: OOMKilled
Exit Code: 137
Restart Count: 8

이 출력에서 Reason이 OOMKilled이고 Exit Code가 137이라는 것은, 애플리케이션 코드 자체의 버그가 아니라 memory 관련 문제라는 강한 신호다. memory limit이 실제 필요량보다 낮게 잡혀 있거나, memory leak이 있거나, 갑작스러운 traffic spike로 순간 사용량이 튀었을 가능성이 크다. 즉시 완화는 rollout을 pause하고 replica를 늘려 개별 pod가 받는 부하를 줄이면서, memory limit을 임시로 올리고 무거운 endpoint에는 rate limit을 거는 것이다. 영구 수정은 memory profile을 분석해서 진짜 원인을 찾고, request/limit을 다시 산정하고, load test로 검증한 뒤, alert에 OOMKilled count를 추가해 다음에는 더 빨리 알아채도록 만드는 것이다. restart count가 안정되고 p99가 회복되고 memory working set이 limit 아래로 유지되면 이 완화와 수정이 제대로 먹힌 것이다.

PRACTICE LAB 02 · Service selector mismatch 판독

pod는 Running인데 서비스가 503을 반환한다.

런타임 자체는 멀쩡한데 트래픽이 도달하지 못하는 상황이라면, 가장 먼저 의심할 곳은 코드가 아니라 Service selector다. 실제 pod label과 selector가 일치하는지 다음으로 확인한다.

kubectl get endpoints api -n production

kubectl get svc api -o yaml

정상적인 경우라면 endpoints에 pod IP가 채워져 있다.

ENDPOINTS: 10.0.12.4:8080,10.0.13.8:8080
selector: app=api

비정상적인 경우에는 selector가 바뀌어 endpoint가 비어 있다.

ENDPOINTS: <none>
selector: app=api-v2

endpoints가 비어 있다는 것은 pod가 죽은 게 아니라 Service가 어떤 pod를 대상으로 삼아야 할지 모른다는 뜻이다. 즉시 완화는 selector를 이전 값으로 rollback하거나 pod label에 hotfix를 적용해 다시 매칭시키는 것이다. 영구 수정은 deployment와 service의 label이 서로 어긋나지 않도록 contract test를 추가하고, rollout 뒤에 자동으로 도는 smoke test를 넣는 것이다. endpoints가 다시 채워지고 target health가 healthy로 돌아오고 503이 줄어들면 이 조치가 제대로 작동한 것이다.

TERM

용어사전

컨테이너·오케스트레이션·Health Check에서 반복적으로 등장하는 운영 용어를 정의, 증거, 오해, 관련 항목 기준으로 정리한다. 장애 중에는 용어 자체보다 해당 용어가 어떤 로그, 지표, 설정, 책임 경계와 연결되는지를 확인한다.

cgroup limit
컨테이너의 CPU, memory 같은 리소스 사용량을 커널 수준에서 강제로 제한하는 기능이다. CPU throttling, memory working set, OOMKilled 지표로 실제 제한이 걸리고 있는지 확인한다. 컨테이너가 VM처럼 독립된 리소스를 자동으로 보장받는다고 생각하기 쉽지만, 실제로는 host의 리소스를 나눠 쓰는 프로세스일 뿐이라 request/limit 설정과 OOM, throttling 여부를 직접 챙겨야 한다.
Deployment
Kubernetes에서 원하는 replica 개수와 rollout 방식을 선언적으로 관리하는 객체다. desired state, rollout status, ReplicaSet으로 실제 상태를 확인한다. Deployment 상태가 정상이면 트래픽도 정상일 거라고 생각하기 쉽지만, Deployment는 어디까지나 원하는 상태를 선언할 뿐이고 실제 트래픽이 흐르려면 ReplicaSet, Pod, Service까지 이어지는 경로가 전부 맞아야 한다.
selector
Service가 어떤 Pod에게 트래픽을 보낼지 label로 골라내는 조건이다. service selector, endpoints, pod label을 대조해서 확인한다. pod가 Running 상태이기만 하면 자동으로 Service의 대상이 된다고 생각하기 쉽지만, 실제로는 label이 selector와 정확히 일치해야만 endpoint 목록에 들어간다. 하나라도 어긋나면 그 pod는 존재해도 트래픽을 받지 못한다.
readiness
Pod가 지금 당장 트래픽을 받아도 되는 상태인지를 판단하는 probe다. readiness status와 endpoint population으로 확인한다. liveness와 같은 endpoint를 재사용해도 된다고 생각하기 쉽지만, 이 둘은 목적이 다르다. readiness는 지금 받아도 되는가, liveness는 재시작이 필요한가를 묻는 서로 다른 질문이라서 같은 기준으로 섞으면 장애 대응이 꼬인다.
liveness
Pod를 재시작해야 하는지를 판단하는 probe다. liveness restart 횟수와 probe event로 확인한다. DB 연결 상태까지 liveness에 포함시켜야 더 안전할 거라고 생각하기 쉽지만, 그렇게 하면 DB가 잠깐 느려졌을 뿐인데 정상적으로 떠 있던 pod까지 전부 재시작되어 장애를 오히려 키운다. 재시작 여부와 dependency 상태는 서로 다른 채널로 분리해서 설계해야 한다.
CASE

장애/운영 시나리오

배포 중 일부 요청이 502로 실패한다. 새 pod가 readiness 통과 전에 트래픽을 받는지, 종료 pod가 connection draining 없이 내려가는지, graceful shutdown 시간보다 terminationGracePeriod가 짧은지 확인한다.

Triage frame

컨테이너·오케스트레이션·Health Check 장애는 증상 → 영향 범위 → 최근 변경 → Pod / Task health 증거 → 완화책 → 복구 검증 → 재발 방지 순서로 기록한다. 이 흐름이 있어야 담당자가 바뀌어도 같은 결론에 도달한다.

처음 10분은 원인을 찾기보다 영향 범위부터 좁힌다. readiness, liveness, startup probe, restart reason, exit code를 기준으로 지금 벌어지고 있는 일의 경계를 확정하는 데 쓴다. 다음 30분은 kubectl get pods, describe pod, logs --previous, rollout status에서 구체적인 증거를 모으고, 그 증거로 완화책을 실행한다. 이 사이클은 다음 배포에서 같은 문제가 사람이 알아채기 전에 자동으로 걸러지는지 확인하고 나서야 끝난 것으로 본다.

Incident packet에는 증상, 완화, 사후 조치를 남긴다. 증상은 rolling update 중 일부 요청이 502로 실패했다는 관찰 사실이고, readiness, drain, terminationGracePeriod, target deregistration delay를 대조해서 정확히 어디가 문제인지 판정한다. 완화는 rollout pause/undo, scale out, bad pod drain 중에서 새 버전이 만드는 폭발 반경을 가장 빨리 줄일 수 있는 조치를 고른다. 사후 조치에서는 probe 설정과 graceful shutdown 로직을 실제 요청으로 다시 검증해서, 다음 배포에서도 같은 문제가 자동으로 걸리는지 확인한다.

RISK

자주 틀리는 판단

컨테이너·오케스트레이션·Health Check에서 자주 틀리는 판단은 컨테이너 런타임와 배포 안정성의 책임 경계를 흐리는 데서 시작된다. 아래 신호가 보이면 설계, runbook, 답변 구조를 다시 점검한다.

  • liveness probe로 DB 상태까지 검사해 전체 pod를 재시작시킨다.
  • readiness 없이 rolling update만 설정한다.
  • resource limit만 두고 request를 비워 scheduling을 불안정하게 만든다.
  • HPA를 CPU 하나로만 판단한다.
EVIDENCE

운영 증거 패킷

Kubernetes 운영 판단은 manifest 의도와 cluster 실제 상태를 같은 시간축에서 대조해야 한다. 이 문서의 실습 기준은 2026-07-09 기준 Kubernetes stable API(apps/v1 Deployment, policy/v1 PDB)와 kubectl/client-server minor skew 1단계 이내로 둔다. 실제 운영에서는 아래 첫 명령 출력으로 cluster 기준 버전을 먼저 고정한다.

kubectl version --short
kubectl get nodes -o wide
kubectl api-resources | grep -E 'deployments|poddisruptionbudgets'
kubectl rollout status deploy/api -n production --timeout=120s

기준 버전·도구는 Kubernetes server/client version, CNI, ingress controller, metrics-server, HPA controller, kubectl version을 남긴다. client와 server 사이 버전 차이가 크거나 PDB API가 policy/v1이 아니라면, 이번 실습에서 확인한 결과를 그대로 production 기준으로 믿어서는 안 된다.

명령 출력은 kubectl describe pod, events --sort-by=.lastTimestamp, logs --previous, rollout history/status를 남긴다. event 기록과 애플리케이션 로그의 timestamp가 서로 맞지 않는다면, 성급하게 원인을 확정하지 말고 raw output을 그대로 보존해야 나중에 다시 검토할 수 있다.

한 번의 배포만 보지 말고 대시보드·쿼리로 추세를 본다. restart count, OOMKilled, probe failure, endpoint count, rollout available replicas, p95/p99 latency가 그 지표다. rollout 자체의 성공과 실제 사용자 경로의 성공을 별개의 지표로 나눠서 닫는 것이 중요하다. rollout이 끝났다고 해서 사용자에게 문제가 없다는 뜻은 아니기 때문이다.

마지막으로 severity와 rollback, 승인 절차를 함께 정한다. endpoint가 0이 되거나 인증·결제 경로에서 5xx가 나면 SEV1, 특정 zone이나 tenant만 저하되면 SEV2, rollout이 단순히 지연되는 정도면 SEV3다. SEV1이나 SEV2 상황이면 rollout pause나 undo를 가장 먼저 검토하고, PDB, selector, probe 설정을 바꾸는 변경은 반드시 service owner의 승인을 거치도록 한다.

Probe/PDB manifest 기준

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 25%
  template:
    spec:
      terminationGracePeriodSeconds: 45
      containers:
        - name: api
          image: registry.example.com/api@sha256:...
          ports:
            - containerPort: 8080
          startupProbe:
            httpGet: { path: /startup, port: 8080 }
            periodSeconds: 5
            failureThreshold: 24
          readinessProbe:
            httpGet: { path: /ready, port: 8080 }
            periodSeconds: 5
            failureThreshold: 3
          livenessProbe:
            httpGet: { path: /live, port: 8080 }
            periodSeconds: 10
            failureThreshold: 3
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sh", "-c", "sleep 10"]
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-pdb
spec:
  minAvailable: 80%
  selector:
    matchLabels:
      app: api

Rollout 실패 실습

readiness path를 잘못 배포하면 kubectl describe pod, kubectl get endpoints api로 확인했을 때 pod는 Running이나 endpoint 수가 줄고 readiness event가 반복된다. kubectl rollout pause 후 probe path를 수정하거나 kubectl rollout undo로 복구한다.

PDB minAvailable을 replica 수와 같게 두면 kubectl get pdb와 drain dry-run event에서 disruptionsAllowed=0으로 node drain이 막힌다. replica를 늘리거나 PDB를 완화하고 maintenance window를 다시 승인받아 복구한다.

새 image가 CrashLoop를 만들면 kubectl logs --previous, rollout history에서 새 revision label에서만 restart와 5xx가 증가한다. rollout undo, image digest 고정, failing revision incident packet 작성으로 복구한다.
