품질 엔지니어링과 릴리즈 시스템

테스트를 많이 하는 것이 아니라 변경을 믿고 내보내는 시스템을 이해합니다.

FORMAT : 개념 → 맥락 → 판단 기준 → 실패 신호 · UPDATED 2026-07
INDEX

이 문서의 위치

품질 엔지니어링과 릴리즈 시스템 문서는 기술명을 외우기보다 이 주제에서 반복되는 압력, 책임 경계, 측정 기준을 읽는 데 초점을 둡니다. 아래 항목을 먼저 훑고 마지막의 수치 앵커와 사례로 판단 기준을 고정합니다.

QUAL-01

품질은 출시 가능성의 언어다

품질 엔지니어링은 버그를 찾는 활동만이 아니라 어떤 변경을 언제 내보내도 되는지 판단하는 기준을 만드는 일이다. 테스트는 그 기준을 실행 가능한 형태로 만든 도구다.

품질 엔지니어링을 버그를 찾는 활동으로만 이해하면, 정작 이 활동의 목적인 출시 판단 기준을 놓친다. 무엇이 깨지면 출시를 멈추는가라는 질문은 blocker 기준으로 답하고, 어떤 변경을 우선 검증하는가라는 질문은 risk-based testing으로 답한다. 출시 뒤 무엇을 관측하는가라는 질문은 crash, error, funnel, support signal로 답한다. 이 세 질문에 답할 수 있어야 테스트를 아무리 많이 돌려도 못 잡는 문제까지 함께 관리할 수 있다.

QUAL-02

테스트 피라미드보다 테스트 목적

unit, integration, e2e는 계층 이름보다 목적이 중요하다. 빠르게 원인을 좁히는 테스트, 계약을 지키는 테스트, 실제 사용자 흐름을 지키는 테스트가 서로 다른 역할을 한다.

unit, integration, e2e를 계층 순서로만 외우면 각 테스트가 실제로 무엇을 위해 존재하는지 놓친다. unit 테스트는 작은 규칙과 edge case를 빠르게 검증하는 역할이고, integration/contract 테스트는 모듈과 API 경계의 계약을 검증하는 역할이다. e2e/smoke 테스트는 핵심 사용자 경로가 실제로 살아있는지 확인하는 역할이다. 이 세 역할이 겹치지 않게 설계돼야 문제가 생겼을 때 어느 테스트가 왜 실패했는지 빠르게 판단할 수 있다.

QUAL-03

Flaky test

가끔 실패하는 테스트는 테스트가 아니라 신뢰 비용이다. randomness, time, network, async wait, shared state, test order 의존성을 제거하지 않으면 CI가 경고음이 아니라 소음이 된다.

가끔 실패하는 테스트를 방치하면 그 테스트는 신뢰를 주는 도구가 아니라 신뢰를 갉아먹는 비용이 된다. flaky test의 원인은 대체로 몇 가지로 갈린다. time은 고정 clock이나 fake timer가 필요한 원인이고, network는 mock, contract fixture, retry 기준이 필요한 원인이다. shared state는 격리된 DB, cleanup, deterministic seed가 필요한 원인이다. 이 원인들을 하나씩 제거하지 않으면 CI가 실패를 알리는 경고음이 아니라 그냥 무시하게 되는 소음으로 전락한다.

QUAL-04

릴리즈 후보와 회귀

Release candidate는 새 기능을 더 넣는 시점이 아니라 현재 변경 묶음을 검증하는 단위다. 회귀 테스트는 모든 것을 다시 누르는 것이 아니라 변경 영향 범위와 핵심 경로를 조합해 위험을 줄인다.

release candidate 단계에서 새 기능을 더 넣으려는 유혹을 참아야 한다. 이 단계의 역할은 확장이 아니라 지금까지 쌓인 변경 묶음을 검증하는 것이기 때문이다. change impact는 어떤 코드가 어떤 기능에 영향을 주는지를 보는 개념이고, test selection은 그 영향 범위에 맞춰 테스트 우선순위를 정하는 개념이다. release note는 변경 사항과 관측 포인트를 배포 단위로 기록하는 개념이다. 이 세 가지가 맞물려야 회귀 테스트를 전부 다시 돌리지 않고도 위험을 충분히 줄일 수 있다.

QUAL-05

핫픽스 판단

핫픽스는 빠른 해결처럼 보이지만 사용자에게 또 다른 변경을 강제한다. 즉시 수정, 다음 릴리즈 반영, feature flag off, rollback 중 무엇이 안전한지 사용자 영향과 재발 가능성으로 판단한다.

핫픽스는 빠른 해결처럼 보이지만, 사용자에게 또 다른 변경을 강제한다는 걸 잊기 쉽다. 그래서 여러 선택지 중 무엇이 안전한지 먼저 따져야 한다. rollback은 이전 버전이 안전하고 데이터 호환성이 유지될 때 선택하고, flag off는 문제 있는 기능만 골라서 끌 수 있을 때 선택한다. hotfix는 영향이 크면서도 수정 범위가 작고 검증이 가능할 때만 선택한다. 이 세 선택지를 사용자 영향과 재발 가능성 기준으로 비교하는 게 핫픽스 판단의 핵심이다.

QUAL-06

읽히는 신호

품질 글을 읽을 때는 테스트 도구 이름보다 기준을 본다. 무엇을 blocker로 보고, 어떤 변경을 위험하다고 보고, 출시 후 어떤 지표로 확인하는지가 있으면 품질 엔지니어링 맥락이 살아 있다.

품질에 관한 글을 읽을 때는 어떤 테스트 도구를 쓰는지보다 어떤 기준으로 판단하는지를 본다. risk tier 신호는 변경의 위험 등급을 어떻게 나누는지를 보여주고, quality gate 신호는 출시를 막는 기준이 무엇인지를 보여준다. post-release monitor 신호는 출시 후에 무엇을 관측하는지를 보여준다. 이 세 신호가 함께 있으면 그 글에는 실제 품질 엔지니어링 경험이 녹아 있는 것이다.

CASE

실무 상황 예시

아래 수치는 이해를 위한 가상 운영 수치입니다. 목적은 특정 회사 사례를 베끼는 것이 아니라, 기술 글에 자주 등장하는 상황·숫자·판단 기준을 읽는 감각을 만드는 것입니다.

Flaky test가 릴리즈를 막는 경우

SITUATION

가상 운영 수치다. 매주 release candidate에는 280개 변경이 들어간다. e2e 회귀 테스트는 90분, smoke test는 12분이고, flaky test rate가 8%라서 실패가 실제 회귀인지 노이즈인지 매번 확인해야 한다.

NUMBERS

flaky test 격리, 고정 clock, network fixture를 적용해 flaky test rate를 1.5%로 낮춘다. 릴리즈 차단은 핵심 경로 smoke test와 위험 변경 test selection으로 제한한다.

LESSON

테스트가 많아도 신뢰할 수 없으면 출시 가능성이 낮아진다. 품질 엔지니어링의 핵심은 테스트 개수가 아니라 실패 신호의 품질이다.

Android 결제 버튼 비활성화 버그

SITUATION

출시 후 Android 13 일부 단말에서 checkout 버튼이 비활성화된다. 전체 결제 시도의 3%가 영향을 받고, 서버 오류율은 정상이라 백엔드 알림은 울리지 않는다.

NUMBERS

flag off는 2분 안에 가능하지만 신규 쿠폰 기능도 함께 꺼진다. hotfix는 수정 30분, 빌드 검증 40분, 스토어 배포 지연이 2~8시간이다.

LESSON

핫픽스 판단은 수정 속도보다 사용자 영향과 검증 가능성으로 한다. 서버 지표만 보면 놓치는 클라이언트 funnel drop도 출시 후 관측에 들어가야 한다.
