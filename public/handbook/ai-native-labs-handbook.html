기획과 사용자
시나리오 설계

요구사항을 정한 뒤에는 AI agent를 사용해 사용자 흐름, 상태 전이, 실패 경로, MVP 범위를 구현 가능한 형태로 만듭니다.

PLAN-00

왜 기획 단계에 AI Loop가 필요한가

기획 단계의 실패는 코드가 아니라 빠진 흐름에서 생깁니다. AI는 happy path만 보는 사람의 습관을 보완해 실패 경로와 상태 전이를 빠르게 펼쳐볼 수 있게 합니다.

기획 산출물AI가 돕는 일사람이 결정하는 일
사용자 시나리오CS 운영자, 환불 관리자, 운영 리더 흐름 분리이번 릴리스에 포함할 운영자 흐름 선택
상태 전이requested, reviewing, approved, rejected, processing_failed 후보 생성실제 DB와 UI에 반영할 상태 확정
정책권한, 중복 처리, 금액 제한, 감사 로그 질문 생성정책 결정과 예외 처리 확정
PLAN-01

기획 AI Loop

PLANNING LOOP 요구사항 입력 -> 사용자 유형 분리 -> happy path 작성 -> 실패 path 작성 -> 상태표 작성 -> MVP 결정 
prompt:
  role: "Product Planner"
  task: "백오피스 환불 승인 기능의 운영자 시나리오와 실패 흐름을 만들어줘"
  constraints:
    - "refund_manager만 승인/반려 가능"
    - "이미 처리된 요청은 재처리 불가"
    - "승인/반려 사유 입력 필수"
  output:
    - happy_path
    - failure_paths
    - state_table
    - out_of_scope
USE

실제로 이렇게 사용한다

기획 단계에서는 AI에게 “기획해줘”라고 하지 않습니다. 요구사항 단계에서 확정한 결정들을 넣고, 사용자 유형별 흐름과 실패 흐름을 분리해서 뽑게 합니다.

내 입력:
아래 결정으로 백오피스 환불 승인 기능의 운영자 흐름을 설계해줘.

결정:
- refund_manager만 승인/반려 가능
- CS 운영자는 요청 목록과 상세를 읽을 수 있음
- 이미 처리된 요청은 409 already_processed
- 승인/반려 사유 입력 필수
- 환불 금액은 결제 금액을 초과할 수 없음
- 자동 환불 정책 엔진과 대량 일괄 승인은 이번 범위 제외

너는 Product Planner야.
출력 형식:
1. 사용자 유형별 happy path
2. failure path
3. 상태 전이표
4. MVP 범위
5. 후속 backlog
AI 출력 예사람이 고칠 점
운영자가 목록에서 여러 건을 일괄 승인한다대량 일괄 승인이 이번 MVP인지 확인한다. 아니면 후속 backlog로 이동
결제사 환불 실패 시 자동 재시도 제공자동 재시도까지 포함할지, 운영 알림만 남길지 결정
reviewing 상태 추가담당자 배정과 검토중 표시가 이번 범위인지 판단한다
state-table.md:
states:
  requested:
    visible_to: ["cs_operator", "refund_manager"]
    next: ["reviewing", "approved", "rejected"]
  approved:
    creates: ["refund_decision", "audit_log"]
    terminal: true
  processing_failed:
    operator_message: "결제사 환불 처리에 실패했습니다"
    next_action: "운영 알림 확인 후 재처리"
개념

기획 단계의 AI Loop는 화면 수를 늘리는 과정이 아니라, 흐름과 상태를 구현 가능한 단위로 줄이는 과정입니다.

PLAN-02

사용자 흐름 예시

흐름단계검토 질문
요청 검색상태/기간/고객명 필터 -> 환불 요청 선택운영자가 가장 먼저 확인해야 할 컬럼은 무엇인가
상세 검토주문/결제/문의/이전 처리 이력 확인승인 판단에 필요한 정보가 한 화면에 있는가
승인환불 금액 확인 -> 사유 입력 -> confirm -> 상태 변경실수 승인과 중복 클릭을 어떻게 막는가
반려반려 사유 입력 -> 고객 안내 문구 확인 -> 상태 변경반려 사유가 감사 로그와 고객 응대에 재사용되는가
PLAN-03

상태표 예시

상태진입 조건가능 행동종료 조건
requested고객 환불 요청 생성상세 보기, 승인, 반려approved/rejected/reviewing
reviewing운영자가 검토 시작담당자 변경, 메모 추가approved/rejected
approved승인 완료없음refund_decision과 audit_log 생성
rejected반려 완료없음반려 사유와 audit_log 생성
processing_failed결제사 환불 처리 실패재처리, 운영 알림 확인approved 또는 failure 유지
