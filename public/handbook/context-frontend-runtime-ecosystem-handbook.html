이 문서의 위치

프론트엔드 빌드·런타임·생태계 문서는 기술명을 외우기보다 이 주제에서 반복되는 압력, 책임 경계, 측정 기준을 읽는 데 초점을 둡니다. 아래 항목을 먼저 훑고 마지막의 수치 앵커와 사례로 판단 기준을 고정합니다.

FER-01

프론트엔드는 빌드 결과가 제품이다

개발자가 쓴 소스가 아니라 브라우저가 받은 HTML, CSS, JS, asset, cache header가 실제 제품이다. 빌드 시스템은 이 산출물을 만드는 compiler pipeline이다.

개발자가 작성한 소스 코드 자체는 사용자에게 아무 의미가 없다. 실제로 사용자가 받는 건 브라우저가 내려받는 HTML, CSS, JS, asset, cache header이고, 빌드 시스템은 소스를 이 최종 산출물로 바꿔주는 compiler pipeline이다. HTML entry는 초기 로딩과 asset 참조를 담당하는 산출물이고, JS chunk는 다운로드, parse, execute 비용을 만드는 산출물이다. CSS/asset은 렌더링 차단, 이미지 최적화, 캐시를 다루는 산출물이다. 이 세 산출물의 비용을 각각 이해해야 소스 코드 수준의 최적화가 실제 사용자 경험으로 이어지는지 판단할 수 있다.

FER-02

번들러의 역할

번들러는 모듈 그래프를 읽고, 변환하고, 쪼개고, 최적화한다. tree-shaking, code splitting, minification, asset hashing은 런타임 성능과 배포 안정성을 만든다.

번들러는 단순히 파일을 하나로 합치는 도구가 아니라, 모듈 그래프를 읽고 변환하고 쪼개고 최적화하는 역할을 한다. tree-shaking은 쓰지 않는 export를 제거하는 기능이고, code splitting은 필요한 시점에만 chunk를 로드하는 기능이다. hashing은 파일 내용에 기반한 이름을 붙여서 캐시를 안정적으로 만드는 기능이다. 이 세 기능이 함께 작동해야 런타임 성능과 배포 안정성이 동시에 확보된다.

FER-03

ESM/CJS와 패키지 경계

프론트엔드 생태계의 많은 문제는 패키지 형식과 module resolution에서 나온다. ESM-only 패키지, dual package hazard, default export 차이, browser field를 이해해야 빌드 오류를 읽을 수 있다.

프론트엔드 생태계에서 겪는 빌드 오류의 상당수는 코드 로직이 아니라 패키지 형식과 module resolution에서 비롯된다. module resolution은 import 문이 실제 파일로 어떻게 해석되는지를 정하는 규칙이고, dual package는 한 패키지가 ESM과 CJS를 동시에 제공할 때 생기는 경계 문제다. browser field는 브라우저 환경을 위한 대체 entry를 지정하는 개념이다. 이 세 가지를 이해하지 못하면 로컬에서는 잘 되던 빌드가 다른 환경에서 이유 없이 깨지는 상황을 설명할 수 없다.

FER-04

Hydration과 클라이언트 런타임

SSR/SSG 앱은 HTML이 먼저 보이고 JavaScript가 나중에 붙는다. hydration mismatch, client-only state, browser API 접근, streaming은 렌더링 전략의 핵심 제약이다.

SSR이나 SSG 앱은 HTML이 먼저 화면에 보이고 JavaScript가 나중에 붙는 구조라서, 그 사이의 불일치가 곧 버그가 된다. hydration mismatch는 서버가 만든 HTML과 클라이언트가 처음 렌더한 결과가 서로 다른 문제이고, client boundary는 브라우저에만 있는 API가 서버에는 없어서 생기는 문제다. islands/partial hydration은 페이지 전체가 아니라 필요한 부분에만 상호작용을 부여하는 접근 방식이다. 이 세 개념을 구분하면 SSR 버그가 실제로는 React 문법 문제가 아니라 서버와 클라이언트 사이의 계약 문제라는 걸 알 수 있다.

FER-05

브라우저 호환성과 Polyfill

브라우저 기능은 사용 가능성과 비용을 함께 본다. polyfill은 호환성을 주지만 번들 비용과 전역 오염을 만들 수 있다.

브라우저 기능을 쓸지 말지는 사용 가능성만이 아니라 비용까지 함께 판단해야 한다. transpile은 새 문법을 낮은 버전의 문법으로 바꿔주는 것이고, polyfill은 아예 존재하지 않는 런타임 기능을 코드로 구현해서 채워주는 것이다. browserslist는 어떤 브라우저까지 지원할지 범위를 정해서 빌드 결과 자체를 바꾸는 설정이다. polyfill은 호환성을 주는 대신 번들 크기와 전역 오염이라는 비용을 만들기 때문에, 이 세 개념을 함께 고려해야 과도한 polyfill로 최신 브라우저 사용자에게까지 비용을 떠넘기는 실수를 피할 수 있다.

FER-06

읽히는 신호

프론트엔드 생태계 글은 사용자 코드보다 빌드 산출물과 브라우저 비용을 자주 다룬다. chunk, ESM, tree-shaking, hydration, cache가 함께 보이면 이 층의 이야기다.

프론트엔드 생태계에 관한 글은 사용자 코드보다 빌드 산출물과 브라우저 비용을 자주 다룬다. bundle analysis 신호는 어떤 코드가 왜 번들에 포함됐는지를 보여주고, runtime cost 신호는 parse, execute, hydration에 드는 비용을 보여준다. compat policy 신호는 어떤 브라우저까지 지원하고 어떤 기준으로 polyfill을 넣는지를 보여준다. chunk, ESM, tree-shaking, hydration, cache라는 단어가 함께 등장한다면 그 글은 사용자 코드가 아니라 이 빌드·런타임 층을 다루고 있는 것이다.

실무 상황 예시

아래 수치는 이해를 위한 가상 운영 수치입니다. 목적은 특정 회사 사례를 베끼는 것이 아니라, 기술 글에 자주 등장하는 상황·숫자·판단 기준을 읽는 감각을 만드는 것입니다.

대시보드 bundle analysis

SITUATION

가상 운영 수치다. 관리자 대시보드 초기 JS는 980KB이고, vendor chunk에는 chart 라이브러리 420KB가 들어 있다. 첫 화면은 표와 필터만 필요하고 차트 탭은 사용자 18%만 연다.

NUMBERS

차트 탭을 dynamic import로 분리하면 초기 JS는 560KB가 된다. 중급 Android에서 LCP는 2.9초에서 1.9초로 줄지만, 차트 탭 첫 진입에는 chunk 다운로드 450ms가 추가된다.

LESSON

code splitting은 비용을 없애는 것이 아니라 필요한 시점으로 옮긴다. 첫 화면이 중요한지, 후속 탭 전환이 중요한지 제품 흐름으로 판단해야 한다.

SSR hydration mismatch

SITUATION

SSR 페이지의 주문 시간이 서버에서는 UTC 기준, 클라이언트에서는 사용자 timezone 기준으로 렌더된다. 전체 세션의 0.7%에서 hydration mismatch 경고와 버튼 이벤트 지연이 발생한다.

NUMBERS

서버와 클라이언트가 같은 formatter와 timezone 입력을 쓰도록 바꾸고, client-only 값은 hydration 이후 렌더한다. mismatch rate는 0.7%에서 0.02%로 내려간다.

LESSON

SSR 문제는 React 문법 문제가 아니라 서버 산출물과 클라이언트 첫 렌더의 계약 문제다. 날짜, 랜덤값, 브라우저 API는 mismatch의 흔한 원인이다.

PACKET

Frontend runtime evidence packet

프론트엔드 생태계 판단은 도구 이름이 아니라 산출물 비용으로 증명한다. 번들러, 패키지 형식, hydration, polyfill 결정을 바꿨다면 초기 JS, parse/execute, LCP/INP, mismatch rate, cache hit을 같은 조건에서 비교해야 한다.

dynamic import 결정은 초기 JS 감소량과 지연된 chunk 첫 진입 비용을 함께 기록해야 통과한다. bundle size만 줄고 사용자가 자주 여는 탭이 늦어지면 반려 신호다.

패키지 교체 결정은 ESM tree-shaking 결과, sideEffects 설정, legacy browser 영향을 기록해야 통과한다. 라이브러리 이름만 바꾸고 vendor chunk diff를 보지 않으면 반려 신호다.

SSR/hydration 결정은 mismatch rate, client-only 값 목록, 서버·클라이언트 formatter 일치 여부를 기록해야 통과한다. 경고를 suppressHydrationWarning으로 덮고 원인을 남기지 않으면 반려 신호다.

polyfill 정책 결정은 browserslist, polyfill byte cost, 실제 사용자 브라우저 분포를 기록해야 통과한다. 모든 polyfill을 전역으로 넣어 최신 브라우저 사용자에게도 비용을 부과하면 반려 신호다.
