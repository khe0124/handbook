플랫폼 도구·운영 기본기 Q&A

Git, Docker, NGINX, 배포, 환경변수, 런타임 운영 도구를 재현성과 복구 기준으로 답하는 훈련 페이지입니다.

TRAINING : 30초 답변 → 90초 확장 → 꼬리질문 방어 → 증거 패킷 확인
GUIDE

훈련 방식

각 문항은 외워서 읽는 답이 아니라, 질문 의도를 파악하고 판단 기준을 말하는 훈련용입니다. 답변은 항상 결론, 메커니즘, trade-off, 실패 모드, 검증 증거 순서로 확장합니다.

answer_loop: 1_conclusion: "질문에 대한 결론을 한 문장으로 말한다" 2_mechanism: "내부 동작이나 시스템 경계를 설명한다" 3_tradeoff: "얻는 것과 잃는 것을 나눈다" 4_failure: "운영 중 깨지는 조건을 말한다" 5_evidence: "테스트, 로그, 지표, 쿼리, ADR 중 하나를 증거로 든다"
Q01

Dockerfile을 리뷰할 때 무엇을 보나요?

멀티스테이지, base image 고정, non-root user, secret 미포함, layer cache, healthcheck, runtime env 주입 방식을 봅니다. 이미지는 빌드 산출물이고 환경별 값은 runtime에 주입해야 합니다.

꼬리질문꼬리질문 답변
build-time env와 runtime env를 왜 구분하나요?build-time 값은 image layer와 artifact metadata에 남을 수 있고, runtime 값은 배포 환경에서 바뀌어야 합니다. 먼저 Dockerfile의 ARG/ENV 사용 위치와 image history를 확인하고, 실행 컨테이너의 redacted env readback으로 실제 주입 상태를 검증합니다.
latest 태그가 왜 위험한가요?latest는 같은 태그가 다른 digest를 가리킬 수 있어 장애 시 어떤 바이너리가 실행됐는지 재현하기 어렵습니다. 배포 기록에는 immutable tag와 digest를 남기고, rollback도 태그명이 아니라 이전 digest로 되돌릴 수 있어야 합니다.
컨테이너가 재시작을 반복하면 무엇을 확인하나요?exit code, restart count, 직전 로그, healthcheck 실패 원인, OOMKilled 여부, config mount 실패를 순서대로 봅니다. 재시작 정책만 완화하면 증상이 가려지므로 `docker inspect`나 orchestrator event와 앱 시작 로그를 맞춰 원인을 닫아야 합니다.
TRAINING EVIDENCE image digest, Dockerfile review, container logs, exit code, env diff
답변 기준

30초 답변은 결론과 기준을 먼저 말하고, 90초 답변은 메커니즘, trade-off, 실패 신호, 테스트 또는 운영 증거까지 확장한다. 경험이 없으면 직접 경험처럼 말하지 말고 설계 지식과 검증 계획으로 경계를 분명히 한다.

Q02

배포가 성공했는데 서비스가 깨졌다면 어떤 순서로 보나요?

배포 artifact, release id, health check, config/env, DB migration, dependency connectivity, error rate, rollback 조건을 순서대로 확인합니다. CI 성공은 런타임 성공의 충분조건이 아닙니다.

꼬리질문꼬리질문 답변
readiness와 liveness를 왜 나누나요?liveness는 프로세스를 재시작할지 판단하고 readiness는 트래픽을 받을 준비가 됐는지 판단합니다. DB 연결이나 migration 대기처럼 일시적으로 준비되지 않은 상태를 liveness 실패로 처리하면 재시작 폭주가 생기므로 probe 결과와 routing 상태를 분리해서 봅니다.
migration 실패 시 rollback이 항상 가능한가요?데이터 삭제, 컬럼 의미 변경, 외부 side effect가 있으면 단순 rollback이 불가능할 수 있습니다. 배포 전 expand-contract 단계, 백업, stop point, forward fix 스크립트를 준비하고 실패 후에는 migration table과 데이터 샘플 readback으로 실제 적용 범위를 확인합니다.
canary에서 어떤 지표를 봐야 하나요?error rate, latency percentile, saturation, business conversion, dependency error를 기존 버전과 같은 segment에서 비교합니다. 트래픽 비율만 작으면 희귀 경로가 빠질 수 있으므로 request id 샘플과 canary 대상 사용자 범위를 함께 확인합니다.
TRAINING EVIDENCE deployment log, artifact hash, health probe, migration status, canary metric

Q03

NGINX나 reverse proxy 문제를 어떻게 좁히나요?

DNS, TLS, routing, upstream health, header forwarding, timeout, body size limit, proxy buffering을 분리합니다. 502는 앱 문제일 수도 있고 upstream 연결, protocol, timeout 문제일 수도 있습니다.

꼬리질문꼬리질문 답변
X-Forwarded-For를 왜 신뢰하면 안 되나요?클라이언트가 임의로 보낼 수 있는 header라 trusted proxy 경계 밖의 값을 그대로 쓰면 audit, rate limit, allowlist가 우회될 수 있습니다. proxy에서 기존 값을 덮어쓰는지와 앱의 trusted proxy 설정을 확인하고, 테스트 요청으로 기록 IP가 기대대로 남는지 검증합니다.
idle timeout이 긴 요청에 어떤 영향을 주나요?proxy, load balancer, upstream 앱의 timeout 중 가장 짧은 값이 긴 요청을 끊을 수 있습니다. access log의 request time과 upstream response time, 앱 로그의 완료 시각을 맞춰 어느 계층이 먼저 연결을 닫았는지 확인합니다.
CDN과 origin 중 어디서 막혔는지 어떻게 구분하나요?응답 header, CDN request id, origin access log 존재 여부, cache status, 직접 origin curl 결과를 비교합니다. CDN에만 로그가 있고 origin request id가 없으면 edge 차단이나 cache 문제를 의심하고, 둘 다 있으면 upstream status와 origin 앱 로그로 이어갑니다.
TRAINING EVIDENCE access/error log, upstream status, curl -v, request id, proxy config diff

Q04

운영 도구 문서가 좋은지 어떻게 판단하나요?

명령어 목록보다 전제 조건, 대상 환경, 성공/실패 판정, 되돌리기 절차가 있어야 합니다. 위험 명령은 dry-run과 readback 확인을 포함해야 합니다.

꼬리질문꼬리질문 답변
로컬에서만 성공한 절차를 어떻게 팀 절차로 바꾸나요?새 환경에서 clean run을 해 보고 필요한 권한, 버전, env var, seed data, network 전제를 문서에 고정합니다. 성공 화면보다 health endpoint, 로그, readback 명령을 남겨 다른 사람이 같은 상태를 확인할 수 있게 해야 합니다.
환경변수 누락을 어떻게 빨리 찾나요?배포 manifest, secret/config key, process env, 앱 startup validation 순서로 봅니다. 민감값은 값 자체가 아니라 key 존재 여부와 version만 redacted dump로 확인하고, 기본값 때문에 조용히 잘못 동작하지 않게 필수 설정은 시작 시 실패시키는 편이 안전합니다.
수동 조치 후 무엇을 기록해야 하나요?대상 host나 namespace, 실행 명령, 변경 전후 diff, readback 결과, 영향 범위, rollback 명령, 코드 반영 PR을 기록합니다. 터미널 성공 출력만 남기면 운영 상태가 맞는지 알 수 없으므로 조회 결과와 로그 타임스탬프로 닫아야 합니다.

Q05

컨테이너 이미지에서 secret이 새면 어떻게 발견하나요?

이미지 layer, build arg, env dump, repository history를 확인합니다. secret은 build artifact에 들어가면 안 되고 runtime secret store나 mounted secret으로 주입해야 합니다.

꼬리질문꼬리질문 답변
ARG와 ENV는 어떻게 다른가요?ARG는 build 중 사용되고 ENV는 image와 runtime process 환경에 남을 수 있습니다. secret 후보가 있으면 Dockerfile, image history, registry scan, 실행 env readback을 함께 확인해 어느 단계에 노출됐는지 분리합니다.
이미 push된 secret은 파일만 지우면 끝인가요?아닙니다. image layer, registry cache, clone된 git history, CI log에 남았을 수 있으므로 키 폐기와 rotation을 먼저 하고 노출 범위를 감사해야 합니다. 삭제 커밋은 재노출을 줄일 뿐 이미 유출된 credential을 무효화하지 못합니다.
secret rotation은 어떤 순서로 하나요?새 secret 발급, 소비자 배포, readback으로 새 version 사용 확인, 이전 secret 폐기, 실패 로그와 접근 로그 감사 순서로 진행합니다. 한 번에 폐기하면 아직 이전 값을 쓰는 pod나 batch가 장애를 낼 수 있어 overlap 시간을 계획해야 합니다.
TRAINING EVIDENCE image history, secret scan, revoked key record, runtime injection config

Q06

컨테이너가 OOMKilled 되면 무엇을 보나요?

exit code, container memory limit, RSS, heap, direct memory, GC log, traffic spike를 봅니다. JVM이면 heap만 줄이면 direct memory나 native memory 문제를 놓칠 수 있습니다.

꼬리질문꼬리질문 답변
memory limit과 JVM heap은 어떻게 맞추나요?container limit 안에 heap, metaspace, direct memory, thread stack, native allocation 여유를 남겨야 합니다. `MaxRAMPercentage`와 실제 RSS 그래프, GC log, OOM event를 같이 보고 heap만 limit에 가깝게 잡지 않았는지 확인합니다.
OOM과 GC thrashing은 어떻게 다르나요?OOM은 할당 실패나 cgroup kill로 프로세스가 종료되는 상태이고, GC thrashing은 살아 있지만 GC 시간이 늘어 처리량과 latency가 무너지는 상태입니다. exit code와 restart event, GC pause 비율, allocation rate를 같이 봐야 합니다.
재시작하면 해결된 것처럼 보이는 이유는?heap과 connection, cache가 초기화되어 일시적으로 메모리 압박이 사라지기 때문입니다. 재시작 전후 RSS, heap dump, traffic pattern, leak suspect를 남기지 않으면 원인이 반복되어 같은 시간대에 다시 장애가 납니다.
TRAINING EVIDENCE container exit code, memory graph, GC log, heap/native memory setting

Q07

환경변수 문제를 어떻게 빠르게 좁히나요?

빌드 시점 변수와 실행 시점 변수를 구분하고, 배포 대상 namespace, secret key, config map, process env readback을 확인합니다. 민감값은 redacted dump로 존재 여부만 확인합니다.

꼬리질문꼬리질문 답변
frontend env와 backend env는 왜 다르게 다루나요?frontend 값은 대개 build artifact에 박히고 사용자에게 노출될 수 있지만 backend 값은 runtime에서 secret store나 env로 주입됩니다. 변경 후에는 bundle 내용, deployment env, 앱 config endpoint의 redacted 출력으로 어느 값이 실제 사용되는지 확인합니다.
기본값을 코드에 넣으면 어떤 위험이 있나요?필수 설정 누락이 조용히 잘못된 endpoint, dev credential, 낮은 timeout으로 이어질 수 있습니다. 운영 필수값은 startup validation으로 실패시키고, 기본값을 둔다면 local 전용인지와 override readback 방법을 문서화해야 합니다.
환경별 설정 drift는 어떻게 막나요?manifest와 secret version을 Git이나 IaC에서 관리하고 배포 후 runtime readback, checksum, drift report로 실제 상태를 비교합니다. 운영에서 직접 바꾼 값은 ticket과 PR로 회수하지 않으면 다음 배포에서 사라지거나 더 위험한 값으로 덮입니다.
