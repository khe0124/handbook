FLOW

이 문서를 관통하는 흐름

이 문서는 보안 경계를 규칙 목록이 아니라, 요청이 인터넷에서 들어와 App과 데이터에 닿기까지 거치는 세 겹의 경계 — 공개면(edge), 신뢰 경계(WAF·방화벽), 권한 경계(IAM·secret) — 로 겹쳐 읽게 만들려고 쓰였다. 세 경계는 각자 다른 계층에서 다른 증거를 요구하고, 그 증거를 뒤섞으면 장애 때 원인 후보를 제대로 배제하지 못한다. 아래 절들은 이 세 경계를 개념에서 증거로, 증거에서 실행 가능한 플레이북과 시나리오로 좁혀가는 순서로 이어진다.

맨 앞 INDEX 절은 본문이 아니라 이 문서를 어떻게 읽을지 정하는 계약이다. 이 문서는 개념 요약이 아니라 운영 판단 연습용 플레이북이며, 각 항목을 "무엇을 아는가"가 아니라 "장애 때 어떤 증거를 보고 어떤 가설을 버리는가" 기준으로 읽으라고 명시한다. 핵심 개념, 주제별 운영 증거, 실무 플레이북, 용어사전, incident packet, 주제별 답변 구조라는 여섯 축이 이후 절 구성을 그대로 예고한다.

본문은 SEC-00 공개면 줄이기에서 시작한다. 공개 표면을 DNS record, CDN, WAF, Load Balancer 정도로 제한하고 App·DB·cache·queue는 private subnet 뒤에 두며 관리 접근은 VPN·bastion·SSO·short-lived credential로만 열라는 것이 첫 원칙이다. SEC-01 WAF와 방화벽은 그 edge 안쪽에서 계층별 책임을 나눈다 — WAF는 L7의 악성 패턴을, security group은 stateful L4 허용 목록을, NACL은 stateless subnet 경계를 맡는다. 차단 로그가 남지 않는 규칙은 나중에 원인 분석을 막으므로, 정상 요청이 WAF rule에 차단됐을 땐 rollback과 exception expiry를 구분해 기록한다. SEC-02 IAM과 secret은 경계를 물리적 네트워크에서 권한과 비밀로 옮긴다. 사람·서비스·pipeline identity를 분리하고 secret이 repo·image·log에 남지 않게 하며, 장기 key와 wildcard 권한은 예외 승인과 만료 조건이 있어야 통과다. SEC-03 검증 질문은 이 세 층을 위협 모델링 언어로 다시 묶어 public ingress·인증 우회·권한 상승·secret 노출·egress 악용·로그 공백이라는 여섯 축으로 "공격 경로는 어디이고 침해 시 무엇으로 추적하는가"를 답하게 만든다.

CHECK 실무 체크리스트는 이 네 절의 판단을 변경 전에 미리 드러내는 검토표로 압축한다. public ingress를 DNS·CDN/WAF·Load Balancer로 제한했는지, IAM이 사람·workload·pipeline 권한을 분리했는지, secret이 노출 경로에 남지 않는지, 위협 모델링으로 인증 우회·권한 상승·egress 악용을 점검했는지를 설계·변경·복구 세 단계의 필수 산출물과 차단 기준으로 다시 확인한다. 설계 단계는 목적·영향 범위·비목표·owner가, 변경 단계는 diff·승인 기록·검증 명령이, 복구 단계는 rollback 또는 forward fix와 담당자·예상 시간이 빠지면 그대로 통과시키지 않는다.

PLAYBOOK 실무 플레이북은 SECURITY BOUNDARY OPERATIONS PLAYBOOK이라는 하나의 serial-card로 이 판단을 실행 순서로 굳힌다 — symptom → scope → recent change → evidence → mitigation → verification → runbook diff. Public ingress, Identity/Secret, Auditability 세 운영 표면마다 볼 증거와 판단 기준을 표로 못박고, 공개면 점검(DNS record·LB listener·WAF rule·security group ingress 목록화), 권한 점검(IAM policy diff·last-used·access review·break-glass ticket), 비밀 점검(secret manager version·rotation date·deploy consumer·log redaction) 각각에 실제로 무엇을 확인하고 어떻게 해석할지까지 이어 붙인다.

PRACTICE 출력 판독 훈련은 그 플레이북을 손에 익히는 실습이다. PRACTICE LAB 01 · IAM 권한 확대 diff 판독은 배포 pipeline role의 권한이 s3:GetObject 하나에서 s3:*·kms:Decrypt *로 확대되고 exceptionExpiry가 비어 있는 policy diff를 그대로 보여준 뒤, 정상 출력과 비정상 출력을 나란히 대조하고, 즉시 완화(wildcard 권한을 되돌리고 필요한 read 권한만 한정)와 영구 수정(diff review gate, last-used review, exception expiry alert)을 분리해 훈련시킨다.

TERM 용어사전은 public ingress, WAF, security group, IAM principal, secret rotation 다섯 용어를 정의·운영 증거·자주 하는 오해·관련 항목으로 정리해 "WAF가 있으면 내부 앱 노출도 괜찮다" 같은 흔한 착각을 미리 차단한다. CASE 장애/운영 시나리오는 외부 공개 API 신규 오픈이라는 단일 사례로 앞의 개념을 다시 묶는다. WAF rule과 rate limit을 먼저 적용하고 App은 private subnet에 두며 배포 권한과 운영 조회 권한을 분리한 뒤, Triage frame — 증상 → 영향 범위 → 최근 변경 → Public ingress 증거 → 완화책 → 복구 검증 → 재발 방지 — 을 처음 10분·다음 30분·종료 조건으로 나누고, 증상·완화·사후 세 칸으로 된 incident packet에 기록한다.

RISK 자주 틀리는 판단은 이 흐름에서 가장 자주 무너지는 지점 네 개를 짚는다 — security group을 0.0.0.0/0으로 열고 WAF만 믿는 것, admin 권한을 장기 access key로 운영하는 것, secret rotation을 배포 절차와 연결하지 않는 것, 차단 로그가 없어 false positive와 공격을 구분하지 못하는 것. EVIDENCE 검증 기준·증거 패킷은 이 리스크들을 마지막으로 통제 가능한 형태로 닫는다. 감사 기준일과 provider·region·계정 전제, 노출·권한·secret·audit 명령 출력 예시, least privilege diff와 rollback rule, containment owner까지 갖춰야 허용 규칙 하나를 "증명됐다"고 부를 수 있다.

그러니 이 문서는 위에서 아래로 한 번 읽고 덮는 자료가 아니라, 장애가 나거나 새 서비스를 열 때마다 다시 펼쳐 보는 참조 자료로 쓰여야 한다. 공개면을 줄이는 설계 단계에는 SEC-00과 CHECK를, 장애가 났을 때는 PLAYBOOK과 CASE를, 명령 출력이 애매할 때는 PRACTICE와 TERM을, 통제를 증명해야 할 때는 EVIDENCE를 다시 펼치는 순환 구조다. 결국 이 문서가 반복해서 묻는 질문은 세 가지로 수렴한다 — 이 서비스의 public ingress는 어디인가, 이 권한과 secret은 누가 언제까지 왜 가지고 있는가, 침해가 의심될 때 어떤 로그로 행위를 추적할 수 있는가.

SEC-00

공개면 줄이기

인터넷에 공개되는 것은 DNS record, CDN, WAF, Load Balancer 정도로 제한한다. App, DB, cache, queue는 private subnet에 두고 관리 접근은 VPN, bastion, SSO, short-lived credential로 제한한다.

운영 질문확인할 증거판단 기준
인터넷 공개면이 의도한 edge 계층으로 제한되어 있는가?public DNS record, CDN/WAF distribution, LB listener, security group ingress, admin access pathApp/DB/cache/queue가 public endpoint 없이 private 경계 안에 있어야 한다.
공개면 줄이기를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?external scan, DNS inventory, LB listener list, SG ingress, bastion/VPN access log외부에서 접근 가능한 표면을 실제로 열거해야 한다.
공개면 줄이기 장애에서 임시 완화와 영구 수정은 어떻게 나누는가?관리 포트 또는 내부 앱이 인터넷에 노출됨public ingress를 닫고 edge/WAF/LB 경로로만 접근하게 복구한다.
SEC-01

WAF와 방화벽

WAF는 L7의 악성 요청 패턴을 줄이고, security group은 stateful L4 허용 목록을 만든다. NACL은 stateless subnet 경계라 응답 포트까지 고려해야 한다. 차단 로그가 남지 않는 규칙은 운영 중 원인 분석을 어렵게 만든다.

운영 질문확인할 증거판단 기준
WAF, security group, NACL이 각 계층 책임에 맞게 동작하는가?WAF rule hit, SG stateful rule, NACL stateless rule, firewall deny log, false positive rateL7 차단과 L4 허용 목록, subnet stateless 경계를 혼동하지 않아야 한다.
WAF와 방화벽을 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?WAF log, SG rule diff, NACL ephemeral port, firewall decision log차단 로그 없이 규칙만 있으면 운영 중 원인 분석이 어렵다.
WAF와 방화벽 장애에서 임시 완화와 영구 수정은 어떻게 나누는가?정상 고객 요청이 WAF rule에 차단됨rule rollback, allow exception expiry, false positive 재튜닝을 기록한다.
SEC-02

IAM과 secret

IAM은 사람, 서비스, pipeline, workload identity를 분리한다. secret은 repo, image, log, frontend bundle에 들어가면 안 된다. rotation 절차에는 revoke, 재발급, 배포, 영향 범위 확인이 포함된다.

운영 질문확인할 증거판단 기준
IAM과 secret이 사람·서비스·pipeline 경계별로 분리되어 있는가?principal, role assumption, policy diff, secret version, rotation date, last-used장기 key와 wildcard 권한은 예외 승인과 만료 조건이 필요하다.
IAM과 secret를 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?IAM access analyzer, policy diff, secret manager version, audit log, deploy consumer listsecret이 repo/image/log/frontend bundle에 남지 않아야 한다.
IAM과 secret 장애에서 임시 완화와 영구 수정은 어떻게 나누는가?secret rotation 후 일부 pod 인증 실패revoke, 재발급, consumer 재시작, 영향 범위 확인을 순서대로 수행한다.
SEC-03

검증 질문

위협 모델링은 public ingress, 인증 우회, 권한 상승, secret 노출, egress 악용, 로그 공백을 먼저 본다. 이 서비스의 public ingress는 어디인가? egress는 어떤 도메인과 포트까지 허용되는가? 관리자 권한은 누가 승인하고 얼마나 유지되는가? 침해 시 어떤 로그로 행위를 추적할 수 있는가?

운영 질문확인할 증거판단 기준
위협 모델이 public ingress, auth, privilege, egress, log gap을 다루는가?public ingress list, auth boundary, admin action log, egress allowlist, audit coverage공격 경로와 탐지 증거가 함께 설명되어야 한다.
검증 질문을 원인 후보에서 배제하려면 어떤 확인 결과가 필요한가?threat model review, access review, WAF/auth/admin/egress log sample통제는 차단뿐 아니라 조사 가능한 로그로 증명되어야 한다.
검증 질문 장애에서 임시 완화와 영구 수정은 어떻게 나누는가?비정상 admin export 후 행위 추적 로그 부족권한 축소, egress 차단, audit alert, runbook diff를 남긴다.
CHECK

실무 체크리스트

보안 경계 체크리스트는 공개면 줄이기, WAF와 방화벽, IAM과 secret, 검증 질문의 변경 위험을 사전에 드러내기 위한 검토표다. 각 항목은 리뷰, 배포 승인, 운영 인수에서 같은 증거로 다시 확인되어야 한다.

  • public ingress를 DNS, CDN/WAF, Load Balancer로 제한한다.
  • IAM은 사람, workload, pipeline 권한을 분리한다.
  • secret은 repo, image, log, frontend bundle에 남지 않게 한다.
  • 위협 모델링으로 인증 우회, 권한 상승, egress 악용을 점검한다.
작업 단계필수 산출물차단 기준
설계목적, 영향 범위, 비목표, owner영향 범위가 사용자·시스템·비용 기준으로 설명되지 않음
변경diff, 승인 기록, 검증 명령production 변경과 staging 검증의 차이가 설명되지 않음
복구rollback 또는 forward fix, 담당자, 예상 시간실패 시 되돌릴 수 없는데 사전 승인과 공지가 없음

PRACTICE

출력 판독 훈련

보안 경계는 개념을 아는 것보다 실제 출력에서 정상과 비정상을 구분하는 훈련이 중요하다. 아래 lab은 명령, 출력, 판단, 완화, 영구 수정을 한 번에 연결한다.

PRACTICE LAB 01 · IAM 권한 확대 diff 판독

배포 pipeline role에 임시 권한을 추가한 뒤 보안 리뷰가 들어왔다.

Command / Query목적
iam policy diff
- s3:GetObject arn:aws:s3:::app-config/*
+ s3:*
+ kms:Decrypt *
lastUsed=never
exceptionExpiry=missing
권한 확대가 최소 권한 원칙과 예외 만료 기준을 만족하는지 확인한다.

CASE

장애/운영 시나리오

외부 공개 API를 신규 오픈한다. WAF rule과 rate limit을 먼저 적용하고, Load Balancer 뒤의 App은 private subnet에 둔다. IAM은 배포 권한과 운영 조회 권한을 분리하고, 인증 실패·차단·권한 거부 로그가 관측 시스템으로 들어오는지 확인한다.

Triage frame

보안 경계 장애는 증상 → 영향 범위 → 최근 변경 → Public ingress 증거 → 완화책 → 복구 검증 → 재발 방지 순서로 기록한다. 이 흐름이 있어야 담당자가 바뀌어도 같은 결론에 도달한다.

이 triage frame을 시간 구간별 행동으로 풀면 다음과 같다.

처음 10분다음 30분종료 조건
DNS, CDN/WAF, LB listener, allowed path, rate limit 기준으로 영향 범위를 고정한다.DNS record, LB listener, WAF rule, security group ingress 목록화 항목에서 증거를 모아 완화책을 실행한다.보안 조치가 운영 절차로 남아야 한다.

RISK

자주 틀리는 판단

보안 경계에서 자주 틀리는 판단은 공개면 줄이기와 검증 질문의 책임 경계를 흐리는 데서 시작된다. 아래 신호가 보이면 설계, runbook, 답변 구조를 다시 점검한다.

  • 보안 그룹을 0.0.0.0/0으로 열고 WAF만 믿는다.
  • admin 권한을 장기 access key로 운영한다.
  • secret rotation을 배포 절차와 연결하지 않는다.
  • 차단 로그가 없어 false positive와 공격을 구분하지 못한다.
EVIDENCE

검증 기준·증거 패킷

보안 경계는 허용 규칙의 의도와 실제 노출면을 함께 증명해야 한다. 공개 ingress, IAM, secret, egress는 기준일과 승인 범위가 없으면 통과로 보지 않는다.
