세 겹의 경계

보안 경계는 규칙 목록이 아니라 요청이 인터넷에서 들어와 App과 데이터에 닿기까지 통과하는 세 겹의 관문이다. 첫 번째는 무엇을 아예 공개할지 정하는 공개면 — DNS record, CDN, WAF, Load Balancer 정도만 열고 App, DB, cache, queue는 private subnet 뒤에 두는 것. 두 번째는 그 edge 안쪽에서 무엇을 걸러낼지 정하는 신뢰 경계다. WAF는 L7의 악성 패턴을 줄이고, security group은 stateful L4 허용 목록이고, NACL은 stateless subnet 경계인데, 이 셋을 섞어서 생각하면 정상 요청이 차단됐을 때도 원인을 못 찾는다. 세 번째는 누가 무엇에 접근할 수 있는지 정하는 권한 경계다. 사람·서비스·pipeline identity를 분리하고, secret이 repo나 image, log에 남지 않게 하고, 장기 key와 wildcard 권한은 예외 승인과 만료 조건이 있어야만 통과시킨다.

이 세 겹을 따로 보는 이유는 각자 요구하는 증거가 다르기 때문이다. 공개면 문제는 external scan과 DNS inventory로, 신뢰 경계 문제는 WAF log와 rule diff로, 권한 문제는 IAM policy diff와 secret rotation 기록으로 확인해야 한다. 증거를 뒤섞으면 장애 때 원인 후보를 제대로 배제하지 못한다. SECURITY BOUNDARY OPERATIONS PLAYBOOK은 이 세 표면을 symptom → scope → recent change → evidence 순서로 연결하고, IAM 권한 확대 diff 판독 실습은 배포 pipeline role이 s3:GetObject 하나에서 s3:*로 확대되고 만료 조건까지 비어 있는 실제 policy diff를 놓고 무엇을 되돌려야 하는지 훈련시킨다.

외부 공개 API를 새로 열 때도 순서는 같다. WAF rule과 rate limit을 먼저 걸고, App은 private subnet에 두고, 배포 권한과 운영 조회 권한을 나눈 다음, 침해가 의심될 때 추적할 로그가 실제로 남는지 확인한다. 이 마지막 확인을 건너뛰는 게 가장 흔한 실패다 — security group을 0.0.0.0/0으로 열고 WAF만 믿거나, admin 권한을 장기 access key로 운영하거나, 차단 로그가 없어서 false positive와 진짜 공격을 구분 못 하는 경우다.

결국 이 문서가 매번 되묻는 건 세 질문이다. 이 서비스의 public ingress는 어디인가, 이 권한과 secret은 누가 언제까지 왜 가지고 있는가, 침해가 의심될 때 어떤 로그로 추적하는가.

SEC-00

공개면 줄이기

인터넷에 공개되는 것은 DNS record, CDN, WAF, Load Balancer 정도로 제한한다. App, DB, cache, queue는 private subnet에 두고 관리 접근은 VPN, bastion, SSO, short-lived credential로 제한한다.

설계 문서에는 항상 "App, DB, cache는 private subnet에 있다"고 깔끔하게 적혀 있다. 문제는 그 문서가 실제 인프라와 항상 일치하지는 않는다는 것이다. 언젠가 정기 보안 점검에서 external scan을 돌렸는데, 내부용으로만 쓰던 관리 포트 하나가 떡하니 인터넷에 열려 있는 걸 발견한 적이 있다. 누군가 디버깅하다가 임시로 열어놓고 닫는 걸 깜빡한 것이었다. 설계 문서만 믿고 "private로 뒀으니 안전하다"고 넘어갔다면 몇 달을 그 상태로 방치했을 것이다.

그래서 이제는 문서를 믿지 않고 매번 직접 열거한다. DNS record, LB listener, security group ingress를 다 뽑아서 실제로 인터넷에서 접근 가능한 표면이 뭔지 눈으로 확인한다. 관리 포트나 내부 앱이 노출된 걸 발견하면 즉시 그 경로부터 닫는다. 하지만 닫는 걸로 끝내면 안 된다. 애초에 그 경로가 왜 열려 있었는지 — 임시 디버깅이었는지, 배포 스크립트 실수였는지 — 를 확인해야, 다음 배포에서 똑같은 구멍이 다시 뚫리지 않는다.

SEC-01

WAF와 방화벽

WAF는 L7의 악성 요청 패턴을 줄이고, security group은 stateful L4 허용 목록을 만든다. NACL은 stateless subnet 경계라 응답 포트까지 고려해야 한다. 차단 로그가 남지 않는 규칙은 운영 중 원인 분석을 어렵게 만든다.

WAF, security group, NACL을 뭉뚱그려 "방화벽"이라고 부르는 사람이 많은데, 이 셋은 보는 층위가 완전히 다르다. WAF는 요청 내용 자체를 들여다보는 L7 통제고, SG는 stateful L4 허용 목록이라 나간 요청의 응답은 자동으로 허용되고, NACL은 stateless subnet 경계라서 응답이 쓸 포트까지 따로 열어줘야 한다. 이 차이를 모르고 있으면, 정상 요청이 갑자기 차단됐을 때 셋 중 어디를 손봐야 할지 감을 못 잡는다.

실제로 정상 고객 요청이 WAF rule에 걸려 차단되는 일이 자주 있다. 신규 배포 직후 특정 브라우저를 쓰는 고객들만 요청이 막히기 시작한 적이 있는데, 알고 보니 새로 추가한 WAF rule이 그 브라우저의 User-Agent 패턴을 봇으로 오탐하고 있었다. 이럴 때는 일단 rule rollback으로 막힌 걸 풀어주고, 그 사이 만들어둔 allow exception에는 만료 조건을 반드시 같이 적어둔다. 여기서 rollback만 하고 false positive 재튜닝을 미루면, 다음 배포 때 누군가 같은 rule을 무심코 다시 켰다가 똑같은 고객들이 또 막힌다. 그리고 이 모든 판단은 차단 로그가 남아 있어야만 가능하다는 걸 잊으면 안 된다. 규칙은 있는데 로그가 안 남으면, 애초에 뭐가 왜 막혔는지 사후에 재구성할 방법이 없다.

SEC-02

IAM과 secret

IAM은 사람, 서비스, pipeline, workload identity를 분리한다. secret은 repo, image, log, frontend bundle에 들어가면 안 된다. rotation 절차에는 revoke, 재발급, 배포, 영향 범위 확인이 포함된다.

IAM access analyzer를 돌려보면 꼭 하나씩은 나온다. 몇 년 전에 만들어놓고 아무도 기억 못 하는 wildcard 권한, 만료 조건 없이 방치된 장기 key. 이런 권한은 그 존재 자체가 이미 위험 신호다. 예외 승인도 없고 만료 조건도 없다면, 이유를 따질 것도 없이 그 자리에서 손봐야 한다. principal이 사람인지 서비스인지 pipeline인지, role assumption 기록은 남아 있는지를 하나씩 대조해보면 이런 유령 권한이 생각보다 많이 나온다.

secret도 마찬가지다. repo, image, log, frontend bundle 어디에라도 secret이 박혀 있으면 그 자체로 유출이다. 넷 중 하나라도 확인을 빼먹으면 그게 바로 구멍이 된다. secret rotation을 돌린 직후에 일부 pod에서 인증 실패가 터지는 걸 겪어본 사람은 알겠지만, 순서를 지키지 않으면 꼭 사고가 난다. revoke하고, 재발급하고, consumer를 재시작하고, 영향 범위를 확인하는 순서를 지켜야 한다. 재발급만 하고 재시작을 건너뛰면 예전 secret을 여전히 물고 있는 pod가 남아서, 며칠 뒤에 뜬금없이 같은 인증 실패가 재발한다.

SEC-03

검증 질문

위협 모델링은 public ingress, 인증 우회, 권한 상승, secret 노출, egress 악용, 로그 공백을 먼저 본다. 이 서비스의 public ingress는 어디인가? egress는 어떤 도메인과 포트까지 허용되는가? 관리자 권한은 누가 승인하고 얼마나 유지되는가? 침해 시 어떤 로그로 행위를 추적할 수 있는가?

위협 모델 문서를 리뷰하다 보면 "public ingress는 WAF로 막혀 있음", "권한 상승은 IAM으로 방지됨"처럼 공격 경로만 나열하고 끝난 경우를 자주 본다. 그런데 "막혀 있다"는 서술만으로는 부족하다. 그 경로에서 실제로 뭔가 시도됐을 때 그걸 탐지할 증거가 있는지까지 설명돼야 위협 모델이 완성된 것이다. 여기서 제일 흔한 함정이 "차단했으니 안전하다"는 결론이다. 통제는 막았다는 사실이 아니라, 나중에 무슨 일이 있었는지 로그로 재구성할 수 있을 때만 완결된다.

실제로 이런 일이 있었다. 관리자 계정에서 대량 admin export가 발생했다는 알림이 왔는데, 정작 그 계정이 그 시점에 뭘 조회했는지 추적할 로그가 거의 남아 있지 않았다. 권한 자체는 정상적으로 부여된 것이었기 때문에 "권한 상승은 없었다"고 보고할 수는 있었지만, 그 export가 정말 필요한 업무였는지는 끝내 확인하지 못했다. 이 사고 이후로 권한 축소, egress 차단, audit alert, runbook diff를 순서대로 남기는 절차를 만들었다. 그리고 이때 가장 중요하게 기록해야 했던 건 사실 "무슨 일이 있었는가"가 아니라 "왜 우리는 그걸 몰랐는가" — 로그 공백 자체를 원인으로 못박아야, 다음번에는 같은 맹점에서 같은 사고가 반복되지 않는다.

CHECK

실무 체크리스트

보안 경계 체크리스트는 공개면 줄이기, WAF와 방화벽, IAM과 secret, 검증 질문의 변경 위험을 사전에 드러내기 위한 검토표다. 각 항목은 리뷰, 배포 승인, 운영 인수에서 같은 증거로 다시 확인되어야 한다.

  • public ingress를 DNS, CDN/WAF, Load Balancer로 제한한다.
  • IAM은 사람, workload, pipeline 권한을 분리한다.
  • secret은 repo, image, log, frontend bundle에 남지 않게 한다.
  • 위협 모델링으로 인증 우회, 권한 상승, egress 악용을 점검한다.

이 체크리스트의 세 관문은 보안 경계 변경에서도 똑같이 적용된다. 설계 단계에서는 목적, 영향 범위, 비목표, owner가 산출물로 남아 있어야 한다. 영향 범위가 사용자·시스템·비용 기준으로 설명되지 않는다면, 이 단계에서 진행을 막아야 한다.

변경 단계에서는 diff, 승인 기록, 검증 명령이 함께 있어야 한다. IAM policy나 WAF rule처럼 눈에 잘 안 띄는 조건이 다를 수 있으니, production 변경과 staging 검증의 차이가 설명되지 않으면 배포해서는 안 된다.

복구 단계에서는 rollback 또는 forward fix, 담당자, 예상 시간이 미리 정해져 있어야 한다. 실패 시 되돌릴 수 없는데 사전 승인과 공지가 없다면 배포를 보류해야 한다.

실무 플레이북

보안 경계 플레이북은 SECURITY BOUNDARY OPERATIONS PLAYBOOK 기준으로 증상, 범위, 최근 변경, 계층별 증거를 연결한다. 목표는 명령어 암기가 아니라 어떤 가설을 버리고 어떤 완화책을 실행할지 결정하는 것이다.

보안 경계 장애를 다룰 때도 "어디가 뚫렸는가"라는 하나의 질문을 세 층위로 나눠서 본다. Public ingress 표면은 "노출되지 말아야 할 것이 노출됐는가"를 DNS, CDN/WAF, LB listener, allowed path, rate limit으로 확인한다. 공개면은 의도한 edge 계층으로만 제한돼야 한다. Identity/Secret 표면은 "노출된 적 없어도 권한 자체가 새어나갈 수 있는가"를 IAM principal, role assumption, secret location, rotation record로 확인한다. 장기 key와 wildcard 권한은 예외로만 관리하는 게 원칙이다. Auditability 표면은 "무슨 일이 있었는지 나중에 재구성할 수 있는가"를 WAF log, auth failure, admin action, egress log, exception expiry로 확인한다. 앞의 두 표면이 아무리 견고해도, 이 세 번째 표면이 비어 있으면 침해가 나도 무엇이 뚫렸는지 알 방법이 없다.

이 세 표면을 실제로 조사하는 순서도 있다. 공개면 점검 단계에서는 DNS record, LB listener, WAF rule, security group ingress를 목록화해서 인터넷에서 접근 가능한 표면을 실제로 열거한다. 권한 점검 단계에서는 IAM policy diff, last-used, access review, break-glass ticket을 보고 필요 권한과 실제 사용된 권한의 차이를 확인한다. 비밀 점검 단계에서는 secret manager version, rotation date, deploy consumer, log redaction을 봐서 secret이 repo/image/log/frontend bundle 어디에도 남지 않았는지 확인한다.

PRACTICE

출력 판독 훈련

보안 경계는 개념을 아는 것보다 실제 출력에서 정상과 비정상을 구분하는 훈련이 중요하다. 아래 lab은 명령, 출력, 판단, 완화, 영구 수정을 한 번에 연결한다.

PRACTICE LAB 01 · IAM 권한 확대 diff 판독

배포 pipeline role에 임시 권한을 추가한 뒤 보안 리뷰가 들어왔다.

권한 확대가 최소 권한 원칙과 예외 만료 기준을 만족하는지 확인하려면 policy diff를 본다.

iam policy diff
- s3:GetObject arn:aws:s3:::app-config/*
+ s3:*
+ kms:Decrypt *
lastUsed=never
exceptionExpiry=missing

정상 출력, 즉 정상적인 경우라면 권한이 배포 범위 안으로 한정돼 있고 만료일도 있다.

Action: s3:GetObject
Resource: arn:aws:s3:::app-config/prod/*
Condition: aws:PrincipalArn pipeline-role
exceptionExpiry=2026-07-05

비정상 출력, 즉 비정상적인 경우에는 권한이 wildcard로 확대돼 있고 만료 조건도 없다.

Action: s3:*
Resource: *
Action: kms:Decrypt
Resource: *
exceptionExpiry=missing

pipeline 권한이 원래의 배포 범위를 넘어섰고 만료 없는 예외라 침해가 발생했을 때 반경이 훨씬 커진다. 즉시 완화는 wildcard 권한을 곧바로 되돌리고 필요한 read 권한만 한정하는 것이다. 영구 수정은 IAM diff review gate, last-used review, exception expiry alert를 추가하는 것이다. wildcard action/resource가 0이 되고 break-glass ticket에 만료일이 존재하며 audit log에서 사용 권한이 확인되면 이 조치가 끝난 것이다.

TERM

용어사전

보안 경계에서 반복적으로 등장하는 운영 용어를 정의, 증거, 오해, 관련 항목 기준으로 정리한다. 장애 중에는 용어 자체보다 해당 용어가 어떤 로그, 지표, 설정, 책임 경계와 연결되는지를 확인한다.

public ingress
인터넷에서 접근 가능한 진입 표면이다. public DNS, CDN/WAF distribution, LB listener로 확인한다. WAF만 세워두면 내부 앱을 그대로 노출해도 괜찮다고 여기는 팀이 많은데, WAF는 들어오는 요청의 패턴을 걸러낼 뿐이지 애초에 노출되면 안 되는 표면을 대신 가려주는 장치가 아니다.
WAF
L7에서 요청 패턴을 보고 악성이거나 비정상적인 요청을 줄이는 통제다. WAF rule hit, false positive rate, deny log로 확인한다. 흔히 네트워크 방화벽의 상위 버전 정도로 생각하는데, WAF는 애플리케이션 계층의 요청 내용을 읽는 것이라 SG나 NACL과는 애초에 보는 층위가 다르다.
security group
stateful하게 동작하는 L4 허용 목록이다. SG inbound/outbound diff, source, port로 확인한다. NACL과 똑같이 동작할 거라 넘겨짚기 쉽지만, SG는 나간 요청의 응답을 자동으로 허용해주는 반면 NACL은 stateless라서 그 응답이 쓸 포트를 따로 열어줘야 한다.
IAM principal
권한을 부여받는 사람, 서비스, pipeline, workload identity를 통칭한다. principal, role assumption, last-used, policy diff로 확인한다. admin key 하나로 다 같이 운영하면 편하긴 하다. 다만 그렇게 하면 누가 언제 무엇을 했는지 사후에 구분할 방법이 없어져서, 정작 침해가 났을 때 아무것도 추적할 수 없다.
secret rotation
비밀값을 revoke하고 재발급하고 배포한 뒤 영향까지 확인하는 절차 전체를 말한다. secret version, rotation date, consumer list로 확인한다. 새 secret을 만들어서 배포하면 rotation이 끝났다고 생각하기 쉬운데, 그걸 여전히 참조하고 있던 이전 consumer가 재시작되지 않으면 며칠 뒤에 뜬금없이 인증 실패가 터진다.
CASE

장애/운영 시나리오

외부 공개 API를 신규 오픈한다. WAF rule과 rate limit을 먼저 적용하고, Load Balancer 뒤의 App은 private subnet에 둔다. IAM은 배포 권한과 운영 조회 권한을 분리하고, 인증 실패·차단·권한 거부 로그가 관측 시스템으로 들어오는지 확인한다.

Triage frame

보안 경계 장애는 증상 → 영향 범위 → 최근 변경 → Public ingress 증거 → 완화책 → 복구 검증 → 재발 방지 순서로 기록한다. 이 흐름이 있어야 담당자가 바뀌어도 같은 결론에 도달한다.

처음 10분은 원인을 찾기보다 영향 범위부터 좁힌다. DNS, CDN/WAF, LB listener, allowed path, rate limit 기준으로 어느 표면이 관련됐는지부터 고정한다. 다음 30분은 DNS record, LB listener, WAF rule, security group ingress를 목록화한 항목에서 증거를 모아 완화책을 실행한다. 보안 조치가 이번 한 번으로 끝나지 않고 운영 절차로 남는 게 종료 조건이다.

장애가 종료된 뒤에는 세 항목을 incident packet에 남긴다. 증상은 비정상 admin export나 외부 스캔 급증이고, actor, source IP, action, resource, WAF/auth log를 하나로 묶어서 판정한다. 완화는 token revoke, WAF rule tighten, role disable, egress block 중에서 고르는데, 임시 차단은 고객 영향과 만료 조건을 항상 같이 기록해야 한다. 사후에는 least privilege diff, audit alert, rotation drill을 추가해서 이번 보안 조치가 일회성으로 끝나지 않고 운영 절차로 남게 한다.

RISK

자주 틀리는 판단

보안 경계에서 자주 틀리는 판단은 공개면 줄이기와 검증 질문의 책임 경계를 흐리는 데서 시작된다. 아래 신호가 보이면 설계, runbook, 답변 구조를 다시 점검한다.

  • 보안 그룹을 0.0.0.0/0으로 열고 WAF만 믿는다.
  • admin 권한을 장기 access key로 운영한다.
  • secret rotation을 배포 절차와 연결하지 않는다.
  • 차단 로그가 없어 false positive와 공격을 구분하지 못한다.
EVIDENCE

검증 기준·증거 패킷

보안 경계는 허용 규칙의 의도와 실제 노출면을 함께 증명해야 한다. 공개 ingress, IAM, secret, egress는 기준일과 승인 범위가 없으면 통과로 보지 않는다.

기준일은 2026-07-09 감사를 기준으로 삼고, 외부 노출이나 권한이 바뀔 때마다 재검토한다. security review ticket, exception 만료일, audit log retention 설정을 남겨서 허용 사유, 승인자, 만료일, 회수 조건이 같은 증거 패킷 안에 있는지 확인한다.

provider/region/version 전제도 명시해야 한다. AWS SG/NACL/IAM/Secrets Manager 또는 Azure NSG/Azure Firewall/Managed Identity/Key Vault, region과 tenant/account를 적어두고 rule diff, policy simulator 결과, secret rotation version, WAF/firewall rule id를 함께 남긴다. stateful인지 아닌지, identity policy인지 resource policy인지는 provider마다 다르므로 답변에서 분리해서 다뤄야 한다.

명령 출력 예시는 노출, 권한, secret, audit 증거를 각각 캡처한다. Reachability Analyzer/Network Watcher, Flow Logs, IAM policy simulation, WAF log, Key Vault/Secrets Manager rotation event를 남기면 allow와 deny가 모두 의도한 peer, action, resource, port에 맞는지 확인할 수 있다.

완료 기준은 least privilege diff, rollback rule, containment owner가 명확한 것이다. before/after policy, denied sample, break-glass 사용 로그를 근거로 삼되, 임시 예외는 만료 시각과 제거 검증 명령까지 포함해야 비로소 닫힌 것으로 본다.
