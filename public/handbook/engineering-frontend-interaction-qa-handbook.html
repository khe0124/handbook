프론트엔드 인터랙션 Q&A

포인터, 키보드, focus, undo, optimistic UI, 복잡한 조작 흐름을 상태 기계로 답하는 훈련 페이지입니다.

TRAINING : 30초 답변 → 90초 확장 → 꼬리질문 방어 → 증거 패킷 확인
GUIDE

훈련 방식

각 문항은 API 암기나 라이브러리 사용법이 아니라, 사용자 흐름, 브라우저 비용, 접근성, 성능, 보안, 운영 증거를 연결해 답하는 훈련용입니다.

frontend_answer_loop: 1_user_impact: "사용자가 겪는 변화와 실패 비용을 먼저 말한다" 2_runtime_boundary: "DOM, network, rendering, cache, browser policy 중 경계를 잡는다" 3_tradeoff: "선택 기준과 포기하는 것을 분리한다" 4_failure_mode: "race, stale data, accessibility, device variance, cache drift를 점검한다" 5_evidence: "trace, screenshot, test, metric, release log 중 하나를 증거로 든다"
Q01

좋은 인터랙션 설계의 출발점은 무엇인가요?

이벤트 핸들러가 아니라 사용자의 의도, 상태, 전이, 취소, 실패 복구를 먼저 모델링합니다. idle, armed, active, committing, failed 같은 상태가 있어야 테스트와 접근성이 붙습니다.

click handler만 구현하면 double submit, pointercancel, route change, stale response에서 상태가 꼬입니다.

꼬리질문꼬리질문 답변
상태 기계가 과한 경우는?hover 색상처럼 전이가 두세 개이고 실패나 비동기 복구가 없으면 명시적 상태 기계까지는 과합니다. 반대로 drag, wizard, optimistic mutation처럼 pointer, keyboard, network, route 전환이 함께 걸리면 idle/active/committing/failed를 전이표로 두는 편이 QA fixture를 만들기 쉽습니다.
전이를 어디에 문서화하나요?컴포넌트 근처에는 상태 이름과 이벤트를 코드 상수나 reducer로 두고, 제품 문서에는 사용자 행동별 전이표를 둡니다. 예를 들어 `pointerdown -> armed`, `Escape -> canceled`, `mutation reject -> failed`처럼 써야 keyboard test와 analytics result event가 같은 언어를 씁니다.
실패 상태는 화면에 어떻게 드러나야 하나요?실패 상태는 사용자가 다음 행동을 선택할 수 있게 보여야 합니다. optimistic 변경은 원래 값으로 되돌리거나 retry/undo를 제공하고, focus는 오류 메시지나 실패한 컨트롤로 이동하며, QA fixture에는 409, 403, timeout, stale response를 각각 넣습니다.
TRAINING EVIDENCE interaction state machine, transition table, QA scenario, accessibility acceptance
Q02

drag and drop에서 가장 위험한 부분은 무엇인가요?

pointer lifecycle, keyboard 대체 조작, drop target 계산, scroll container, 취소/rollback을 함께 설계해야 합니다.

마우스 기준으로만 만들면 touch, pen, keyboard, iframe, pointercancel에서 조작이 끊기고 접근성 검증을 통과하지 못합니다.

꼬리질문꼬리질문 답변
pointer capture는 왜 쓰나요?드래그 중 포인터가 원래 요소 밖으로 나가도 move/up 이벤트를 같은 요소에서 받기 위해 씁니다. capture를 쓰면 iframe 경계, pointercancel, lostpointercapture를 함께 처리해야 하며, 취소 시 ghost와 선택 상태를 rollback하는 fixture가 필요합니다.
드래그 중 스크롤은 어떻게 처리하나요?scroll container의 edge auto-scroll, touch에서의 page scroll 충돌, sticky header offset을 별도로 계산합니다. 드래그 좌표는 viewport가 아니라 container 기준으로 보정하고, Playwright나 pointer trace로 스크롤 중 drop target이 바뀌는 케이스를 검증합니다.
키보드 사용자는 어떻게 재정렬하나요?grab 상태를 Space나 Enter로 토글하고 Arrow로 위치를 이동한 뒤 다시 Space/Enter로 확정하게 합니다. 이동 결과는 aria-live로 짧게 알리고 focus는 이동한 item에 유지하며, 같은 state machine을 keyboard DnD test fixture로 돌립니다.
TRAINING EVIDENCE pointer trace, keyboard DnD test, drop target fixture, rollback scenario
Q03

focus management의 완료 기준은 무엇인가요?

focus는 사용자의 현재 작업 위치입니다. modal, popover, route change, validation error, async content 삽입 뒤 focus 이동과 복귀 위치를 명시합니다.

DOM이 바뀌었는데 focus가 body로 빠지면 keyboard 사용자와 screen reader 사용자가 흐름을 잃습니다.

꼬리질문꼬리질문 답변
focus trap은 언제 필요한가요?modal처럼 배경 조작을 막고 현재 결정에 머물러야 하는 UI에서 필요합니다. popover나 combobox는 trap보다 roving focus나 active descendant가 맞을 수 있으며, trap fixture는 Tab 순환, Shift+Tab, Escape, trigger 제거 케이스를 포함해야 합니다.
닫힌 뒤 focus는 어디로 돌아가나요?기본은 overlay를 연 trigger입니다. trigger가 삭제되었거나 route가 바뀌었으면 새 화면의 heading, 완료 메시지, 다음 가능한 action으로 보내고 body로 빠지지 않게 focus restoration test를 둡니다.
validation error에 focus를 옮겨야 하나요?submit 실패처럼 사용자가 즉시 수정해야 하는 오류라면 첫 오류 필드나 오류 summary로 focus를 옮깁니다. onChange 중 매번 focus를 빼앗으면 입력을 방해하므로, submit 시점과 async validation 완료 시점을 나눠 screen reader announcement를 확인합니다.
TRAINING EVIDENCE focus path test, tab order recording, screen reader smoke, modal fixture
Q04

키보드 인터랙션은 어떻게 설계하나요?

WAI-ARIA pattern을 참고해 Tab, Arrow, Enter, Space, Escape의 의미를 컴포넌트별로 고정합니다.

브라우저 기본 동작과 충돌하거나 role만 바꾸고 key handling을 빼면 조작 가능한 듯 보이지만 실제로는 접근 불가 UI가 됩니다.

꼬리질문꼬리질문 답변
Enter와 Space는 같은가요?native button에서는 둘 다 activation이지만 text input에서는 Enter가 submit이나 선택 확정이고 Space는 문자 입력입니다. custom role을 쓰면 기본 동작을 잃기 쉬우므로 keydown/keyup 시점과 중복 click 발생 여부를 keyboard fixture로 확인합니다.
Arrow navigation은 언제 쓰나요?menu, tablist, grid, combobox처럼 한 composite widget 안에서 항목을 이동할 때 씁니다. 일반 페이지 탐색은 Tab 순서에 맡기고, roving tabindex나 aria-activedescendant를 선택해 focus 표시와 screen reader announcement가 맞는지 검증합니다.
Escape는 무엇을 닫아야 하나요?가장 안쪽의 열린 modal, popover, menu, drag armed 상태부터 닫아야 합니다. Escape가 route navigation이나 입력 취소와 충돌하는 경우 우선순위를 문서화하고, 닫은 뒤 focus가 trigger나 편집 중 필드로 돌아가는지 확인합니다.
TRAINING EVIDENCE keyboard spec, role/aria audit, Playwright keyboard test, screen reader note
Q05

optimistic UI는 언제 도입하나요?

성공 확률이 높고 실패 복구가 명확하며 중복/순서 문제를 제어할 수 있을 때 사용합니다.

실패 시 rollback, 서버 최종 상태 reconcile, 중복 mutation 처리 없이 쓰면 화면과 서버가 어긋납니다.

꼬리질문꼬리질문 답변
좋아요 버튼과 결제 버튼은 왜 다르나요?좋아요는 실패해도 원래 상태로 rollback하거나 retry하면 피해가 작지만, 결제는 외부 side effect와 금전 상태가 걸려 UI만 되돌리면 안 됩니다. 결제는 pending state, idempotency key, 서버 최종 결과 조회, 중복 제출 방지를 우선합니다.
실패했을 때 toast만 띄우면 되나요?아니요. optimistic 변경 자체를 rollback하거나 실패 상태로 고정해 사용자가 현재 서버 상태를 알 수 있어야 합니다. toast는 보조 알림이고, 버튼 상태, inline error, retry/undo action, analytics error result가 같이 남아야 합니다.
동시 optimistic update는 어떻게 합치나요?mutation ledger에 client id, 대상 entity, 순서, inverse patch를 남기고 서버 응답이 도착할 때 최신 pending 목록과 재계산합니다. 같은 row를 빠르게 수정하는 fixture와 stale response fixture로 늦은 응답이 최신 UI를 덮지 않는지 확인합니다.
TRAINING EVIDENCE mutation ledger, rollback fixture, server reconcile log, duplicate click test
Q06

undo 기능은 어떻게 설계하나요?

되돌릴 수 있는 command와 되돌릴 수 없는 side effect를 분리하고, undo window, server commit timing, audit log를 정합니다.

이미 외부 알림이나 결제가 나간 작업을 단순 UI undo로 처리하면 사용자는 취소됐다고 믿지만 시스템은 진행됩니다.

꼬리질문꼬리질문 답변
undo와 cancel은 무엇이 다른가요?cancel은 작업이 commit되기 전에 armed, editing, pending 상태를 중단하는 것이고 undo는 이미 적용된 command를 반대 command로 되돌리는 것입니다. 그래서 undo에는 audit log, compensation API, 만료 시간, analytics undo event가 필요합니다.
server commit 후 undo는 어떻게 하나요?서버가 inverse operation을 지원해야 합니다. 삭제는 soft delete로 복구하고, 이동은 이전 위치를 command log에 남기며, 외부 알림처럼 되돌릴 수 없는 side effect는 undo 대신 취소 가능 시간이나 confirmation을 둡니다.
삭제 undo에서 데이터 보존 기간은?undo window와 서버 보존 기간을 분리해 정합니다. UI에서는 5초 undo를 제공하더라도 서버는 감사와 복구 정책에 맞춰 soft delete 상태를 더 오래 보관할 수 있고, fixture는 window 만료 후 복구 버튼이 사라지는지를 봅니다.
TRAINING EVIDENCE command log, undo timeout, compensation API, audit event
Q07

toast는 어떤 정보를 담아야 하나요?

결과, 영향 범위, 다음 행동, 복구 가능성을 짧게 알려야 합니다. 중요한 오류는 toast만으로 끝내지 않고 inline error나 persistent status를 둡니다.

모든 오류를 toast로 처리하면 screen reader announcement, 재시도, 사용자가 놓친 오류 추적이 어렵습니다.

꼬리질문꼬리질문 답변
성공 toast는 항상 필요한가요?항상 필요하지 않습니다. 버튼 상태, inline saved marker, route 전환처럼 결과가 화면에 명확하면 toast를 줄이는 편이 낫습니다. 사용자가 배경 작업이나 bulk action 결과를 놓칠 수 있을 때만 영향 범위와 undo/retry를 담습니다.
aria-live politeness는?성공 저장, 검색 결과 수 변경처럼 흐름을 끊지 않아도 되는 내용은 polite가 맞습니다. 세션 만료, 위험한 실패처럼 즉시 알아야 하는 내용만 assertive를 쓰고, 같은 메시지가 반복 낭독되지 않게 live region fixture를 둡니다.
toast queue가 쌓이면 어떻게 하나요?같은 원인의 toast는 합치고, 우선순위와 최대 개수를 둔 뒤 오래된 정보는 persistent log나 notification center로 넘깁니다. bulk action은 item별 toast 100개 대신 성공/실패 집계와 실패 행 링크를 제공합니다.
TRAINING EVIDENCE toast policy, aria-live test, error persistence fixture, retry action log
Q08

modal과 drawer는 어떻게 구분하나요?

modal은 현재 작업을 막고 결정을 요구할 때, drawer는 맥락을 유지한 보조 작업이나 상세 탐색에 적합합니다.

모든 것을 modal로 만들면 deep link, mobile viewport, focus trap, history handling이 복잡해집니다.

꼬리질문꼬리질문 답변
modal 안에 modal은 허용하나요?가능하면 피하고 단일 modal 안에서 step이나 confirm 영역으로 풀어야 합니다. 꼭 필요하면 stack 순서, aria-hidden 처리, Escape 우선순위, focus trap 중첩, backdrop pointer 차단을 fixture로 검증해야 합니다.
drawer를 URL과 연결해야 하나요?상세 조회나 공유 가능한 편집처럼 새로고침, deep link, 뒤로가기가 의미 있으면 URL에 연결합니다. 단순 보조 필터나 임시 설정이면 local open state가 낫고, URL drawer는 route 전환 시 focus restoration과 page_view 정책을 같이 정합니다.
ESC 동작은 어떻게 정하나요?Escape는 가장 최근에 열린 overlay를 닫되, dirty form이나 저장 중 상태에서는 바로 닫지 않고 guard를 거칩니다. 닫힘이 cancel인지 discard인지 copy로 분명히 하고, 닫은 뒤 trigger focus와 analytics cancel event를 확인합니다.
TRAINING EVIDENCE interaction pattern decision, focus trap test, mobile screenshot, route behavior
Q09

popover와 tooltip은 무엇이 다른가요?

tooltip은 보조 설명이고 focus 가능한 콘텐츠를 담지 않습니다. popover는 상호작용 가능한 작은 레이어이며 열림/닫힘, focus, outside click 정책이 필요합니다.

tooltip 안에 버튼을 넣으면 keyboard와 screen reader 사용자가 접근하기 어렵습니다.

꼬리질문꼬리질문 답변
hover 전용 정보는 왜 위험한가요?touch 기기와 keyboard 사용자는 hover를 만들 수 없고, screen reader는 hover 설명을 같은 방식으로 얻지 못합니다. 꼭 필요한 정보는 visible text나 focus-triggered tooltip으로 제공하고 hover/focus parity fixture를 둡니다.
mobile에서 tooltip은?모바일에서는 tooltip보다 inline helper text, info button으로 여는 popover, bottom sheet가 안정적입니다. tap으로 연다면 밖 탭, 뒤로가기, focus 이동, safe area, viewport resize를 함께 설계합니다.
outside click과 blur는 어떻게 다르나요?outside click은 pointer target이 overlay 밖인지 보는 것이고 blur는 focus가 빠져나갔는지 보는 것입니다. mouse down으로 focus가 먼저 바뀌는 순서, portal, shadow DOM을 고려해 pointerdown/click/blur 순서를 fixture로 고정합니다.
TRAINING EVIDENCE overlay pattern spec, focus test, hover/focus parity, outside click fixture
Q10

입력 지연을 줄이는 인터랙션 전략은 무엇인가요?

입력 즉시 feedback을 주고 비싼 계산은 debounce, transition, worker, virtualization으로 분리합니다.

debounce만 걸면 느린 느낌은 줄 수 있지만 CPU long task나 render 폭증의 원인은 남아 있습니다.

loading도 읽어야 하나요?사용자가 기다려야 하거나 버튼이 pending으로 바뀌는 경우는 '저장 중' 같은 상태를 알려야 합니다. 매우 짧은 loading은 낭독 소음이 될 수 있어 지연 threshold를 두고, 완료/실패 announcement와 짝을 맞춥니다.

Q23

context menu는 어떻게 안전하게 만들죠?

마우스 우클릭뿐 아니라 keyboard trigger, focus, permission, destructive action guard, mobile 대체 UI를 둡니다.

커스텀 메뉴가 브라우저 기본 기능을 막고 keyboard 접근을 제공하지 않으면 사용성이 떨어집니다.

꼬리질문꼬리질문 답변
브라우저 기본 메뉴를 막아도 되나요?앱 객체에 대한 명령이 명확한 영역에서는 막을 수 있지만, 텍스트 입력이나 링크처럼 기본 복사/열기 기능이 중요한 곳은 막지 않는 편이 낫습니다. 막는 경우에도 keyboard와 mobile 대체 메뉴를 제공해야 합니다.
키보드에서 어떻게 여나요?Context Menu 키나 Shift+F10, 또는 명시적 more button으로 열 수 있어야 합니다. 열릴 때 첫 메뉴 항목이나 현재 선택 항목에 focus를 두고 Arrow/Escape 동작을 menu pattern에 맞춥니다.
메뉴 밖 클릭은?밖 pointerdown은 메뉴를 닫되, 메뉴 action 클릭과 blur 순서가 충돌하지 않게 처리합니다. 닫힌 뒤 focus는 trigger나 선택 row로 돌아가야 하며, destructive action은 메뉴 닫힘과 별개로 confirmation이나 undo를 거칩니다.

Q24

인터랙션 테스트는 어떤 수준으로 나누나요?

state machine 단위 테스트, component interaction test, Playwright E2E, accessibility smoke로 나눕니다.

E2E만 믿으면 느리고 원인 파악이 어렵고, unit만 믿으면 실제 포커스/키보드/브라우저 동작을 놓칩니다.

꼬리질문꼬리질문 답변
user-event와 fireEvent 차이는?user-event는 click, typing, tab처럼 실제 사용자 동작에 가까운 이벤트 순서를 만들고 focus 변화도 포함합니다. fireEvent는 단일 이벤트를 직접 쏘기 때문에 edge case 재현에는 유용하지만 keyboard/pointer 상호작용 검증의 기본값으로는 부족합니다.
모든 브라우저에서 E2E를?모든 케이스를 모든 브라우저에서 돌리기보다 핵심 journey와 브라우저 차이가 큰 focus, input, scroll, pointer gesture를 matrix로 나눕니다. Chromium 전체, WebKit/Safari smoke, mobile viewport fixture처럼 위험 기반으로 잡습니다.
flaky test는 어떻게 줄이나요?시간 sleep 대신 상태 전이를 기다리고, network fixture와 clock을 제어하며, animation은 test mode에서 줄입니다. 실패 시 Playwright trace, screenshot, event log를 남겨 pointer/focus/route 어느 단계에서 흔들렸는지 보게 합니다.
TRAINING EVIDENCE test pyramid, user-event tests, Playwright trace, axe report
Q25

route 전환 중 사용자 입력은 어떻게 다루나요?

pending navigation, unsaved changes, abortable requests, optimistic mutation, focus restoration을 설계합니다.

사용자가 저장 중 이동하면 요청은 성공했지만 화면은 이전 상태를 보여주거나 반대로 변경을 잃을 수 있습니다.

꼬리질문꼬리질문 답변
unsaved changes prompt는 언제?사용자가 작성한 draft가 있고 route 전환으로 잃을 수 있을 때만 띄웁니다. 서버에 이미 저장됐거나 자동 저장이 성공한 상태에서는 띄우지 않고, browser back, internal link, modal close를 같은 dirty state guard로 처리합니다.
route loader 실패는?이전 화면을 유지할지 error boundary route로 갈지 정해야 합니다. 실패 화면에는 retry, 권한 오류, offline 구분을 두고 focus는 error heading으로 보내며, analytics에는 page_view가 아니라 route_load_failed 같은 result event를 남깁니다.
뒤로가기 중 mutation은?pending mutation은 abort 가능한 요청이면 취소하고, 이미 서버에 도달한 요청이면 완료 후 cache를 reconcile해야 합니다. optimistic UI가 적용된 상태라면 history 이동 후에도 mutation ledger가 남아 stale 화면을 다시 그리지 않게 합니다.
TRAINING EVIDENCE navigation guard test, pending mutation log, abort signal fixture, focus restore
Q26

복잡한 인터랙션의 QA 시나리오는 어떻게 만들까요?

happy path보다 rapid click, keyboard-only, mobile touch, network slow, permission change, stale data를 먼저 넣습니다.

시나리오가 성공 흐름만 있으면 실제 운영에서 나오는 race와 취소 이벤트를 잡지 못합니다.

꼬리질문꼬리질문 답변
QA에 꼭 넣을 3가지는?keyboard-only 경로, 느린 네트워크와 stale response, 권한 변경이나 403 복구를 우선 넣습니다. 여기에 pointercancel 또는 rapid click을 더하면 state machine의 취소와 중복 제출 전이가 드러납니다.
네트워크 지연은 어떻게 재현하나요?MSW, Playwright route fulfill delay, DevTools throttling으로 latency, timeout, out-of-order response를 만듭니다. 자동완성은 이전 query가 늦게 오는 fixture, optimistic mutation은 reject와 duplicate click fixture를 둡니다.
권한 변경은 어떻게 테스트하나요?초기에는 버튼이 보이지만 action 직전 403이 나는 fixture와, 화면에 머무는 동안 role이 내려가는 fixture를 분리합니다. UI는 버튼 숨김만이 아니라 실패 후 상태 수렴, focus 위치, audit log, analytics error result까지 확인합니다.

Q27

인터랙션과 analytics는 어떻게 연결하나요?

사용자 의도 단위로 event를 정의하고 exposure, action, result, error를 나눕니다.

DOM click만 추적하면 의미 없는 이벤트가 쌓이고 실패/취소/재시도 같은 중요한 흐름을 놓칩니다.

꼬리질문꼬리질문 답변
click event와 action event 차이는?click event는 DOM 발생 사실이고 action event는 사용자가 의도한 작업입니다. 같은 저장 action이 keyboard shortcut, button click, command palette에서 발생해도 하나의 action schema로 묶고 result, error code, source를 속성으로 둡니다.
중복 이벤트는 어떻게 막나요?state machine의 committing 전이에서 한 번만 보내고, retry와 undo는 별도 event로 분리합니다. route 전환 중 page_view 중복, double click, optimistic retry를 event id나 mutation id로 dedupe하는 QA log가 필요합니다.
개인정보는 어디서 제거하나요?event 생성 경계에서 raw input, email, token, 검색어 원문 같은 값을 보내지 않게 schema로 제한합니다. 필요한 경우 category나 length 같은 파생값만 보내고, privacy review와 debug event log로 payload를 확인합니다.
TRAINING EVIDENCE event taxonomy, funnel chart, error result event, privacy review
Q28

인터랙션 구현에서 senior-level 리뷰 포인트는 무엇인가요?

상태 전이, 입력 장치 다양성, 접근성, 실패 복구, 관측 증거, 테스트 fixture가 있는지 봅니다.

시각적으로 동작하는 데모만 있으면 실제 사용자의 빠른 조작과 보조기술 환경에서 깨질 수 있습니다.

꼬리질문꼬리질문 답변
리뷰에서 바로 막아야 할 위험은?keyboard 경로가 없거나 focus가 사라지는 overlay, rollback 없는 optimistic update, permission check 없이 노출된 destructive action, route 전환 중 draft 유실은 막아야 합니다. 각각은 사용자가 작업을 잃거나 잘못된 action을 실행하는 직접 위험입니다.
데모와 운영 기능 차이는?데모는 정상 click만 보여줘도 충분해 보이지만 운영 기능은 pointercancel, 빠른 재클릭, 403, 느린 응답, mobile viewport, screen reader announcement를 견뎌야 합니다. 그래서 PR에는 trace, fixture, state table이 필요합니다.
증거가 부족하면 무엇을 요구하나요?관련 state machine이나 transition table, keyboard/focus 녹화, Playwright trace, 실패 API fixture, analytics debug log 중 변경 위험에 맞는 증거를 요구합니다. UI 캡처만으로는 route, permission, network race를 판단할 수 없습니다.

Q29

경험이 없는 인터랙션 질문은 어떻게 답하나요?

직접 운영 경험과 설계 지식을 분리해 말하고, 상태 기계, 접근성 패턴, 실패 fixture로 검증하겠다고 답합니다.

해본 것처럼 말하면 꼬리질문에서 실제 장애, 측정, 테스트 증거를 요구받을 때 무너집니다.

꼬리질문꼬리질문 답변
모르면 모른다고 해야 하나요?네, 직접 운영 경험이 없으면 없다고 말하고 대신 어떤 위험을 검증할지 제시합니다. 예를 들어 DnD 경험이 적다면 pointer lifecycle, keyboard 대체, rollback fixture, mobile touch test를 기준으로 설계하겠다고 답합니다.
대체 경험은 어떻게 연결하나요?비슷한 상태 전이 경험을 연결합니다. wizard의 guard와 draft 저장 경험은 modal flow나 route 전환 guard에, optimistic update 경험은 inline edit와 undo 설계에 연결하되 다른 점도 함께 말합니다.

Q30

인터랙션에서 permission change는 어떻게 처리하나요?

사용자가 화면에 머무는 동안 권한이나 소유권이 바뀔 수 있으므로 action 직전 서버 결과를 기준으로 UI를 수렴시켜야 합니다.

초기 렌더 때 보인 버튼만 믿으면 만료된 권한으로 실패하거나 잘못된 optimistic UI를 보여줄 수 있습니다.

꼬리질문꼬리질문 답변
버튼을 숨기면 충분한가요?충분하지 않습니다. 숨김은 사용성 힌트일 뿐이고 서버가 action 직전에 권한을 다시 판단해야 합니다. 버튼이 보이는 상태에서 권한이 내려가는 fixture, keyboard shortcut이나 command palette 우회, optimistic mutation reject를 함께 검증합니다.

권한 cache는 어떻게?권한 cache는 짧은 staleTime이나 서버 push/invalidation과 함께 써야 하며 보안 판단의 원본이 되면 안 됩니다. route loader, menu filtering, command palette가 같은 permission source를 쓰게 하고 role change fixture로 cache 수렴을 확인합니다.
