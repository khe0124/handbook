TypeScript·JavaScript 런타임

TypeScript는 코드를 실행하기 전에 일부 모순을 찾지만, 사용자의 브라우저에 도착할 때 타입 정보는 사라집니다. 안전한 프론트엔드는 정적 타입이 보장하는 범위와 실제 런타임에서 다시 확인해야 하는 경계를 구분합니다.

MODEL

컴파일 시점과 런타임은 다른 세계다

TypeScript는 개발 중인 소스 코드를 분석하지만, 브라우저는 변환된 JavaScript와 외부에서 들어온 실제 값만 실행합니다. 타입 오류가 없다는 사실은 코드 내부의 약속이 서로 맞는다는 뜻이지 네트워크 응답, 저장소 데이터, 브라우저 환경까지 올바르다는 보장은 아닙니다.

개발자는 API 응답을 User라고 선언할 수 있지만 서버가 name: null을 보내는 것을 그 선언만으로 막을 수는 없습니다. as User는 값을 검사하지 않고 컴파일러의 의심만 제거합니다. 외부 값은 unknown으로 받아 실제 구조를 검사한 뒤에야 애플리케이션 내부 타입으로 승격해야 합니다.

반대로 모든 값에 런타임 검사를 반복할 필요는 없습니다. 신뢰 경계에서 한 번 파싱한 도메인 모델은 내부 모듈에서 타입 계약을 따라 사용할 수 있습니다. 핵심은 외부 입력 → 런타임 검사 → 내부 타입 → 출력 직렬화의 경계를 명확히 두는 것입니다.

TS-01

타입 경계

타입은 코드 안쪽의 약속이고, 네트워크·스토리지·URL·사용자 입력은 타입 시스템 밖에서 들어옵니다.

TYPE SAFETY BOUNDARY MODEL
1 unknown input → 2 runtime parse → 3 typed domain model
→ 4 UI view model → 5 mutation command → 6 serialized output
경계입력필수 방어나쁜 냄새
API responseJSONschema parse, nullability 처리response as SomeType
URL paramsstringenum/range/default 파싱page as number
localStorageold stringversioned schema, migrationJSON.parse 결과 즉시 사용
postMessage외부 windoworigin check, message type guardevent.data 신뢰

타입 경계는 값이 애플리케이션의 통제 밖에서 안으로 들어오는 지점입니다. 네트워크뿐 아니라 URL, 브라우저 저장소, 파일 업로드, 웹소켓 메시지, 오래된 Service Worker도 외부 입력입니다. 이전 버전의 코드가 저장한 값이나 다른 탭이 보낸 메시지는 현재 타입 선언과 다를 수 있습니다.

경계에서 파싱하면 이후 코드의 책임이 단순해집니다. 예를 들어 페이지 번호를 문자열 상태로 계속 전달하지 않고 URL에서 양의 정수로 변환하고 기본값을 정하면, 화면 내부는 유효한 숫자만 받는다고 가정할 수 있습니다. 실패를 경계에서 발견하지 않으면 오류는 실제 원인과 멀리 떨어진 렌더링 코드에서 나타납니다.

TS-02

런타임 스키마

zod, valibot, io-ts 같은 스키마 도구는 타입을 만드는 도구가 아니라 신뢰 경계를 통과시키는 검문소입니다.

const UserSchema = z.object({
  id: z.string(),
  name: z.string().min(1),
  role: z.enum(["admin", "member"]),
});

const result = UserSchema.safeParse(await response.json());
if (!result.success) {
  throw new DataContractError("user_response_invalid", result.error);
}
대상스키마 전략실패 처리
서버 응답route별 response schema사용자 메시지와 telemetry를 분리한다
폼 draftfield schema + submit schema입력 중 오류와 제출 오류를 나눈다
저장소versioned schema마이그레이션 실패 시 초기화 또는 읽기 전용 fallback
feature flagstrict enum알 수 없는 variant는 control로 보낸다

스키마는 단순히 필드 타입을 확인하는 데서 끝나지 않습니다. 문자열을 날짜나 식별자로 변환하고, 선택 필드의 기본값을 정하며, 서버 DTO를 화면에서 쓰는 도메인 모델로 정규화하는 역할도 맡을 수 있습니다. 파싱 결과가 성공과 실패를 명시적으로 반환하면 호출자는 안전한 대체 화면이나 오류 보고를 선택할 수 있습니다.

스키마의 엄격함은 데이터 성격에 맞춰 정합니다. 결제나 권한 응답처럼 잘못 해석하면 위험한 데이터는 예상하지 못한 값에서 실패시키는 편이 안전합니다. 점진적으로 배포되는 부가 필드는 모르는 필드를 무시하되 필수 필드의 의미는 검증할 수 있습니다. 중요한 것은 파싱 실패를 일반 네트워크 오류와 구분해 계약 회귀로 관측하는 것입니다.

JS-03

비동기 실행 모델

race condition, input delay, stale closure는 문법 문제가 아니라 이벤트 루프와 렌더링 타이밍 문제입니다.

ASYNC RACE REVIEW PACKET
trigger event
in-flight request id
abort signal
latest-wins or first-wins rule
stale closure guard
cleanup on unmount
telemetry for cancellation
문제원인대응
늦게 온 응답이 최신 화면을 덮음요청 순서와 완료 순서를 혼동request id, AbortController, latest-wins 정책
입력 중 화면이 멈춤main thread long taskdebounce, transition, worker, chunking
effect가 오래된 값을 사용closure와 dependency 경계 누락dependency 정리, ref 사용 기준, reducer 전환
unmount 후 setStatecleanup 누락subscription cleanup, abort, mounted guard 최소화

비동기 코드는 작성 순서대로 완료되지 않습니다. 검색어 A 요청을 보낸 뒤 B 요청을 보내도 A 응답이 더 늦게 도착할 수 있습니다. “마지막으로 도착한 응답”과 “현재 사용자가 원하는 응답”은 다르므로 latest-wins, first-wins, queue 같은 정책을 기능별로 정해야 합니다.

AbortController는 브라우저가 응답 소비를 중단하게 할 수 있지만 서버에서 이미 시작된 작업까지 자동으로 되돌리지는 않습니다. 쓰기 요청에는 멱등성이나 서버 측 취소 계약이 별도로 필요합니다. 또한 React effect의 cleanup은 구독과 요청 수명을 컴포넌트 수명에 맞추는 장치이지 모든 경쟁 상태를 해결하는 만능 패턴은 아닙니다.

stale closure는 함수가 만들어진 시점의 값을 기억하는 JavaScript 특성에서 생깁니다. dependency를 무작정 늘리거나 ref로 모두 우회하기보다, 로직이 어떤 시점의 상태를 사용해야 하는지 먼저 결정합니다. 여러 이벤트가 하나의 상태 전이를 구성한다면 reducer나 상태 기계가 시간 관계를 더 명확하게 표현할 수 있습니다.

TS-04

모듈 경계

프론트엔드 코드베이스가 커질수록 타입 안정성은 파일 내부보다 모듈 공개 API에서 깨집니다.

FRONTEND MODULE PUBLIC API GATE
feature exports only public entry
domain model does not import UI
API client returns parsed result
components receive view model
shared package has owner and change log
경계허용금지
featurepublic index에서 화면, route, command만 공개내부 hook과 store deep import
domain순수 타입, parser, 정책 함수React, router, query client import
shared UIvariant, size, state, accessibility contract도메인 전용 prop 누수
API clientrequest command와 parsed responseraw fetch response를 화면에 전달

모듈 경계는 다른 코드가 무엇을 알아도 되는지를 제한합니다. feature의 공개 진입점이 내부 폴더와 hook을 숨기면 구현을 바꿔도 소비자에게 미치는 영향이 작습니다. 반대로 deep import가 퍼지면 내부 파일 이동도 전체 코드베이스의 변경이 되고, 타입이 맞더라도 아키텍처 계약은 깨집니다.

도메인 모듈은 React나 라우터를 몰라도 계산할 수 있는 규칙을 담고, API 어댑터는 외부 응답을 파싱해 도메인 값으로 바꿉니다. 화면 컴포넌트는 원시 응답의 nullable 필드와 전송 형식을 직접 해석하지 않고 표현에 필요한 view model을 받습니다. 이렇게 의존 방향을 정하면 테스트와 런타임 검증의 위치도 자연스럽게 결정됩니다.

JS-05

오류 모델

throw, rejected promise, render error, resource load error는 서로 다른 위치에서 발생하고 서로 다른 복구 경로가 필요합니다.

오류잡는 곳복구로그 필드
render errorError Boundary부분 fallback, route 복귀component stack, route, release_id
async errorquery/mutation handlerretry, stale data, toast, field erroroperation, status, traceId
chunk load errorglobal handler + router새로고침 안내, cache bustchunk url, build version
schema parse errorAPI boundary안전 fallback, reportschema name, field path, endpoint

오류를 모두 catch해서 토스트 하나로 바꾸면 발생 위치와 복구 범위를 잃습니다. 렌더링 오류는 컴포넌트 트리를 중단시키므로 Error Boundary가 가까운 화면 영역을 대체해야 하고, mutation 오류는 사용자가 입력을 수정하거나 재시도할 수 있도록 요청 상태에 남아야 합니다.

예상 가능한 실패와 프로그래밍 결함도 구분합니다. 권한 거부나 계약된 검증 오류는 정상적인 제품 흐름이지만, 존재해야 할 값이 없거나 지원하지 않는 분기에 도달한 경우는 코드 결함일 수 있습니다. 사용자 메시지는 안전하고 간결하게 제공하되 로그에는 route, release, operation, trace ID처럼 원인을 재현할 정보가 필요합니다.

JS-06

빌드와 런타임 차이

타입 체크와 번들 빌드가 통과해도 사용자의 브라우저 런타임에서는 네트워크, 캐시, polyfill, CSP, 브라우저 버전 때문에 깨질 수 있습니다.

영역빌드에서 보이는 것런타임에서 깨지는 것검증
환경변수문자열 치환잘못된 API URL, secret 노출runtime config audit
브라우저 지원transpile 결과API 미지원, CSS 차이browserslist, device smoke
코드 분할chunk 생성chunk load error, 캐시 불일치release id, cache header, reload path
CSP대개 통과inline script/style 차단preview CSP report

빌드는 개발자의 환경에서 소스가 산출물로 변환되었다는 사실만 확인합니다. 사용자의 브라우저는 이미 캐시된 HTML과 이전 chunk를 가지고 있을 수 있고, 확장 프로그램·보안 정책·네트워크 프록시의 영향도 받습니다. 따라서 빌드 성공과 실제 실행 성공 사이에는 배포와 브라우저 환경이라는 별도의 검증 구간이 있습니다.

특히 코드 분할에서는 새 HTML과 이전 asset, 또는 이전 HTML과 삭제된 asset이 섞이면 일부 사용자에게만 chunk 오류가 납니다. 해시가 붙은 이전 asset을 일정 기간 보존하고, release ID와 sourcemap을 연결하며, 복구 가능한 새로고침 안내를 제공해야 합니다. 브라우저 지원 정책도 문서가 아니라 실제 대상 기기 smoke test와 운영 오류로 확인합니다.

GATE

리뷰 게이트

TypeScript 리뷰는 any 금지 캠페인이 아니라 런타임에서 깨질 경계를 찾는 일입니다.

TYPESCRIPT RUNTIME REVIEW GATE
□ 외부 입력은 unknown에서 시작하는가
□ API/URL/storage 경계에 parser가 있는가
□ as, non-null assertion, any가 신뢰 경계를 숨기지 않는가
□ async race와 cancellation 정책이 있는가
□ module public API가 내부 구현을 노출하지 않는가
□ parse failure와 chunk failure가 관측되는가
산출물포함 내용통과 기준
schema boundary mapAPI, URL, storage, message 경계와 parser외부 입력이 바로 domain type으로 들어오지 않는다
async race fixtureslow response, abort, unmount, rapid input최신 화면이 낡은 응답으로 덮이지 않는다
module API reportpublic export, forbidden import, ownerdeep import 없이 feature가 조립된다

리뷰에서는 타입 오류 개수보다 타입이 사실을 과장하는 지점을 찾습니다. 외부 입력을 assertion으로 통과시키거나, nullable 값을 non-null assertion으로 숨기거나, 실패할 수 있는 함수가 항상 값을 반환하는 것처럼 보이면 런타임 위험이 타입 뒤에 가려집니다.

좋은 타입은 가능한 상태를 정확히 좁힙니다. 로딩·성공·실패를 서로 독립된 boolean으로 두기보다 판별 가능한 union으로 표현하면 동시에 로딩이면서 성공인 모순을 막을 수 있습니다. 다만 타입 모델이 실제 UI 상태 전이와 맞는지는 경쟁 요청과 실패 fixture를 실행해 확인해야 합니다.
