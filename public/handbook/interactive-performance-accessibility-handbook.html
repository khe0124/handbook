Performance & Accessibility

빠른 화면이 아니라 모든 사용자의 의도에 제때 응답하는 경험 만들기

INTERACTIVE WEB MASTERY · UPDATED 2026-10
START

빠르고 사용할 수 있다는 것

성능과 접근성은 서로 다른 마감 작업이 아니다. 둘 다 사용자의 입력이 누락되지 않고, 이해 가능한 상태 변화로, 감당 가능한 시간과 감각 비용 안에서 전달되는지를 다룬다.

60fps인 canvas라도 keyboard로 조작할 수 없으면 사용할 수 없다. semantic이 완벽한 menu라도 main thread가 막혀 focus 이동이 수초 늦으면 사용할 수 없다. reduced-motion에서 완료 feedback까지 제거하면 빠르지만 이해할 수 없다. 품질 기준은 기술 수치 하나가 아니라 사용자가 목표를 발견하고 입력하고 결과를 인지하고 회복하는 전체 경로다.

CORE MODEL

INPUT → EVENT → STATE → RENDER → PRESENT → PERCEIVE → NEXT ACTION을 하나의 계약으로 본다. pointer, keyboard, switch, screen reader 명령이 들어오면 main thread가 제때 처리하고, DOM·Canvas·GPU가 상태를 표현하며, 시각·청각·촉각 또는 보조 기술을 통해 결과가 인지되어야 한다. 각 단계에서 시간 지연, 의미 손실, 초점 손실, 과도한 움직임, 메모리 압박이 생길 수 있으므로 trace와 실제 과업 테스트를 함께 사용한다.

품질 질문성능 관점접근성 관점
행동을 시작할 수 있는가?초기 콘텐츠와 control이 제때 나타남이름·역할·상태가 있고 입력 방식에 독립적

01

한 번의 입력이 화면에 도착하기까지

클릭에서 화면 변화까지는 하나의 함수가 아니라 여러 scheduler와 렌더링 단계를 건너는 경로다. 어디가 막혔는지 알아야 올바르게 고친다.

1 · Inputpointer, key, touch, assistive technology
2 · Dispatchevent가 task로 main thread에서 처리됨
3 · State의도와 현재 상태로 다음 상태 계산
4 · Renderstyle, layout, paint 또는 GPU 명령 생성
5 · Presentcompositor가 frame을 화면에 표시
6 · Perceive사용자가 변화와 다음 행동을 이해

event handler가 2ms여도 그 앞에 200ms JavaScript task가 실행 중이면 입력은 기다린다. state는 바뀌었어도 layout과 paint가 무거우면 다음 frame에 결과가 표시되지 않는다. 화면은 바뀌었어도 accessible name이나 live 상태가 갱신되지 않으면 screen reader 사용자는 결과를 얻지 못한다. 그래서 측정은 입력 timestamp부터 실제 presentation과 사용자 인지까지 이어져야 한다.

사례 · 저장 버튼

버튼을 누른 즉시 pressed/busy 상태를 보여주는 일은 네트워크 완료보다 먼저 가능하다. main thread가 막히거나 버튼 이름이 갱신되지 않으면 사용자는 중복 입력한다. 성능과 접근성 문제 모두 같은 “입력 접수 feedback 단절”로 나타난다.

02

프레임 예산과 브라우저 렌더링

부드러움은 평균 FPS가 아니라 필요한 순간의 frame이 제시간에 표시되는가의 문제다. 화면 주사율이 높아질수록 한 frame에 사용할 수 있는 시간은 짧아진다.

nominal frame interval = 1000ms ÷ refresh rate 60Hz ≈ 16.7ms · 90Hz ≈ 11.1ms · 120Hz ≈ 8.3ms 실제 애플리케이션 예산은 브라우저와 OS 작업을 위해 이보다 작게 잡는다.
단계하는 일비용이 커지는 사례
JavaScript입력 처리, state와 animation 값 계산긴 loop, JSON 처리, 동기식 측정, 과도한 framework render
Style어떤 CSS rule이 element에 적용되는지 계산큰 DOM과 광범위한 invalidation
Layoutbox의 크기와 위치 계산geometry 변경, 반복되는 layout read/write
Painttext, 배경, 그림자 등을 pixel 명령으로 기록큰 영역의 blur, shadow, clip과 잦은 invalidation
Rasterpaint 결과를 bitmap tile로 만듦고DPR·큰 layer·복잡한 paint
Compositelayer를 transform·opacity와 함께 합성과도한 layer, texture upload, 큰 투명 surface

Transform과 opacity도 “공짜”는 아니다

layout과 paint를 피할 가능성이 높다는 뜻이지 비용이 0이라는 뜻은 아니다. 합성 layer는 GPU memory를 쓰고, 큰 layer 이동은 fill과 bandwidth를 소비한다. 실제 trace에서 paint와 composite 경계를 확인하고 will-change는 변화 직전에 제한적으로 사용한다.

Layout thrashing

loop 안에서 element의 위치를 읽고 곧바로 style을 쓴 뒤 다음 element 위치를 다시 읽는다. write가 layout을 무효화하고 다음 read가 동기 layout을 강제하는 패턴이 반복된다.

Read와 write 분리

필요한 geometry를 먼저 한꺼번에 읽고 계산한 뒤 write를 묶는다. 더 나아가 매 frame 측정이 정말 필요한지, ResizeObserver나 고정 mapping으로 바꿀 수 있는지 검토한다.

03

입력 반응성: frame보다 먼저 의도를 지킨다

animation frame이 부드러워도 click, keydown, drag가 늦게 처리되면 제품은 느리다. 입력 반응성은 event 대기, handler 실행, 다음 화면 표시를 함께 본다.

지연 구간원인개선 방향
Input delay앞선 long task가 main thread를 점유작업 분할, 불필요한 동기 작업 제거, 우선순위 재설계
Processinghandler 자체가 많은 계산·DOM 변경 수행즉시 필요한 state만 처리하고 무거운 작업 지연·worker 검토
Presentation delay처리 뒤 style/layout/paint가 무거움업데이트 범위 축소, renderer와 표현 방식 개선

Long task는 main thread가 오랫동안 다른 입력을 처리하지 못하게 만드는 작업이다. 무조건 worker로 옮길 수 있는 것은 아니다. DOM 조작은 main thread 책임이므로 데이터 parsing, simulation, image 계산처럼 분리 가능한 순수 작업을 worker 후보로 삼고 메시지 복사·직렬화 비용도 측정한다.

Drag에서 최신 의도를 우선하기

pointermove마다 비싼 render를 전부 실행하면 event가 쌓일 수 있다. 최신 pointer 위치를 state로 보존하고 다음 animation frame에 한 번 시각화하면 입력 빈도와 display 빈도를 분리할 수 있다. 다만 raw 입력이 필요한 drawing 앱은 coalesced events나 별도 sampling 전략을 검토한다.

먼저 반응하고 나중에 완성

필수 feedback을 무거운 결과와 함께 기다리게 하지 않는다. 예를 들어 filter 선택 즉시 선택 상태와 “결과 갱신 중”을 표시하고, 큰 chart 계산은 분할하거나 worker에서 처리한다. 즉시성은 모든 계산을 즉시 끝내는 것이 아니라 사용자의 의도를 즉시 인정하는 것이다.

04

느리다는 인상을 병목으로 바꾸는 법

최적화는 추측이 아니라 재현 → 기록 → 병목 분류 → 한 가지 변경 → 같은 조건 비교의 과정이다.

  1. 과업을 고정한다. 예: 첫 방문 후 carousel을 세 번 drag하고 modal을 연다.
  2. 환경을 기록한다. device, viewport, DPR, refresh rate, network/CPU 조건과 build를 남긴다.
  3. 사용자 증상을 표시한다. 입력이 늦었는지, frame이 끊겼는지, 콘텐츠가 늦게 나타났는지 구분한다.
  4. Trace에서 원인을 찾는다. long task, style/layout, paint, raster, GPU, network와 GC 중 시간을 쓴 주체를 확인한다.
  5. 한 가설을 수정한다. 여러 최적화를 동시에 넣으면 원인과 효과를 알 수 없다.
  6. 같은 fixture로 비교한다. 중앙값뿐 아니라 느린 frame과 반복 실행의 편차를 본다.
관찰가능한 원인추가 증거
scroll 중 main thread가 꽉 참handler, layout, framework renderevent callback과 forced layout, DOM update 범위
main thread는 여유지만 frame dropGPU/raster/compositor 병목큰 layer, overdraw, shader/pass, GPU timing
몇 초 뒤 주기적 멈춤allocation과 garbage collectionheap allocation timeline, frame마다 생성되는 객체
화면 전환 후 계속 느려짐listener·timer·RAF·GPU resource leak반복 진입 전후 heap과 active resource 비교
첫 interaction만 멈춤lazy code, asset decode, shader compilenetwork, compile, image decode와 첫 사용 timestamp
나쁜 진단

“GPU를 쓰면 빨라질 것” 또는 “React가 느리다”는 병목이 아니다. 어떤 사용자 행동에서 어느 thread/단계가 몇 번 예산을 초과하며, 변경 뒤 어떤 증거가 달라졌는지 적어야 한다.

05

GPU·메모리·에너지 비용

Interactive graphics는 main thread만 최적화해서 끝나지 않는다. pixel 수, pass, texture, 자원 수명과 계속 도는 render loop가 기기 전체 비용을 만든다.

비용대표 실패대응
Fill rate / overdraw고DPR fullscreen blur와 투명 layer를 여러 pass로 그림DPR cap, 영역·pass 축소, 불투명 rendering과 해상도 tier
Texture memory보이지 않는 고해상도 asset과 render target을 계속 보존크기·format·mipmap 검토, 지연 로딩, 명시적 dispose
Draw call / state change작은 객체마다 material을 바꾸며 개별 drawbatch, instance, shared material, culling
Allocation / GC매 frame vector·array·material 생성재사용, pooling, mutation 범위 통제와 profile
Background work보이지 않는 tab/section에서도 RAF와 simulation 지속visibility와 viewport에 따라 pause, delta clamp
Resource leakroute 재진입마다 listener, texture, geometry 누적ownership과 cleanup 계약, 반복 mount/unmount test

낮은 frame rate가 유일한 피해가 아니다. 지속적인 GPU 부하는 발열과 battery 소모를 만들고 thermal throttling 뒤에는 처음보다 더 느려질 수 있다. 10초 profile뿐 아니라 실제 체류 시간과 반복 navigation도 시험한다.

pixel workload grows with area: work ∝ CSS width × CSS height × DPR² × pass count × overdraw DPR 1 → 2는 한 변이 2배지만 대략 다루는 pixel 면적은 4배가 된다.
06

적응형 품질은 열화가 아니라 계약이다

모든 기기에서 같은 pixel과 효과를 강제하는 것이 일관성은 아니다. 같은 정보와 조작을 유지하면서 표현 비용을 조절하는 편이 더 일관된 경험이다.

지켜야 하는 것조절 가능한 것
콘텐츠, 현재 상태, control과 완료 결과particle 수, shadow/blur 품질, texture 해상도
입력 mapping과 취소·복구DPR cap, post-process pass, reflection update 빈도
브랜드의 색·구성·핵심 전환 의미장식 loop, parallax 깊이, secondary motion

초기 tier를 user agent 이름 하나로 정하지 않는다. viewport, DPR, preference, API/feature 지원과 보수적인 기본값을 사용하고, 실제 frame 상태가 지속적으로 나쁠 때 단계적으로 낮춘다. 짧은 spike 한 번마다 품질을 오르내리면 화면이 불안정해지므로 hysteresis와 최소 유지 시간을 둔다.

High충분한 조건에서 full particles, 고품질 shadow, 필요한 post effect.
Balancedparticle·DPR·pass를 줄이되 핵심 spatial transition은 유지.
Essential정적 또는 단순 fade, DOM 콘텐츠와 모든 control 유지.
Failedrenderer 초기화 실패 시 poster/DOM fallback과 재시도 또는 설명 제공.
07

의미와 접근성 트리

보이는 모양만으로 control의 역할은 전달되지 않는다. HTML의 의미가 이름, 역할, 상태와 관계를 접근성 트리에 제공한다.

질문확인할 것실패 사례
무엇인가?button, link, heading, input 같은 올바른 native elementclick handler가 붙은 div를 버튼처럼 사용
이름은 무엇인가?보이는 label과 accessible name의 일치아이콘만 있고 “더보기” 대상이 불명확
현재 상태는?expanded, selected, checked, invalid, busy 상태색과 animation만 바뀌고 semantic state는 그대로
무엇과 연결됐나?label-description-error-control 관계오류 문구가 필드와 programmatically 연결되지 않음
언제 발표해야 하나?비동기 결과의 중요도와 live announcement모든 frame 변화를 live region에 보내 과도하게 낭독

ARIA는 native semantics가 없는 custom widget을 설명하는 도구이지 동작을 자동으로 구현하지 않는다. role="button"을 붙여도 Space/Enter 처리, focus, disabled 행동은 직접 책임져야 한다. 가능한 경우 native element를 먼저 선택한다.

Canvas와 WebGL의 semantic layer

GPU scene의 모든 triangle을 접근성 tree로 복제하지 않는다. 사용자가 달성해야 할 목표를 기준으로 DOM control, 현재 선택, 결과 요약과 대체 데이터 표현을 제공한다. 제품 3D 회전은 drag 외에 “왼쪽/오른쪽 회전” 버튼을 제공하고, 데이터 그래픽은 핵심 insight와 table/filter를 제공한다.

08

키보드와 초점: 현재 위치를 잃지 않기

Keyboard 접근성은 Tab이 된다는 뜻을 넘어 논리적인 순서, widget 내부 조작, 보이는 focus, 열고 닫은 뒤의 위치를 포함한다.

패턴필수 focus 행동흔한 실패
Modal적절한 초기 focus, 내부 탐색, Escape, 닫은 뒤 trigger로 복귀배경으로 focus가 빠지거나 body만 scroll lock
Menu / Listbox패턴에 맞는 arrow key와 현재 option 관리모든 항목이 Tab stop이 되어 페이지 탐색이 길어짐
Carousel이전/다음 control, 현재 slide 정보, 자동 재생 정지swipe와 hover만 제공
Route transition새 화면 제목과 main 영역 인지, 의도적인 focus 이동화면은 바뀌었지만 focus가 사라진 element에 남음
Reorder / Dragkeyboard 대안, pickup/drop 상태와 새 위치 발표pointer 좌표만 상태 모델로 사용

focus ring을 브랜드와 맞춘다는 이유로 제거하지 않는다. 배경과 명확히 구분되고 element 경계를 따라야 하며, transform 중에도 현재 대상에서 떨어져 보이지 않아야 한다. exit animation이 끝날 때까지 닫힌 modal의 focusable element를 남겨 두는 식으로 시각 timeline과 interaction state가 충돌하지 않게 한다.

성능과 focus의 교차점

virtualized list에서 화면 밖 DOM을 제거하면 focus 대상도 사라질 수 있다. 재사용 row의 accessible name이 잘못 남거나 screen reader 위치 정보가 틀어질 수도 있다. virtualization은 node 수를 줄이지만 focus·검색·위치 인식 계약을 함께 설계해야 한다.

09

안전한 모션: 줄여도 정보는 남긴다

prefers-reduced-motion은 animation을 전부 없애라는 단일 규칙이 아니라 큰 이동, zoom, rotation, parallax와 자동 움직임을 줄여 같은 목표를 안전하게 제공해 달라는 신호다.

위험 또는 비용예대안
큰 시야 이동전체 화면 zoom, 깊은 parallax, camera fly-through정적 composition, 짧은 crossfade, 직접 navigation
지속적 자동 움직임자동 carousel, 배경 particle, tickerpause/stop, 기본 정지, 사용자 시작
빠른 flash강한 대비가 반복되는 glitch·strobeflash 제거, 낮은 대비의 단일 강조와 안전성 검토
주의 경쟁읽는 동안 여러 loop와 notification motiontask 중 장식 정지, 하나의 우선 attention signal
시간 통제 상실읽기 전에 자동으로 사라지는 안내지속 상태 또는 사용자가 닫는 control

duration만 0.001ms

큰 transform이 순간이동해 오히려 방향을 잃을 수 있고 animation event에 의존한 state도 깨질 수 있다. “모션을 실행하되 거의 0초”는 안전한 variant 설계가 아니다.

역할을 보존한 variant

drawer의 공간 이동은 즉시 상태 전환 또는 짧은 fade로 바꾸고, 제목·focus·expanded 상태를 갱신한다. 성공 bounce를 없애도 icon·문구·live 결과는 남긴다.

@media (prefers-reduced-motion: reduce) {
  .parallax-layer,
  .ambient-particles { animation: none; transform: none; }
  .route-panel { transition: opacity 80ms linear; }
}

사용자가 OS 설정을 실행 중에 바꿀 수 있으므로 필요한 앱은 matchMedia 변경을 구독한다. 제품 내부 설정을 제공한다면 OS 선호를 기본값으로 존중하고, 계정 설정의 우선순위와 저장 범위를 명확히 한다.

10

보이는 것, 들리는 것, 이해되는 것

접근성은 screen reader만의 문제가 아니다. 대비, 확대, reflow, target 크기, 오류 이해, 시간 압박과 인지 부하가 실제 과업을 좌우한다.

색과 대비상태를 색 하나로 구분하지 않고 text, icon, pattern을 함께 사용한다.
Zoom과 reflow확대·좁은 viewport에서 콘텐츠가 잘리거나 fixed UI에 가리지 않는다.
Target과 spacingtouch target이 충분하고 인접한 위험 행동을 실수로 누르기 어렵다.
시간과 제어시간 제한, 자동 갱신, 사라지는 메시지를 사용자가 연장·정지·다시 확인할 수 있다.
오류와 회복오류 위치, 원인, 수정 방법을 연결하고 사용자가 입력한 값을 보존한다.
인지 비용일관된 pattern, 평이한 label, 단계별 정보로 기억과 추측을 줄인다.

성능 최적화가 이 계약을 훼손할 수 있다. font를 늦게 적용해 text가 크게 이동하거나, skeleton을 실제 구조와 다르게 만들어 사용자의 공간 기억을 흔들거나, lazy load가 keyboard 탐색 직전에 콘텐츠를 재배치할 수 있다. 속도 지표와 함께 읽기·탐색 안정성을 확인한다.

11

사례로 함께 진단하기

사례 A · Scroll narrative

증상원인개선
scroll이 끊기고 text가 늦게 나타남scroll event마다 layout read/write, 고DPR canvas redraw입력 sampling과 frame render 분리, geometry cache, DPR/pass tier
keyboard로 다음 section에 갈 수 없음scroll position만 상태이고 실제 문서 구조가 없음semantic section과 heading, 정상 문서 흐름을 source of truth로 유지
motion 축소에서도 parallax가 계속됨duration만 줄이고 scroll mapping은 유지정적 composition과 즉시 콘텐츠 노출, 같은 순서·설명 보존

사례 B · 대량 데이터 dashboard

10,000행을 모두 DOM에 그려 typing이 늦어지면 virtualization과 계산 분리를 검토한다. 그러나 row focus, screen reader 위치, 검색과 export를 잃어서는 안 된다. 필터 입력은 즉시 표시하고 결과 계산 상태를 알리며, chart는 summary와 table을 함께 제공한다. 성능 개선의 성공 기준은 row 수가 아니라 keyboard와 보조 기술을 포함한 filter 과업 완료다.

사례 C · WebGL 제품 hero

첫 화면에서 model·texture·shader를 모두 준비할 때까지 제목과 CTA를 숨기지 않는다. DOM 콘텐츠와 poster를 먼저 제공하고 graphics는 enhancement로 초기화한다. 보이지 않는 동안 render loop를 멈추고, memory 압박이나 context loss에서는 poster로 돌아간다. reduced motion에서는 camera orbit과 pointer distortion을 제거해도 제품 정보와 CTA는 그대로 남는다.

사례 D · Animated modal

열기 animation은 이미 열린 interaction state와 충돌하면 안 된다. trigger 입력 직후 modal semantics와 focus를 설정하되 화면 밖 transform 때문에 focus ring이 사라지지 않게 한다. 닫을 때는 background interaction을 너무 일찍 풀지 않고, exit 후 trigger로 focus를 복귀한다. 빠른 open/close에서도 stale completion callback이 상태를 뒤집지 않는지 시험한다.

12

자동 검사와 실제 과업 테스트

자동화는 반복 가능한 규칙을 잘 찾지만 “사용자가 이해하고 완료할 수 있는가”를 전부 판정하지 못한다. 세 종류의 증거를 묶는다.

기계적 증거

HTML/ARIA 검사, focusable 상태, color 규칙, bundle·trace·memory와 성능 회귀

수동 과업

keyboard-only, screen reader, zoom/reflow, touch, reduced motion, 저성능 기기

사용자 증거

실제 사용자의 목표 완료, 오류와 회복, 상태 설명, 불편·피로와 제어감

검사확인할 수 있는 것놓칠 수 있는 것
정적 접근성 검사일부 이름·role·관계·대비 문제논리적 label, widget 동작, 실제 읽기 순서의 이해
Keyboard script정해진 focus 경로와 key 동작 회귀focus가 시각적으로 보이는지, 경로가 자연스러운지
Synthetic performance고정 환경의 전후 비교와 회귀실제 기기 다양성, 장시간 열·메모리, 사용자 입력 패턴
Field telemetry실사용 환경의 분포와 느린 꼬리왜 막혔는지의 세부 원인과 장애 사용자 경험
Assistive technology test실제 발표, 탐색, 상태 변화한 도구·브라우저 조합을 전체 사용자로 일반화할 위험

평균만 보고 통과시키지 않는다. device/입력 방식별 분포, 느린 구간, 반복 navigation 뒤 memory 변화와 실패율을 본다. 접근성도 “스크린리더 한 번 켜 봄”이 아니라 핵심 과업과 기대 결과를 fixture로 관리한다.

성능 budget은 대상 기기, 화면 주사율, 과업과 제품 위험에 맞춰 정한다. 접근성은 숫자 하나로 대체하지 않는다. 기준을 통과했다는 말에는 재현 fixture, trace, keyboard 경로, 보조 기술 결과, reduced-motion 화면과 남은 예외가 함께 있어야 한다.

관찰하고 실패시키는 실습

Lab 1 · Jank 원인 세 갈래

같은 카드 drag에 long JavaScript task, layout thrashing, 큰 paint/blur를 각각 넣는다. 화면상 끊김이 비슷해도 trace에서 다른 단계가 비용을 쓰는지 표시하고, 한 원인씩 수정한 전후 기록을 남긴다.

Lab 2 · Full / Reduced / No-animation

scroll narrative를 세 variant로 만든다. 각 mode에서 heading 순서, keyboard navigation, 현재 section, 완료 feedback이 같아야 한다. reduced는 큰 이동과 parallax를 제거하고 no-animation은 animation event 없이도 최종 state가 완전해야 한다.

Lab 3 · GPU scene endurance

제품 hero를 20회 mount/unmount하고 foreground/background를 반복한다. RAF, listener, geometry, material, texture, render target이 남는지 확인한다. DPR과 post-process tier별 frame·memory·발열 변화를 기록한다.

Lab 4 · 접근 가능한 대량 목록

virtualized list를 keyboard와 screen reader로 탐색한다. filter 중 입력 반응, focus 유지, 현재 위치 정보, 빈 결과, loading과 error를 검증하고 200% 이상 zoom과 좁은 viewport에서 과업을 반복한다.
