K8S-01

Object model

Kubernetes 객체는 desired state를 API server에 선언하고 controller가 실제 상태를 맞추는 구조입니다. YAML은 결과물이 아니라 의도이며, 실제 판단은 status, events, controller condition으로 합니다.

KUBERNETES MODEL

판단 질문 선언한 상태와 실제 상태가 어디서 어긋났는가?

확인 증거 metadata generation, observedGeneration, status condition, event, ownerReference

실패 신호 YAML은 적용됐지만 controller가 권한, quota, image pull, scheduling 문제로 원하는 상태를 만들지 못합니다.

K8S-02

Pod와 Deployment

Pod는 Kubernetes의 실행 단위이고 Deployment는 replica와 rollout을 관리합니다. ReplicaSet은 특정 template revision의 Pod 수를 유지합니다. Deployment가 정상이어도 새 Pod가 image pull, env, permission, resource 부족 때문에 준비되지 않을 수 있습니다.

kubectl get deploy,pod -n app
kubectl describe pod web-abc123 -n app
kubectl logs web-abc123 -n app --previous
WORKLOAD EVIDENCE

볼 것 desired/available replicas, pod phase, restart count, waiting reason, last termination state

판단 기준 Running은 traffic ready와 다릅니다. Ready condition과 Service endpoint 포함 여부까지 확인해야 합니다.

K8S-03

Service와 Ingress

Service는 label selector로 Pod를 endpoint에 묶고 안정적인 cluster IP 또는 load balancer를 제공합니다. Ingress는 외부 HTTP 경로와 host를 Service로 연결합니다. selector가 어긋나면 정상 Pod도 트래픽을 받지 못합니다.

Service selectorrouting
Service가 어떤 Pod를 endpoint로 삼을지 정합니다. app label 하나가 다르면 endpoint가 비어 503이 됩니다.
Ingress ruleedge
host, path, TLS, backend service를 묶습니다. path rewrite와 backend port가 어긋나면 특정 route만 깨집니다.
EndpointSliceevidence
실제로 트래픽을 받을 Pod endpoint 목록입니다. Service 정상 여부는 endpoint가 있어야 판단할 수 있습니다.
kubectl get svc,ingress,endpointslices -n app
kubectl describe svc web -n app
kubectl describe ingress web -n app
K8S-04

Probe와 rollout

readiness probe는 Pod가 트래픽을 받아도 되는지, liveness probe는 재시작이 필요한지, startup probe는 느린 시작을 보호하는지 판단합니다. liveness에 DB 의존성을 넣으면 외부 장애가 Pod 재시작 폭풍으로 바뀔 수 있습니다.

PROBE DECISION

판단 질문 앱이 준비되지 않은 동안 트래픽이 들어오지 않도록 막고 있는가?

확인 증거 readiness path, liveness path, startup delay, terminationGracePeriodSeconds, preStop hook, rollout status

실패 신호 rollout complete인데 실제 사용자 path는 실패하거나, liveness가 너무 공격적이라 정상 부팅 중인 Pod를 계속 죽입니다.

kubectl rollout status deploy/web -n app
kubectl rollout history deploy/web -n app
kubectl describe deploy web -n app
K8S-05

Config·Secret·Resource

ConfigMap과 Secret은 설정 주입 경계이고, request/limit은 scheduler와 runtime resource 경계입니다. 설정 변경이 Pod 재시작 없이 반영되는지, secret rotation이 어떤 rollout 절차를 요구하는지 명확해야 합니다.

  • ConfigMap/Secret은 앱이 읽는 env 또는 mounted file과 실제 값 readback을 비교합니다.
  • CPU/memory request는 scheduling 기준이고 limit은 runtime 제한입니다.
  • HPA는 평균 CPU만이 아니라 request 기준, warmup, queue length 같은 지표와 연결해서 봅니다.
  • namespace quota와 service account 권한은 배포 실패의 원인이 될 수 있습니다.
PRACTICE

출력 판독

Kubernetes 장애는 `kubectl get` 한 줄보다 describe, events, logs, endpoints, rollout history를 같은 시간축에 놓을 때 빨리 좁혀집니다.

PRACTICE LAB

Command / Query `kubectl get pod,svc,ingress`, `kubectl describe pod`, `kubectl logs --previous`, `kubectl rollout status`를 실행합니다.

정상 출력 desired와 available replica가 같고, Ready Pod가 Service endpoint에 포함되며 Ingress backend가 올바른 service port를 가리킵니다.

비정상 출력 ImagePullBackOff, CrashLoopBackOff, readiness failure, empty endpoint, wrong selector, rollout timeout이 보입니다.

판단 훈련 scheduling, image pull, app boot, probe, service routing, ingress rule 문제를 분리합니다.

즉시 완화 rollout pause, rollback, replica 조정, 불량 Pod drain, Ingress rule rollback으로 영향 범위를 줄입니다.

영구 수정 probe 기준, resource request/limit, deployment strategy, selector naming rule, runbook query를 보강합니다.

검증 기준 canary 또는 rolling update 후 p95 latency, 5xx, endpoint count, restart count가 기준선으로 돌아옵니다.
