프론트엔드 품질·릴리스 Q&A

보안, 테스트, 배포, sourcemap, CDN cache, rollback, 릴리스 증거를 답변으로 훈련합니다.

TRAINING : 30초 답변 → 90초 확장 → 꼬리질문 방어 → 증거 패킷 확인
GUIDE

훈련 방식

각 문항은 API 암기나 라이브러리 사용법이 아니라, 사용자 흐름, 브라우저 비용, 접근성, 성능, 보안, 운영 증거를 연결해 답하는 훈련용입니다.

frontend_answer_loop: 1_user_impact: "사용자가 겪는 변화와 실패 비용을 먼저 말한다" 2_runtime_boundary: "DOM, network, rendering, cache, browser policy 중 경계를 잡는다" 3_tradeoff: "선택 기준과 포기하는 것을 분리한다" 4_failure_mode: "race, stale data, accessibility, device variance, cache drift를 점검한다" 5_evidence: "trace, screenshot, test, metric, release log 중 하나를 증거로 든다"
Q01

프론트엔드 릴리스 품질 기준은 무엇인가요?

기능 성공뿐 아니라 보안, 접근성, 성능, 브라우저 호환성, observability, rollback 가능성을 통과해야 합니다.

로컬에서 보이는 화면만 확인하면 CDN cache, env, sourcemap, 권한, 실제 사용자 성능 문제를 놓칩니다.

꼬리질문꼬리질문 답변
작은 변경도 릴리스 게이트가 필요한가요?문구 수정처럼 위험이 낮은 변경은 가벼운 smoke와 리뷰로 충분할 수 있지만, 인증·결제·권한·라우팅·캐시·분석 이벤트를 건드리면 작은 diff라도 강한 게이트가 필요합니다. 변경 크기보다 사용자 영향 경로와 복구 비용으로 등급을 나눕니다.
게이트를 자동화하려면?CI에서 lint, typecheck, unit, component, 핵심 E2E, axe smoke, bundle budget, sourcemap 업로드 검증을 자동으로 돌립니다. 수동 확인이 필요한 항목은 release checklist에 증거 링크를 남기고, 실패 시 배포를 막는 항목과 경고만 주는 항목을 구분합니다.
배포 후 몇 시간 보나요?트래픽 패턴에 맞춰 최소 한 번의 핵심 사용 시간대를 봅니다. 보통 첫 30분은 error spike와 blank screen, 2~4시간은 Web Vitals와 conversion, 24시간은 브라우저·지역·버전 segment를 확인하고 release version 기준으로 이전 배포와 비교합니다.
TRAINING EVIDENCE release checklist, E2E trace, Web Vitals, error dashboard, rollback drill
Q02

프론트엔드 XSS 방어는 source와 sink를 어떻게 끊나요?

untrusted source가 HTML/JS execution sink로 들어갈 때 발생합니다. escaping, sanitization, Trusted Types, CSP, unsafe sink 금지가 필요합니다.

React가 기본 escape를 해도 dangerouslySetInnerHTML, markdown, SVG, URL, third-party widget에서 우회 경로가 생깁니다.

꼬리질문꼬리질문 답변
React면 XSS가 없나요?없어지는 것이 아닙니다. JSX 텍스트 interpolation은 escape되지만 dangerouslySetInnerHTML, ref로 DOM을 직접 쓰는 코드, URL href, SVG, third-party widget, 번역 문자열의 HTML 삽입은 별도 검증이 필요합니다. source-to-sink 표로 어떤 값이 어느 sink에 닿는지 확인합니다.
markdown 렌더링은?markdown은 HTML을 허용하는 순간 사용자 입력이 DOM sink로 들어갑니다. 허용 태그와 속성을 whitelist로 제한하고, javascript: URL, event handler, style 속성, SVG payload를 fixture로 테스트해야 합니다. sanitizer 버전과 설정도 보안 리뷰 대상입니다.
CSP는 무엇을 막나요?CSP는 inline script, 외부 script, frame, image, connect 대상 같은 실행·로드 경계를 제한해 XSS의 폭발 반경을 줄입니다. 하지만 취약한 sink를 고치는 대체재는 아니며, report-only로 violation을 수집한 뒤 nonce 또는 hash 기반 정책으로 단계적으로 강화합니다.
TRAINING EVIDENCE source-sink map, XSS fixture, CSP violation report, sanitizer test
Q03

CSRF와 프론트엔드의 관계는?

cookie 기반 인증에서는 브라우저가 자동으로 cookie를 보내므로 SameSite, CSRF token, origin 검증이 필요합니다.

token을 JS에서 직접 보내는 구조와 cookie 세션 구조를 혼동하면 방어가 빠집니다.

꼬리질문꼬리질문 답변
SameSite=Lax면 충분한가요?기본 방어로는 유용하지만 충분하다고 단정하면 안 됩니다. 브라우저 차이, top-level navigation, legacy client, OAuth redirect, iframe 요구가 있으면 예외가 생깁니다. 상태 변경 요청에는 서버가 검증하는 CSRF token과 Origin 또는 Referer 검증을 같이 둡니다.
CORS와 CSRF 차이는?CORS는 다른 origin의 응답을 브라우저 JS가 읽을 수 있는지를 제한합니다. CSRF는 응답을 읽지 못해도 인증 쿠키가 자동 전송되어 상태 변경 요청이 실행되는 문제입니다. CORS를 닫아도 CSRF 토큰 검증이 없으면 POST 부작용은 남을 수 있습니다.
SPA도 CSRF가 있나요?cookie 세션이나 httpOnly refresh cookie를 쓰는 SPA라면 있습니다. Authorization header에 bearer token을 직접 붙이는 구조는 CSRF보다 XSS 탈취 위험이 커지고, cookie 기반 구조는 SameSite, token, credentials 설정, preflight 정책을 함께 검증해야 합니다.
TRAINING EVIDENCE SameSite policy, CSRF negative test, request header audit, server validation log
Q04

토큰 저장은 어떻게 판단하나요?

XSS, CSRF, refresh rotation, session revocation, UX 요구를 기준으로 httpOnly secure cookie, memory, storage를 비교합니다.

access token을 localStorage에 두면 XSS 시 탈취되기 쉽고, cookie는 CSRF 방어가 필요합니다.

꼬리질문꼬리질문 답변
httpOnly cookie 단점은?JS에서 읽을 수 없어 탈취면에서는 강하지만, 브라우저가 자동 전송하므로 CSRF 방어가 필요합니다. SameSite, Secure, domain/path 범위, CORS credentials, logout revocation, multi-subdomain 요구를 함께 설계해야 합니다.
memory 저장은 새로고침 때?memory 저장은 XSS로 영구 탈취되는 위험을 줄이지만 새로고침, 탭 복제, 앱 재시작에서 access token이 사라집니다. 짧은 access token과 httpOnly refresh cookie, silent refresh 실패 시 명확한 re-auth UX를 조합하는 방식이 흔합니다.
refresh token은 어디에?브라우저에서 refresh token을 직접 읽을 수 있는 storage에 두는 것은 위험합니다. 가능하면 httpOnly Secure cookie에 저장하고 rotation, reuse detection, device/session revocation, logout 시 서버 폐기를 적용합니다. 모바일 WebView나 BFF 구조라면 저장 경계가 달라질 수 있습니다.
TRAINING EVIDENCE token storage decision, threat model, logout test, rotation log
Q05

프론트엔드 secret은 왜 존재하면 안 되나요?

브라우저 bundle은 사용자에게 전달되므로 API key나 secret은 노출된 값으로 봐야 합니다.

환경변수 이름이 SECRET이어도 build 시 bundle에 들어가면 누구나 볼 수 있습니다.

꼬리질문꼬리질문 답변
public API key는?지도나 analytics처럼 public key가 전제인 서비스도 있습니다. 이 경우 secret으로 보지 말고 origin 제한, quota, scope, abuse monitoring, server-side proxy 필요성을 검토합니다. 결제 secret, admin token, private API credential은 절대 bundle에 넣지 않습니다.
env prefix는?Vite의 VITE_, Next의 NEXT_PUBLIC_처럼 public prefix가 붙으면 브라우저 번들에 노출됩니다. 이름에 SECRET이 들어가도 public prefix로 주입되면 공개 값입니다. build output과 source map에서 실제 문자열이 포함되는지 스캔해야 합니다.
노출된 secret은 어떻게 대응?이미 배포된 값은 회수됐다고 봐야 합니다. 즉시 revoke 또는 rotate하고, 사용 로그에서 악용 여부를 확인하며, 해당 값이 들어간 sourcemap과 CDN asset의 purge 범위를 정리합니다. 이후 secret scanning과 PR gate로 재발을 막습니다.
TRAINING EVIDENCE bundle scan, source map audit, secret scanning, network request review
Q06

CORS 오류를 어떻게 진단하나요?

브라우저 보안 정책, origin, preflight, credentials, allowed headers/methods, server response를 확인합니다.

프론트에서 header를 억지로 추가해 해결하려 하면 실제로는 서버 CORS 정책이 맞지 않는 경우가 많습니다.

꼬리질문꼬리질문 답변
CORS는 보안인가요?CORS는 브라우저가 cross-origin 응답을 JS에 노출할지 결정하는 정책입니다. 서버 자체를 보호하는 인증·인가를 대신하지 않습니다. 악성 서버나 curl은 CORS를 따르지 않으므로 API는 별도의 auth, rate limit, input validation을 가져야 합니다.
credentials true이면?cookie나 client certificate을 포함하려면 fetch credentials와 서버의 Access-Control-Allow-Credentials가 맞아야 합니다. 이때 Access-Control-Allow-Origin은 *를 쓸 수 없고, 허용 origin을 정확히 반사하거나 allowlist로 검증해야 합니다.
wildcard origin은 왜 위험?인증이 필요 없는 public resource에는 가능할 수 있지만, 사용자별 데이터나 credentials가 얽히면 다른 origin이 응답을 읽는 길이 열릴 수 있습니다. origin allowlist, method/header 최소화, preflight cache 정책을 서버 config diff로 확인합니다.
TRAINING EVIDENCE preflight capture, response header audit, credentials test, server config diff
Q07

E2E 테스트는 무엇을 검증해야 하나요?

핵심 사용자 여정의 실제 브라우저 동작, route, network, auth, accessibility smoke, visual state를 검증합니다.

모든 케이스를 E2E로 넣으면 느리고 flaky해지며, 반대로 하나도 없으면 통합 회귀를 놓칩니다.

꼬리질문꼬리질문 답변
무엇을 E2E로 올리나요?로그인, 결제, 저장, 권한 변경, 검색, 대시보드 조회처럼 여러 컴포넌트와 API가 이어지는 핵심 여정을 올립니다. 단일 컴포넌트의 조건 분기는 component test로 두고, E2E는 실제 라우팅·네트워크·브라우저 동작이 깨지는지 확인합니다.
mock과 real API 선택은?릴리스 게이트에서는 계약이 안정적인 mock으로 빠른 회귀를 잡고, 별도 smoke나 staging에서는 real API로 auth, CORS, schema, latency를 확인합니다. mock은 OpenAPI/GraphQL schema나 contract sample과 동기화해야 drift를 줄일 수 있습니다.
flaky는 어떻게 줄이나요?고정 sleep을 줄이고 locator, network wait, test id, deterministic fixture를 사용합니다. 테스트별 독립 계정과 데이터 reset을 보장하고, Playwright trace와 retry report로 race, animation, backend latency 원인을 분류해 제거합니다.
TRAINING EVIDENCE Playwright trace, critical journey list, flake report, test pyramid
Q08

컴포넌트 테스트는 어디까지 하나요?

props/state 조합, 사용자 이벤트, 접근성 role/name, error/loading 상태를 검증합니다.

구현 세부 DOM 구조만 테스트하면 리팩터링에 취약하고 실제 사용자 행동을 검증하지 못합니다.

꼬리질문꼬리질문 답변
snapshot test는?넓은 DOM snapshot은 작은 markup 변경에도 깨져 신호가 약합니다. 디자인 시스템 토큰이나 serializable output처럼 안정적인 대상에는 제한적으로 쓰고, 대부분은 role, name, visible text, user-event 결과를 검증하는 편이 낫습니다.
role query가 좋은 이유는?사용자가 보조기술로 인식하는 의미와 테스트가 같은 기준을 쓰게 됩니다. getByRole로 버튼 이름, dialog 제목, form field label을 찾으면 접근성 이름 누락과 잘못된 semantic element를 빨리 발견할 수 있습니다.
CSS는 어떻게 검증?순수 스타일 값은 unit test보다 visual regression과 story viewport가 맞습니다. 상태별 class나 data attribute는 component test로 확인하고, overflow, focus ring, responsive break는 screenshot diff와 브라우저 matrix에서 봅니다.
TRAINING EVIDENCE Testing Library queries, user-event test, story coverage, axe check
Q09

시각 회귀 테스트는 언제 필요한가요?

디자인 시스템, 핵심 화면, 차트/그래픽, responsive layout처럼 시각 깨짐 비용이 큰 곳에 필요합니다.

단위 테스트가 통과해도 spacing, overflow, z-index, 반응형 깨짐은 놓칠 수 있습니다.

꼬리질문꼬리질문 답변
threshold는?픽셀 차이를 무조건 0으로 두면 font rendering이나 antialiasing 때문에 불안정해질 수 있습니다. 컴포넌트 성격에 따라 threshold를 작게 두되, 버튼 위치·텍스트 overflow·z-index·차트 축처럼 의미 있는 변화는 reviewer가 확인하도록 diff workflow를 둡니다.
동적 데이터는?날짜, 랜덤 아바타, 실시간 수치, 애니메이션은 fixture와 clock freeze로 고정합니다. 외부 이미지나 chart 데이터는 deterministic sample을 쓰고, skeleton·loading·error 상태도 별도 baseline으로 관리합니다.
모든 페이지에 필요?모든 페이지에 같은 강도로 적용하면 유지비가 커집니다. 디자인 시스템 primitive, 고매출 funnel, 복잡한 responsive grid, chart, editor, 3D/canvas preview처럼 시각 오류 비용이 큰 곳부터 coverage를 둡니다.
TRAINING EVIDENCE visual baseline, viewport matrix, diff threshold, review workflow
Q10

접근성 테스트 자동화의 한계는?

axe 같은 도구는 일부 규칙을 잡지만 keyboard flow, screen reader 맥락, 문구 의미는 사람이 확인해야 합니다.

자동 검사 통과를 접근성 완료로 보면 focus order와 실제 announcement 문제를 놓칩니다.

꼬리질문꼬리질문 답변
자동화로 몇 퍼센트 잡나요?정확한 비율보다 어떤 유형을 못 잡는지 아는 것이 중요합니다. color contrast, missing label, landmark 같은 규칙은 잘 잡지만, 업무 문맥에 맞는 오류 문구, focus 이동 의도, screen reader announcement의 자연스러움은 수동 확인이 필요합니다.

Q11

sourcemap은 어떻게 운영하나요?

에러 추적에는 필요하지만 공개 접근, source 노출, release id mapping, 업로드 보안 정책을 관리해야 합니다.

sourcemap을 공개 CDN에 그대로 두면 내부 소스 구조와 주석이 노출될 수 있습니다.

꼬리질문꼬리질문 답변
sourcemap을 배포하지 않으면?사용자 오류 stack이 minified 위치로만 남아 원인 분석 시간이 크게 늘어납니다. 공개 CDN에 노출하지 않더라도 Sentry 같은 error tracker에는 private sourcemap을 업로드하고 release id와 commit sha를 맞춰 deobfuscation되게 해야 합니다.
private sourcemap은?빌드 산출물과 별도 artifact로 저장하고 접근 권한을 제한합니다. 업로드 로그, 보존 기간, 프로젝트별 token scope를 관리하며, sourceContent 포함 여부와 민감 주석·내부 URL 노출 가능성을 audit합니다.
release id는 왜?브라우저가 실행한 bundle version과 sourcemap artifact를 정확히 연결하기 위해 필요합니다. CDN 캐시나 canary가 섞이면 같은 오류도 version별 원인이 다를 수 있으므로 release id, build id, commit sha를 error event에 포함합니다.

Q12

CDN cache 때문에 배포가 깨지는 경우는?

content hash 없는 asset을 길게 cache하면 사용자가 오래된 코드를 계속 받습니다.

꼬리질문꼬리질문 답변
HTML은 어떻게 cache?HTML은 최신 asset manifest를 가리켜야 하므로 짧은 TTL이나 revalidation을 둡니다. 정적 asset과 달리 오래 cache하면 새 라우트나 chunk 이름을 못 찾아 blank screen이 날 수 있어 cache-control과 CDN purge 정책을 함께 검증합니다.
immutable asset은?content hash가 붙은 JS/CSS/image는 긴 max-age와 immutable을 줄 수 있습니다. 같은 URL의 내용을 바꾸지 않는 것이 핵심이고, hash 없는 vendor.js 같은 파일에 immutable을 주면 rollback과 partial deployment에서 stale 코드가 남습니다.
rollback과 cache는?이전 HTML이 새 asset을 참조하거나 새 HTML이 purge된 asset을 참조하는 조합을 피해야 합니다. rollback artifact를 보존하고, CDN purge 순서, service worker cache, chunk compatibility를 smoke fixture로 확인합니다.
TRAINING EVIDENCE cache header audit, asset hash, purge log, stale bundle fixture
Q13

환경변수 drift는 어떻게 막나요?

환경별 required env schema, build-time/runtime 구분, validation, release diff를 둡니다.

staging에는 있고 production에는 없는 env가 배포 후 런타임 오류를 만들 수 있습니다.

꼬리질문꼬리질문 답변
프론트 env는 왜 build-time인가요?대부분의 프론트 env는 build 시 bundle에 문자열로 치환됩니다. 배포 후 서버 env만 바꿔도 이미 생성된 JS에는 반영되지 않으므로 API base URL, feature flag default, public key 변경은 rebuild나 runtime config endpoint 전략을 명확히 해야 합니다.

기본값을 코드에 넣어도?dev 편의 기본값은 production에서 위험할 수 있습니다. production build에서는 required env가 없으면 실패하게 하고, staging·preview·production의 config diff를 release note에 남깁니다. fallback URL이나 debug flag가 운영으로 들어가지 않게 테스트합니다.

Q14

배포 후 모니터링은 무엇을 보나요?

client error rate, route-specific Web Vitals, API failure, conversion, blank screen signal, release adoption을 봅니다.

서버가 정상이어도 프론트 bundle 오류나 특정 브라우저 오류로 사용자는 장애를 겪을 수 있습니다.

몇 시간 봐야 하나요?첫 10~30분은 syntax error, chunk load failure, 5xx, auth loop처럼 즉시 드러나는 문제를 봅니다. 이후 주요 트래픽 시간대까지 Web Vitals, conversion, route-specific error, browser segment를 보고, 하루 단위로 long-tail 기기와 CDN region을 확인합니다.
브라우저별 segment는?Safari iOS, Android WebView, 오래된 Chromium, enterprise browser처럼 runtime 차이가 큰 segment를 따로 봅니다. release version, route, device memory, network type과 묶어야 특정 브라우저에서만 나는 blank screen이나 CSS 깨짐을 발견할 수 있습니다.
blank screen은 어떻게 감지?window error만으로는 부족합니다. root element가 일정 시간 비어 있는지, critical route marker가 렌더됐는지, chunk load failure와 hydration error가 있었는지 client heartbeat로 보냅니다. synthetic smoke도 대표 route를 주기적으로 열어 확인합니다.

Q15

rollback 기준은 어떻게 정하나요?

error rate, core journey failure, Web Vitals regression, conversion drop, security issue 같은 threshold를 미리 정합니다.

감으로 결정하면 복구가 늦고, 반대로 작은 오류에 과도하게 rollback할 수 있습니다.

꼬리질문꼬리질문 답변
forward fix와 rollback 선택은?원인이 명확하고 수정·검증·배포가 rollback보다 빠르면 forward fix를 선택할 수 있습니다. 인증, 결제, blank screen, 보안 노출처럼 영향이 큰 문제는 원인 분석을 기다리지 않고 rollback이나 flag off로 사용자 영향을 먼저 줄입니다.
DB/API 변경이 있으면?프론트만 되돌려도 API contract나 데이터 migration이 이미 바뀌었으면 깨질 수 있습니다. backward compatible API, expand-contract 순서, feature flag, migration rollback 가능성을 릴리스 전에 확인하고 playbook에 책임자를 명시합니다.

TRAINING EVIDENCE rollback playbook, release health window, threshold alert, decision log

flag default, targeting, exposure logging, kill switch, stale cleanup, permission과의 차이를 검증합니다.

flag가 켜진 사용자와 꺼진 사용자의 cache/state가 섞이면 재현 어려운 버그가 생깁니다.

브라우저 호환성은 어떻게 관리하나요?

Q18

프론트엔드 보안 리뷰에서 source-sink 분석은?

입력 검증만 보고 실제 sink를 보지 않으면 sanitizer bypass와 DOM XSS를 놓칩니다.

꼬리질문꼬리질문 답변
URL도 sink인가요?네. href, src, location.assign, window.open, CSS url()은 사용자 입력이 javascript:, data:, file:, open redirect로 이어질 수 있는 sink입니다. URL parser로 protocol과 host를 검증하고 allowlist와 rel=noopener 정책을 적용합니다.
style injection은?style 속성이나 CSS 변수에 사용자 입력을 넣으면 url(), expression legacy, layout overlay, clickjacking 보조 경로가 될 수 있습니다. 허용 값은 enum이나 numeric range로 제한하고 raw CSS 문자열 조합을 피합니다.
postMessage는?message event의 data는 외부 source입니다. origin, source window, schema version을 검증하지 않고 routing, token 전달, DOM update에 쓰면 cross-origin 주입이 됩니다. 수신부를 source-sink table에 포함해야 합니다.
TRAINING EVIDENCE source-sink table, negative fixture, sanitizer config, Trusted Types report
Q19

postMessage는 어떻게 안전하게 쓰나요?

wildcard와 schema 검증 누락은 다른 origin이 메시지를 주입하는 경로가 됩니다.

targetOrigin *는 언제 위험?민감 데이터, auth 상태, user id, payment result를 보낼 때 *를 쓰면 의도하지 않은 frame이 메시지를 받을 수 있습니다. 수신 origin을 정확히 알고 있으면 명시하고, 동적 origin은 allowlist 검증 뒤에만 사용합니다.

Q20

프론트엔드 테스트 데이터는 어떻게 관리하나요?

Q22

TRAINING EVIDENCE mock/schema diff, contract test, error fixture, latency simulation
Q23

릴리스 노트에는 무엇을 남겨야 하나요?

사용자 공지는?사용자가 워크플로 변경, 데이터 표시 변경, 중단 시간, 브라우저 지원 종료를 체감하면 공지가 필요합니다. 단순 버그 수정은 내부 changelog면 충분할 수 있지만, UI 위치 변경이나 권한 정책 변경은 help center와 support script를 함께 갱신합니다.

Q24

프론트엔드 장애 postmortem은 무엇을 다루나요?

영향 route, browser/device segment, release version, detection gap, rollback time, 재발 방지 action을 다룹니다.

서버 장애 형식만 복사하면 bundle/cache/browser-specific 원인을 놓칩니다.

꼬리질문꼬리질문 답변
고객 영향은 어떻게 산정?영향 route의 방문자 수, 실패 event, conversion drop, support ticket, browser/device segment, release adoption 비율을 합쳐 봅니다. 서버 uptime이 정상이어도 프론트 blank screen이나 chunk error가 있으면 실제 사용자 실패로 계산해야 합니다.

액션 아이템 좋은 기준은?소유자, 기한, 검증 방법이 있어야 합니다. cache smoke 추가, sourcemap release id 검증, Safari E2E 추가, flag kill switch drill처럼 다음 릴리스에서 실제로 같은 장애를 잡을 수 있는 항목이어야 합니다.

Q25

보안 헤더는 프론트 품질과 어떻게 연결되나요?

CSP, HSTS, X-Frame-Options/frame-ancestors, Referrer-Policy, Permissions-Policy는 브라우저 실행 환경을 제한합니다.

헤더는 백엔드/인프라에서 설정되지만 프론트 기능과 충돌할 수 있어 함께 검증해야 합니다.

꼬리질문꼬리질문 답변
CSP rollout은?처음부터 강제하면 기존 inline script나 third-party tag가 깨질 수 있습니다. report-only로 violation을 수집하고, nonce/hash, script-src, connect-src, frame-src를 서비스별로 정리한 뒤 핵심 route에서 강제 정책을 적용합니다.
frame-ancestors와 X-Frame-Options?둘 다 clickjacking 방어와 관련 있지만 CSP frame-ancestors가 더 세밀하고 현대적입니다. embed가 필요한 파트너 origin이 있으면 allowlist를 명확히 하고, 그렇지 않으면 none 또는 sameorigin으로 막습니다.
Referrer-Policy는?외부 이동 시 URL path나 query에 포함된 민감 정보가 넘어가지 않도록 제한합니다. analytics attribution과 privacy 사이에서 정책을 정하고, UTM·token·email 같은 값이 URL에 섞이지 않도록 route 설계도 함께 고칩니다.
TRAINING EVIDENCE security header audit, CSP report, clickjacking fixture, permissions policy test
Q26

품질 게이트가 개발 속도를 늦추지 않게 하려면?

위험 기반으로 필수 자동화와 수동 증거를 나누고, 변경 범위별 checklist를 다르게 둡니다.

모든 변경에 같은 무거운 절차를 요구하면 팀이 우회하고 품질 체계가 무력화됩니다.

꼬리질문꼬리질문 답변
핫픽스는?핫픽스는 절차를 없애는 것이 아니라 최소 생존 게이트를 둡니다. 영향 route smoke, typecheck, targeted E2E, rollback 확인, owner 승인, 배포 후 짧은 health watch를 수행하고, 빠진 테스트는 후속 ticket로 닫습니다.
문서 변경은?순수 문서라면 전체 E2E는 과합니다. 링크 검사, markdown build, 검색 색인 생성, 접근성 heading 구조 정도면 충분할 수 있습니다. 다만 docs site의 route, SEO metadata, sitemap을 바꾸면 해당 영역 smoke를 추가합니다.
예외 승인은?예외는 구두로 넘기지 않고 위험, 만료 시점, 보상 통제, 승인자, 후속 조치를 기록합니다. 예외가 반복되면 게이트가 현실과 맞지 않는 신호이므로 CI 시간, flaky 테스트, 소유권을 개선해야 합니다.

릴리스 Q&A에서 senior-level 답변은?

성공 빌드보다 실제 사용자 영향, 보안 경계, 관측성, rollback, 재발 방지를 먼저 말합니다.

테스트 통과만 말하면 production 운영 책임을 이해하지 못한 답변으로 보입니다.

꼬리질문꼬리질문 답변
테스트가 충분한지 어떻게?테스트 수가 아니라 위험 경로 coverage로 판단합니다. 인증, 결제, 권한, 데이터 손실, XSS/CSRF, CDN cache, sourcemap, 브라우저 호환성, Web Vitals, analytics event가 변경 영향 안에 있으면 각각 어떤 증거로 닫았는지 설명해야 합니다.
빌드 성공 후 무엇을?artifact가 의도한 env로 빌드됐는지, sourcemap과 release id가 맞는지, CDN cache header가 올바른지, smoke route가 열리는지, error tracker와 RUM이 새 version을 받는지 확인합니다. 빌드는 릴리스 검증의 시작일 뿐입니다.
외부 검증 증거는?Playwright trace, error dashboard, RUM release segment, CSP report, bundle diff, cache header capture, URL별 smoke screenshot, rollback drill log가 증거가 됩니다. 답변에서는 추상적 자신감보다 이 자료를 어떤 순서로 확인했는지를 말합니다.

Q28

품질 경험이 적으면 어떻게 답변하나요?

test pyramid, XSS/CSRF 기본 threat model, sourcemap/cache/env/rollback 체크리스트, 배포 후 모니터링 계획을 구체화합니다.

막연히 꼼꼼히 테스트한다고 말하면 검증 가능한 기준이 없습니다.

꼬리질문꼬리질문 답변
실제 장애 경험이 없으면?없다고 인정하고 대신 샘플 프로젝트에서 만든 runbook을 설명합니다. 예를 들어 chunk load failure, stale CDN cache, XSS markdown fixture, 401 refresh 실패를 가정해 재현, 탐지 지표, rollback 기준, 후속 테스트를 어떻게 만들었는지 말하면 실무 사고를 보여줄 수 있습니다.
보안 질문이 깊어지면?모르는 세부 exploit은 추측하지 말고 threat model 경계로 답합니다. XSS는 source와 sink, CSRF는 cookie 자동 전송, token 저장은 탈취와 revocation, CORS는 브라우저 응답 노출 정책으로 나누고 확인할 로그와 fixture를 제시합니다.
테스트 수치가 없으면?coverage percentage를 꾸며내지 말고 앞으로의 측정 계획을 말합니다. 핵심 여정 E2E 수, component state matrix, axe violation, visual baseline, error budget, release health window를 정의하고 첫 릴리스부터 dashboard와 회고에 남기겠다고 답합니다.

Q29

canary release는 프론트엔드에서 어떻게 적용하나요?

사용자 세그먼트, route, feature flag, release version 기준으로 점진 노출하고 error/Web Vitals/conversion guardrail을 봅니다.

전체 사용자에게 한 번에 배포하면 브라우저·기기 특정 회귀의 blast radius가 커집니다.

꼬리질문꼬리질문 답변
canary 표본은?트래픽이 너무 작으면 브라우저별 오류나 conversion 하락을 볼 수 없고, 너무 크면 장애 반경이 커집니다. 내부 사용자, 저위험 계정, 특정 region, 1% 외부 트래픽처럼 단계별로 키우며 error rate, Web Vitals p75, chunk load failure, 핵심 funnel을 봅니다.
flag와 canary 차이는?canary는 새 artifact나 release version을 일부 사용자에게 노출하는 배포 전략이고, feature flag는 코드 안의 기능 경로를 켜고 끄는 제어 장치입니다. 둘을 함께 쓰면 새 bundle의 안정성과 특정 기능의 안정성을 분리해서 볼 수 있습니다.
성공 판정은?정해둔 guardrail을 이전 release와 비교해 통과해야 합니다. client error, blank screen, Web Vitals, API failure, conversion, support ticket이 threshold 안에 있고, 특정 브라우저·route segment에서 spike가 없으면 다음 단계로 확대합니다.

Q30

dependency rollback은 왜 준비해야 하나요?

프론트엔드 dependency는 build output, runtime behavior, polyfill, CSS까지 바꿀 수 있어 빠른 되돌리기 경로가 필요합니다.

패키지 업데이트 후 빌드는 통과해도 특정 브라우저나 route에서 런타임 오류가 날 수 있습니다.

꼬리질문꼬리질문 답변
patch update도 위험한가요?semantic versioning상 patch라도 bundler plugin, CSS-in-JS runtime, sanitizer, polyfill, date library처럼 전역 동작에 가까운 패키지는 회귀를 만들 수 있습니다. lockfile diff와 bundle diff를 보고 핵심 route smoke와 브라우저 matrix를 최소 확인합니다.
lockfile은?lockfile은 실제 설치되는 transitive dependency를 고정하므로 리뷰 대상입니다. dependency PR에서는 package.json뿐 아니라 lockfile 변경, 새 install script, registry source, duplicate version, bundle size 변화를 함께 확인해야 재현 가능한 rollback이 됩니다.
보안 업데이트면?critical 취약점이면 빠르게 올리되 무검증 배포는 피합니다. exploit reachability, patch changelog, override 가능성, sanitizer나 auth 관련 회귀 테스트를 확인하고, 문제가 생기면 이전 버전으로 되돌릴지 대체 패키지로 갈지 playbook을 둡니다.
